# 模型鉴定流水线

## 1. 目标收窄

总纲 4.4 的第一句话就把目标钉死了：

> **目标收窄**：不是"这是哪个模型"，而是"**这个 key 提供的模型是否与声称的名字相符**"。

这两件事差得很远：

| 问法 | 含义 | 可行性 |
|---|---|---|
| "这是哪个模型？" | 在全世界所有模型里做**开集识别** | 不可行。总纲 4.4 的硬教训 2 说得很清楚：参考库匹配只是"库内的**封闭集合**排序"，库外模型也会得到一个"最像"的候选 |
| "它是不是它声称的那个？" | 对一个**给定的候选**做**是/否**判定 | 可行。我们有任选的参考样本、有可观测的能力边界、有可设计的探针 |

**为什么这个收窄是整篇文档的前提**：需求原文是"检验用户提交的 key 对应的模型与模型名是否匹配（避免假模型）"——注意主语是"提交的 key 与**它声称的名字**"。我们要防的是**冒充**（拿便宜模型套上贵模型的名字卖给我们），不是"识别未知模型"。目标一旦写成后者，方案就必然滑向"训练一个模型分类器"，而硬教训 1 与 2 已经证明那条路会给出**看起来很像但其实无根据**的结论。

需求还明确了一条兜底：**对于无鉴定方案的冷门模型默认放行**。这条贯穿全篇（第 5 节）。

## 2. 已调研的三个方案与三条硬教训

总纲 4.4 的结论，原样引用（不含任何新结论或新数字）：

| 方案 | 做法 | 局限 |
|---|---|---|
| [zing-audit](https://pypi.org/project/zing-audit/) | 九维度黑盒审计，自带 85 个模型档案 / 7 平台 YAML 知识库 | 也有非 chat 面（embed / rerank / image / audio） |
| [lm-detector / lmfpd](https://github.com/Ikaleio/lm-detector/) | 让模型凭第一反应写约 300 个随机整数，比对**数值偏好分布**（与语义无关） | 结果是"参考库内的**封闭集合**排序"，库外模型也会得到"最像"的候选 |
| [which-llm](https://arxiv.org/html/2608.29930v1) | 30 个受控文本比对 `usage.prompt_tokens` | 留出集只 6/12 对有效，**token 计数一致只证明"共享分词栈"，不能证明模型血缘** |

**三条硬教训**（总纲原文，本项目的设计前提）：

1. token 计数不足以证明模型血缘（同家族不同版本会落到阈值下）；
2. 参考库匹配只是封闭集合排序，**排名分数不是身份证明**；
3. 元数据（`usage`）可以一行伪造 → 权重必须按**伪造抵抗性**分配。

**这三条直接决定了两件事**：

- **不能靠单一信号下结论**。任何单点信号都有反例：token 计数（教训 1）、指纹排名（教训 2）、自报身份（教训 3）。
- **信号必须有等级，且等级由"伪造难度"决定**（教训 3）。一个上游改一行响应就能骗过的信号，权重不能等同于要它真的换一套权重才能骗过的信号。

## 3. 信号按伪造抵抗性分级

总纲 4.4 的分级，原样：

| 级别 | 信号 | 为什么在这一级 |
|---|---|---|
| **强** | 数值随机指纹（lmfpd）、能力边界（上下文实测 / 视觉 / 工具调用）、logprobs 分布、已知答案金丝雀 | 它们要么统计模型内部的数值偏好（与语义无关，改不了），要么需要真的具备某个能力 / 真的换掉权重才能通过 |
| **中** | 知识边界 KBF、计费一致性（独立 tokenizer 估算 vs 上报用量） | 需要"知道"才能答对，但可以被一个更大更贵的模型代答；计费一致性要伪造得同时改用量与分词行为 |
| **弱** | usage token 差值、自报身份、回显 `model` 字段、响应头、错误格式 | **一行响应就能伪造**（教训 3），或干脆是同族模型共享分词栈的自然结果（教训 1） |

### 3.1 使用规则

| 规则 | 说明 |
|---|---|
| **弱信号不能单独定案** | 它们只能作为**辅助**与**排查线索**，不能支撑 `suspect` 判定 |
| **强信号可以单独触发 `suspect`** | 例如数值指纹与库中该模型的参考分布显著不符——这是"要它改权重才能骗过"的失败，风险足够高 |
| **中信号需要两条互相独立** | 单条中信号可能是"更大模型代答"，两条不同维度的中信号同时失败，代答解释就不成立了 |
| **所有信号失败方向都要记录** | 判定要能回答"是哪条信号判的"，见第 5.3 节 |

**为什么把"能力边界"放在强信号**：它需要的成本最不对称——声称支持 200k 上下文的假模型**必须在真的有 200k 上下文**才能通过实测（[01-catalog.md](01-catalog.md) 2.3 里 `context_window` 的来源之一就是 L2 的上下文二分实测）。

> **待定**：各级信号的**具体权重与阈值**（多少个随机整数样本、相似度多少算达标、KBF 要多少题）。总纲只给了分级与方案，没给数值；这些必须用我们自己的池子采样标定，不能照抄上游项目的默认值。

## 4. 三级流水线

总纲 4.4 的 L0 / L1 / L2，原样：

```
L0 形式校验   /v1/models 是否含声称 id · 端点黑白名单 · 响应形状
   ↓        （几秒，全部贡献必经）
L1 标准鉴定   数值指纹 + 自报 + 知识截止 + 能力探针 + 计费一致性 + 金丝雀
   ↓        （~1 分钟，决定入池与否）
L2 深度鉴定   上下文二分 + 视觉 + logprobs + 流式真实性 + 隐藏 system prompt
            （抽检 / 可疑时跑）
```

### 4.1 各级的职责边界

| 级 | 耗时 | 跑谁 | 决定什么 |
|---|---|---|---|
| L0 | 几秒 | **全部贡献，无例外** | 能不能进入 L1。这是最便宜的一道筛，用来挡住明显不是"某个模型的 key"的输入（比如把 embedding 端点填成 chat 模型） |
| L1 | ~1 分钟 | 通过 L0 的全部贡献 | **是否入池**，以及入池后的判定（第 5 节） |
| L2 | 分钟级 | 抽检 + 可疑 + 定时复检 | 复核与升级判定；也是"升级到 `verified`"的证据来源 |

### 4.2 为什么 L0 必须"全部必经"

贡献是**即生效、无审核**的（总纲 4.1）。没有人工把关，唯一的入口闸门就是 L0。如果 L0 允许跳过，攻击者可以直接把任意 endpoint 塞进池子，让我们的用户流量打到他的服务器上——这是总纲 13 章"贡献的凭据被上游封禁 / 被盗用"之外的第三类风险：**贡献者反过来拿到我们的流量与用户数据**。

所以 L0 的成本必须极低（几秒、纯 HTTP 探测、不产生 token 消耗），这样"全部必经"才不会把贡献流程拖慢。**这是"廉价闸门"的设计**：宁可 L0 只挡掉最明显的垃圾，也不能为了筛得准而让每个贡献都等几分钟（那会直接杀死贡献意愿）。

### 4.3 为什么 L1 决定入池，L2 不

L1 是**默认准入线**：一分钟内跑完，信号覆盖面已经包含数值指纹、能力探针、金丝雀这几条强信号。L2 成本高、耗时长，且里面的项（上下文二分、隐藏 system prompt 探测）会**大量占用上游额度**——对众包贡献的凭据，我们不能一进门就烧掉它几十万 token。

L2 的定位是**抽检与复核**：随机抽一部分升级为 `verified`，对 `suspect` / 回归告警做深挖，以及定期复检时轮转覆盖。

> **待定**：L2 的抽检比例与轮转周期。

## 5. 判定与放行

### 5.1 四态

总纲 4.4 的判定表，原样：

| 情况 | 处置（`verify_status`） |
|---|---|
| 库中有参考指纹且达标 | `verified` → 入池 |
| 有指纹但不达标 | `suspect` → **拒绝入池**并给证据 |
| **库中无指纹（冷门模型）** | `unverified` → **默认放行**入池，标「未鉴定」，进复检队列 |
| 官方域名 | `trusted` → 免检 |

`verify_status` / `verify_detail` 落在 `upstream_credentials` 表（总纲第 10 章）。

### 5.2 为什么冷门模型默认放行

这条与安全直觉相反，必须说清为什么：

- **"库里没有"不等于"可疑"**。参考库来自上游项目的知识库与我们的自建采样，它覆盖的是**热门**模型。冷门模型（尤其国产新模型与平台自建模型）天然不在库里。若"不在库"即拒绝，我们等于宣布"只接受热门模型"，而众包贡献的价值恰恰在于**长尾供给**。
- **误杀成本高于误放**。判 `suspect` 是**拒绝入池**——对一个正常贡献者来说，他做了一件对我们有利的事却被打回，且理由是他无法理解的技术细节（"你的模型不在我们的指纹库里"）。这种体验会让贡献者直接流失。
- **有兜底**：`unverified` 的方案是"入池 + 标记 + 复检队列"，而不是"入池就当没事"。落到路由上是健康降权：`unverified` 凭据在 [01-catalog.md](01-catalog.md) 7.2 的健康取位上不会被当作 `healthy`，而排序里由 `speed`（读滚动延迟/失败率）自然排后——注意**不能靠过滤掉它来实现降权**，那样它永远拿不到流量，复检也就永远没有输入（[01-catalog.md](01-catalog.md) 7.3）。

**这条设计的前提是"回滚容易"**：一个 `unverified` 的假模型进池后，靠运行时健康（[01-catalog.md](01-catalog.md) 第 7 节）与定时复检（第 7 节）把它赶出去，代价是有限的流量损失；而误杀一个真贡献者的代价是**供给端的长期损失**。

### 5.3 `verify_detail` 必须可执行

每种判定都要落**证据**，且证据要能让贡献者自己行动：

| 判定 | 应给出的证据 |
|---|---|
| `suspect` | 哪条信号失败、失败方向（如"数值指纹与库中 `X` 的参考分布不符"）、**不泄露我们的探针细节** |
| `unverified` | 明确写"库中无该模型的参考指纹，已放行并进入复检队列" |
| `trusted` | 命中的官方域名 |

**为什么不给贡献者完整探针细节**：探针一旦公开，就会有一条稳定的"照着探针作弊"的路径。证据给到"哪一类信号失败"就够贡献者判断是不是自己填错了模型名。

> **待定**：探针细节对管理端可见、对贡献者脱敏的分界在哪。

### 5.4 判定与生命周期的关系

`verify_status` 是"声称是否相符"的判定；凭据的 `status` 是"可用性"的生命周期（见 [../contributions/02-credentials.md](../contributions/02-credentials.md) 第 5 节）。两者**正交**：

- 一个 `verified` 的凭据可以因为上游封禁而 `revoked`；
- 一个 `unverified` 的凭据可以正常在池子里被调用、并产出真实流量。

混用这两个字段会导致"复检失败"直接表现为"凭据被删"，把可恢复的问题变成不可恢复的。

## 6. 指纹库

总纲 4.4 的三个来源，原样：

1. lmfpd 可导出的参考库；
2. zing 的 85 模型 YAML；
3. **用自己池里的官方渠道采样自建**。

### 6.1 一条硬约束

> **参考样本绝不能取自待检的可疑渠道。**

**为什么**：用待检对象自己的输出建参考，再用这个参考去检验它，是**循环论证**——它永远会"达标"。这条约束决定了自建采样的**唯一合法来源是平台自有凭据**（`owner_account_id = NULL`，即我们自己配的官方 key，见 [../contributions/02-credentials.md](../contributions/02-credentials.md) 第 6 节）。贡献来的凭据无论看起来多正常，都不能进指纹库。

由此还有一条工程推论：**样本采集要打标来源**，且采集路径与检验路径共用同一套代码也能用"来源"字段隔离（防止未来有人把两条路不小心接起来）。

### 6.2 指纹库的版本与可追溯

判定结果依赖指纹库的内容，因此：

- 指纹库必须有**版本号**，`verify_detail` 要记下判定时用的是哪一版；
- 指纹库更新后，**已入池的 `verified` 不需要回溯重判**（第 7 节的定时复检会覆盖），但 `unverified` 的复检队列应按新库重新排队。

**为什么记录版本**：总纲 4.4 的硬教训 2 说明匹配只是排序。同一份样本在两个版本的库里可能得出不同结论——没有版本号，事后根本说不清"当时为什么判它 verified"。

> **待定**：指纹库的落库形态（`settings` 表内的 JSON / 独立文件 / 独立表）、更新方式（手动导入 / 跟随上游项目版本）与大小上限。

## 7. 定时复检与回归告警

总纲 4.4：**防"今天真、下周转假"** —— 移植 `zing watch` 的**定时复检 + 回归告警**（得分下滑也告警）。

### 7.1 为什么这是必需的

- 上游的中转站可以在**任何时候**把后端从一个模型换成另一个（它们自己也在做成本优化）；
- 一条已经 `verified` 的凭据，今天真不代表下周期真。**没有一个复检机制，"鉴定"就只是一次性快照**，而快照会随时间腐烂。
- "得分下滑也告警"这一条尤其重要：如果只在"不达标"时告警，我们会看到一条**从 99 分慢慢滑到 60 分**的曲线而毫无察觉，然后在某个时刻突然被触发。趋势必须比阈值更早报警。

### 7.2 复检的三种触发

| 触发 | 范围 |
|---|---|
| **定时** | 轮转覆盖全部入池凭据（含 `unverified` 的复检队列） |
| **可疑** | `suspect` 后的人工复核、以及用户投诉 / 异常流量触发的定向复检 |
| **回归告警** | 得分下滑超阈值即告警，并提高该凭据的复检频率 |

### 7.3 复检结果的处置

| 结果 | 动作 |
|---|---|
| 持续达标 | 保持或升级判定；`unverified` → `verified` |
| 得分下滑 | 告警 + 提高频率 + **降权**（[03-strategy.md](03-strategy.md) `speed` 键变差、健康降至 `degraded`，不剔除） |
| 不达标 | 判 `suspect`，凭据**移出候选**（不删除，保留证据与归因） |

**为什么下滑先降权而不是直接移出**：降权是**可逆**的，移出不是。一个得分下滑的凭据可能只是上游临时降级了某个模型（比如高峰期把 `pro` 路由到了 `flash`），几小时后会恢复。先降权既保护了用户（它排在后面），又保住了供给。

## 8. 成本由谁承担

鉴定的成本构成：

| 成本 | 说明 |
|---|---|
| **token 消耗** | L1 / L2 的探针都要真实调用上游，产生 token |
| **额度占用** | 消耗的是**贡献凭据自己的额度**（它在我们手里就是用来被调用的） |
| **时间** | L1 约 1 分钟，L2 分钟级 |
| **复检的持续成本** | 全池轮转，是本项最大的一笔持续支出 |

总纲 4.4 只给了流水线与判定，**没有指定成本承担方**，这是必须拍板的一项：

> **待定**：鉴定成本由谁承担。三个候选：
> ① **全部由平台承担**——贡献体验最好（贡献者什么都不用做），成本随池子规模线性增长；
> ② **全部由贡献者承担**——即用他自己的额度跑鉴定，平台零成本，但这会**直接削弱贡献意愿**，与"贡献即生效、无需审核"的轻量体验冲突；
> ③ **混合**——首次 L1 由平台承担（把人拉进来），定时复检与 L2 深挖由平台承担但**限频限额**，超过一定频率的复检走贡献者额度（相当于对"反复出问题的凭据"收费）。
> 另外还需要配套决定：单个凭据入驻时的**鉴定额度上限**（防止一次贡献把 300 个随机整数探针刷成天文数字）。
