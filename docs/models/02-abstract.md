# 抽象模型与能力声明

## 1. 这一篇管什么

本篇定义**抽象模型**本身：它是什么、怎么命名、候选集怎么声明、能力声明怎么算、以及它对外呈现什么契约。

## 2. 两层模型与可见性

### 2.1 已定决策

| 层 | 谁看得见 | 出口 |
|---|---|---|
| 真实模型 | **只有管理员** | 管理端目录；`requests` 表的解析落点仅管理端可见 |
| 抽象模型 | **只有租户** | `/v1/models`、`/v1/chat/completions` 等全部对外端点 |

对外只有抽象模型：

- `/v1/models` 只列抽象模型；
- 客户端直接请求真实模型名（含限定名 `dsh:...` 与裸上游 id）→ **404**；
- 组的模型授权对象是抽象模型；
- 上游 `aggregate/*` 不作候选来源（见 [01-catalog.md](01-catalog.md) 第 5 节）。

**为什么必须两层**：`/v1/models` 是任何人都能拉的公开端点。如果它列出真实模型，等于把我们 20 个渠道 / 116 个模型的**渠道构成**免费送出去——别人照着抄一个池子，同时我们的上游账号身份暴露在请求里（每个渠道对应一批真实账号，风控很容易顺着挖）。抽象模型这一层同时承担三个作用：**隐藏供给结构**、**稳定对外契约**（上游变动不动客户端配置）、**承载管理员策略**。

### 2.2 数据结构

```
abstract_model {
  id,
  name,                  -- 对外名称，唯一
  display_name,          -- 管理端与租户端展示名
  strategy,              -- 策略链，见 03-strategy.md
  capability_mode,       -- strict / filter，见第 5 节
  capabilities,          -- 对外能力声明，见第 4 节
  status,                -- active / deprecated / disabled，见 04-deprecation.md
  replacement_model_id,  -- 自引用替代目标
  deprecated_at,
  sunset_at,
  note
}

abstract_candidate {
  abstract_model_id,
  real_model_id,         -- 指向 01-catalog.md 的真实模型
  constraint_json,       -- 约束（渠道范围 / 凭据范围 / 模态 / 档位），见第 3 节
  weight                 -- 相对权重，供 cheapest / weighted 使用
}
```

字段与总纲第 10 章一致；`capabilities` 与 `constraint_json` 的内部结构由本篇展开。

### 2.3 命名规则

| 规则 | 理由 |
|---|---|
| 只允许小写字母、数字、`-`、`_` | 保证能安全地进 URL 路径（`Link` 头要写 `</docs/models/smart>`）与 JSON 键 |
| **禁止包含 `:`** | 与真实模型的限定名 `dsh:...` 在字符串层面互斥，杜绝"客户端拿着真实名当抽象名用"的歧义（[01-catalog.md](01-catalog.md) 2.1） |
| 全局唯一，创建后**不可改** | 客户端配置里写死的就是这个名字；改名等于一次强制迁移 |
| 建议短（`smart` / `fast`） | 它是配置项，出现在各种客户端界面里 |

> **待定**：是否预置一组通用抽象模型名（总纲 3.7 已提，建议 `fast` / `balanced` / `smart` / `vision` / `long-context`）。这一条不定，初始化向导就不能自动建好第一版对外模型。

> **待定**：`name` 与（P1）兼容别名（把 `gpt-4o` 等真实名映射到抽象模型）是否共用同一命名空间。若共用，别名不得与任何真实模型名相撞；若不共用，需要两张表。

## 3. 候选集：声明式，不绑凭据

### 3.1 一个候选是什么

> **候选** = 真实模型 × 渠道范围 × 约束。

```
candidate = {
  real_model_id,        -- 必须是池内真实模型
  constraint: {
    channel_scope:      -- 渠道范围
      { mode: any | include | exclude, channels: [...] },
    credential_scope:   -- 凭据来源范围
      { mode: any | platform_only | contributed_only },
    require_modalities: ["text" | "image" | ...],
    min_context:        <int>,
    require_efforts:    ["high", "max", ...]     -- 思考档位要求（可选）
  },
  weight
}
```

### 3.2 运行时展开

候选**只有声明**；能不能用要等运行时把它展开：

```
候选（声明）
  × 当前有资格承载它的凭据实例（有 contributor 类的账户贡献的 / 平台自有）
  = 可路由的具体路径（候选 × 凭据实例）      ← 交给策略引擎三段式
```

### 3.3 为什么不绑凭据

| 理由 | 展开 |
|---|---|
| 凭据是**流动**的 | 任何人随时可以贡献（总纲 4.1），贡献者也可以随时撤销。若候选写死凭据 id，凭据一撤候选就失效，管理员得手工修配置——这是把运维成本压给了"供给越多、配置越烂"的方向 |
| 凭据**不可自选**的隔离要求 | 总纲 2.3 第 3 条：贡献者不能指定自己的请求走自己的凭据。若候选能写凭据，管理员配置里就出现了"这个模型只走张三的号"的合法表达，隔离立刻被绕开 |
| 归因需要**两层解耦** | `requests` 表同时记 `resolved_real_model_id` 与 `resolved_credential_id`。声明层不带凭据，才能做到"同一个候选上换了凭据"这件事在用量大屏上不改变任何统计口径 |
| 平台自有凭据与贡献凭据**同构** | 平台自有凭据用 `owner_account_id = NULL` 表达（见 [../contributions/02-credentials.md](../contributions/02-credentials.md) 第 6 节）。同构的前提就是没人把凭据写进声明 |

### 3.4 保存时的校验

候选在**保存**时逐条校验，任一不过直接拒绝（不给"先存着"的机会）：

| 校验 | 不通过时 |
|---|---|
| `real_model_id` 存在 | 拒绝 |
| `excluded_from_candidates = false` | 拒绝，提示"上游聚合模型不能作候选" |
| `status != missing` | 拒绝，提示"该模型已被标为下线" |
| `require_modalities` 是真实模型模态的**子集** | 拒绝；否则这条候选永远不会通过过滤（见 [03-strategy.md](03-strategy.md) 第 2 节），是无意义的配置 |
| `min_context` ≤ 真实模型上下文 | 同上 |
| 至少 1 个候选 | 拒绝空候选集（没有候选的抽象模型必然 503，不该被保存） |

**为什么要"保存即校验"而不是运行时再说**：抽象模型的错误只有两个出口——运行时 503（用户看到故障）或保存时报错（管理员看到原因）。总纲 13 章把"策略配错 → 全站不可用"列为风险，对策就是保存前干跑；这里是最便宜的第一道防线。

## 4. 能力声明：取保守下界

### 4.1 默认（严格模式）

抽象模型对外声明的能力**默认取候选的最小值 / 交集**：

| 能力 | 默认算法 |
|---|---|
| 上下文窗口 | 全部候选的 **min** |
| 最大输出 | 全部候选的 **min** |
| 视觉 | 全部候选的**交集**（有一个不支持 → 声明为不支持） |
| 工具调用 | 全部候选的**交集** |
| JSON mode | 全部候选的**交集** |

对一组候选 `A(上下文 128k, 支持视觉)` 与 `B(上下文 32k, 不支持视觉)`，严格模式声明出来的是 `32k + 无视觉`。

### 4.2 为什么保守

总纲 3.4 的原文理由：**宁可保守声明（客户端少用一点能力），也不要声称支持然后中途失败**。

展开一下这条为什么特别重要：

1. **失败位置不同，代价差一个数量级**。声明保守 → 客户端从一开始就不发图片，最多是"用不上"；声明激进 → 图片发上来了、上游报 400 或用静默截断，请求在中途失败。后者在流式下还叠加了"已经吐出部分内容"的问题（[03-strategy.md](03-strategy.md) 第 4 节：此时不能再换候选）。
2. **用户不会去读能力文档**。他们会照着失败报错来投诉。让能力声明保守，等于把"上游不一致"这件事在我们这一层吸收掉，而不是把它转嫁给每一个使用者。
3. **抽象模型的意义就是稳定**。如果 `smart` 今天支持图片、明天因为池子换了一批候选就不支持了，它就不是一个稳定的对外契约，客户端无法围绕它做任何设计。

### 4.3 候选能力未知时

某个真实模型的能力**未知**（上游目录不提供、管理员也没填，例如 `context_window` 见 [01-catalog.md](01-catalog.md) 2.3）时：

- **严格模式**：按"不支持 / 取最小值"处理，即未知项**不进入交集**。
- **过滤模式**：该候选在需要这项能力的请求上**被过滤掉**。

**为什么与总纲 9.1 的"默认拒绝"同向**：能力这件事上，我们唯一能承诺的是"我们确切知道的"。未知就当作不具备，代价是少用一点能力，与 4.2 的取舍一致。

### 4.4 声明是"对外"，不是"对内"

能力声明有**两个读者**，不要混：

| 读者 | 看到 | 用途 |
|---|---|---|
| 租户 / 客户端 | 抽象模型的**声明值** | 决定要不要发图片、要不要开工具 |
| 策略引擎 | 每个**候选**的真实能力 | 过滤与排序（[03-strategy.md](03-strategy.md)） |

`capabilities` 只是给前者的摘要，**不作为路由依据**。路由必须按候选各自的真实能力判断，否则过滤模式（第 5 节）根本无法工作——它需要知道"哪个候选支持图片"。

## 5. 能力模式

### 5.1 两种模式

| | 严格模式 `strict`（默认） | 过滤模式 `filter` |
|---|---|---|
| 声明值 | min / 交集 | 并集 / 取最大 |
| 谁被限制 | **所有客户端**（被声明值限制） | **候选**（不支持该能力的在路由前被筛掉） |
| 候选集要求 | 无 | 需要存在"满足请求要求"的候选子集 |
| 风险 | 能力用不满 | 请求要求的候选可能一个都没有 → 503 |

### 5.2 过滤模式的语义

1. 抽象模型声明值取**并集**（对外声称能力更强）；
2. 每次请求先根据**本次请求实际需要的能力**（是否带图片、是否要工具调用、上下文多大）过滤候选；
3. 过滤后为空 → 走 503 `no_candidate`（第 6 节）。

### 5.3 什么时候允许用过滤模式

**只在候选池里确实存在能力差异、且管理员接受"部分请求无候选"** 时使用。典型场景：`smart` 挂了一堆候选，其中混着不支持视觉的小模型——严格模式下整个 `smart` 都不敢声明视觉，而管理员其实只想让"带图片的请求"落到那几个大模型上。

**为什么默认不用**：过滤模式把"客户端看不到的能力差"变成了"客户端随机踩到的 503"。它的可用性完全取决于候选集健康度，而候选集是众包供给喂出来的（[../contributions/01-flow.md](../contributions/01-flow.md)），供给质量波动大。所以默认严格模式，过滤模式是**管理员明确想要时才打开的开关**，且管理端应在编辑页显著提示 503 风险。

> **待定**：过滤模式下 503 的错误码是否应与严格模式区分（例如额外错误码表示"本次请求的能力要求无候选"），以便客户端针对性重试（去掉图片重发）。

## 6. 对外契约

### 6.1 `/v1/models`

| 项 | 取值 |
|---|---|
| `id` | 抽象模型的 `name` |
| 列表范围 | **只列抽象模型**；`status != active` 的是否列出见 6.4 |
| 可见性 | 进一步叠加租户所属组的授权（[../security/03-groups.md](../security/03-groups.md)）与 Key 白名单（[../security/05-keys.md](../security/05-keys.md)） |

**为什么 `/v1/models` 也要按 Key 过滤**：总纲 11.3 的三层收敛是"组的模型授权 ∩ Key 白名单 = 实际可用"。若 `/v1/models` 列出全部抽象模型，用户会看到自己有 Key 但用不了的模型——这既是误导，也泄露了"本站还有哪些模型"的运营信息。

### 6.2 请求与响应

| 环节 | 行为 |
|---|---|
| 请求 `model` = 抽象模型名 | 正常路由 |
| 请求 `model` = 真实模型名（裸 id 或限定名） | **404**（不区分"不存在"与"不可见"，避免泄露池结构） |
| 响应 `model` | **回显抽象模型名**，永不含真实模型名 |
| 流式 | 同上，每个分片与最终 usage 事件里的 `model` 都是抽象模型名 |

### 6.3 调试响应头

管理端、以及管理员指定的组，可开启 `x-fr-trace` 响应头，看到真实落点。

| 头字段 | 内容 | 可见范围 |
|---|---|---|
| `x-fr-trace` | 抽象模型 → 命中候选 → 真实模型 → 凭据标识（不含量与明文） | 仅管理端与白名单组 |
| `x-free-router-request-id` | 请求 ID，用于与 providers-hub 对账（总纲 11.4） | 全部请求 |

**两条约束**：

- **用户日志只出现抽象模型名**，真实目标与**贡献者归因仅管理端可见**（总纲 3.7）。这是保护贡献者的必要条件：若贡献者能从日志里知道"刚才那一单走的是我的号"，总纲 2.3 第 3 条"贡献者不能指定自己的请求走自己的凭据"就会被绕过（他可以反复试直到命中自己的号）。
- `x-fr-trace` **不能包含凭据明文**，也不能包含能反查到具体账户的信息（用内部 id，不用贡献者显示名）。

### 6.4 弃用状态的呈现

`status = deprecated` 的抽象模型**仍然出现在 `/v1/models`**，因为弃用不是关闭（[04-deprecation.md](04-deprecation.md)）。

`status = disabled` 的不出现在列表里，直接请求返回 404 / 410 Gone。

### 6.5 无候选：503

| 情况 | 响应 |
|---|---|
| 模型不存在 / 不可见 / 请求了真实模型名 | **404** |
| 模型存在且在授权范围内，但**本次请求无候选可用** | **503 + 专用错误码** |

**为什么必须区分**：404 告诉客户端"换个模型"，503 告诉客户端"稍后重试同一模型"。混在一起会让客户端在池子短暂抖动时永久性地切走。总纲 14 章验收第 11 条明确要求这两者分开，且**不能用 500**——500 会让上游故障看起来像我们的 bug，掩盖真实原因。

### 6.6 用户日志

用户可见的日志/看板里：

- 只出现**抽象模型名**；
- 不出现渠道名、真实模型 id、凭据标识；
- 用量聚合按抽象模型维度（`usage_daily.abstract_model_id`），真实模型维度只在管理端看板出现。

## 7. 接口签名

```
-- 抽象模型 CRUD（管理面）
Create(model AbstractModel) -> (id, error)
Update(id, patch AbstractModelPatch) -> error        -- 含能力模式、策略链、候选集
SetStatus(id, status, replacement *id) -> error      -- 见 04-deprecation.md
Delete(id) -> error                                  -- 仅限从未被引用

-- 校验（保存前，含干跑）
Validate(model AbstractModel) -> ValidationReport    -- 见 03-strategy.md 第 6 节
RecomputeCapabilities(id) -> Capabilities            -- 候选变更后重算声明

-- 运行时
Resolve(name, key_id) -> (Resolved, error)           -- 唯一出口；含替代链解析
ListVisible(key_id) -> []AbstractModelBrief          -- /v1/models 的数据源
```

`ListVisible` 的输入是 Key 而不是账户：可见性由"组的授权 ∩ Key 白名单"决定，而 Key 已经绑定到账户与组。

## 8. 待定项汇总

> **待定**：抽象模型名与（P1）兼容别名是否共用命名空间，见第 2.3 节。

> **待定**：过滤模式下"能力要求无候选"是否要用独立错误码与 503 区分，见第 5.3 节。
