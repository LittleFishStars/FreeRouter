# 策略引擎：过滤 · 排序 · 切换

## 1. 三段式总览

```
① 过滤  能力匹配 · 上下文够长 · 额度充足 · 渠道未禁用 · 健康 · 不在冷却
   ↓
② 排序  expiry-first（默认）· cheapest · fastest · weighted · round-robin
        · quality-tier · quota-aware    ← 可组合成排序链
   ↓
③ 切换  候选失败换下一个 —— 仅在「还没吐出任何可见内容」时
```

三段式的输入是 [02-abstract.md](02-abstract.md) 第 3.2 节展开出来的**可路由路径**（候选 × 凭据实例），输出是一条**被选中的路径**。

| 段 | 做什么 | 语义 |
|---|---|---|
| ① 过滤 | 剔除**不可用**的路径 | 硬门槛：不通过 = 不存在 |
| ② 排序 | 给剩下的路径**排优先级** | 软偏好：排后面的仍可能被用到 |
| ③ 切换 | 按序尝试，失败换下一个 | 只在**没有可见输出**前有效 |

**为什么必须把三段分开而不是写成一个大函数**：

- **归因**。日志里要能回答"为什么这单走了 B 而不是 A"——是被过滤掉了（能力/额度/健康），还是排序排到了后面？两者对管理员是完全不同的信号：前者要去修池子，后者只要调权重。
- **干跑**（第 6 节）需要单独验证每一段。过滤可以静态验证（候选是否存在、能力是否够），排序只能看输出顺序，切换只能在真实流量里验证。
- **可替换**。总纲 3.3 明确「可组合成排序链」，说明排序这一段本来就设计成可插拔的；过滤条件清单也会随功能增长（比如 P1 的组级共享额度池会加一条过滤条件）。

## 2. 第一段：过滤

### 2.1 条件清单

| # | 条件 | 判据 | 数据来源 | 不通过时 |
|---|---|---|---|---|
| F1 | **能力匹配** | 本次请求需要的能力（模态 / 工具调用 / JSON mode）候选都支持 | 真实模型 `modalities`、能力探针结果（[05-verification.md](05-verification.md)） | 剔除该路径 |
| F2 | **上下文够长** | 请求估算输入 + 声明的最大输出 ≤ 候选上下文 | `real_models.context_window`、IR 里的消息长度估算 | 剔除 |
| F3 | **额度充足** | 承载该路径的凭据还有可用额度 / 未被上游限流 | providers-hub 积分与余额（总纲 5.1） | 剔除 |
| F4 | **渠道未禁用** | 渠道、真实模型、凭据都未被管理员禁用 | `real_models` 状态、凭据 `status` | 剔除 |
| F5 | **健康** | 路径的运行时健康不是 `degraded` 以下 | 运行时健康（[01-catalog.md](01-catalog.md) 第 7 节） | `degraded` **不剔除**（只降权）；`cooldown` / `blocked` 剔除 |
| F6 | **不在冷却** | 该路径没有活动的冷却窗口 | 运行时熔断状态 | 剔除 |
| F7 | **存在可路由路径** | 该候选至少有一条可用的凭据路径 | 运行时展开（[02-abstract.md](02-abstract.md) 3.2） | 剔除该候选 |
| F8 | **不在弃用链的坏状态** | 替代链解析成功（未成环、未超深） | [04-deprecation.md](04-deprecation.md) 第 2 节 | 见 04 分册：降级为"无替代"，不报错 |

> 说明：F1～F8 全部是总纲 3.3 过滤条件清单（能力匹配 · 上下文够长 · 额度充足 · 渠道未禁用 · 健康 · 不在冷却）的**可判定化**，其中 F7 / F8 是"路径存在性"与"替代链"这两件在三段式之前就已经发生的事，列在这里是为了让实现有一个完整清单，不引入新条件。

### 2.2 过滤是硬门槛，不降权

**不通过 = 这条路径在本次请求里不存在**，绝不"排到最后再试一次"。

为什么：

- **能力不匹配的候选，重试多少次都不会成功**（把图片发给不支持视觉的模型，永远是 400）。把它留在候选列表里只会浪费一次尝试窗口，而这个窗口在流式场景下极其宝贵（第 4 节）。
- **额度耗尽的凭据重试会加重上游风控**。总纲 13 章把"贡献的凭据被上游封禁"列为风险，对策是候选级熔断 + 冷却 + 降权。如果过滤阶段不把没额度的凭据剔掉，熔断阈值会被大量必然失败的请求迅速打满，好的凭据也跟着被冷却。
- **降权是排序的事**。健康为 `degraded`（有失败也有成功）的路径**不剔除**，靠 [01-catalog.md](01-catalog.md) 7.2 的降权 + 第 3 节的 `quality-tier` 处理——它还能用，只是别优先用。把"还能用"和"不能用"混在一个机制里会同时丢这两件事。

### 2.3 过滤后为空

返回 **503 + 专用错误码 `no_candidate`**（[02-abstract.md](02-abstract.md) 6.5），**不是** 500。

同时必须落一条可诊断的记录：**过滤后为空时，记录"如果在更早的某一级放宽该条件，还剩几条路径"**（例如"若忽略健康，还剩 2 条"）。为什么：503 是管理员最常遇到的故障，而"所有候选都被过滤了"这句话没有信息量。有了这级"险些可用"的诊断，管理员一眼能看出是池子空了、还是健康全红了、还是额度全干了。

> **待定**：`no_candidate` 的错误体内是否暴露"原因分类"（池子空 / 能力不匹配 / 全冷却 / 全无额度）。暴露便于用户自助排查，但也把供给结构漏给租户；建议只给**分类**不给数量与模型名。

## 3. 第二段：排序

### 3.1 排序链

`abstract_model.strategy` 里存的是**一条排序链**，按顺序应用：**上一级相等时，用下一级决胜**（tie-break）。

默认链：

```
[ expiry-first, round-robin ]
```

- `expiry-first` 是总纲 3.3 钉死的默认；
- `round-robin` 只作为**平局决胜**。

**为什么默认要带一个决胜项**：`expiry-first` 的排序键是"额度作废时间"，而同一个渠道的多个账号往往共享同一个到期时间。如果并列时按稳定顺序取第一个，结果是**每次都打同一个账号**——它在被限流前会先被打爆，而其他同到期的账号一直被闲置。加一级轮询把并列摊开，等于不花任何代价提升了整个池子的吞吐上限。

### 3.2 七种排序策略

| 策略 | 排序键 | 依据 | 适用 | 主要失效场景 |
|---|---|---|---|---|
| `expiry-first` | 额度作废时间**升序**（最快作废的先用） | providers-hub 的到期逻辑（总纲 5.1） | **默认**，订阅额度池的通用最优解 | 无到期概念的凭据（纯 API Key）该键为空 |
| `cheapest` | 候选声明的**相对权重**升序 | `abstract_candidates.weight` | 想优先消耗"便宜"的供给 | 权重是人工声明，不代表真实成本 |
| `fastest` | 观测 **TTFT 中位数**升序 | `requests.ttft_ms` | 交互式客户端（Claude Code 这类） | 冷启动无样本；样本量小时抖动大 |
| `weighted` | 按 `weight` **概率抽样** | `abstract_candidates.weight` | 想按比例分摊流量 | 结果不确定，不能用于干跑复现 |
| `round-robin` | 序号轮转 | 运行时游标 | 平局决胜 / 均摊 | 单进程内存游标，多节点下不共享（P2） |
| `quality-tier` | 质量档位**降序** | 鉴定判定（[05-verification.md](05-verification.md)）+ 观测成功率 | 供给质量参差时 | 冷门模型被判 `unverified` 会天然靠后 |
| `quota-aware` | 剩余额度**比例**降序 | providers-hub 积分 / 余额 | 额度即将用尽时延后使用 | 上游不报余额时该键为空 |

逐条补充说明它们是**为什么存在**：

**`expiry-first`**——订阅额度池的核心经济学：额度到期即归零，没用掉就是浪费。总纲 5.1 说 providers-hub 本来就有"临期排序"，我们复用它。这条策略存在的理由是"**额度是消耗品，且过期不可逆**"，任何其他排序都不如它直接对应钱。

**`cheapest`**——总纲 1.3 明确**删掉了 `cost` 字段**（订阅额度没有单价，算不出真钱）。所以 `cheapest` **不可能按货币金额排序**，只能按候选声明的**相对权重**（`weight`）排序，含义是"管理员认为这条供给更便宜"。这是相对量，不是金额，文档与 UI 都必须这样写，否则管理员会以为自己在设单价。**为什么不直接删掉这个策略**：权重在"平台自有凭据 vs 贡献凭据"之间是有意义的——自有凭据是明确的成本，贡献凭据的边际成本接近零，管理员可以用权重表达"能不用自己的就先不用"。

> **待定**：`weight` 的取值语义与默认值（越小越优先？还是越大越优先？`cheapest` 用升序、`weighted` 用正比抽样，两个方向必须统一约定，否则同一份权重会被解释成相反的意思）。

**`fastest`**——TTFT 是用户唯一真实感知的性能指标。总纲 14 章验收第 5 条之外，"Claude Code 能不能顺畅跑"这件事基本由 TTFT 决定。数据来自我们自己 `requests.ttft_ms`，不需要上游配合。

**`weighted`**——与 `cheapest` 共用权重但语义不同：前者是**确定性排序**，后者是**概率分摊**。存在理由是"不得罪贡献者"：如果排序永远优先某几条路径，剩下的贡献凭据长期拿不到流量，贡献者会很快不干了（回报机制见 [../contributions/02-credentials.md](../contributions/02-credentials.md) 第 7 节）。

**`round-robin`**——最简单的均摊，也是唯一没有外部依赖的决胜手段。

**`quality-tier`**——把总纲 4.4 的鉴定判定（`trusted` > `verified` > `unverified`）与运行时观测成功率合成为档位。**为什么不能只用鉴定判定**：鉴定是**时点**结论（见 [05-verification.md](05-verification.md) 第 7 节，模型可能"今天真、下周转假"），而观测成功率是连续信号。两者合成才能同时覆盖"当初就不对"和"后来变坏了"。

**`quota-aware`**——与 `expiry-first` 的区别：`expiry-first` 关心**什么时候过期**，`quota-aware` 关心**还剩多少**。一个还剩 5% 但三周后才过期的账号，应该排在一个还剩 80% 但明天过期的账号后面。

### 3.3 确定性与可复现

除 `weighted` / `round-robin` 外，排序必须**确定性**：同样的输入（候选集 + 凭据集 + 运行态）必须输出同样的顺序。

为什么这是硬要求：

- 第 6 节的**干跑**只有在确定性下才有意义——否则"回放历史请求"得到的结果不可复现，干跑就成了掷骰子；
- 故障排查时，管理员需要能回答"为什么这单走了它"，非确定性排序会让这个问题无法回答；
- `weighted` / `round-robin` 因此**必须带随机种子或游标快照**进日志，否则它们的决策同样不可追溯。

## 4. 第三段：切换

### 4.1 唯一的硬约束

> 一旦已经向客户端吐出**可见内容**（文本 / 工具调用），就**不能**再换候选。

这是全篇最重要的一条，总纲 3.3 原文："流式串话是 providers-hub 已经踩过的坑"。

**为什么**：切换发生在 HTTP 响应已经开始写之后。此时前一个候选已经写了 `text_delta`，如果换一个候选从头开始生成，客户端会看到**两段拼接的内容**（前一半来自 A，后一半来自 B），而且：
- 流式协议上我们无法"撤回"已发的分片；
- A 和 B 是两个不同模型，风格与上下文理解不一致，拼接结果可能语义错乱；
- 用户会把它当作我们的模型质量问题，而不是上游故障。

**代价我们接受**：这一路请求失败、用户看到错误。因为"明确失败"远比"悄悄给出错误答案"好——后者用户可能直接拿去用了。

### 4.2 什么是"可见内容"

按总纲 6.1 的流式事件定义逐项判定：

| 事件 | 是否算已吐出可见内容 | 说明 |
|---|---|---|
| `start` | ❌ 不算 | 只有元信息，还没有任何模型产出 |
| `usage` | ❌ 不算 | 只有计数 |
| `error` | ❌ 不算 | 本身就是失败信号 |
| `done` | — | 请求已结束，不涉及切换 |
| `text_delta` | ✅ **算** | 明确列入总纲 |
| `tool_call_start` / `delta` / `end` | ✅ **算** | 明确列入总纲 |
| `thinking_delta` | ✅ **按算处理**（保守） | 见下 |

`thinking_delta` 这一格的处理是**保守解释**：思维内容是模型已经产生的输出，部分客户端（Claude Code、Cherry Studio 等）会把它渲染出来。若在已发 `thinking_delta` 后切换，这些客户端同样会看到两段拼接的思考。**宁可让这一路失败，也不冒串话风险**——这与 4.1 的取舍一致。

> **待定**：`thinking_delta` 是否计入"可见内容"。若不渲染思维过程的客户端占多数，可以放宽为"可切换"，从而提升在长思考模型上的成功率。需要按目标客户端实测后拍板。

### 4.3 非流式请求的切换窗口

非流式（`stream:false`）下，切换窗口 = **请求发出 → 收到完整响应之前**。表面上窗口更大，但本质相同：一旦上游开始返回内容，我们就在累积一个"不可撤销的答案"。因此非流式的切换判定用同一套逻辑，只是"吐出"的时机变成了"响应体开始非空"。

### 4.4 切换 vs 重试

两件事必须分开，落在不同的层：

| | 重试 | 切换 |
|---|---|---|
| 对象 | **同一条路径**（同候选同凭据） | 换一条路径 |
| 层 | L3 上游客户端（总纲 6 架构 `call`） | L2 内核 `abstract` |
| 触发 | 连接层失败（总纲 5.3 实测偶发 `http=000`）、超时 | 该路径确定不可用（401/403/额度耗尽/上游 5xx） |
| 幂等要求 | 只在**未产生任何上游副作用**时重试 | 不要求幂等（换了路径） |
| 上限 | 由上游客户端配置 | 由切换预算（4.5） |

**为什么必须分开**：总纲 5.3 实测上游有偶发连接失败，这条必须靠**重试**解决（同一个候选重试就通了，换候选是浪费）；而凭据被封禁这类问题重试多少次都没用，必须靠**切换**。混在一起实现会导致：要么把偶发网络失败当成候选坏掉而误冷却（把好账号踢出池子），要么在凭据被封时反复重试同一个死账号。

### 4.5 切换预算

一次请求的切换次数与总时长都必须有上限，超限后返回错误（不是无限尝试）。

为什么：候选池是众包供给喂出来的，理论上可能存在"一大批候选同时坏掉"的情况。没有预算上限时，一次请求会依次打遍所有候选——用户等到超时，上游侧则被我们的重试放大成一次小规模打击，容易触发上游风控，进而伤到贡献者的账号（总纲 13 章明确把"贡献者凭据被盗用/被封禁"列为高危）。

> **待定**：切换次数上限与单请求总超时。总纲没有给数，需要结合客户端（Claude Code 的超时比较敏感）与实际池子质量压测后定。

## 5. 策略链的组合与保存

| 项 | 规则 |
|---|---|
| 存储 | `abstract_models.strategy`（排序链） |
| 默认值 | `[expiry-first, round-robin]` |
| 组合 | 按顺序生效，前一级相等时看下一级 |
| 重复项 | 拒绝保存（同一策略出现两次无意义，且会掩盖配置错误） |
| 空链 | 视为默认链 |
| 变更 | 进审计；变更后**必须重跑干跑** |

**为什么"重复项"要拒绝而不是静默去重**：管理员手写策略链时写出 `[expiry-first, expiry-first, round-robin]`，通常说明他在试图表达某个别的东西（比如"到期时间一样时再按别的排"），静默去重会把他的意图掩盖掉。报错让他说清楚。

## 6. 干跑校验

总纲 13 章对策："保存前**干跑**（用历史请求回放验证候选可达）；无候选时返回 503 + 明确错误码而非 500"。

### 6.1 干跑做什么

| 检查 | 方法 | 不通过 |
|---|---|---|
| 候选可达性 | 对每条候选 × 凭据路径做一次**只读探测**（`GET /v1/models` 或最小请求） | 报错：不可达 |
| 过滤后为空 | 用**历史请求**回放第①段 | 报错：历史流量会 503 |
| 能力是否够 | 从历史请求里提取真实需求（是否带图 / 上下文多大），对照候选能力 | 警告：部分历史请求将无候选 |
| 排序可产出 | 回放第②段，检查是否产生确定顺序 | 报错：策略链无法产生顺序 |
| 声明是否可信 | 用当前候选重算 `capabilities`，与已保存的声明比对 | 警告：声明将发生变化（客户端可能受影响） |

### 6.2 阻断与警告

- **阻断保存**：候选不可达、过滤后为空、策略链无法产出顺序。
- **仅警告**：能力覆盖不全、声明会变化。

**为什么区分**：前者是"配上去必然出故障"，后者是"配上去可能少用一点"。总纲 13 章的风险对策针对的是前者（全站不可用）；后者只是运营取舍，不该拦住管理员。

### 6.3 没有历史请求时

新建的抽象模型没有任何历史流量，干跑降级为**静态校验**：只跑候选存在性、能力子集、策略链合法性（[02-abstract.md](02-abstract.md) 3.4）。此时**必须告知管理员"未做流量回放"**，不能让一次空跑冒充"已验证"。

**为什么强调这一点**：干跑给人的信心与它的实际覆盖面必须一致。一个跑了 0 条请求的干跑报告如果显示"通过"，会诱导管理员跳过上线后的观察。

## 7. 运行时观测

每次请求都必须能回答三个问题，落进 `requests` 表：

| 问题 | 字段 |
|---|---|
| 最终走了哪个真实模型、哪条凭据 | `resolved_real_model_id`、`resolved_credential_id` |
| 请求的是哪个抽象模型 | `virtual_model_id` |
| 结果如何（含切换了几次） | `status`、`http_status`、`error_code`、`ttft_ms`、`total_ms` |

**为什么切换次数要进日志**：它是**池子质量的直接指标**。切换率高 = 有大量候选在"看起来能用、实际不能用"的状态，说明健康状态判定或有更多结构性问题。这是管理员最需要的一个报警信号。

> **待定**：是否把"切换次数 / 被过滤原因"作为独立字段落库（当前 `requests` 表没有这些列）。加列会增大写放大；不加则只能靠日志文本检索。

## 8. 接口签名

```
-- 三段式主体（纯函数式，便于干跑复用）
Route(req RequestContext, model AbstractModel, paths []Path) -> (Path, RouteTrace)

-- 单段，供干跑与调试分别调用
Filter(req RequestContext, paths []Path)    -> ([]Path, []FilteredOut)
Rank(paths []Path, chain []StrategyID)      -> []Path
SwitchPolicy(req RequestContext)            -> SwitchBudget

-- 干跑
DryRun(model AbstractModel, sample []HistoricalRequest) -> DryRunReport

-- 可见性判定（供第 4 节使用，被流式层调用）
EmittedVisibleContent(streamState) -> bool
```

`Filter` 返回被剔除的路径**及原因**，这样第 2.3 节的"险些可用"诊断和第 7 节的切换率统计都能直接从它派生。

> **待定**：切换次数与过滤原因是否作为独立字段落库，见第 7 节。
