# 策略引擎：过滤 · 排序 · 切换

## 1. 三段式总览

```
① 过滤  能力匹配 · 上下文够长 · 凭据额度充足 · 渠道未禁用 · 健康 · 不在冷却
        · 请求级配额（账户额度 + 所属组共享池）—— 见 2.4，在候选展开**之前**判一次
   ↓
② 排序  管理员手动声明的顺序（声明序即使用序，2026-11-01 定案）
        不可用的排到末尾但不剔除（跳过但保留兜底）
   ↓
③ 切换  候选失败换下一个 —— 仅在「还没吐出任何可见内容」时
```

三段式的输入是 [02-abstract.md](02-abstract.md) 第 3.2 节展开出来的**可路由路径**（候选 × 凭据实例），输出是一条**被选中的路径**。

| 段 | 做什么 | 语义 |
|---|---|---|
| ① 过滤 | 剔除**不可用**的路径 | 硬门槛：不通过 = 不存在 |
| ② 排序 | 按**管理员声明的次序**排位 | 声明即事实：排后面的只在前面不可用时才用 |
| ③ 切换 | 按序尝试，失败换下一个 | 只在**没有可见输出**前有效 |

**为什么必须把三段分开而不是写成一个大函数**：

- **归因**。日志里要能回答"为什么这单走了 B 而不是 A"——是被过滤掉了（能力/额度/健康），还是**在管理员排的次序里本来就靠后**？两者对管理员是完全不同的信号：前者要去修池子，后者去候选集里调顺序。
- **干跑**（第 6 节）需要单独验证每一段。过滤可以静态验证（候选是否存在、能力是否够），排序只能看输出顺序，切换只能在真实流量里验证。
- **可替换**。排序这段曾经是「可插拔的策略链」，但 2026-11-01 定案把它收敛成**唯一形态**（手动序）——可插拔的代价是两套语义并存，而排序的收益并不足以承担它。**过滤**这一段的可增长性已经应验：组级共享池（[../security/03-groups.md](../security/03-groups.md) 第 4 节）就是一个**不属于"候选路径"的过滤条件**，它判的是"这个请求能不能发"，而不是"哪条路能走"，因此单独成 2.4 节，而不是塞进 F1～F8。

## 2. 第一段：过滤

### 2.1 条件清单

| # | 条件 | 判据 | 数据来源 | 不通过时 |
|---|---|---|---|---|
| F1 | **能力匹配** | 本次请求需要的能力（模态 / 工具调用 / JSON mode）候选都支持 | 真实模型 `modalities`、能力探针结果（[05-verification.md](05-verification.md)） | 剔除该路径 |
| F2 | **上下文够长** | 请求估算输入 + 声明的最大输出 ≤ 候选上下文；`context_window` **未知时放行**（2026-10-30 改策：hub 目录只给裸模型 id，目录来源候选窗口恒未知，「未知即剔」曾令整个目录池永远 503；放行的最坏后果是上游报超限，可自愈） | `real_models.context_window`、IR 里的消息长度估算 | 窗口已知且不够 → 剔除；未知 → 放行 |
| F3 | **凭据额度充足** | 承载该路径的凭据还有可用额度 / 未被上游限流 | providers-hub 积分与余额（总纲 5.1） | 剔除 |
| F4 | **渠道未禁用** | 渠道、真实模型、凭据都未被管理员禁用 | `real_models` 状态、凭据 `status` | 剔除 |
| F5 | **健康** | 路径的运行时健康不是 `degraded` 以下 | 运行时健康（[01-catalog.md](01-catalog.md) 第 7 节） | `degraded` **不剔除**（只降权）；`cooldown` / `blocked` 剔除 |
| F6 | **不在冷却** | 该路径没有活动的冷却窗口 | 运行时熔断状态 | 剔除 |
| F7 | **存在可路由路径** | 该候选至少有一条可用的凭据路径 | 运行时展开（[02-abstract.md](02-abstract.md) 3.2） | 剔除该候选 |
| F8 | **弃用链状态正常** | 替代链解析成功（未成环、终点为 `active`） | [04-deprecation.md](04-deprecation.md) 第 2 节 | 见 04 分册：降级为"无替代"，不报错 |

> **术语注意**：F3 判的是**上游凭据**的额度（供给侧，providers-hub 积分/余额），与 2.4 节的**请求级配额**（需求侧，你这个账户这个组还能不能再要）是两件不同的事。总纲 3.3 的"额度充足"指的是 F3；2.4 是本次细化新增的一道闸。
>
> 说明：F1～F8 全部是总纲 3.3 过滤条件清单（能力匹配 · 上下文够长 · 额度充足 · 渠道未禁用 · 健康 · 不在冷却）的**可判定化**，其中 F7 / F8 是"路径存在性"与"替代链"这两件在三段式之前就已经发生的事，列在这里是为了让实现有一个完整清单，不引入新条件。

### 2.2 过滤是硬门槛，不降权

**不通过 = 这条路径在本次请求里不存在**，绝不"排到最后再试一次"。

为什么：

- **能力不匹配的候选，重试多少次都不会成功**（把图片发给不支持视觉的模型，永远是 400）。把它留在候选列表里只会浪费一次尝试窗口，而这个窗口在流式场景下极其宝贵（第 4 节）。
- **额度耗尽的凭据重试会加重上游风控**。总纲 13 章把"贡献的凭据被上游封禁"列为风险，对策是候选级熔断 + 冷却 + 降权。如果过滤阶段不把没额度的凭据剔掉，熔断阈值会被大量必然失败的请求迅速打满，好的凭据也跟着被冷却。
- **降权是排序的事**。健康为 `degraded`（有失败也有成功）的路径**不剔除**，靠 [01-catalog.md](01-catalog.md) 7.2 的降权 + 第 3 节的 `speed` 处理（失败率高的路径延迟与成功率双双变差，会自然排到后面）——它还能用，只是别优先用。把"还能用"和"不能用"混在一个机制里会同时丢这两件事。

### 2.3 过滤后为空

返回 **503 + 专用错误码 `no_candidate`**（[02-abstract.md](02-abstract.md) 6.5），**不是** 500。

同时必须落一条可诊断的记录：**过滤后为空时，记录"如果在更早的某一级放宽该条件，还剩几条路径"**（例如"若忽略健康，还剩 2 条"）。为什么：503 是管理员最常遇到的故障，而"所有候选都被过滤了"这句话没有信息量。有了这级"险些可用"的诊断，管理员一眼能看出是池子空了、还是健康全红了、还是额度全干了。

> **待定**：`no_candidate` 的错误体内是否暴露"原因分类"（池子空 / 能力不匹配 / 全冷却 / 全无额度）。暴露便于用户自助排查，但也把供给结构漏给租户；建议只给**分类**不给数量与模型名。

### 2.4 请求级配额：两道闸

F1～F8 判的是**单条候选路径**能不能走；本节判的是**这个请求本身该不该被受理**。两者性质不同：
前者决定"去掉哪条路"，后者决定"要不要发这一单"。因此它**在候选展开之前**先判一次，不通过就整体拒绝，
不进入候选筛选，也不消耗切换预算。

| # | 闸 | 判据 | 数据来源 | 不通过时 |
|---|---|---|---|---|
| Q1 | **账户额度** | 本账户当期已用量 + 本次估算 ≤ 该 (unit, period) 的额度行（`account_quotas` 合计行；请求命中的抽象模型另有按模型限额行时再判一行） | `account_quotas` 当期行 | 429 `quota_exceeded`（按模型行命中时错误体带 `model`） |
| Q2 | **所属组共享池** | 所属组中**所有**已配置的池都满足 `pool_used + cost <= pool_limit` | `group_quota_pools`（**在结算时由单条条件 UPDATE 权威判定**，见下） | 429 `pool_exhausted` |

**"未配置"与"配置为 0"必须区分**：某组没设池（数据库里没有那一行）时 Q2 **不构成一道闸**，不是"额度为 0 所以全拒"；
账户额度未设同理。为什么：把"未配置"解释成 0 会让所有组默认全停，而把 0 解释成"不设"会让一个想全停的配置静默失效。
两者是相反的错误，所以数据层用"有行/无行"承载它（[../architecture/05-storage.md](../architecture/05-storage.md#33-组与授权) 的"不设池 = 没有这一行"），
过滤段不需要任何额外分支。**两种限制都不设 = 该请求在配额维度上不受约束**，但仍受全局预算熔断与速率限制约束。

**判定顺序：Q1 先、Q2 后，且 Q1 失败即短路。** 为什么：Q1 是一次按 `(day, account_id)` 的等值查询（廉价），
Q2 最终落在一次带条件的原子 `UPDATE` 上（相对贵）。把便宜的放前面，可以让"本就被账户额度挡住"的请求
根本不碰池。这是纯性能选择，**不改变语义**——两道闸是交集，谁先拒都是拒。

**关键的实现约束：Q2 在这里是"预判"，不是"判定"。** 真正的判定只发生在结算时那条
`UPDATE … WHERE pool_used + :cost <= pool_limit`（[../architecture/05-storage.md](../architecture/05-storage.md#74-组级共享池的并发扣减与惰性重置)）。
过滤阶段只能做一次**不加锁的读**（读当前 `pool_used`），它可能因为并发而乐观通过。
为什么仍要读一次：如果不读，请求会先经过完整的排序与切换、打到上游、拿到 token，才在结算时被拒——
那时代价已经付出（上游额度真实消耗、用户白等一个响应）。所以**过滤阶段读一次用来"早点拒"，
结算阶段那条 `UPDATE` 才是"绝不超卖"的权威**。两层职责不同，不能合并成一层。

**Q2 耗尽时是"整体拒绝"还是"过滤掉某个候选"？** 整体拒绝。为什么：

- 池是**组级**资源，与候选无关——换一个候选、换一个真实模型、换一条凭据，消耗的仍是同一个池子。把池判据挂到候选上，会得到一个可笑的结论：某个候选因池子耗尽被剔除，另一个候选却仍在，而后者同样会撞同一个池。
- 若把它做成"过滤掉候选"，池子耗尽将表现为 `no_candidate`（503，"供给侧没有可用的路"），而用户与运维该得到的信号是"额度用完了"（429）。**这两件事的可操作动作完全相反**：前者要去看上游健康与凭据，后者只能等重置或找管理员（详见 [../security/03-groups.md](../security/03-groups.md) 第 4 节"池子耗尽的错误码与文案"）。
- 同理，池子耗尽**不消耗切换预算**（[4.5](#45-切换预算)）——换路解决不了配额问题，让它消耗预算只会把一个额度问题伪装成"全都试过了还是失败"。

### 2.4.1 额度在账户级，不在 Key 级

Q1 判的是**账户**，不是 Key。这看着是细节，但它是一条必须钉死的口径：

| 层级 | 持有的额度 | 为什么 |
|---|---|---|
| **账户** | `account_quotas` 的合计行 + 按模型限额行 + `rpm_limit` / `tpm_limit` / `max_concurrency`（-1 = 不限） | 一个账户就是一个计费与限流的整体 |
| **Key** | **没有任何额度字段** | 它只回答“这是什么身份”，不回答“能用多少” |

**Key 还剩什么能力**：认证（它是什么身份）、**模型白名单**（`key_model_allow`，只能从账户可访问的抽象模型里**收窄**，不能放大）、生命周期（创建/禁用/过期/吊销）。

**为什么额度必须上提到账户级**：否则“同一账户多开 10 把 Key”就等于额度翻 10 倍，账户级额度形同虚设。这把 Key 从“一个配额容器”降为“一个可吊销的凭证”——而它本来就应该只是后者：如果用户需要两份独立额度，他要的是**两个账户**，不是两个 Key。

**写文档与写代码时的口径陷阱**：凡是出现“Key 的额度”“每把 Key 的 rpm”“Key 打满日额度”的地方，一律改为**账户级**表述。

| 错误说法 | 正确说法 |
|---|---|
| 该 Key 打满日额度 → 拒绝 | 该账户日额度打满 → 拒绝（该账户所有 Key 一起被拦） |
| 这把 Key 的并发不够 | 该账户并发已达 `max_concurrency` |

**一个直接推论：额度耗尽不可能是“某个 Key 的问题”**，所以错误响应里没有任何理由拿 `key_id` 作为原因——带上了只会让用户去删 Key 重试，而问题根本不在那里。

**Q1 与 Q2 的记分与归因必须分开**：请求记录里 `error_code` 分别是 `quota_exceeded` 与 `pool_exhausted`,
后者额外带 `group_id`。为什么：一个组的池子天天耗尽是**运营信号**（该扩容或该拆组），
一堆账户额度耗尽是**增长信号**（用户变多了）。混在一个码里，这两条曲线就看不出来了。

> **待定**：Q2 的"预判读"要不要也缓存（如每 5 秒一次的进程内快照）。倾向**不缓存**：池子是全组争用的资源，
> 缓存会让"已经耗尽"的组在缓存窗口内继续放行请求，而收益只是省一次命中主键的读。需与整体缓存策略一起拍板。

### 2.5 额度计量：三种维度

额度不是一个数，而是**按维度计的量**。一条额度配置可以是下列三种之一，也可以同时设多种：

| 维度 | 单位 | 怎么算 |
|---|---|---|
| `request` | 次数 | 一次请求 = 1，与 token 无关 |
| `token` | token 数 | `in_tokens + out_tokens` |
| `credit` | Credits | 按价格乘数折算，见 2.5.2 |

**同时设多种时各自独立判定，哪个先到算哪个**。为什么不做加权合成：三项的单位根本不同（次 / token / Credits），合成需要一个人为的权重，而那个权重会成为第二个无人能解释的参数；分开判则每条额度都有自己的、可直接向用户解释的含义（“你这个月次数用完了”）。

#### 2.5.1 为什么需要三种而不是一种

| 维度 | 它拦的是什么 | 只用别的一种会错在哪 |
|---|---|---|
| `request` | 高频小请求（探测、健康检查、脚本循环） | 只按 token 计，一万次空请求几乎不耗 token，但会把上游连接与 QPS 配额吃满 |
| `token` | 大上下文、长输出 | 只按次数计，一个 1M 上下文请求与一个 10 token 请求同价 |
| `credit` | 不同模型的**价格差异** | 只按 token 计，用贵模型与用便宜模型一样价，等于鼓励打贵模型 |

三者是**三个正交的滥用面**，合成一个维度必然漏掉至少一个。

#### 2.5.2 Credits 的算法

以 `deepseek-flash` 为基准（乘数 = 1），其他模型按价格乘数放大：

```
credits = (in_tokens * in_multiplier + out_tokens * out_multiplier) / BASE
```

| 项 | 含义 |
|---|---|
| `in_multiplier` / `out_multiplier` | 该模型输入 / 输出的价格乘数（相对 `deepseek-flash`） |
| `BASE` | 基准常数，使 `deepseek-flash` 的 1 token ≈ 1 credit 的量级 |
| 输入与输出分开 | 因为几乎所有上游的输入与输出单价都不同（输出通常贵 2～4 倍） |

- **内置一份常见模型价格表**，**表里没有的模型乘数默认 1**；
- 管理员可以在管理面**手动调整**任意模型的乘数（改动进审计）；
- 价格乘数表与 `price` 排序策略（3.1）**共用同一份数据**。

**为什么乘数表里没有就默认 1**：乘数表是个不完整的知识库，它不可能追上新模型出现的速度；而默认值必须是“不会把流量畸形的值”——若默认成 0，新模型完全免费（鼓励滥用），若默认成一个大数，新模型无人使用。默认 1 = “按基准价收费”，它是**不被惩罚的中间态**，并且管理员一旦发现某个新模型很贵，补一条即可。

**为什么价格表与 `price` 策略共用一份数据**：否则会出现一个自相矛盾的场景——“计费认为 A 比 B 贵，但对账说 B 更优先”。同一份乘数表是两个功能的共同真相，改一处两边同时生效，管理员也只需要学习一个概念。

**数据模型**：额度表（`accounts` 的额度字段）加 `unit` 字段，取值 `request` / `token` / `credit`；`group_quota_pools` 的 `unit` 也走这三值。

### 2.6 扣减时机：请求结束后立即扣减

“实时扣减”的准确含义是：**一次请求结束后立马扣减，不是流式逐段扣**。

| 情形 | 是否扣 | 为什么 |
|---|---|---|
| 请求成功，拿到 usage | 扣 | 这是正常路径 |
| 请求失败但上游已产生消耗（如上游 500 但已算 token） | **按实际 usage 扣** | 上游已经真真切切消耗了我们的额度；不扣就等于平台替这次失败买单 |
| 完全没打到上游（本地拒绝） | **不扣** | 没有产生任何成本 |

**扣减在同一次事务里**：写用量 + 扣额度必须原子，否则会出现“用量记了但额度没扣”或反之的账实不符。

**为什么不是流式逐段扣**：

- 流式下一个请求会产生几十到上百个 chunk，逐段扣就是几十次写事务，对数据库是纯粹的写放大；
- 中途断开时已扣的量与实际 usage 对不上，还得做补偿逻辑；
- 而“结束后扣”在**语义上无损**。后文两条约束（在途不占额度、结算条件 UPDATE 权威）已经保证了不超卖。

**两个已有说清楚的点必须保留**：

1. **在途请求不占额度**，所以超发上界 = 峰值并发 × 单请求消耗。这是“结束后扣”的必然代价，也是它的可量化代价——管理员可以据此判断并发上限该定多少。
2. **组共享池的权威判定在结算那条条件 `UPDATE` 上**，过滤段的检查（Q2）只是**预判**。

## 3. 第二段：排序（2026-11-01 定案：管理员手动排序）

### 3.1 语义：声明序即使用序

> **定案（2026-11-01，用户）**：候选的使用顺序改为**管理员手动排序**，
> 仅当前一个不可用时才使用下一个。

```
候选的使用顺序 = 管理员在候选集编辑器里排列的顺序（abstract_candidates.sort_order）
                ↓
       仅当前一个候选被判定「不可用」时，才使用下一个
```

规则的三个组成部分，每一部分都对应一个实现事实：

| 规则 | 含义 | 实现落点 |
|---|---|---|
| **声明序即使用序** | 候选数组的先后就是实际尝试的先后，没有任何测量量重新排列它们 | `abstract_candidates.sort_order`（迁移 0008）；`routing.Order` 原样保持该次序 |
| **不可用才跳下一个** | 在册（可用）的候选没有「轮换」「平摊」——第一个能用的就一直是第一个 | `routing.Order` 只做一次稳定分区，不比较任何键 |
| **不可用不是剔除** | 不可用的候选排到末尾但仍在场；全池都不在册时按序兜底试一遍 | `routing.Order` + `routing.Cooldowns.Apply`；见 3.3 |

**为什么手动序取代了自动策略**（这是本次定案最需要写下来的理由）：

- **自动排序的输入都是近似值**。到期时间、余额、TTFT 都来自上游的**不完整**披露（很多渠道不报余额、目录不提供窗口）。同一份配置在不同测量状态下会给出不同顺序——故障因此**不可复现**：管理员照着重现步骤走，得到的是另一个顺序。
- **两套语义并存的成本**。若保留成「可选模式」，管理员必须理解「什么时候该用哪套」，而这个判断本身没有客观依据；它把一个本该是配置的问题变成了一个需要领域经验的问题。
- **手动序天然可解释**。trace 里的顺序就是管理员排的顺序，不需要再解释「为什么 B 排在 A 前面」——那是策略的输出，不是人的决定。归因因此收敛到一句话。

### 3.2 已退役的策略（连同它们的脚手架）

原有的四种内置排序策略与平局决胜**整体退役**，不留「可切回」开关：

| 旧策略 | 原按什么排 | 处置 |
|---|---|---|
| `expiry-first` | 额度作废时间升序 | **退役**（连同比较器、`orderFuncs` 注册表、链校验） |
| `balance` | 余额升序 | **退役**；`BalanceLoop`（后台 provider 余额探测）随之删除——它只为这个键供数 |
| `speed` | 最近 TTFT / 总耗时升序 | **退役**；`LatencySampler` 的读面从路由移除（采样器本身保留给用量大屏） |
| `price` | Credits 价格乘数升序 | **退役**（价格乘数表本身保留，它仍服务于额度计量 §2.5.2） |
| `round-robin` | 平局组内轮转 | **退役**，连同按抽象模型持有的游标（`RoundRobinCursor`） |

**删除而不是停用**：一个「配置了但不再生效」的策略链会让管理端显示一行看起来还在工作的配置，而线上行为与它无关——那是下一次排查最大的陷阱。`abstract_models.strategy` 列也随迁移 0014 一起 `DROP COLUMN`。

### 3.3 不可用候选的处理：跳过但保留兜底

| 情形 | 行为 | 为什么 |
|---|---|---|
| 候选**在册**（可用） | 按声明序参与，排在所有不可用候选之前 | 声明序就是唯一的次序来源 |
| 候选**不可用**（在不可用台账里） | 排到声明序的末尾，**不剔除** | 见下 |
| **全部候选都不可用** | 仍按声明序返回完整序列，依次试一遍 | 台账可能已经过时（探测最长 1h 一轮），而「还能试一次」永远优于 503 |

**为什么不剔除不可用候选**：剔除会让「一次误判」直接变成 `no_candidate`（503）。误判的来源很多——上游抖动、临时 401、网关抽风——它们都可能在几十秒内自愈，而此刻池子里可能只有这一条候选。**503 与「还能试一次的」之间，永远选后者**。

分区分两层，语义各不相同（都在末尾，但顺序有讲究）：

```
在册且不冷却 → 冷却中 → 不可用（最末尾）
```

- **冷却**（`routing.Cooldowns`，30s 量级）说的是「它刚失败过，别立刻再打」；
- **不可用**（`model_unavailability` 台账）说的是「探测确认过它坏了」。

后者更硬，所以排得更后。一次**真实成功**会同时清掉两者（`Cooldowns.Clear` + 台账出册）——否则会出现「台账里已经没有它，但它还排在最后一位」这种自相矛盾的状态。

### 3.4 不可用台账与指数退避探测

> **定案（2026-11-01，用户）**：记录每个不可用的模型，使用指数退避循环检测
> （超过 1h 后每 1h 检测一次）是否可用。

#### 3.4.1 记账口径：哪些失败够格

**唯一的判定事实源是 `classifyAttemptFailure`**（`internal/app/unavailability.go`）。记账与不记账各有明确理由：

| 失败类 | 记不记 | 理由 |
|---|---|---|
| `upstream_auth`（401/403） | ✅ 记 | 凭据坏了，换请求也救不了 |
| `upstream_quota`（额度耗尽） | ✅ 记 | 同上 |
| `upstream_5xx` | ✅ 记 | 上游服务端坏了 |
| `connect` / `tls` / `conn_reset` / `timeout` | ✅ 记 | 端点挂了或网络不通 |
| `protocol`（响应不可解析） | ✅ 记 | 协议层坏了（自建网关吐半截 JSON 的典型形态） |
| **`rate_limited`（429）** | ❌ **不记** | 「现在太挤」，几十秒后自己好。记了会把一个健康模型因一次限流压到末尾并开始 1h 级探测周期——这是本机制最容易造成的误伤。冷却账本已覆盖「别立刻再打」 |
| `bad_request` / 请求侧问题（能力缺失、方言冲突） | ❌ 不记 | 换一次请求就好了，让上游背锅会永久误伤 |
| `internal_bug` | ❌ 不记 | 我们的程序错 |
| **认不出类**的错误 | ✅ 记（原因码 `unknown`） | 偏向记入：漏记的后果是反复打坏上游；误记的代价只是多一次后台探测（成功即出册） |

#### 3.4.2 退避曲线

```
attempts:  1    2    3    4     5     6     ≥7
间隔:      1m   2m   4m   8m   16m   32m   1h（封顶，此后恒 1h）
```

**封顶后恒 1h 而不是继续翻倍**：继续翻倍会让一个 6 小时才能恢复的上游被排到「下次检测：明天」，而「超过 1h 后每 1h 检测一次」正是用户定案可接受的最坏恢复延迟上限。`attempts = 0` 或负数按 1 次处理——**绝不返回 0 间隔**，否则探测循环会每 tick 都打上游。

#### 3.4.3 探测方式：真实推理 ping

| 为什么不用「列模型 / HEAD」 | 为什么用真实推理 |
|---|---|
| 轻量检查只能证明网络与凭据通，**证明不了这个模型本身可服务**。模型下线/改名/配额耗尽的典型表现正是「网关 200，但这个模型 404/400」 | 打穿「候选 → 凭据 → 出站 → 响应解析」全链路，与业务流量同一条管线、同一个出站面板 |

参数：`max_tokens = 256`（**不是 1**——推理型模型会把 1 个 token 全花在思考上、返回零内容块，把「正常服务」误判成不可用）；单条超时 30s；单轮最多 8 条；扫描 tick 30s。

#### 3.4.4 排期落库，不落进程内

排期是小时级的，**进程重启不该把排期清零重新从 1m 开始**——那等于每次重启都白打一轮探测（打上游、花额度）。所以台账落库（`model_unavailability`），内存视图只是热路径的读缓存（写穿库）。

#### 3.4.5 恢复的三条路径

| 触发 | 行为 | 为什么 |
|---|---|---|
| **一次真实流量成功** | 立即出册 + 清冷却 | 最快、最权威的恢复信号；不必等探测周期 |
| **后台探测成功** | 出册 | 覆盖「没有流量」的抽象模型 |
| **行被删除 / 上游停用 / 已排除出候选** | 出册（不算「恢复」） | 那是「不该用」不是「不可用」。留着会让管理端看到不存在的模型「仍不可用」——僵尸记录 |

### 3.5 确定性与可复现

手动序的确定性是**结构性**的：没有比较器、没有测量输入，所以没有「稳定排序」这回事——切片的先后就是唯一的次序来源。同样输入必然同样输出，且**不需要任何样本量前提**（旧策略的「冷启动无样本」问题随之一并消失）。

`routing.Order` 还保证两条实现纪律：

1. **返回副本**：调用方手里的 paths 还会被 trace/诊断复用，返回同一段底层数组会让「排位前」与「排位后」变成同一个观察点。
2. **不做二次比较**：`Unavailable` 分区内部保持原相对序（不排序、不去重）。

### 3.6 trace 里怎么记录

`x-fr-trace` 的 `order` 数组就是最终尝试顺序，每项带 `unavailable` / `cooled_down` 标记；`order_mode` 恒为 `"manual"`（原 `strategy` 数组已彻底消失）。`build_trace` 不再收 chain 参数——**没有链**。

## 4. 第三段：切换

### 4.1 唯一的硬约束

> 一旦已经向客户端吐出**可见内容**（文本 / 工具调用），就**不能**再换候选。

这是全篇最重要的一条，总纲 3.3 原文："流式串话是 providers-hub 已经踩过的坑"。

**为什么**：切换发生在 HTTP 响应已经开始写之后。此时前一个候选已经写了 `text_delta`，如果换一个候选从头开始生成，客户端会看到**两段拼接的内容**（前一半来自 A，后一半来自 B），而且：
- 流式协议上我们无法"撤回"已发的分片；
- A 和 B 是两个不同模型，风格与上下文理解不一致，拼接结果可能语义错乱；
- 用户会把它当作我们的模型质量问题，而不是上游故障。

**代价我们接受**：这一路请求失败、用户看到错误。因为"明确失败"远比"悄悄给出错误答案"好——后者用户可能直接拿去用了。

### 4.2 什么是"可见内容"

按总纲 6.1 的流式事件定义逐项判定：

| 事件 | 是否算已吐出可见内容 | 说明 |
|---|---|---|
| `start` | ❌ 不算 | 只有元信息，还没有任何模型产出 |
| `usage` | ❌ 不算 | 只有计数 |
| `error` | ❌ 不算 | 本身就是失败信号 |
| `done` | — | 请求已结束，不涉及切换 |
| `text_delta` | ✅ **算** | 明确列入总纲 |
| `tool_call_start` / `delta` / `end` | ✅ **算** | 明确列入总纲 |
| `thinking_delta` | ✅ **按算处理**（保守） | 见下 |

`thinking_delta` 这一格的处理是**保守解释**：思维内容是模型已经产生的输出，部分客户端（Claude Code、Cherry Studio 等）会把它渲染出来。若在已发 `thinking_delta` 后切换，这些客户端同样会看到两段拼接的思考。**宁可让这一路失败，也不冒串话风险**——这与 4.1 的取舍一致。

> **待定**：`thinking_delta` 是否计入"可见内容"。若不渲染思维过程的客户端占多数，可以放宽为"可切换"，从而提升在长思考模型上的成功率。需要按目标客户端实测后拍板。

### 4.3 非流式请求的切换窗口

非流式（`stream:false`）下，切换窗口 = **请求发出 → 收到完整响应之前**。表面上窗口更大，但本质相同：一旦上游开始返回内容，我们就在累积一个"不可撤销的答案"。因此非流式的切换判定用同一套逻辑，只是"吐出"的时机变成了"响应体开始非空"。

### 4.4 切换 vs 重试

两件事必须分开，落在不同的层：

| | 重试 | 切换 |
|---|---|---|
| 对象 | **同一条路径**（同候选同凭据） | 换一条路径 |
| 层 | L3 上游客户端（总纲 6 架构 `call`） | L2 内核 `abstract` |
| 触发 | 连接层失败（总纲 5.3 实测偶发 `http=000`）、超时 | 该路径确定不可用（401/403/额度耗尽/上游 5xx） |
| 幂等要求 | 只在**未产生任何上游副作用**时重试 | 不要求幂等（换了路径） |
| 上限 | 由上游客户端配置 | 由切换预算（4.5） |

**为什么必须分开**：总纲 5.3 实测上游有偶发连接失败，这条必须靠**重试**解决（同一个候选重试就通了，换候选是浪费）；而凭据被封禁这类问题重试多少次都没用，必须靠**切换**。混在一起实现会导致：要么把偶发网络失败当成候选坏掉而误冷却（把好账号踢出池子），要么在凭据被封时反复重试同一个死账号。

### 4.5 切换预算

一次请求的切换次数与总时长都必须有上限，超限后返回错误（不是无限尝试）。

为什么：候选池是众包供给喂出来的，理论上可能存在"一大批候选同时坏掉"的情况。没有预算上限时，一次请求会依次打遍所有候选——用户等到超时，上游侧则被我们的重试放大成一次小规模打击，容易触发上游风控，进而伤到贡献者的账号（总纲 13 章明确把"贡献者凭据被盗用/被封禁"列为高危）。

> **待定**：切换次数上限与单请求总超时。总纲没有给数，需要结合客户端（Claude Code 的超时比较敏感）与实际池子质量压测后定。

## 5. 候选顺序的组合与保存

| 项 | 规则 |
|---|---|
| 存储 | `abstract_candidates.sort_order`（迁移 0008；整表替换时按入参顺序编号） |
| 表达 | 候选集编辑器里排列的先后，**没有别的地方能影响它** |
| 保存 | `PUT /admin/abstract-models/{id}/candidates` 整表替换（数组顺序 = 新顺序） |
| 校验 | 候选必须存在、不重复；`real_model_id` 形状合法 |
| 变更 | 进审计（旧集合进 `Detail`） |

**为什么用「整表替换」而不是增量的上移/下移端点**：候选是一个集合，增量 API 在并发下会丢更新（两个人同时调序，最终顺序取决于谁最后提交，而中间态谁也说不清）。整表替换让「保存后的顺序」只有一个来源：那一次 PUT 的数组。

**一次保存 = 一次顺序变更**，所以保存后**不需要**重跑干跑：干跑校验的是「候选可达 / 过滤后是否为空 / 能力声明是否可信」，这些都不随顺序变化。顺序只改变「先试谁」，不改变「能不能试」。

## 6. 干跑校验

总纲 13 章对策："保存前**干跑**（用历史请求回放验证候选可达）；无候选时返回 503 + 明确错误码而非 500"。

### 6.1 干跑做什么

| 检查 | 方法 | 不通过 |
|---|---|---|
| 候选可达性 | 对每条候选 × 凭据路径做一次**只读探测**（`GET /v1/models` 或最小请求） | 报错：不可达 |
| 过滤后为空 | 用**历史请求**回放第①段 | 报错：历史流量会 503 |
| 能力是否够 | 从历史请求里提取真实需求（是否带图 / 上下文多大），对照候选能力 | 警告：部分历史请求将无候选 |
| 排序可产出 | 检查保存后的候选数组是否非空且无重复（手动序恒能产出确定顺序） | 报错：候选集为空 |
| 声明是否可信 | 用当前候选重算 `capabilities`，与已保存的声明比对 | 警告：声明将发生变化（客户端可能受影响） |

### 6.2 阻断与警告

- **阻断保存**：候选不可达、过滤后为空、候选集为空。
- **仅警告**：能力覆盖不全、声明会变化。

**为什么区分**：前者是"配上去必然出故障"，后者是"配上去可能少用一点"。总纲 13 章的风险对策针对的是前者（全站不可用）；后者只是运营取舍，不该拦住管理员。

### 6.3 没有历史请求时

新建的抽象模型没有任何历史流量，干跑降级为**静态校验**：只跑候选存在性、能力子集、候选集非空（[02-abstract.md](02-abstract.md) 3.4）。此时**必须告知管理员"未做流量回放"**，不能让一次空跑冒充"已验证"。

**为什么强调这一点**：干跑给人的信心与它的实际覆盖面必须一致。一个跑了 0 条请求的干跑报告如果显示"通过"，会诱导管理员跳过上线后的观察。

## 7. 运行时观测

每次请求都必须能回答三个问题，落进 `requests` 表：

| 问题 | 字段 |
|---|---|
| 最终走了哪个真实模型、哪条凭据 | `resolved_real_model_id`、`resolved_credential_id` |
| 请求的是哪个抽象模型 | `virtual_model_id` |
| 结果如何（含切换了几次） | `status`、`http_status`、`error_code`、`ttft_ms`、`total_ms` |

**为什么切换次数要进日志**：它是**池子质量的直接指标**。切换率高 = 有大量候选在"看起来能用、实际不能用"的状态，说明健康状态判定或有更多结构性问题。这是管理员最需要的一个报警信号。

> **待定**：是否把"切换次数 / 被过滤原因"作为独立字段落库（当前 `requests` 表没有这些列）。加列会增大写放大；不加则只能靠日志文本检索。

## 8. 接口签名

```
-- 三段式主体（纯函数式，便于干跑复用）
Route(req RequestContext, model AbstractModel, paths []Path) -> (Path, RouteTrace)

-- 单段，供干跑与调试分别调用
Filter(req RequestContext, paths []Path)    -> ([]Path, []FilteredOut)
Rank(paths []Path, chain []StrategyID)      -> []Path
SwitchPolicy(req RequestContext)            -> SwitchBudget

-- 干跑
DryRun(model AbstractModel, sample []HistoricalRequest) -> DryRunReport

-- 可见性判定（供第 4 节使用，被流式层调用）
EmittedVisibleContent(streamState) -> bool
```

`Filter` 返回被剔除的路径**及原因**，这样第 2.3 节的"险些可用"诊断和第 7 节的切换率统计都能直接从它派生。

## 9. 待定项汇总

> **待定**：`abstract_candidates.weight` 是彻底移除还是改作纯展示字段（内置四种策略已不读它），见第 3.3.2 节。

> **待定**：`thinking_delta` 是否计入"可见内容"，见第 4.2 节。

> **待定**：单请求切换次数上限与总超时，见第 4.5 节。

> **待定**：切换次数与过滤原因是否作为独立字段落库，见第 7 节。

> **待定**：Q2 的"预判读"是否加进程内缓存，见第 2.4 节。倾向不缓存（池是全组争用资源，缓存窗口内会继续放行已耗尽的组）。

> **待定**：Q1（账户额度）与 Q2（组池）在**同一请求**里是否会同时不满足，以及此时先报哪个。当前实现顺序是先 Q1 后 Q2，
> 因此会报 `quota_exceeded`；但"两个都不满足"其实意味着这个用户**双重受限**，可能需要一条独立的诊断信息给管理员
> （不是给用户）——待与用量页/审计的落库字段一起定。
