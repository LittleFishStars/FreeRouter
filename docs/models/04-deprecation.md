# 弃用与替代链

## 1. 三种状态

### 1.1 状态定义

抽象模型在任一时刻处于三态之一：

| 状态 | 对外可见 | 接受请求 | 行为 |
|---|---|---|---|
| `active` | 是 | 是 | 正常路由 |
| `deprecated` | **是** | **是**（仍然接受请求） | 内部路由到**替代目标**，响应附 `Deprecation` 等头 |
| `disabled` | 否 | 否 | 404 / **410 Gone** |

### 1.2 弃用 ≠ 关闭

**弃用是"通知 + 继续服务"，不是关闭**。这是总纲 3.5 的核心决策，也是 RFC 9745 的原意。

为什么：

- 客户端配置里写死的是抽象模型名。如果我们直接 404，所有用户会在同一秒集体爆掉，然后来问"为什么突然不能用了"——而他们什么错都没犯。
- 我们**有能力继续服务**：这个抽象模型的候选池里还有别的可用真实模型。既然能继续服务，就没有理由制造一次全站投诉。
- 迁移需要时间。用户要改配置、要测试、要发版。`deprecated` 状态 + `Deprecation` / `Sunset` 响应头正好把这个迁移窗口的表达方式标准化了：客户端与用户能从 HTTP 响应里读到"此物将废、何时废、去哪看"。

### 1.3 状态迁移

```
active --(管理员弃用)--> deprecated --(到达 sunset_at，自动)--> disabled
                              |                                    ↑
                              +--(管理员手动提前关闭)--------------+
disabled --(管理员重新启用)--> active        （替代配置保留）
```

| 迁移 | 触发 | 副作用 |
|---|---|---|
| `active → deprecated` | 管理员操作 | **必须**指定替代目标并通过能力校验（第 4 节）；启用后开始发响应头 |
| `deprecated → disabled` | `sunset_at` 到期自动 / 管理员手动 | 从 `/v1/models` 消失；请求返回 410；审计 |
| `disabled → active` | 管理员手动 | 清除 `deprecated_at` / `sunset_at` 或保留历史（见待定） |

**为什么到期要"自动"关闭**：`Sunset` 是一个对外承诺的日期。承诺了却因为管理员忘了点按钮而没关，等于我们的头在说谎；更糟的是，用户会据此认为"这个日期不重要"，从此忽略我们所有的声明。让数据库/定时任务来执行已声明的日期，是把承诺变成硬约束。

> **待定**：`disabled → active` 回滚时，`deprecated_at` / `sunset_at` 是清空还是保留为历史字段。保留便于审计，但显示逻辑要明确"曾经的弃用日期不再有效"，否则会误导。

> **待定**：`disabled` 返回 404 还是 410。总纲写的是"404/410 Gone"，两者对客户端行为影响不同（404 让客户端认为模型不存在，410 明确告知已永久移除），且 410 会泄露"这个模型曾经存在"。

## 2. 替代链

### 2.1 链的表示

`abstract_models.replacement_model_id` 是**自引用**：弃用的模型指向替代它的另一个抽象模型，后者自身也可以处在 `deprecated` 状态，于是形成一条链。

```
Alice 的旧配置 ──> A(old) ──> B(old) ──> C(active)
                    第 1 手     第 2 手    链终点
```

### 2.2 多跳与上限

| 项 | 取值 | 理由 |
|---|---|---|
| 跳数上限 | **5 跳** | 超过 5 跳的链在实践中已经是"管理失控"的信号；同时它给了运行时一个硬上界 |
| 链是否压缩 | **不压缩**，保留"第几手" | 见 2.3 |
| 达到上限 | 降级为"无替代"，**不报错** | 见 2.5 |

### 2.3 为什么不把链压平

一个常见做法是"发现 A → B → C 就把 A 直接指向 C"，让链永远只有一跳。我们不这么做：

- **链里每一跳都承载着一个日期**。`A` 的 `Sunset` 可能是明天，`B` 的是下个月，`C` 是长期模型。若把 `A` 压平成 `C`，我们就丢失了"A 明天就该消失"这条信息，用户的迁移看起来比实际更宽松。
- **多跳能表达"分阶段迁移"**。管理员常常这样设计：先把 `smart` 切到 `smart-v2`，几个月后 `smart-v2` 再被 `smart-v3` 取代。压缩会把这个时间结构抹掉。
- **调试需要**。用户的请求打到 `A` 却走成了 `C` 时，管理员需要看到中间这一跳是谁把谁换了。

### 2.4 环检测

两处都要有，缺一不可：

| 位置 | 时机 | 作用 |
|---|---|---|
| **配置时** | 保存替代关系那一刻，沿 `replacement_model_id` 走一遍 | 报错并**拒绝保存**，让管理员当场看到环 |
| **运行时** | 解析链时维护 `visited` 集合 | **兜底**：防止历史数据、并发写入或直接改库造成的环把请求打成无限循环 |

**为什么两处都要**：配置时检测是"防患于未然"，但它挡不住所有路径——两个管理员并发把 A→B 和 B→A 同时存下来，或者有人直接改库，链就成环了。运行时 `visited` 是最后一道防线，且它的成本极低（一个哈希集合）。

### 2.5 检出环 / 超限时的降级

**降级为"无替代"，不报错**——即按"这个模型没有替代目标"处理。

为什么不是报错：报错的后果是用户拿到 500 或奇怪的错误码，而"无替代"至少是一个**语义明确**的结果（→ 该模型自身没有可用候选时返回 503 `no_candidate`）。故障链里，一个破损的配置不应该把请求变成 500；它应该是"配置坏了，服务降级但语义清晰"。

同时必须**告警**：环与超限都是配置事故，管理端要有显著告警（展示落点见 [../ui/03-admin.md](../ui/03-admin.md)，审计留痕见 [../security/06-audit.md](../security/06-audit.md)）。

## 3. 响应头

`deprecated` 状态下的每次成功响应都带这三个头。**两个日期头的格式不同**，这是本节最容易写错的地方。

### 3.1 `Deprecation`（RFC 9745）

```
Deprecation: @1688169599
```

- 值是一个 **Structured Field Date**：`@` + Unix 秒。
- 它表示"**此资源从此刻起已被弃用**"。
- 我们填 `deprecated_at`。

### 3.2 `Sunset`（RFC 8594）

```
Sunset: Sun, 30 Jun 2026 23:59:59 GMT
```

- 值是一个 **HTTP-date**（IMF-fixdate 格式），**不是** `@` 时间戳。
- 它表示"**此资源将在此刻之后不再可用**"。
- 我们填 `sunset_at`；**此头可选**。

### 3.3 两个头的对比（易错点）

| | `Deprecation` | `Sunset` |
|---|---|---|
| RFC | 9745 | 8594 |
| 值格式 | Structured Field Date：`@1688169599` | HTTP-date：`Sun, 30 Jun 2026 23:59:59 GMT` |
| 语义 | 什么时刻**开始**弃用 | 什么时刻**终止**服务 |
| 是否必填 | `deprecated` 状态下必填 | 可选 |
| 时区 | UTC 秒（无时区问题） | 必须带 `GMT` |

**为什么会写错**：两个头的名字看起来是"同一类东西"，直觉上会用同一个格式化函数。但一个是 SF Date（`@<整数>`）、一个是 HTTP-date（含星期、月份缩写、GMT）。实现上必须**分别格式化**，绝不能共用一个 helper（这是本节的硬性实现约束，也是总纲明确点出这一点的原因）。

**互相约束**：`Sunset` 若设置，必须**晚于** `Deprecation`。否则我们等于宣告"先关闭、后弃用"，用户按这个顺序准备迁移必然踩空。保存时校验。

**为什么 `Sunset` 是可选的**：很多弃用是没有终点的——比如 `smart` → `smart-v2` 只是一个长期兼容壳，我们希望老名字一直能用来服务老客户端。这时给一个虚假的截止日期反而有害。总纲保留了这种"永久兼容壳"的表达能力。

### 3.4 `Link: rel="deprecation"`

```
Link: </docs/models/smart-v3>; rel="deprecation"
```

指向**链终点**（最终真正服务的那个 `active` 模型），**不是**中间那一跳。

为什么：

- 用户拿到的请求实际落到了链终点。头里的链接是"**该去看什么、该迁到哪**"的答案。若指向中间节点（可能自身也是 `deprecated`），用户点进去发现"这也是个已弃用的东西，还要再跳一次"，等于没给答案。
- 若指向中间节点，客户端无法用一个头就判断"我要迁移到哪"，会需要递归拉取——但 RFC 9745 的 `rel="deprecation"` 是给文档链接用的，不是给链式解析用的。

**为什么是文档链接而不是模型名**：`rel="deprecation"` 指向的是**说明文档**，人可读的迁移指南（在我们的部署里是 `/docs/models/<name>` 这类页面）。这一点与"替代目标是抽象模型"不同——模型名在响应体 `model` 字段里回显，头里给的是文档。

> **待定**：`Link` 头是否需要同时带 `rel="successor-version"`（RFC 5829）指向替代的抽象模型名，以便程序化客户端自动切换。总纲只钉了 `rel="deprecation"`。

### 3.5 头里用谁的时间

| 头 | 取值 |
|---|---|
| `Deprecation` | **本模型**（发起请求的那个模型）的 `deprecated_at` |
| `Sunset` | **本模型**的 `sunset_at` |
| `Link` | 链终点 |

**为什么时间用本模型而不是链终点**：用户关心的是"**我正在用的这个名字**什么时候废"。链终点是 `active`、没有弃用日期。若把头里的日期换成终点的（不存在的）日期，头就空了；若换成整条链里最早的日期，用户会看到一个与他使用的模型名无关的日子。

**由此产生的一个特性**：用户如果一直用旧名，随着链"向前推进"，他会陆续收到**多个不同的** `Deprecation` 日期（每个中间节点被弃用时一次），这是正确行为——每次都是在告诉他"你现在依赖的东西又老了一岁"。

### 3.6 哪些响应带这些头

| 响应 | 是否带 |
|---|---|
| 走替代链成功的正常响应 | **带**（本模型的日期 + 终点的 Link） |
| 流式响应 | 带，在响应头里（HTTP 头在流开始前已发出） |
| 错误响应（4xx/5xx） | **不带**。错误响应不是"服务成功但已弃用"的语境，混入弃用头会让客户端误判 |
| `/v1/models` 列表 | 见待定 |

> **待定**：`/v1/models` 是否对 `deprecated` 的条目也给出弃用信息（列表级头无法逐条表达，可能需要靠条目内的字段或头里的 `Link`）。总纲只规定了响应头，没规定列表端点怎么表达。

## 4. 替代目标的能力约束

**硬约束：替代目标的能力必须逐项 ≥ 原模型，否则禁止保存。**

| 能力项 | 比较 |
|---|---|
| 上下文窗口 | 替代 ≥ 原 |
| 最大输出 | 替代 ≥ 原 |
| 工具调用 | 原支持 → 替代必须支持（原不支持 → 替代随意） |
| 视觉 | 同上 |

校验用的取值：**抽象模型的对外能力声明**（[02-abstract.md](02-abstract.md) 第 4 节），即已经按严格模式取过 min / 交集的保守下界。

**为什么要逐项 ≥**：弃用是一次**无感的内部替换**——用户的配置一字未改，我们用替代模型替他继续服务。如果替代模型能力更弱：

- 用户发一张图片，以前能用，现在报 400。他会认为"这个服务退化了"，而且**完全不知道为什么**（他在用同一个模型名）。
- 上下文变短后，长对话会在中途被截断或被上游拒绝——这是最糟的一类故障，因为它可能**静默地产生错误结果**。

所以"能力只能升级不能降级"是外部承诺的一部分：`deprecated` 期间，用户能做的事只能变多，不能变少。

**为什么用声明值而非候选真实能力**：声明值是用户与客户端实际依赖的东西。用候选真实能力比较会得出"理论上更强"但用户根本看不到（因为被声明挡住了）的结论。

> **待定**：替代链是**逐跳比较**（每跳 ≥ 上一跳）还是**终点 vs 原模型比较**。逐跳更严格（等价于传递性保障），但限制管理员先建弱链再逐步升级的操作空间。

## 5. 管理面链预览

管理端在配置替代关系时必须**实时预览整条链**，而不是让管理员自己脑补。

预览内容：

| 项 | 说明 |
|---|---|
| 完整链 | `A → B → C`，含每一跳的名称与状态 |
| 链终点 | 最终提供服务的模型；若为 `deprecated` 则是链没走完（异常，报错） |
| 跳数 | 与上限 5 的对比 |
| 环 | 当场标红并拒绝保存 |
| 每跳的日期 | 每层的 `deprecated_at` / `sunset_at` |
| 能力对比 | 终点 vs 原模型的四项能力，逐项列出 |

**为什么必须"预览"而不是"保存后报错"**：管理替代链是**图编辑**，人脑不擅长在图上推演。一个链预览能把"我这一改会不会把 A 的请求打到某个更弱的模型上"这个问题在**保存之前**回答完。这与 [03-strategy.md](03-strategy.md) 第 6 节的"干跑"是同一个设计思想：**让错误在保存时暴露，而不是在用户请求时暴露**。

## 6. 运行时解析与缓存

```
请求 model = A（deprecated）
  → 解析链（visited 集合，上限 5 跳）
  → 终点 C
  → 用 C 走 03-strategy.md 的三段式
  → 响应头带 A 的弃用信息 + 指向 C 的 Link
```

| 项 | 说明 |
|---|---|
| 缓存 | 链解析结果可缓存；**链配置变更必须立即失效缓存** |
| 失败 | 环 / 超限 / 终点不存在 → 降级为"无替代"（2.5） |
| 记录 | `requests` 表记 `virtual_model_id`（用户请求的那个）与最终落点 |

**为什么头里用 A、路由用 C**：对用户而言 `A` 一直是他的模型；对上游而言只有 `C` 是真实存在的候选。这两件事必须解耦，否则"弃用"这个功能本身无法实现。

> **待定**：链解析结果报 `model` 字段回显 `A` 还是 `C`。按 [02-abstract.md](02-abstract.md) 6.2 的精神应回显用户请求的名字（`A`），但某些客户端会把响应 `model` 当作"实际模型"用于对账。

## 7. 接口签名

```
-- 弃用配置（管理面）
Deprecate(id, replacement_id, deprecated_at, sunset_at *time) -> error
    -- 校验：链最终可终止 / 跳数 ≤ 5 / 无环 / 逐项能力 ≥ / sunset > deprecation
Enable(id) -> error
Disable(id, reason) -> error

-- 链解析
ResolveChain(id) -> (Chain, error)       -- 配置时与预览用，返回完整链
ResolveTerminal(id) -> (id, Chain, error) -- 运行时用，返回终点 + visited 记录

-- 响应头
DeprecationHeaders(id) -> (Deprecation string, Sunset string, Link string)
    -- 严格区分两种日期格式：@unix 与 HTTP-date，禁止共用格式化函数
```

## 8. 待定项汇总

> **待定**：`disabled → active` 回滚时 `deprecated_at` / `sunset_at` 是清空还是保留，见第 1.3 节。

> **待定**：`disabled` 一律返回 404 还是 410 Gone，见第 1.3 节。

> **待定**：`Link` 是否额外带 `rel="successor-version"` 指向替代的抽象模型名，见第 3.4 节。

> **待定**：`/v1/models` 如何表达条目级的弃用信息，见第 3.6 节。

> **待定**：能力校验是逐跳比较还是终点 vs 原模型比较，见第 4 节。

> **待定**：弃用后响应 `model` 字段回显原名 `A` 还是终点 `C`，见第 6 节。
