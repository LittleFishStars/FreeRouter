# 真实模型目录与健康

## 1. 这一篇管什么

本篇定义**真实模型目录**：上游池子里的模型在我们站内怎么登记、怎么命名、怎么被人工覆盖、怎么巡检、以及"这个模型现在能不能用"这件事怎么表达。

三条边界先说清楚：

| 边界 | 说明 |
|---|---|
| 只写真实模型 | 抽象模型的定义在 [02-abstract.md](02-abstract.md)；本篇不定义对外契约 |
| 只管目录，不管路由 | 目录只回答"池子里有什么、叫什么、状态如何"；"选谁"是策略引擎的事，见 [03-strategy.md](03-strategy.md) |
| 真实模型只有管理员可见 | 见总纲 3.1；租户侧看不到任何真实模型名 |

**为什么要把目录单独成册**：真实模型的增减**不动对外契约**（总纲 3.6）。只要对外暴露的抽象模型名不变，上游换了几个渠道、某个渠道下线了某个模型，客户端完全无感。把这件事收在一个内聚的目录层里，我们才能在 116 个模型持续变动的上游面前保持对外稳定；反之若让候选集直接引用活的目录，每次上游变动都会被迫改抽象模型配置。

## 2. 真实模型与限定名

### 2.1 限定名格式

```
dsh:<渠道>/<上游模型 id>
```

| 片段 | 取值 | 例 |
|---|---|---|
| 固定前缀 | `dsh:` | `dsh:` |
| 渠道 | 上游前缀，实测 20 个（`deepseek-official` / `aggregate` / `cline`… 见总纲 5.1） | `deepseek-official` |
| 上游模型 id | 上游 `GET /v1/models` 条目里的 `id` **冒号之后的原样部分** | `deepseek-flash` |

完整例子：`dsh:deepseek-official/deepseek-flash`。

**为什么加 `dsh:` 前缀**（上游 id 本来就已经是 `渠道/模型` 形态，看着像多此一举）：

1. **留命名空间**。上游目前有三种来源（总纲 10 的 `upstreams.kind`）：`relay`（providers-hub 账号池直连）、`vendor`（贡献者凭据直连官方）、`selfhosted`（本地或自建 OpenAI 兼容端点）。其中只有 `relay` 的模型 id 天然带 `渠道/模型` 形态，另两种没有——但它们都叫“上游”，迟早会撞名字。前缀现在就钉死，将来加新来源不必迁移历史数据。
2. **防混用**。限定名带 `:`，抽象模型名禁止带 `:`（见 [02-abstract.md](02-abstract.md) 命名规则），于是"客户端拿到了一个真实模型名"这件事在字符串层面就能一眼识别，不必查库。
3. **归因可读**。`requests` 表里落的是解析后的真实模型，管理员看日志时渠道与模型在同一串字符里，不用二次 join。

**唯一性**：`UNIQUE(upstream_id, upstream_model_id)`。同一个上游里同一个模型 id 只能有一行。

### 2.2 数据结构

```
real_models {
  id,                    -- 内部主键
  upstream_id,           -- 来源（relay / vendor / selfhosted），见总纲 10 upstreams
  upstream_model_id,     -- 上游原样 id，如 "deepseek-official/deepseek-flash"
  display_name,          -- 管理端显示名，默认取上游 name 字段
  group_name,            -- 目录分组（不是权限组，见第 4 节）
  context_window,        -- 上下文窗口
  modalities,            -- 模态，来自上游 input[]
  efforts,               -- 思考档位，来自上游 reasoning.efforts[]
  status,                -- normal / missing
  hidden,                -- 管理端列表是否折叠
  sort_order,            -- 置顶排序
  source,                -- auto / override
  excluded_from_candidates,  -- 是否禁止被抽象模型引用（aggregate/* 默认为 true）
  last_seen_at,
  missing_since
}
```

各字段的落点与总纲第 10 章一致；本篇只补充三个 PLAN 未展开的语义：`group_name`、`hidden`、`excluded_from_candidates`（第 4、5 节）。

### 2.3 上游目录字段的映射

上游 `GET /v1/models` 条目 → `real_models` 的对应关系：

| 上游字段 | 落到 | 说明 |
|---|---|---|
| `id` | `upstream_model_id` | 原样存，不改写 |
| `owned_by` | 派生 `渠道` | 限定名里的渠道段取自这里 |
| `name` | `display_name` 初值 | 如 `DeepSeek-V4.1-Flash`；可被人工覆盖 |
| `input[]` | `modalities` | `text` / `image` |
| `reasoning.efforts[]` | `efforts` | 含 `canonical` 的档位映射（如 `off` ↔ `none`） |
| *（上游不提供）* | `context_window` | 上游目录样本里没有这个字段，必须另找来源 |

`context_window` 的来源是一处**已知空缺**：

> **待定**：`context_window` 由谁提供——① 管理员逐条维护；② 用总纲 4.4 的 L2 深度鉴定"上下文二分"实测回填；③ 维护一份静态对照表。三者维护成本与准确性差别很大，需要拍板后再定巡检流程。

## 3. 自动发现与人工覆盖

### 3.1 事实：目录是上游权威的

启动自举时拉一次目录（总纲 11.1），之后按周期刷新。上游是**唯一事实源**——我们的池子就是它的投影。

### 3.2 两类字段

`source` 是**行级**标记（`auto` / `override`），但"刷新不覆盖人工改动"这句话要落到**字段级**才有意义：

| 字段类 | 字段 | 刷新行为 |
|---|---|---|
| **上游权威字段** | `upstream_model_id`、`modalities`、`efforts`、`last_seen_at`、`status` | **永远随刷新更新**，人工不可改 |
| **人工展示字段** | `display_name`、`group_name`、`hidden`、`sort_order` | 一旦被人工改过即冻结，刷新不覆盖 |
| **临时字段** | `context_window` | 按第 2.3 节的待定结论处理 |

行级 `source` 的作用是**标记"这一行至少有一个字段被人工改过"**，让管理端能一眼筛出"被人碰过的模型"，而不是用来决定整行是否冻结。

### 3.3 为什么不用"整行冻结"

如果人工改一个显示名就让整行永久冻结，会有两个后果：

- 上游把某个模型的上下文扩到 1M、或新增了一个思考档位，我们这边**永远不知道**，于是过滤阶段会按过期的能力把本来可用的候选剔除 → 白丢可用额度。
- 上游给某模型改名（比如 `name` 字段从 v1 改成 v2），我们要么拿不到新名，要么被旧名钉死。

**所以"不覆盖人工改动"保护的必须是人工字段，不是整行。** 这条收紧之后，`source=override` 只影响展示，不影响路由正确性。

### 3.4 刷新时的三种差分

| 差分 | 处置 | 理由 |
|---|---|---|
| 上游新增 | 插入 `real_models`，`source=auto`，`status=normal` | 新模型应当立刻可被配置，不必等人工登记 |
| 上游仍在 | 更新上游权威字段，清 `missing_since` | — |
| 上游消失 | 不改 `status`，交给巡检（第 6 节） | 单次刷新拉空可能只是上游抖动或连接失败（总纲 5.3 实测有偶发 `http=000`），一次看不到就判死会造成假告警 |

### 3.5 变动→立即通知管理员（`admin_inbox`）

目录刷新是**无人监听的定时任务**，它检测到的变动如果只落在库里，就等于没发生：管理员不会天天去比 116 行目录，他只会发现某天早上“模型不能用”。所以每一次真实变动都要在检测到的**当时**写一条待处理事项。

**写 `admin_inbox` 的触发条件**（只列目录侧）：

| 变动 | `kind` | `severity` | 为什么算“要人管” |
|---|---|---|---|
| 上游新增模型 | `model_added` | `info` | 不一定要处理，但它是“可以开新候选了”的唯一信号 |
| 上游模型消失 | `model_missing` | `warn` | 直接影响候选可用性（第 6 节巡检的口径） |
| 上游属性变化（`context_window` / `modalities` / `efforts` / 名称） | `model_changed` | `warn` | 属性变**小**会把候选能力声明拉低（[02-abstract.md](02-abstract.md) 第 5 节取 min/交集），可能导致原本能跑的请求变成被拒 |
| 渠道整体失联 / 连续失败超阈 | `upstream_down` | `error` | 这是故障，不是变动 |
| 凭据失效 / 鉴定失败 | `credential_issue` | `error` | 贡献侧故障，影响供给量 |
| 新账户待审核 | `account_pending` | `info` | `tenant` 类需审核（总纲 2.7） |
| 组共享池告警 / 全站熔断 | `pool_alert` | `error` | 直接对应服务不可用 |

**为什么区分 `severity`**：待处理事项页的全部价值在于“有限注意力该先放哪”。一律 `info` 会让真正的故障埋在几十条“新模型上线”里；一律 `error` 则会让告警疲劳。

**为什么“变动”要立即写而不是聚合到日报**：“立即”买的是**因果可读性**——管理员看到“模型 X 在 14:03 属性变了”与“14:05 开始出现 503”时，能立刻把两件事连起来；如果变动到第二天才进日报，这两件事就会变成两条无关的历史事实。

**为什么不做实时推送**：轮询 + 登录时拉未读计数已经能满足这个需求，而推送引入连接管理、重发、离线补发一整套机制——它的复杂度远高于它省下的那几十秒。

**幂等要求**：同一个 `(kind, related_id)` 在未读期间**不重复写**，否则每轮刷新都会新增一条，一天就是上百条。读到同一变动第二次时只更新 `detail_json` 里的最新值，不新建行。

**数据模型**（总纲对齐规范 G）：

```sql
admin_inbox(
  id, kind, severity, title,
  detail_json,       -- 变动的 before/after，供待处理事项页展开
  related_id,        -- 关联对象（real_model_id / credential_id / account_id）
  created_at, read_at, read_by
)
```

**为什么 `detail_json` 记 before/after 而不是只记 after**：“变了”这个事实本身没有信息量，管理员真正要判断的是“变成了什么、变成了多少”。只存 after 则无法描述变化方向——`context_window` 从 128k 变成 32k（变差）与从 32k 变成 128k（变好）在 after 里长得一样。

`unique(kind, related_id) where read_at is null` 是上述幂等要求的落地形式。

> **待定**：变动通知的合并窗口（同一模型短时间内多次属性变动是否合并为一条，以及合并后 `detail_json` 的形态）。
> **待定**：已读/未读之外的第三态（“已忽略”）是否需要——有些变动确实无需处理，但让它一直未读会抬高未读计数。
## 4. 目录分组、置顶与隐藏

三件事都只作用于**管理端列表的呈现**，不影响路由。

| 字段 | 作用 | 为什么不影响路由 |
|---|---|---|
| `group_name` | 管理员自由分组，如"官方直连"、"第三方 key" | 这是**目录分组**，不是术语表里的**组**（组 = 一组策略 + 一批成员，管授权）。两者同名不同物，数据也不在 `groups` 表 |
| `sort_order` | 置顶排序 | 排序只决定管理员先看到谁 |
| `hidden` | 列表折叠 | **隐藏 ≠ 禁用**。`hidden` 只是"别在 116 行里占我视线"；能不能被选由 `status`、`excluded_from_candidates` 与运行时健康决定 |

**为什么必须写清"目录分组不是组"**：`groups` 是权限模型的核心对象，管理员一旦误以为 `group_name` 是权限分组，就会期待"把模型放进某个分组 = 授权给某组人"。这两条链路完全不相干（授权链路见 [../security/03-groups.md](../security/03-groups.md)）。为避免实现时被 `GROUP BY group_name` 这种巧合带偏，命名上建议管理端 UI 显示为"目录标签"。

## 5. 上游 `aggregate/*` 默认排除

总纲 1.4 钉死的决策：

> 上游的 `aggregate/*` 不作为抽象模型的候选来源（默认排除）。

落地方式：

- 目录刷新时，凡是渠道为 `aggregate` 的条目，`excluded_from_candidates = true`；
- 抽象模型保存候选时（见 [02-abstract.md](02-abstract.md) 第 3 节），若引用的真实模型 `excluded_from_candidates = true` → **保存被拒**，报错必须指出"聚合模型不能作候选"；
- `aggregate/*` 仍然在目录里可见（22 个），管理员能看、能比较，只是选不了。

**为什么**：上游的 `aggregate/*` 是**上游自己的一层策略**（跨渠道归并同一真实模型）。我们的抽象模型也是策略层。两层策略重叠后，出现"某请求代价变高 / 质量变差"时**无法归因**：是我们的排序选错了，还是上游的聚合把请求转到了另一个账号？弃用链、`expiry-first`、候选级冷却这些机制全部会因为上游内部又切了一次而失效。归因能力是这个项目能长期跑下去的前提，所以宁可主动放弃这 22 个条目。

> **待定**：是否允许管理员**显式**解除单个 `aggregate/*` 的排除（默认保持排除，解除需二次确认并进审计）。总纲只写了"默认排除"，没说能不能开例外。

## 6. `missing` 巡检

### 6.1 规则

1. 每轮刷新记录命中情况；
2. 某真实模型**连续 N 天**未在上游目录出现 → `status = missing`，`missing_since` 落时间；
3. 管理端提示：「建议弃用 / 已下线」，管理员**一键确认或忽略**；
4. 已产生的用量与日志**不追溯**（总纲 3.6），历史记录里保留旧引用。

`N` 的取值：

> **待定**：连续 N 天未出现才标 `missing`。取值太短会被上游抖动误伤（总纲 5.3 实测有偶发连接失败），太长则候选长期挂在池子里每次都失败。建议值 3～7 天，需按实际上游稳定性拍板。

### 6.2 为什么不自动弃用

`missing` 只**提示**，不自动改状态。理由：

- 上游目录短暂残缺可能来自抓取失败，判"下线"会让正在服务的抽象模型瞬间无候选（→ 503）；
- 弃用是一个**对外语义变更**（要发 `Deprecation` 响应头、要维护替代链，见 [04-deprecation.md](04-deprecation.md)），必须由人拍板；
- 候选的"这只手现在不好用"是**运行时健康**该管的事（第 7 节），不该用目录状态表达。

### 6.3 一键确认之后做什么

管理端的"确认下线"是一个**引导动作**，不是状态迁移的终态：

| 选择 | 结果 |
|---|---|
| 弃用 | 跳到 [04-deprecation.md](04-deprecation.md) 的弃用配置（必填替代目标，能力需逐项 ≥） |
| 仅移出候选 | 把引用它的候选从抽象模型里摘掉（不动对外模型名） |
| 忽略 | 清 `missing_since` 的告警标记，下轮巡检重新计数 |

## 7. 健康状态的取值与归属

### 7.1 两类状态必须分开

| | 目录状态 | 运行时健康 |
|---|---|---|
| 落在哪 | `real_models.status` | 候选 × 凭据实例（运行时展开后的临时对象） |
| 变化频率 | 天级 | 秒～分钟级 |
| 语义 | "上游还认不认这个模型" | "这一条路现在还走得通吗" |
| 取值 | `normal` / `missing` | `healthy` / `degraded` / `cooldown` / `blocked` |

**为什么必须分开**：一个模型可能在上游目录里活得好好的（`normal`），但此刻所有可用凭据都在冷却（`cooldown`）；反过来，一个 `missing` 的模型若还有存量凭据能打通，运行时它可能是 `healthy`。把两者塞进一个字段，过滤阶段就说不清"到底该剔谁"。

> 说明：这里定义的是总纲 3.3 过滤条件「健康」「不在冷却」的**取值**，不是新概念。

### 7.2 取值定义

| 取值 | 含义 | 是否参与路由 |
|---|---|---|
| `healthy` | 滚动窗口内成功率达标，且无活动冷却 | 参与，正常权重 |
| `degraded` | 有失败也有成功（成功率低于阈值） | **参与**，被降权（降权体现在 `speed` 键与切换率上，见 7.3） |
| `cooldown` | 候选级熔断：连续失败达阈值，暂停一段时间 | 不参与（被过滤剔除），期满半开恢复 |
| `blocked` | 管理员显式禁用该渠道 / 该真实模型 | 不参与（被过滤剔除），**不会自动恢复** |

`cooldown` 与 `blocked` **必须分开**：前者是自动的、会自愈的；后者是人的意志，必须一直有效直到有人解除。若共用一个值，半开恢复逻辑会把管理员的禁用悄悄放开——这正是总纲 13 章"贡献的凭据被上游封禁"与"渠道禁用"两条风险要用不同对策的原因。

### 7.3 状态迁移

```
healthy  --失败率越阈值-->  degraded
degraded --连续失败达阈值--> cooldown        （自动，带冷却时长）
cooldown --冷却期满/半开探测成功--> healthy
cooldown --冷却期满仍失败--> cooldown        （加倍冷却，上限封顶）
任意     --管理员禁用-->      blocked        （仅人工解除）
任意     --长期无流量-->      healthy        （视为无信号，不惩罚）
```

最后一条**为什么重要**：一个刚贡献进来、还没被调用过的候选不该被当作"可疑"而排到最后。这是**可靠性要求**，不是公平要求：

- **没有样本的候选，我们不知道它到底怎么样**。密钥是否还有效、端点是否还活着、真实错误率是多少，都需要**被真实调用过**才看得出。错误率统计需要样本，零样本的候选在排序里既不该被奖励也不该被惩罚——"视为无信号"就是这个意思（`speed` 键为空时退回下一级策略，而不是被当作无限慢）；
- **排到最后会让故障推迟到第一次真实流量才爆**。若它永远排在后位，前几个候选就很少把它当切换目标，它也就永远拿不到流量；直到某天它恰好被选中，故障在真实请求上直接出现，而不是在低频调用里提前暴露；
- **冷门模型的 `unverified` 靠"已放行 + 进复检"收信号**（[05-verification.md](05-verification.md) 5.3）。不给流量，复检队列就没有输入，"未鉴定"会永久停在未鉴定。

贡献侧的影响只在统计上：没有流量的一条贡献，在贡献统计里就是零调用（[../contributions/02-credentials.md](../contributions/02-credentials.md) 第 7.2 节）。

### 7.4 数据落点

健康是**运行态派生**，不建独立表：

- 成功 / 失败 / 耗时从 `requests` 表按滚动窗口聚合（`status`、`ttft_ms`、`total_ms`）；
- 熔断与冷却状态放**内存**（进程内），重启即清。

**为什么不落库**：健康是短周期信号，落库会带来写放大（每条请求都改状态行）与陈旧状态（进程崩了状态还留着，重启后要判"这个 `cooldown` 是刚进的还是昨天的"）。重启清空是**安全侧**的选择：清空等于"给所有候选一次机会"，代价只是可能的少量失败重试——而总纲 3.3 的第③段本来就允许在未吐内容前换候选。

> **待定**：滚动窗口长度、失败率阈值、连续失败次数、冷却时长与封顶值。这些是**可调参数**，建议做成 `settings` 表项而非硬编码，具体默认值需压测后定。
