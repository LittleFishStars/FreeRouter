# 公网安全基线

本册是**上线前必须逐条勾选**的清单。FreeRouter 是公网暴露的多用户中转站，
上游额度是真实的账号——**没有这些措施就等于把账号送出去**。

**为什么这份清单是硬性的**：与内网工具不同，公网暴露意味着任何人（包括
自动化扫描器）都能到达我们的鉴权面。上游额度一旦被白嫖，损失记在账号主头上，
且可能触发上游风控导致账号被封，影响的是**所有**使用该渠道的租户。

---

## 1. 威胁模型

### 1.1 要防的四类事

| # | 威胁 | 后果 | 主要对策章节 |
|---|---|---|---|
| T1 | **Key 泄露 → 白嫖上游额度**（入口 a：Key 被读出；入口 b：**明文传输被中间人截获**） | 额度损失 + 上游风控 | §2 §4 §5 |
| T2 | **账户被盗 → 拿到 Key 或管理权**（本版无类级提权：**一笔登录 = 该账户全部权限**） | 同 T1，管理权失守更严重 | §3 §6 |
| T3 | **贡献凭据被我们泄露** | 极严重，破坏众包信任基础 | §4 |
| T4 | **滥用（刷量、爬取、转售）** | 额度耗尽、上游告警 | §5 §7 |

**为什么 T2 的对策全压在 §3**：登录一次即获得该账户所有权限类的全部权限，
「管理面被盗」与「普通账户被盗」抵抗力的差距只剩一个：管理员账户上有更多账户、
组、抽象模型可以改。两者的防线是同一套：argon2id 参数、退避曲线、锁定阈值、
24 小时会话、改密即吊销。不再有「即使密码被猜到、进管理面还要再验一次」这层缓冲，
所以对 §3 的要求从「做好」变成「必须定值并逐项验证」。

**为什么 T1 有两个入口**：Key 被「读出」（拖库、日志、前端回显）是大家自然会想到的
那一条；但**明文传输被中间人截获**同样能拿到一个可用的 Bearer Key，而且它不需要
攻破任何服务端组件——同一网络路径上的任何一跳都能做到。默认形态是直连 HTTP
（默认不启 TLS），所以这条入口必须摆在威胁模型里，不能因为「默认行为改了」
就当它不存在。缓解手段是**二者其一**：启用内置 TLS（`tls.mode=files`），
或自行在前面加一层反代由它终止 TLS，见 §2。

### 1.2 设计原则

1. **默认拒绝**：账户注册即 `pending`；新建 Key 默认额度 0、白名单为空。
2. **显式授权**：任何能力都要有人明确授予（权限类、组、Key 白名单）。
3. **额度护栏先行**：限速与配额在**功能之前**实现——没有护栏的出口不能上线。
4. **最小可见**：凭据明文任何人不可见（含贡献者本人）；租户看不到真实模型名。

**为什么强调「默认拒绝」**：几乎所有中转站的泄露事故都来自「功能先上、
护栏后补」，而护栏后补时已经有真实流量在白嫖。反过来做没有额外成本。

### 1.3 不在防御范围（要清楚）

- 上游供应商自身的风控判决——我们只能降低触发概率，不能保证不被封。
- 贡献者自己把上游账号密码泄露到别处——我们只能保证自己这一侧不泄露。
- 租户把 Key 主动发给别人——无法技术阻止，靠额度上限兜底。

不假装能防住。写清楚边界，避免上线后误判责任。

## 2. 传输与边界

**默认形态是「直连 IP + 端口」（HTTP）**：FreeRouter 开箱即可用
`http://<ip>:<port>` 直接对外服务，**不依赖反代、不强制 HTTPS**。
反代是**可选形态**，需要时由部署者自行配置（见
[02-deploy.md](02-deploy.md#6-反代前置形态-c可选) 第 6 节）。

- [ ] **默认只监听回环**：`server.listen` 默认 `127.0.0.1:8080`；
      切到公网地址是部署者的**显式动作**，不做自动探测。
- [ ] **内置可选 TLS**：给 `tls.cert_file` / `tls.key_file`（`tls.mode=files`）
      即由本进程自己终止 TLS，**不依赖反代**。本版**不支持** `acme`
      （无域名，配置校验直接拒绝）。
- [ ] **TLS 只有一个终止点**：内置 TLS 与「反代终止 TLS」**不同时使用**。
- [ ] **非回环监听且 `tls.mode=off`**：启动日志打印**醒目警告**；管理员可把
      `server.insecure_public_listen` 设为 `deny`，把它升级为**拒绝启动**。
- [ ] 端口由部署者设定（默认 `8080`）；
      **管理面不单开端口**，走同一端口不同路径。
- [ ] `TRUSTED_PROXIES` 显式配置；**未配置时忽略 `X-Forwarded-For`**。
- [ ] 安全响应头：CSP、`X-Content-Type-Options: nosniff`、
      `Referrer-Policy: same-origin`、`X-Frame-Options: DENY`；
      **HSTS 只在启用 TLS 时下发**（理由见下）。
- [ ] CORS 默认关闭（同源）；跨域需显式白名单，**禁止 `Access-Control-Allow-Origin: *`
      与凭据同时出现**。
- [ ] 入站请求体上限默认 **32 MiB**，超限返回 413（早于上游的 300 MiB 限制）。
- [ ] 服务器 banner 不泄露版本号。

**为什么默认是「警告」而不是「拒绝启动」**：用户 2026-10-19 拍板「不用反代，
默认直接通过 IP + 端口访问」，且部署位置是「先本地跑」。若默认拒绝启动，就会出现
「`127.0.0.1` 上跑得好好的、把监听地址一改成公网 IP 就起不来」的断层——卡住的
恰好是部署者最需要看日志的那一刻，而他并没有做错什么。警告把「你正在明文对外」
这件事**说出来**但不阻断启动，让「先本地跑通、再按需加固」这条路径成立。

**为什么仍然必须保留「升级为拒绝启动」的开关**：明文下 Bearer Key 与请求正文
全部裸奔，一次中间人截获就等于拿到该 Key 的**全部站点额度**（不是单次请求的额度）。
默认警告是**便利性妥协**，不是「明文无所谓」的结论。对已经确定要暴露在不可信网络的
部署，管理员必须能把这条妥协**收回**——一个配置开关比「记得每次自己去看日志」
可靠得多。这是本册唯一一处「默认不拦、但可一键变硬」的设计，它存在的原因正是
默认值本身不够硬。

**为什么内置 TLS 与反代 TLS 不同时使用**：两者同时终止 TLS 时，外层证书与内层证书
会不一致（HSTS、`Secure` Cookie、重定向 URL 都可能指错），而且「到底谁在终止」
会成为排障时的长期歧义。二选一让链路上只有一个终止点，也让 `server.behind_proxy`
这个「我知道自己在明文后面」的声明有确定含义。

**为什么 HSTS 只在启用 TLS 时下发**：浏览器只在**安全传输**上采纳
`Strict-Transport-Security`（RFC 6797），明文响应里带这个头会被直接忽略——
写了既无用，又多一条误导性的「已加固」假象。所以默认直连形态下不发它；
一旦启用 TLS 就必须发：它是防降级的关键，缺了它中间人可以把一次 `https://` 访问
降回明文。

**为什么 `TRUSTED_PROXIES` 是硬项**：IP 限速是防刷的第一层，而 `X-Forwarded-For`
是客户端可任意伪造的头。如果无条件信任它，攻击者每次请求换一个假 IP，
IP 限速就完全失效——**看起来有防护，实际没有**，比不做更危险。

**为什么这条在直连形态下是默认安全的**：直连时链路上没有任何反代，
`X-Forwarded-For` 必定是客户端伪造的，而「未配置就忽略」正好就是正确行为。
**反代是可选形态，所以这条在直连时默认生效且不需要任何配置**；
只有选择形态 C 的部署才需要往里填反代地址段。

**为什么入站上限要小于上游的 300 MiB**：上游给 300 MiB 是因为它面向
「单条消息允许 200 MiB 原图、base64 膨胀 4/3」的客户端；我们面对的是公网，
更大的 body 意味着更大的内存与 DoS 面。提前拒绝比传完再拒更省资源。

## 3. 账户与认证

- [ ] 密码 **≥12 字符**，argon2id（参数：内存 ≥64 MiB、迭代 ≥3、并行度 = CPU 数）。
- [ ] **防枚举**：注册与登录对「已存在 / 不存在」的**响应时间恒定**且**文案一致**。
- [ ] **登录防爆破**：失败计数 + 指数退避 + 锁定窗口；失败记录含 IP / UA 进审计。
- [ ] **登录强度三项必须定值**（本版**没有类级提权**，登录是唯一防线）：
      **① argon2id 参数**：内存 / 迭代 / 并行度取具体数值，不随硬件自动调；
      **② 退避曲线**：起点、倍数、上限；**③ 锁定阈值**：失败次数、锁定时长、解除方式。
      三项写进配置表并在上线检查里逐项核对（见 §8 第 5 项）。
- [ ] **禁用联动**：账户转 `disabled` → 名下所有 Key **立即** 401、会话立即吊销。
      鉴权层**实时查账户状态**，不依赖可能有延迟的缓存。
- [ ] 会话 Cookie：`HttpOnly` + `SameSite=Lax`；登录成功后轮换 session id；
      **`Secure` 跟随 `tls.mode`**：启用 TLS（`files`）或形态 C 时必须加，
      明文直连（`tls.mode=off`）时不加，并在启动警告中一并提示。
- [ ] 改密 / 禁用即吊销该账户全部会话。
- [ ] **管理面不限来源 IP**：**不提供 IP 白名单功能**（用户 2026-10-19 拍板）。
      补偿手段：登录强度三项定值（argon2id 参数 / 退避曲线 / 锁定阈值）+
      **会话 24 小时过期** + 改密或禁用即吊销全部会话。
- [ ] **OAuth 登录得到的会话与密码登录等价**：不做「低权限上下文」，
      也不要求额外提权；能做什么完全由该账户的权限类集合决定。

**为什么 `Secure` 要跟随 `tls.mode` 而不是无条件加上**：浏览器不会在 `http://` 上
回传带 `Secure` 的 Cookie（`localhost` 是特例）。无条件加 `Secure` 的结果是
**默认直连形态下会话直接不工作**——登录成功、下一页就是未登录，而这种失败
在日志里看起来像“随机掉登录”，极难排。反过来，明文下不加 `Secure` 也不会
凭空增加新的泄露面：明文链路上 Cookie 本来就已经裸奔，这是同一个风险，
已由 §2 的启动警告与 `deny` 开关统一承担，而不是在 Cookie 层再假装防一次。

**为什么管理面不做 IP 白名单，而不是「做个开关默认关」**：本版**没有类级提权**，
登录一次即获得该账户所有权限类的全部权限，管理面的门槛就是登录本身。在这个前提下，
IP 白名单能提供的只是「你在某个网段里」——它挡不住已拿到管理员凭据的人（那个人可以
从任意一台机器发起请求），却一定会误锁从移动网络 / CGNAT 出口登录的管理员。
留一个默认关闭的白名单配置项，还会留下一个长期无人维护的配置面，并在文档里持续
暗示「这里有个可加固项」，把注意力从真正该做强的登录环节上引开。
把防御压在登录强度（argon2id 参数、退避曲线、锁定阈值）+ 24 小时会话 + 改密吊销上，
与真实威胁更贴近。

**为什么「禁用联动」必须实时**：缓存 30 秒看似无害，但被封禁的账户在
这 30 秒内可以继续消耗上游额度。禁用是应急手段，**应急手段不能有延迟**。

**为什么四项危险操作只剩界面二次确认**：提权取消后，删账户、改组、改抽象模型、
改弃用这四项不再有「再验一次因子」这一层，改为界面上的**不可跳过确认对话框**
（读完影响说明再二次点击）。必须说清这层保护的性质：**它不是认证，是防误点**——
会话一旦被劫持，攻击者点两下就过去了，这件事由「24 小时会话 + 改密/禁用即吊销 +
登录强度」承担，不要再在界面层把它当成第二道认证来论证。保留它的理由只有一条：
这四项不可逆或影响全站，而误点比恶意更常见。
边界见 [../security/02-authn.md](../security/02-authn.md) 第 6 节。

## 4. 密钥与凭据

### 4.1 API Key

- [ ] 格式 `fr-` + 32 字节随机（base62）；**只存 SHA-256**，明文仅创建时返回一次。
- [ ] 列表只显示前缀 + 后 4 位（`fr-xxxx…xxxx`）。
- [ ] 比较用 `crypto/subtle.ConstantTimeCompare`（防时序侧信道）。
- [ ] 支持即时吊销；吊销后**立即**生效（同样不依赖缓存）。
- [ ] 允许设置过期时间。

### 4.2 上游凭据

- [ ] 落库前用 **AES-GCM** 加密；主密钥来自环境变量或 `0600` 文件，**永不入库**。
- [ ] **凭据明文永不回显**——包括贡献者本人、包括管理端。
- [ ] 数据库文件权限 `0600`，且不在 Web 可访问路径下。
- [ ] 凭据使用记录（何时被哪个请求用过）只记**凭据 ID**，不记内容。
- [ ] 贡献者可一键撤销；撤销后该凭据立即退出候选池。

**为什么主密钥不入库**：密钥与密文放在同一处等于没加密——拿到数据库文件的人
同时也拿到了解密能力。分开存放使得「拖库」与「解密」成为两次独立事件。

**为什么贡献者本人也不可见**：凭据明文一旦能回显，它就必然会出现在
截图、日志、工单、浏览器历史里。**能看见就会泄露**，这是一条经验规律而非过度设计。

## 5. 限速、配额与护栏

- [ ] **三维令牌桶**：全局 / 按账户 / 按 IP；超限返回 `429` + `Retry-After`。
- [ ] **额度在账户级，Key 没有自己的额度**：账户按 `request` / `token` / `credit`
      三种计量维度设上限（`unit` 取三值之一）；**同一账户的所有 Key 共享同一份额度**。
      “三种维度能否同时启用”不在本册拍板，见
      [../security/05-keys.md](../security/05-keys.md) 的待定项。
- [ ] 账户级并发上限与 RPM / TPM 上限（同样在账户级，不落到 Key）。
- [ ] **全局预算熔断**：全站当日用量超标自动拒绝并告警。
- [ ] **异常用量检测**：单账户单位时间用量突增 → 告警（可选自动暂停）。
- [ ] 账户级上限：Key 数量、每人额度（由组的限制类策略取最严得出）。
- [ ] 注册速率限制（按 IP），可选邀请码。

**为什么是三维而不是单维**：只有按账户限速时，攻击者可以刷注册拿新账户；
只有按 IP 限速时，同一 IP 的多租户会互相影响。三维各自堵一类漏洞：
IP 挡注册滥用、账户挡租户超用、全局挡整体失控。

**为什么额度必须落在账户级而不是 Key 级**：同一账户可以开多把 Key。如果每把 Key
各有额度，那么「多开 10 把」就等于额度翻 10 倍，账户级的总量控制形同虚设。
把额度放在账户上、Key 只负责认证 + 模型白名单收窄 + 生命周期，才是一道真实的闸。

**为什么默认额度是 0**：新建账户若带默认额度，用户「先建了再说」就会产生
无授权消耗。默认 0 强制发生一次显式授权动作，把责任与可见性交给创建者。

## 6. 审计与可观测

- [ ] 审计日志 **append-only**：管理操作、鉴权失败、额度熔断、上游错误、
      **组变更**、**凭据增删**、**待处理事项的标记已读与处理**。
- [ ] 每条审计记录含 `account_id + acting_class + ip + ua + result`。
- [ ] **默认不记录请求正文**；排查时开脱敏模式（保留结构、抹掉文本）并在 UI 明示。
- [ ] 请求日志记录：端点、抽象模型、**真实落点（仅管理端可见）**、状态码、
      TTFT、耗时、输入/输出 token、错误码。
- [ ] 指标：QPS、P50/P95 延迟、错误率、上游健康、额度消耗速率。
- [ ] 告警渠道（至少一种）：额度熔断、上游持续失败、鉴定复检失败、
      异常用量。

**为什么默认不记正文**：中转站会流经用户的代码、文档、凭据片段。
默认记录正文等于建了一个高价值泄露目标，而且一旦泄露无法挽回。
「默认不记」把风险设为 opt-in，需要时由管理员显式开启并告知。

**为什么审计要记 `acting_class`**：同一账户可能同时是管理员和租户。
不记类就无法区分「他改了配置」与「他调了模型」，
事后追责时会把两种行为混为一谈。

## 7. 运行态加固

- [ ] 容器**非 root** 运行；`--read-only` 根文件系统 + 仅数据目录可写；
      `--cap-drop=ALL`。
- [ ] `/healthz`（进程存活）与 `/readyz`（含上游连通性）**分离**。
- [ ] 结构化日志（`slog` JSON）+ 日志轮转，不无限增长。
- [ ] CI 跑 `govulncheck ./...`，无高危才允许发布。
- [ ] 依赖版本锁定（`go.sum`）；定期更新。
- [ ] 优雅关闭：收到信号后停止接受新连接、drain 进行中的流式请求。
- [ ] 数据库备份见 [02-deploy.md](02-deploy.md#7-备份与恢复)。

**为什么 healthz 与 readyz 要分开**：上游短暂不可用时进程是健康的，
不应该被编排系统重启（重启解决不了上游问题，反而丢失连接池与进行中的请求）。
分开之后，负载均衡可以停止导流而不杀进程。

## 8. 上线前检查清单（总表）

按顺序执行，**任一项不通过就不上线**。

| # | 检查 | 验证方式 |
|---|---|---|
| 1 | 明文对外有明确感知，且可升级为拒绝启动 | 绑非回环 + `tls.mode=off` → 启动日志出现醒目警告；再把 `server.insecure_public_listen` 设为 `deny` → 同一配置应拒绝启动 |
| 2 | 伪造 `X-Forwarded-For` 不能绕过 IP 限速 | 未配 `TRUSTED_PROXIES` 时带假头打请求，限速仍生效 |
| 3 | 新建 Key 无法直接使用 | 建 Key 后账户额度仍为 0 且白名单为空 → 请求被拒 |
| 4 | 账户 `disabled` 后名下 Key 立即 401 | 禁用账户，立刻用旧 Key 请求 |
| 5 | 登录强度三项已按定值配置 | 读配置回显：argon2id 参数 / 退避曲线 / 锁定阈值均为**具体值**；再用错密码连测到阈值 → 退避与锁定生效 |
| 6 | 凭据明文不可获取 | 遍历所有页面与 API，确认无回显 |
| 7 | 审计覆盖组变更与凭据增删 | 改一次组、删一条凭据 → 审计各有一条记录 |
| 8 | 429 带 `Retry-After` | 打满 RPM |
| 9 | 全局熔断生效 | 调低阈值触发 |
| 10 | 容器非 root | `docker exec id` |
| 11 | `govulncheck` 无高危 | CI 输出 |
| 12 | 防枚举 | 已存在/全新用户名响应时间与文案一致 |

### 8.1 哪些项可以延到 M10，哪些不行

用户 2026-10-19 拍定「先本地跑、默认只监听 `127.0.0.1`」。在这个前提下，总表
里依赖**公网暴露**才能验证的项，逻辑上无法在本地完成，但**不能不实现**：

| 分类 | 条目 | 何时做 |
|---|---|---|
| **无论如何必须有** | 3（Key 默认不可用）、4（禁用联动）、5（登录强度三项定值）、6（凭据不可回显）、7（组变更与凭据增删进审计）、12（防枚举） | M3–M4，它们不依赖公网 |
| **可延到 M10** | 1（明文警告）、2（`X-Forwarded-For`）、8（429 + `Retry-After`）、9（全局熔断）、10（容器非 root）、11（`govulncheck`） | M10；其中 10 / 11 在 CI 里就能做 |

**为什么“可延”不等于“可删”**：默认回环只改变**暴露面**，不改变代码路径。
限速、熔断、转发头这些逻辑一旦在本地没写好，第一次真绑到 `0.0.0.0` 就会
同时暴露一个「没护栏」的端点。可在本地验证的部分（限速、熔断）应该在
M4 就做；项 1 / 2 / 8 / 9 的“可延”仅指**公网环境下的实测**。
