# 授权判定链

## 1. 判定链的输入与输出

> **主体 + 操作 + 资源 → 允许 / 拒绝**

| 要素 | 含义 | 来源 |
|---|---|---|
| 主体 | `Subject = 账户 ID + acting_class` | 会话（管理面）或 API Key 归属（模型面） |
| 操作 | 闭集合：读 / 写 / 建 / 删 / 调用 / 贡献等 | 路由声明，不靠运行时猜 |
| 资源 | 被操作对象：账户、组、抽象模型、Key、凭据、用量、审计 | 请求里的目标 ID |

**两种结果**（2026-10-20 取消类级提权后由三值收敛为两值）：

| 结果 | 含义 | 为什么这一档就够了 |
|---|---|---|
| **允许** | 直接执行 | — |
| **拒绝** | 不执行，返回明确错误 | 拒绝必须可与"不存在"区分（见第 7 节），否则排障无从下手 |

- **为什么不再有"需提权"这一档**：它原本是类级提权在判定链上的落点——"主体有权限，但当前上下文不足"。取消提权后，`acting_class` 是该账户真实拥有的类，判定只回答"这个类能不能做这件事"，不再有"权限够但此刻不算数"的中间态。少一个取值也就少一组"该引导去哪一步"的界面分支（见 [02-authn.md](02-authn.md#6-为什么不需要类级提权)）。
- **界面二次确认不在判定链里**：危险操作的 AlertDialog 是 UI 层拦截（防误点），不产生新的身份证明，也不改变判定结果。判定链只看"这个类能不能做"。

**为什么主体要带 `acting_class` 而不是只带账户**：一个账户可同时有多个类（见 [01-accounts.md](01-accounts.md#3-隔离的准确含义)）。判定必须知道"本轮操作是以哪一重身份做的"，否则 `admin` 类的存在会自动抬高 `tenant` 侧的能力，能力不互授当场破功。

## 2. 三层收敛

可见性与可用性经过三层收敛（PLAN 2.6、3.1、11.3）：

```
第一层（管理员）：∪ 所属组的抽象模型
        ↓ ∩
第二层（用户侧）：Key 白名单（只能收窄，不能放宽）
        ↓
第三层（对外契约）：全部以抽象模型呈现，真实模型名对租户不可见
```

```
实际可用 = (∪ 所属组的抽象模型) ∩ Key 白名单
```

| 层 | 谁决定 | 方向 | 为什么在这一层 |
|---|---|---|---|
| 组的模型授权 | 管理员（组策略，放开类取并集） | 给出**上界** | 只有管理员知道上游池里有什么、哪些能给 |
| Key 白名单 | 用户自己 | **只能收窄**，从组授权集合中取子集 | 用户对自己的 Key 应有收窄权（"这把 Key 只给 `fast` 用"）；但收窄权不能变成放宽权，否则用户自建 Key 就等于自我提权 |
| 抽象模型层 | 系统 | 真实模型名一律不可见 | 池结构（有哪些上游、哪些贡献者）是运营与安全信息，租户看到只会带来攻击面与解释成本 |

**为什么第二层只能收窄**：Key 是用户自己生成的机器凭据，用户对它拥有完全控制。如果白名单可以超出组授权，那么"组授权"就只是建议——用户建一把新 Key 就能拿回全部模型，组策略失去约束力。

**为什么第三层要在判定链里而不是只在前端**：客户端可以直接请求真实模型名。若判定只在界面隐藏，一次手写请求就能探测池结构（PLAN 3.1：客户端请求真实模型名 → 404）。

**额度不参与这三层收敛**（2026-10-20 定案）：额度在**账户级**，全部 Key 共享一份（见 [01-accounts.md](01-accounts.md#额度在账户级不在-key-上)）。Key 只负责认证、白名单收窄与生命周期。

## 3. 决策表

### 模型面（`tenant` 类）

| 操作 | 资源 | 需要的类 | 附加条件 | 判定依据 |
|---|---|---|---|---|
| 调用模型 | 抽象模型 | `tenant` | 见第 4 节运行时顺序 | PLAN 2.2、2.6 |
| 创建 Key | API Key | `tenant` | 组策略允许建 Key；数量未超组上限 | PLAN 2.6 |
| 列举 / 改名 / 禁用 / 吊销自己的 Key | API Key | `tenant` | `key.account_id == 主体.account_id` | PLAN 2.2 |
| **设置 Key 的模型白名单** | API Key | `tenant` | **只能收窄**：白名单 ⊆ 组授权 | PLAN 2.6、11.3 |
| 看自己的用量与调用日志 | `requests` / `usage_daily` | `tenant` | 只出现抽象模型名与真实落点的**非归因**部分 | PLAN 2.2、3.7 |
| 看真实模型名 / 候选 / 渠道构成 | 真实模型 | `admin` | — | PLAN 2.2、3.1 |
| 看某次请求的真实落点与贡献者归因 | `requests` | `admin` | — | PLAN 3.7 |

- **为什么"设置 Key 的额度"这一行消失了**：额度是账户属性，不存在"给某一把 Key 单独设额度"这个动作。同一行改成"设置 Key 的模型白名单"——Key 上唯一可配置的东西。若允许改 Key 额度，则多开 Key 就是额度翻倍（见 [05-keys.md](05-keys.md#4-key-没有自己的额度)）。
- **账户级额度由谁改**：管理员在账户详情页改（`account_quotas` 的合计行与**按模型限额行**，加 `rpm_limit` / `tpm_limit` / `max_concurrency` 单列；2026-10-20 定案：额度行化后不再有账户上的 `quota_limit/quota_unit` 单列），属管理面操作；本人只读。为什么本人不能改：额度是管理员给出的上界，用户自改等于自我提权。按模型限额行的上限受组侧 `group_model_quota_caps` 的 min 封顶，管理员手改若超出组上界属越权写入，保存时拒绝（见 [03-groups.md](03-groups.md) 第 3.5 节两层关系）。

| 关闭某条凭据的登录用途 | `upstream_credentials.login_enabled` | `contributor` | — | PLAN 第 10 章 |

### 管理面（`admin` 类）

| 操作 | 资源 | 需要的类 | 界面二次确认 | 判定依据 |
|---|---|---|---|---|
| 进管理页 / 读管理数据 | 管理面 | `admin` | 否 | PLAN 2.2 |
| 审批 / 批准账户 | 账户 | `admin` | 否 | PLAN 2.2 |
| 拒绝账户 | 账户 | `admin` | 是 | PLAN 2.2 |
| 授予 / 撤销权限类 | 账户 | `admin` | 是 | PLAN 2.7 |
| **禁用账户** | 账户 | `admin` | **是** | PLAN 2.5、9.3 |
| 建组 / 改名 / 改描述 | 组 | `admin` | 否 | PLAN 2.6 |
| **改组的策略 / 成员 / 默认组 / 删组** | 组 | `admin` | **是** | PLAN 2.6 |
| **改抽象模型** | 抽象模型 | `admin` | **是** | PLAN 2.5 |
| **改弃用（含替代链）** | 抽象模型 | `admin` | **是** | PLAN 2.5、3.5 |
| 上游目录与鉴定处置 | 真实模型、凭据 | `admin` | 是 | PLAN 2.2、3.6 |
| 改账户级额度与速率 | 账户 | `admin` | 是 | PLAN 2.6 |
| 读审计日志 | `audit_log` | `admin` | 否 | PLAN 2.2 |
| 重置他人密码 / 吊销他人会话 | 账户、会话 | `admin` | 重置密码需、吊销不需要 | PLAN 8 |

- **为什么"禁用账户"从"删账户"改成了它的实际形态**：本系统没有物理删除（见 [01-accounts.md](01-accounts.md#5-账户状态机)），危险操作的实际落点就是"停掉一个账户"。把它写在表里，是为了让"这一行需要二次确认"显式可见——判定链本身只判 `admin` 类。
- **为什么"改账户级额度"要二次确认而不需要额外认证**：它一次只影响一个账户（与"改组"的一对多不同），但会让该账户立刻多出可用额度。二次确认里必须显示旧值与新值。
- **为什么管理面不再有"逐次重验"列**：取消类级提权后，没有任何操作需要第二因子。原先的"恰好四项"清单连同 `DangerOp` 常量一起作废；原先靠重验挡的风险改由界面二次确认 + 会话 24h 过期 + 改密/禁用即吊销承担（见 [02-authn.md](02-authn.md#6-为什么不需要类级提权)）。

### 永远不允许（任何类）

| 操作 | 结果 | 为什么 |
|---|---|---|
| 指定自己的请求走自己的凭据 | 拒绝 | PLAN 2.3 凭据不可自选 |
| 读凭据明文（含本人自己的） | 拒绝 | PLAN 9.4 凭据明文永不回显 |
| 读他人 Key / 凭据 / 用量 | 拒绝（404 或空集） | PLAN 2.3 资源分表归属 |
| 请求真实模型名 | 404 | PLAN 3.1 |
| 账户之间建立归属 / 邀请关系 | 拒绝 | PLAN 1.3、14 反面验收 |
| 本人修改自己的账户级额度 | 拒绝 | 额度是管理员给出的上界；见上文 |
| `admin` 类调用模型 | 拒绝（以 `admin` 身份） | 换 `tenant` 身份即可，见下 |

**关于"`admin` 类调用模型"的拒绝**：这不是"管理员不能用模型"，而是"**不能以 `admin` 这个 `acting_class` 去调用**"。管理员账户同时带 `tenant` 类时，他在模型面上是以 `tenant` 身份行动的（PLAN 2.2：两件事走两套账）。判定链拒绝的是跨类冒充，不是管理员本人。

## 4. 运行时鉴权顺序（入站模型请求）

顺序是设计的一部分，不是实现细节。原则：**先做便宜的检查、先做与外部状态无关的检查、任何计数与扣费都发生在"确定要执行"之后**。

| 序 | 检查 | 失败结果 | 为什么在这个位置 |
|---|---|---|---|
| 1 | TLS 与协议边界（明文拒绝、请求体 ≤ 32 MiB） | 拒绝 / 413 | 最便宜的检查放在最前，防止后续步骤为垃圾流量付出成本（PLAN 9.2） |
| 2 | 解析 `Authorization`，识别 Key 前缀 → 查 `key_hash`，**常数时间比较** | 401 | 无 Key 就不必查库、不必看账户（PLAN 9.4） |
| 3 | Key 自身属性：存在 / 未过期 / 未吊销 | 401 | Key 状态独立于账户状态，先本地判定可减少对账户表的压力 |
| 4 | **账户实时状态：`active` + 带 `tenant` 类**（不依赖缓存） | 401 | 禁用联动要求实时（见第 5 节）；把账户检查放在 Key 之后，是因为它是"更贵但必须每请求做"的一步 |
| 5 | 抽象模型可见性：`model ∈ (组授权 ∩ Key 白名单)` | **404** | 不可见的模型对请求者一律"不存在"，不泄露模型目录；放在配额之前，避免"不存在的模型"消耗计数 |
| 6 | 额度与限速预检：**账户级**额度（`account_quotas`：合计行按请求命中的抽象模型另查按模型行）、RPM、TPM、并发、全局预算熔断 | 429（+ `Retry-After`）/ 拒绝 | 先拒绝再计费；这一层只读计数器（等值查询，含命中模型的限额行），代价低 |
| 7 | 抽象模型状态解析：`active` 直接用；`deprecated` 解析到替代模型并附弃用信号；`disabled` 拒绝 | 404 / 410 Gone | 解析放这里的原因：替代链的落点也需要过可见性校验（见待定） |
| 8 | 候选展开 + 策略引擎（过滤 → 排序 → 切换） | 无可用候选 → 503 + 专用错误码 | 这是最贵的一步（要选真实模型与凭据），必须放在前七步都通过之后 |
| 9 | 转发请求、计量、写 `requests` / `usage_daily` / 账户额度 | — | 只有真正发出去了才产生用量 |
| 10 | 审计与告警（鉴权失败、熔断、上游错误） | — | 与成功路径共用同一条 append-only 记录线（见 [06-audit.md](06-audit.md)） |

**为什么"账户状态实时查"排在第 4 位而不是第 2 位**：Key 的存在性与有效性可以完全由本地数据判定（`key_hash` + 状态），而账户状态必须读账户表或版本号。把便宜的判定放前面，可以让大量"拿着已吊销 Key 的扫描"在碰到账户表之前就被拒掉。

**为什么第 6 步查的是账户而不是 Key**：额度只有一个归属（账户）。同一账户的两把 Key 在第 6 步读的是同一行 `account_quotas`（按 `(account_id, 0|model, unit, period)` 等值命中主键），因此"开两把 Key 分担流量"不会绕过任何一道额度。按模型限额也在本步一并判：请求解析出的抽象模型命中 `abstract_model_id > 0` 的行时多一次等值查询，无行 = 该模型不设单独闸。

**为什么候选展开排在最后**：它需要查询真实模型目录、渠道范围与凭据池。任何一次无谓的候选展开，都是对上游池结构的一次无意义读放大。

## 5. 禁用联动

> **账户转 `disabled` → 名下所有 Key 立即 401，不依赖可能有延迟的缓存。**（PLAN 9.3；验收 8）

| 触发 | 效果 | 时延要求 |
|---|---|---|
| 账户转 `disabled` | 名下全部 Key 立即 401 | **立即** |
| 撤销账户的 `tenant` 类 | 名下全部 Key 立即 401 | 立即 |
| 账户级额度耗尽 | 名下全部 Key 一起被拒（见第 7 节） | 立即 |
| Key 被吊销（本人或管理员） | 该 Key 立即 401 | 立即 |
| 账户被合并为 `merged` | 该账户全部 Key 立即 401（Key 已改挂 target，由其 Key 继续服务） | 立即 |

**为什么必须"不依赖缓存"**：缓存的价值是省一次查询，代价是"最坏情况下，禁用一个账户后它的 Key 还能继续用整个 TTL"。在一个按额度计费的公网中转站上，这段窗口就是可被利用的额度窗口——一个正在被滥用的账户，在被禁用的那一刻起每一秒都在花钱。因此：

- Key 自身的属性（白名单、过期时间、名字）**可以**缓存，它们的变更只影响"这支能调什么"，不影响"这一支还能不能用"；
- **账户状态、类、额度**不进入长 TTL 缓存；若实现层确实需要缓存，必须带失效机制（版本号 / 主动逐出），且判定结果必须与"实时读账户状态"等价。

**为什么禁用返回 401 而不是 403**：Key 是机器凭据。401 在客户端库与运维习惯里都表示"这把凭据不可用"，403 表示"身份有效但权限不足"。返回 401 让客户端立刻停止重试并把问题指向"换 Key"，与"账户被禁用"这一事实相符。

## 6. 管理面鉴权顺序

| 序 | 检查 | 失败结果 | 为什么 |
|---|---|---|---|
| 1 | 会话存在、未过期（24h 固定窗口） | 401 | 最便宜 |
| 2 | 账户状态 `active` | 401 | 与模型面同一原则：禁用即失效 |
| 3 | 账户带 `admin` 类 | 403 | 有会话但无管理类 → 权限不足，与"没有会话"区分 |
| 4 | 逐端点校验：`Subject.op` + 资源归属 | 403 / 404 | 判定链主体逻辑，见第 3 节 |
| 5 | 危险端点：界面二次确认（客户端已确认标志） | 400 | 防误点，不是认证；服务端只校验"前端确实走过了确认流程"，不新增身份证明 |

- **为什么从 6 步减到 5 步**：原第 5 步"提权有效"与第 6 步"危险操作逐次重验"随类级提权一起删除。删掉之后管理面的判定链与模型面结构完全同构（会话/Key → 账户状态 → 类 → 资源），少一套只有管理面才有的状态。
- **为什么第 3 步返回 403 而第 1 步返回 401**：401 表示"你没有可用身份"，403 表示"你有身份但不该做这件事"。把两者混在一起来"防止探测"是错的——`admin` 类的存在与否在 UI 上本来就可见（PLAN 2.4：有 admin 类才渲染管理入口），隐藏这个区别只会拖慢排障。
- **为什么第 5 步不能当作安全边界**：客户端标志由前端发出，可以被绕过。它存在的唯一目的是让"手滑点错"在一次额外确认前停下，而真正的边界是第 1–4 步。

## 7. 拒绝的响应形态

| 场景 | HTTP | 说明 | 为什么是这个码 |
|---|---|---|---|
| 无 Key / Key 格式非法 / Key 不存在 / Key 已吊销 | 401 | — | 凭据层面不可用 |
| 账户 `disabled` / 被 `rejected` / 被 `merged` / 无 `tenant` 类 | 401 | 见第 5 节 | 与"凭据不可用"同层 |
| 模型不在可见集合（组授权 ∩ Key 白名单之外） | **404** | 与"模型不存在"同形 | 不泄露模型目录的存在性 |
| 请求体 `model` 是真实模型名 | **404** | PLAN 3.1 | 同上；此规则同时封住了池结构探测 |
| 抽象模型 `disabled` | 404 / **410 Gone** | 术语表口径：不接受请求 | 与上游暂时不可用区分（后者是 503） |
| 抽象模型 `deprecated` | 正常 200 | 解析到替代模型 + 弃用信号 | 弃用不是关闭（术语表口径） |
| 无候选可用（存在但暂不可用） | **503** + 专用错误码 | 与 404 明确区分 | 前者是"运维问题"，后者是"你不该知道"；混用会把运维故障误导成权限问题（PLAN 3.1） |
| RPM / TPM / 并发超限 | **429** + 有值 `Retry-After` | PLAN 9.5；验收 4 | 客户端需要知道"多久后重试" |
| **账户额度耗尽**（合计行或按模型行、`request` / `token` / `credit` 任一维度到顶） | 429 `quota_exceeded` + 日志留痕 | 验收 4；该账户**所有 Key** 一起被拦 | 已在 [../api/03-errors.md](../api/03-errors.md) 落定：同 429 但 `code` 与 `rate_limited` 分开；按模型行命中时错误体带 `model`，提示可改用其他模型 |
| 全局预算熔断 | 拒绝 + 告警 | PLAN 9.1 | 这是全站行为，不是账户行为 |

- **为什么额度拒绝的措辞必须写"账户"而不是"Key"**：额度是账户级的一份。写"这把 Key 的额度用完了"会让用户立刻去建一把新 Key——而新 Key 用的是同一份额度，什么都不会变，只会让问题看起来像 bug。正确表述是"该账户的额度已用尽"。

**为什么"可见性之外"返回 404 而不是 403**：403 等于确认"这个模型存在，只是你没权限"。对租户来说，模型目录本身就是需要保护的信息（PLAN 3.1、14 反面验收：租户界面看不到任何真实模型名）。让不可见的模型一律等于"不存在"，是最省事也最一致的答案。

## 8. 判定链接口签名

```go
type Decision int

const (
    DecisionAllow Decision = iota // 允许
    DecisionDeny                  // 拒绝
    // 2026-10-20 取消类级提权：不再有 DecisionNeedStepUp。
    // 判定只回答"这个类能不能做"，不存在"权限够但此刻不算数"的中间态。
)

// Op 是操作闭集合；资源相关操作必须显式声明，不由路由拼接猜测。
type Op string

// Resource 是被操作对象的引用：类型 + ID。
type Resource struct {
    Kind string // account / group / abstract_model / real_model / api_key / credential / usage / audit / session / inbox
    ID   string
}

type AuthzService interface {
    // Check 是判定链的唯一入口：主体 + 操作 + 资源 → 允许 / 拒绝。
    // 管理面与模型面共用同一条链；差异只在"主体从哪来"（会话 vs Key）。
    Check(subject Subject, op Op, res Resource) (Decision, error)

    // CheckModelCall 是模型面的运行时顺序（第 4 节 1–8 步）：
    // 返回解析后的抽象模型与配额预检结论，失败时返回原因与应返回的 HTTP 状态。
    CheckModelCall(key string, requestedModel string, ip string) (*ModelCallPlan, error)

    // EffectiveModels 给出"组授权 ∩ Key 白名单"的结果（第 2 节）。
    EffectiveModels(accountID, keyID string) ([]string, error)

    // AccountUsable 是禁用联动的单点：账户状态、类与额度必须实时读，不依赖长 TTL 缓存。
    AccountUsable(accountID string, required Class) (bool, error)
}

type ModelCallPlan struct {
    AbstractModelID string // 对外层
    RealModelID     string // 内部层，仅管理端可见
    CredentialID    string // 由策略引擎选出，不接受调用方指定
    Deprecated      bool   // 命中的是弃用模型，附弃用信号
    QuotaUnits      []QuotaDim // 本次要计入哪些额度维度（合计行 + 命中模型的按模型行），逐一条件判定
}
```

## 9. 待定

> **待定**：弃用模型解析到替代模型后，若替代模型不在本请求者的可见集合内（组授权 ∩ Key 白名单之外），返回 404 还是按原模型返回 503——总纲未定义这一交叉情况。

> **已定（2026-10-20）**：额度耗尽与限速同用 429，但 `code` 分开（`quota_exceeded` vs `rate_limited`），已在 [../api/03-errors.md](../api/03-errors.md) 落地；按模型限额命中复用 `quota_exceeded`，错误体带 `quota` 对象（`unit` / `period` / `model?`）供客户端自动降级。多维度都不够时只报第一个命中的闸（按合计→按模型→池的判定顺序），不暴露定价细节。

> **待定**：管理员的"停用账户"是否需要一个独立的"只停 Key、不停账户"的中间动作——当前只有账户级 disabled 与 Key 级 disabled 两档。

> **已定（2026-10-19）**：管理面不提供 IP 允许列表（总纲 9.3 已同步），判定链无需该步。

> **待定**：`x-fr-trace` 调试头（PLAN 3.7）的判定归属——它是否属于"看真实落点"这一 `admin` 类操作，以及能否开放给特定组。
