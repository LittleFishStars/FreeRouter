# 授权判定链
## 1. 判定链的输入与输出
> **主体 + 操作 + 资源 → 允许 / 拒绝 / 需提权**
| 要素 | 含义 | 来源 |
|---|---|---|
| 主体 | `Subject = 账户 ID + acting_class + elevated` | 会话（管理面）或 API Key 归属（模型面） |
| 操作 | 闭集合：读 / 写 / 建 / 删 / 调用 / 贡献等 | 路由声明，不靠运行时猜 |
| 资源 | 被操作对象：账户、组、抽象模型、Key、凭据、用量、审计 | 请求里的目标 ID |

三种结果缺一不可：

| 结果 | 含义 | 为什么必须有这一档 |
|---|---|---|
| **允许** | 直接执行 | — |
| **拒绝** | 不执行，返回明确错误 | 拒绝必须可与"不存在"区分（见第 7 节），否则排障无从下手 |
| **需提权** | 主体有权限，但当前上下文不足 | 这是"类级提权"在判定链上的落点；没有这一档，提权就只能做成"权限不足"的伪装，用户看不到出路 |

**为什么主体要带 `acting_class` 而不是只带账户**：一个账户可同时有多个类（见 [01-accounts.md](01-accounts.md#3-隔离的准确含义)）。判定必须知道"本轮操作是以哪一重身份做的"，否则 `admin` 类的存在会自动抬高 `tenant` 侧的能力，能力不互授当场破功。

## 2. 三层收敛

可见性与可用性经过三层收敛（PLAN 2.6、3.1、11.3）：

```
第一层（管理员）：∪ 所属组的抽象模型
        ↓ ∩
第二层（用户侧）：Key 白名单（只能收窄，不能放宽）
        ↓
第三层（对外契约）：全部以抽象模型呈现，真实模型名对租户不可见
```

```
实际可用 = (∪ 所属组的抽象模型) ∩ Key 白名单
```

| 层 | 谁决定 | 方向 | 为什么在这一层 |
|---|---|---|---|
| 组的模型授权 | 管理员（组策略，放开类取并集） | 给出**上界** | 只有管理员知道上游池里有什么、哪些能给 |
| Key 白名单 | 用户自己 | **只能收窄**，从组授权集合中取子集 | 用户对自己的 Key 应有收窄权（"这把 Key 只给 `fast` 用"）；但收窄权不能变成放宽权，否则用户自建 Key 就等于自我提权 |
| 抽象模型层 | 系统 | 真实模型名一律不可见 | 池结构（有哪些上游、哪些贡献者）是运营与安全信息，租户看到只会带来攻击面与解释成本 |

**为什么第二层只能收窄**：Key 是用户自己生成的机器凭据，用户对它拥有完全控制。如果白名单可以超出组授权，那么"组授权"就只是建议——用户建一把新 Key 就能拿回全部模型，组策略失去约束力。

**为什么第三层要在判定链里而不是只在前端**：客户端可以直接请求真实模型名。若判定只在界面隐藏，一次手写请求就能探测池结构（PLAN 3.1：客户端请求真实模型名 → 404）。

## 3. 决策表

### 模型面（`tenant` 类）

| 操作 | 资源 | 需要的类 | 需提权 | 附加条件 | 判定依据 |
|---|---|---|---|---|---|
| 调用模型 | 抽象模型 | `tenant` | 否 | 见第 4 节运行时顺序 | PLAN 2.2、2.6 |
| 创建 Key | API Key | `tenant` | 否 | 组策略允许建 Key；数量未超组上限 | PLAN 2.6 |
| 列举 / 改名 / 吊销自己的 Key | API Key | `tenant` | 否 | `key.account_id == 主体.account_id` | PLAN 2.2 |
| 设置 Key 的额度与白名单 | API Key | `tenant` | 否 | **只能收窄**：白名单 ⊆ 组授权，额度 ≤ 组上限 | PLAN 2.6、11.3 |
| 看自己的用量与调用日志 | `requests` / `usage_daily` | `tenant` | 否 | 只出现抽象模型名与真实落点的**非归因**部分 | PLAN 2.2、3.7 |
| 看真实模型名 / 候选 / 渠道构成 | 真实模型 | `admin` | 是 | — | PLAN 2.2、3.1 |
| 看某次请求的真实落点与贡献者归因 | `requests` | `admin` | 是 | — | PLAN 3.7 |

### 贡献面（`contributor` 类）

| 操作 | 资源 | 需要的类 | 需提权 | 附加条件 | 判定依据 |
|---|---|---|---|---|---|
| 贡献上游凭据 | `upstream_credentials` | `contributor` | 否 | `UNIQUE(provider, external_id)` 不冲突 | PLAN 4.2 |
| 列举自己的凭据 | `upstream_credentials` | `contributor` | 否 | **只见 label / 状态 / 鉴定结果**，无明文 | PLAN 2.3、9.4 |
| 看自己贡献的鉴定结果 | 凭据、真实模型 | `contributor` | 否 | — | PLAN 2.2 |
| 停用 / 删除自己的凭据 | `upstream_credentials` | `contributor` | 否 | 删除影响已在途请求的处置见 [../contributions/02-credentials.md](../contributions/02-credentials.md#5-生命周期与撤销) | PLAN 4.5 |
| 关闭某条凭据的登录用途 | `upstream_credentials.login_enabled` | `contributor` | 否 | — | PLAN 第 10 章 |

### 管理面（`admin` 类）

| 操作 | 资源 | 需要的类 | 需提权 | 危险操作（每次重验） | 判定依据 |
|---|---|---|---|---|---|
| 进管理页 / 读管理数据 | 管理面 | `admin` | **是** | 否 | PLAN 2.5 |
| 审批 / 拒绝账户 | 账户 | `admin` | 是 | 否 | PLAN 2.2 |
| 授予 / 撤销权限类 | 账户 | `admin` | 是 | 否（但授予 `admin` 类后果等同危险操作） | PLAN 2.7 |
| **删账户** | 账户 | `admin` | 是 | **是** | PLAN 2.5 |
| 建组 / 改名 / 改描述 | 组 | `admin` | 是 | 否 | PLAN 2.6 |
| **改组的策略 / 成员 / 默认组 / 删组** | 组 | `admin` | 是 | **是** | PLAN 2.5、2.6 |
| **改抽象模型** | 抽象模型 | `admin` | 是 | **是** | PLAN 2.5 |
| **改弃用（含替代链）** | 抽象模型 | `admin` | 是 | **是** | PLAN 2.5、3.5 |
| 上游目录与鉴定处置 | 真实模型、凭据 | `admin` | 是 | 见待定 | PLAN 2.2、3.6 |
| 读审计日志 | `audit_log` | `admin` | 是 | 否 | PLAN 2.2 |
| 重置他人密码 / 吊销他人会话 | 账户、会话 | `admin` | 是 | 见待定 | PLAN 8 |

### 永远不允许（任何类、任何提权状态）

| 操作 | 结果 | 为什么 |
|---|---|---|
| 指定自己的请求走自己的凭据 | 拒绝 | PLAN 2.3 凭据不可自选 |
| 读凭据明文（含本人自己的） | 拒绝 | PLAN 9.4 凭据明文永不回显 |
| 读他人 Key / 凭据 / 用量 | 拒绝（404 或空集） | PLAN 2.3 资源分表归属 |
| 请求真实模型名 | 404 | PLAN 3.1 |
| 账户之间建立归属 / 邀请关系 | 拒绝 | PLAN 1.3、14 反面验收 |
| `admin` 类调用模型 | 拒绝（以 `admin` 身份） | 换 `tenant` 身份即可，见下 |

**关于"`admin` 类调用模型"的拒绝**：这不是"管理员不能用模型"，而是"**不能以 `admin` 这个 `acting_class` 去调用**"。管理员账户同时带 `tenant` 类时，他在模型面上是以 `tenant` 身份行动的（PLAN 2.2：两件事走两套账两套额度）。判定链拒绝的是跨类冒充，不是管理员本人。

## 4. 运行时鉴权顺序（入站模型请求）

顺序是设计的一部分，不是实现细节。原则：**先做便宜的检查、先做与外部状态无关的检查、任何计数与扣费都发生在"确定要执行"之后**。

| 序 | 检查 | 失败结果 | 为什么在这个位置 |
|---|---|---|---|
| 1 | TLS 与协议边界（明文拒绝、请求体 ≤ 32 MiB） | 拒绝 / 413 | 最便宜的检查放在最前，防止后续步骤为垃圾流量付出成本（PLAN 9.2） |
| 2 | 解析 `Authorization`，识别 Key 前缀 → 查 `key_hash`，**常数时间比较** | 401 | 无 Key 就不必查库、不必看账户（PLAN 9.4） |
| 3 | Key 自身属性：存在 / 未过期 / 未吊销 | 401 | Key 状态独立于账户状态，先本地判定可减少对账户表的压力 |
| 4 | **账户实时状态：`active` + 带 `tenant` 类**（不依赖缓存） | 401 | 禁用联动要求实时（见第 5 节）；把账户检查放在 Key 之后，是因为它是"更贵但必须每请求做"的一步 |
| 5 | 抽象模型可见性：`model ∈ (组授权 ∩ Key 白名单)` | **404** | 不可见的模型对请求者一律"不存在"，不泄露模型目录；放在配额之前，避免"不存在的模型"消耗计数 |
| 6 | 配额与限速预检：日/月 token、RPM、TPM、并发、全局预算熔断 | 429（+ `Retry-After`）/ 拒绝 | 先拒绝再计费；这一层只读计数器，代价低 |
| 7 | 抽象模型状态解析：`active` 直接用；`deprecated` 解析到替代模型（≤5 跳）并附弃用信号；`disabled` 拒绝 | 404 / 410 Gone | 解析放这里的原因：替代链的落点也需要过可见性校验（见待定） |
| 8 | 候选展开 + 策略引擎（过滤 → 排序 → 切换） | 无可用候选 → 503 + 专用错误码 | 这是最贵的一步（要选真实模型与凭据），必须放在前七步都通过之后 |
| 9 | 转发请求、计量、写 `requests` / `usage_daily` | — | 只有真正发出去了才产生用量 |
| 10 | 审计与告警（鉴权失败、熔断、上游错误） | — | 与成功路径共用同一条 append-only 记录线（见 [06-audit.md](06-audit.md)） |

**为什么"账户状态实时查"排在第 4 位而不是第 2 位**：Key 的存在性与有效性可以完全由本地数据判定（`key_hash` + 状态），而账户状态必须读账户表或版本号。把便宜的判定放前面，可以让大量"拿着已吊销 Key 的扫描"在碰到账户表之前就被拒掉。

**为什么候选展开排在最后**：它需要查询真实模型目录、渠道范围与凭据池。任何一次无谓的候选展开，都是对上游池结构的一次无意义读放大。

## 5. 禁用联动

> **账户转 `disabled` → 名下所有 Key 立即 401，不依赖可能有延迟的缓存。**（PLAN 9.3；验收 8）

| 触发 | 效果 | 时延要求 |
|---|---|---|
| 账户转 `disabled` | 名下全部 Key 立即 401 | **立即** |
| 撤销账户的 `tenant` 类 | 名下全部 Key 立即 401 | 立即 |
| Key 被吊销（本人或管理员） | 该 Key 立即 401 | 立即 |
| 账户被合并为 `merged` | 该账户全部 Key 立即 401（Key 已改挂 target，由其 Key 继续服务） | 立即 |

**为什么必须"不依赖缓存"**：缓存的价值是省一次查询，代价是"最坏情况下，禁用一个账户后它的 Key 还能继续用整个 TTL"。在一个按额度计费的公网中转站上，这段窗口就是可被利用的额度窗口——一个正在被滥用的账户，在被禁用的那一刻起每一秒都在花钱。因此：

- Key 自身的属性（额度、限速、白名单）**可以**缓存，它们的变更只影响配额精度，不影响"能不能用"；
- **账户状态与类**不进入长 TTL 缓存；若实现层确实需要缓存，必须带失效机制（版本号 / 主动逐出），且判定结果必须与"实时读账户状态"等价。

**为什么禁用返回 401 而不是 403**：Key 是机器凭据。401 在客户端库与运维习惯里都表示"这把凭据不可用"，403 表示"身份有效但权限不足"。返回 401 让客户端立刻停止重试并把问题指向"换 Key"，与"账户被禁用"这一事实相符。

## 6. 管理面鉴权顺序

| 序 | 检查 | 失败结果 | 为什么 |
|---|---|---|---|
| 1 | 会话存在、未过期 | 401 | 最便宜 |
| 2 | 账户状态 `active` | 401 | 与模型面同一原则：禁用即失效 |
| 3 | 撤销 `admin` 类时提权状态已清零 | — | 见 [02-authn.md](02-authn.md#5-会话管理) |
| 4 | 账户带 `admin` 类 | 403 | 有会话但无管理类 → 权限不足，与"没有会话"区分 |
| 5 | 提权有效（`elevated_until > now`） | **需提权**（引导到提权流程） | 提权需要用户交互，代价最高，放最后 |
| 6 | 危险操作 → 逐次重新验证 | 需提权 | PLAN 2.5：四项危险操作**每次**重验，不认 15 分钟窗口 |

**为什么第 4 步返回 403 而第 1 步返回 401**：401 表示"你没有可用身份"，403 表示"你有身份但不该做这件事"。把两者混在一起来"防止探测"是错的——`admin` 类的存在与否在 UI 上本来就可见（PLAN 2.4：有 admin 类才渲染管理入口），隐藏这个区别只会拖慢排障。

## 7. 拒绝的响应形态

| 场景 | HTTP | 说明 | 为什么是这个码 |
|---|---|---|---|
| 无 Key / Key 格式非法 / Key 不存在 / Key 已吊销 | 401 | — | 凭据层面不可用 |
| 账户 `disabled` / 被 `rejected` / 被 `merged` / 无 `tenant` 类 | 401 | 见第 5 节 | 与"凭据不可用"同层 |
| 模型不在可见集合（组授权 ∩ Key 白名单之外） | **404** | 与"模型不存在"同形 | 不泄露模型目录的存在性 |
| 请求体 `model` 是真实模型名 | **404** | PLAN 3.1 | 同上；此规则同时封住了池结构探测 |
| 抽象模型 `disabled` | 404 / **410 Gone** | 术语表口径：不接受请求 | 与上游暂时不可用区分（后者是 503） |
| 抽象模型 `deprecated` | 正常 200 | 解析到替代模型 + 弃用信号 | 弃用不是关闭（术语表口径） |
| 无候选可用（存在但暂不可用） | **503** + 专用错误码 | 与 404 明确区分 | 前者是"运维问题"，后者是"你不该知道"；混用会把运维故障误导成权限问题（PLAN 3.1） |
| RPM / TPM / 并发超限 | **429** + 有值 `Retry-After` | PLAN 9.5；验收 4 | 客户端需要知道"多久后重试" |
| 日 / 月 token 额度耗尽 | 拒绝 + 日志留痕 | 验收 4 | 状态码选择见待定 |
| 全局预算熔断 | 拒绝 + 告警 | PLAN 9.1 | 这是全站行为，不是账户行为 |

**为什么"可见性之外"返回 404 而不是 403**：403 等于确认"这个模型存在，只是你没权限"。对租户来说，模型目录本身就是需要保护的信息（PLAN 3.1、14 反面验收：租户界面看不到任何真实模型名）。让不可见的模型一律等于"不存在"，是最省事也最一致的答案。

## 8. 判定链接口签名

```go
type Decision int

const (
    DecisionAllow      Decision = iota // 允许
    DecisionDeny                       // 拒绝
    DecisionNeedStepUp                 // 需提权
)

// Op 是操作闭集合；资源相关操作必须显式声明，不由路由拼接猜测。
type Op string

// Resource 是被操作对象的引用：类型 + ID。
type Resource struct {
    Kind string // account / group / abstract_model / real_model / api_key / credential / usage / audit / session
    ID   string
}

type AuthzService interface {
    // Check 是判定链的唯一入口：主体 + 操作 + 资源 → 允许 / 拒绝 / 需提权。
    Check(subject Subject, op Op, res Resource) (Decision, error)

    // CheckModelCall 是模型面的运行时顺序（第 4 节 1–8 步）：
    // 返回解析后的抽象模型与是否需要提权无关，失败时返回原因与应返回的 HTTP 状态。
    CheckModelCall(key string, requestedModel string, ip string) (*ModelCallPlan, error)

    // EffectiveModels 给出"组授权 ∩ Key 白名单"的结果（第 2 节）。
    EffectiveModels(accountID, keyID string) ([]string, error)

    // AccountUsable 是禁用联动的单点：账户状态与类必须实时读，不依赖长 TTL 缓存。
    AccountUsable(accountID string, required Class) (bool, error)
}

type ModelCallPlan struct {
    AbstractModelID string // 对外层
    RealModelID     string // 内部层，仅管理端可见
    CredentialID    string // 由策略引擎选出，不接受调用方指定
    Deprecated      bool   // 命中的是弃用模型，附弃用信号
}
```

## 9. 待定

> **待定**：弃用模型解析到替代模型后，若替代模型不在本请求者的可见集合内（组授权 ∩ Key 白名单之外），返回 404 还是按原模型返回 503——总纲未定义这一交叉情况。

> **待定**：日 / 月 token 额度耗尽时的状态码是否与限速的 429 复用，还是需要一个独立错误码（客户端需要区分"限速、稍后即可"与"额度用尽、今天没戏"）。

> **待定**：管理员重置他人密码、吊销他人会话是否应列入"危险操作·每次重验"清单（PLAN 2.5 只明定了四项）。

> **待定**：上游目录与鉴定处置（改变某个真实模型的可用性）是否应列入危险操作清单。

> **已定（2026-10-19）**：管理面不提供 IP 允许列表（总纲 9.3 已同步），判定链无需该步。

> **待定**：`x-fr-trace` 调试头（PLAN 3.7）的判定归属——它是否属于"看真实落点"这一 `admin` 类操作，以及能否开放给特定组。
