# 审计与可观测

## 1. 目标与三条边界

| 边界 | 内容 | 为什么 |
|---|---|---|
| **append-only** | 只追加，不提供修改 / 删除接口（PLAN 9.5） | 可被编辑的审计等于没有审计：一旦"改一条记录"成为可能，事后就无法区分"真的没发生"与"被抹掉了" |
| **默认不记录请求正文** | 默认只记结构与元数据；排查时显式开启脱敏模式（PLAN 9.5） | 中转站没有理由长期持有用户的业务文本；默认持有会把一次数据库泄露的后果从"凭据泄露"升级为"用户内容泄露" |
| **分账** | 每条记录带 `account_id + acting_class`（PLAN 9.5、10） | 隔离的追责层（见 [01-accounts.md](01-accounts.md#3-隔离的准确含义)）：一个账户有多重身份时，必须能说清是哪一重做的 |

**三个数据集不是一回事**，混用会同时牺牲审计完整性与查询性能：

| 数据集 | 表 | 记什么 | 谁看 | 可变性 |
|---|---|---|---|---|
| 审计 | `audit_log` | **行为**：谁在什么时候做了什么、结果如何 | 管理端 | 只追加 |
| 请求日志 | `requests` | **计量**：每次调用的端点、抽象模型、真实落点、状态、TTFT、耗时、token（PLAN 8） | 用户看自己那部分；管理端看归因 | 只追加 |
| 用量聚合 | `usage_daily` | **汇总**：日 × **账户** × 抽象模型 × 真实模型的计数 | 用户 / 管理端 | 幂等累加 |

- 为什么审计不合并进 `requests`：`requests` 是**每一笔业务调用**，量级比审计大几个数量级，而审计要回答的问题（谁改了策略、谁在爆破、谁把额度调高了）绝大多数与业务调用无关。把两者放一张表，等于用噪声最高的数据集回答最需要精度的问题。
- 为什么用量聚合独立于请求日志：额度判定发生在每个请求之前（见 [04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求) 第 6 步），实时聚合全表会让鉴权成本随历史增长（见 [05-keys.md](05-keys.md#4-key-没有自己的额度)）。
- 为什么 `usage_daily` 的粒度是**账户**而不是 Key（2026-10-20 定案）：额度是账户级的一份，全部 Key 共享。按 Key 汇总仍然要再按账户加一次才能判定额度，多一张中间表只会多一处口径漂移。**按 Key 的用量仍然在 `requests` 里**（每行带 `key_id`），需要时按 Key 聚合即可。

## 2. 字段

`audit_log(id, ts, account_id, acting_class, action, target, ip, ua, result, detail)`（PLAN 第 10 章）

| 字段 | 语义 | 为什么必须有 |
|---|---|---|
| `id` | 自增 / 单调 ID | 分页与"从上次位置继续读"；也便于证明顺序 |
| `ts` | 事件时间 | 一切排查从时间线开始 |
| `account_id` | 主体账户 | 归属；合并后旧记录仍保留原 ID（见 [01-accounts.md](01-accounts.md#4-账户合并)） |
| `acting_class` | **本次行为以哪个类进行** | 不可从 `account_id` 推导——同一账户可同时有 `admin` 与 `tenant`（PLAN 2.3）。缺这个字段，"管理员账户出事"就永远分不清是管理面失守还是 Key 泄露 |
| `action` | 动作标识（闭集合） | 分类统计与告警规则的基础（见第 3 节） |
| `target` | 被操作对象（类型 + ID） | 与 `action` 组成"谁对什么做了什么" |
| `ip` / `ua` | 来源 | 爆破特征是"同源多目标 / 同目标多源"，只能从聚合中看出（见 [02-authn.md](02-authn.md#10-防爆破)） |
| `result` | 成功 / 失败 / 拒绝 | 无 `result` 的日志无法区分"发生了"与"被拦住了"，而后者才是安全事件的信号 |
| `detail` | 结构化补充（JSON） | 差异信息（改了哪个策略键、从什么改成什么）。**必须经过第 4 节的脱敏** |

**为什么不再有 `elevated` 字段**（2026-10-20 取消类级提权）：该字段原本回答"这条管理动作是不是在提权窗口内做的"，用来区分同一条动作的风险等级。取消提权后，**没有任何一条记录存在"提权中 / 非提权中"两种状态**——所有动作都在"登录一次即全部权限"的同一上下文中发生，字段恒为同一值，留着它只会让读日志的人去猜一个永远不成立的区分。风险等级改由 `action` + `result` + `target` 表达（例如"改组"这个 `action` 本身就是高风险动作，无需额外的状态位）。

**为什么 `acting_class` 保留而 `elevated` 删除**：两者的性质不同。`acting_class` 表达的是"以哪一重身份行动"，这是一个**真实存在的多样性**（同一账户在不同面上确实是不同身份，能力不互授）。`elevated` 表达的是"身份是否被临时加强"，取消提权后这种临时状态不存在了。删掉一个恒为假的字段，比留着它更不容易误导。

**为什么 `ua` 要存而不是只存 IP**：共享出口（校园、公司、运营商 NAT）会让同一个 IP 承载大量无关用户。UA 是在 IP 之外唯一还能把同源事件**归并或拆开**的低成本信号。

**禁止出现在审计里的东西**（任何情况下都不写，包括 `detail`）：

| 禁止项 | 理由 |
|---|---|
| API Key 明文 | PLAN 9.4：只存哈希，明文仅创建时返回一次 |
| 会话令牌、密码、恢复码 | 同理；审计是"谁都可能读到"的表 |
| 上游凭据明文 | PLAN 9.4：永不回显，连贡献者本人也不行 |
| 请求 / 响应正文 | 默认不记录（PLAN 9.5）；脱敏模式下的例外见第 4 节 |

## 3. 事件分类表

`action` 是闭集合，按类别分组。新增事件必须先归入某一类，否则告警规则无法覆盖它。

### 认证与会话

| 事件 | 触发点 | 必带字段 |
|---|---|---|
| 登录成功 / 失败 | 密码登录、OAuth 登录、恢复码登录 | `account_id`（失败时可为空）、`ip`、`ua`、`result`、失败原因类别 |
| 登出 | 用户主动 | `account_id`、会话 ID |
| 改密（自助）/ 重置（管理员） | 见 [02-authn.md](02-authn.md#4-密码策略) | `acting_class`、目标账户、联动的会话吊销数 |
| 会话吊销 | 登出 / 改密 / 撤销 `admin` 类 / `disabled` / 合并 | 触发原因 |
| 登录退避与锁定 | 连续失败达到阈值 | `ip`、`ua`、账户、失败次数、退避值 / 锁定截止时间 |

- 为什么登录**失败**也要记：爆破与撞库的特征只存在于失败样本里（PLAN 9.3 明定失败记录含 IP / UA 进审计）。
- 为什么退避与锁定要单独成条而不是只靠"登录失败"累计：取消提权后，**登录本身成为唯一一次身份证明**，退避与锁定就是这套证明的全部防线（见 [02-authn.md](02-authn.md#6-为什么不需要类级提权)）。它是否真的触发、参数是否合适，只能从审计里看出来。

### 账户与权限类

| 事件 | 说明 |
|---|---|
| 注册 | 自助注册 → `pending`；带来源 IP |
| 审核批准 / 拒绝 | 批准必须记录**选中的组与账户级额度**（PLAN 2.7） |
| 禁用 / 恢复 | 转 `disabled` 必须记录联动失效的 Key 数量 |
| 权限类授予 / 撤销 | 单独成条（`account_classes` 的增删）；撤销 `admin` 类必须记录联动的会话吊销数 |
| **账户级额度 / 速率变更** | 记录 `quota_limit`、`quota_unit`、`rpm_limit`、`tpm_limit`、`max_concurrency` 各自的旧值 / 新值 |
| 账户合并 | 记录 source / target；见 [01-accounts.md](01-accounts.md#4-账户合并) |
| 管理员导入（批次） | 一条批次事件：操作者、行数、成功 / 失败数 |
| 管理员导入（单体） | 每个成功账户一条创建事件（见 [02-authn.md](02-authn.md#3-管理员导入账密)） |

- **为什么"账户级额度变更"必须逐字段记旧值 / 新值**：额度搬到了账户级（2026-10-20 定案），它是"一个人能用多少"的唯一开关。一个账户忽然跑出十倍用量时，第一件要查的事就是"最近有没有人调过它的额度"。只记"改过额度"而不记改成了多少，等于把这条线索丢掉。

### 组

| 事件 | 说明 |
|---|---|
| 创建 / 改名 / 改描述 | — |
| 改策略（放开 / 限制） | 记录策略键、旧值、新值 |
| **共享池变更**（`group_quota_pools`） | 记录 `unit`、`period`、`limit` 的旧值 / 新值 |
| 成员增 / 删 | 记录账户集合；**成员列表本身不对成员可见**（见 [03-groups.md](03-groups.md#7-组可见性)） |
| 默认组变更 | — |
| 删组 | 记录成员退回默认组的数量（见 [03-groups.md](03-groups.md#6-删组不删人)） |

- **为什么池的变更要单列**：改组是"一对多"的高风险动作，而池的 `limit` 直接决定整个组能不能继续用——把一个组的月池从 10000 改成 100，等价于一次性停掉这个组的全部服务。它与"改策略"同属改组，但它的影响面是"全组立刻"，值得单独成条以便告警规则直接盯它。

### API Key

| 事件 | 说明 |
|---|---|
| 创建 | 记录前缀（不是明文） |
| 改名 | — |
| 停用 / 恢复 | 可恢复的运营动作 |
| **吊销** | 不可恢复；记录操作者（本人 / 管理员） |
| 白名单变更 | 记录抽象模型集合的差异 |

- **为什么这里没有"限额变更"**（2026-10-20 定案）：Key 上已经没有额度字段（见 [05-keys.md](05-keys.md#4-key-没有自己的额度)）。额度变更一律走上一节的"账户级额度变更"，Key 上只剩"白名单"这一个可配置项。

### 凭据（贡献）

| 事件 | 说明 |
|---|---|
| 新增贡献（登录态 / 未登录） | 未登录时记录新建的 `contributor` 账户与恢复码的**发放事实**（不记恢复码本身） |
| 与既有 `UNIQUE(provider, external_id)` 冲突 | 记录"已拒绝，未覆盖"（PLAN 4.2） |
| 停用 / 删除 | — |
| 登录用途开关（`login_enabled`） | — |
| 鉴定结论变化 | 记录新旧状态（`verified` / `suspect` / `unverified` / `trusted`） |

### 抽象模型与弃用

| 事件 | 说明 |
|---|---|
| 创建 / 修改 | 记录策略引擎配置、能力声明 |
| 弃用 / 撤销弃用 | 记录 `deprecated_at`、`sunset_at`；弃用是单向的（不可从 `deprecated` 回到 `active`） |
| 替代链变更 | 记录新的替代目标；**不设跳数上限**，但每次变更都要能回答"这一跳为什么指向它" |
| 禁用 | `disabled` 不接受请求（404 / 410 Gone）；记录操作者与原因 |

- **为什么替代链变更不再记录"第几跳 / 是否超过上限"**（2026-10-20 对齐）：链不再有深度上限，也就不存在"超限降级"这个事件。保留的是每条边本身的变更记录——链的形状由这些边重建，而不是由某一次"整体校验通过"的快照记录。

### 真实模型与鉴定（仅管理端）

| 事件 | 说明 |
|---|---|
| 目录自动变化 | `source = auto` 的新增 / 消失（`missing_since`） |
| 人工覆盖 | `source = override` 的改动 |
| `hidden` 切换 | — |
| 鉴定处置 | 对 `unverified` 模型的放行 / 拦阻决定 |

### 请求与额度（安全信号类）

| 事件 | 触发点 | 为什么算安全事件 |
|---|---|---|
| 鉴权失败 | 判定链第 2–4 步（见 [04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求)） | 无效 / 已吊销 Key 的持续使用是扫描或泄露后重放的信号 |
| **账户额度拒绝** | `request` / `token` / `credit` 任一维度耗尽（该账户**全部 Key** 一起被拦） | PLAN 验收 4 要求留痕；它同时是"某账户正在被滥用"的第一手信号 |
| 限速触发（429） | RPM / TPM / 并发 | 与正常用量区分 |
| 全局预算熔断 | 全站当日超标 | PLAN 9.1：必须告警 |
| 无候选可用（503） | 策略引擎无可用候选 | 运维故障信号，与 404 区分（PLAN 3.1） |
| 上游错误 | 上游返回错误 | 关系到贡献凭据的健康度 |

- **为什么额度拒绝要记"账户"而不是"Key"**：额度是账户级的一份，同一账户所有 Key 共享。记成 Key 会让排查者去找"这把 Key 有什么问题"——而它什么问题都没有，只是账户的额度用完了。审计里的 `target` 应当写 `account:<id>`，`detail` 里可以附上触发的那把 Key 以便定位请求来源。
- **为什么结算失败（扣减未完成）也要有一条记录**：扣减发生在请求结束后、与写用量同一个事务里（见第 5 节）。事务失败意味着"请求已消耗上游额度但账没记上"，这是**钱的问题**，不是日志问题。

### 管理与系统

| 事件 | 说明 |
|---|---|
| 管理面进入 | 首次进入管理页（会话建立后） |
| ~~管理 IP 允许列表拒绝~~ | **不适用**（2026-10-19 定案：不提供该功能） |
| 配置变更（`settings`） | 键、旧值、新值 |
| **价格乘数表变更** | 记录真实模型 / 抽象模型、旧乘数、新乘数（影响 `credit` 计量与 `price` 排序） |
| 数据迁移 | 迁移编号与结果 |
| **`admin_inbox` 待处理事项产生 / 已读** | 见第 3.1 节 |

### 3.1 `admin_inbox` 待处理事项

`admin_inbox(id, kind, severity, title, detail_json, related_id, created_at, read_at, read_by)`

管理员不是全天候盯着系统的人。**一个只在"管理员主动去看"时才被发现的问题，等于没有被发现**——审核队列积压时用户等不到批准，上游模型静默消失时租户先收到 503，凭据失效时贡献者与租户都不知道原因。`admin_inbox` 把这些"需要人做一件事"的信号收拢成一页未读列表，登录时显示未读数。

| `kind` | 来源 | 为什么必须进收件箱（而不是只进审计） |
|---|---|---|
| `account_pending` | 新注册待审核 | 不处理，新用户永远无法使用；这是唯一一个"越积压越糟糕"的队列 |
| `model_added` | 目录刷新检测到新上游模型 | 新模型默认进入候选池，但可能不该给所有人；需要人确认一次 |
| `model_missing` | 上游模型消失（`missing_since`） | 若不处理，租户会在候选耗尽时收到 503，而原因只在管理端可见 |
| `model_changed` | 上下文窗口 / 模态 / efforts 等属性变化 | 能力声明会跟着变（取保守下界），可能让某个抽象模型突然"不够用" |
| `channel_failing` | 某渠道连续失败 | 上游故障，不处理就是持续 503 |
| `credential_invalid` | 贡献凭据失效 | 归因到具体贡献者，需要决定是通知、停用还是移除 |
| `verification_failed` | 鉴定结论为 `suspect` 或复检回归 | `unverified` 默认放行入池，这条是"放行之后才发现的坏消息"，必须有人看 |
| `pool_exhausted` | 组共享池耗尽 | 该组全员被拦，只有管理员能改池 |
| `global_budget` | 全站预算熔断 | 全站停止服务，等级最高 |
| `key_anomaly` | 单账户单位时间用量突增 | PLAN 9.1 的异常用量检测（可选自动暂停见待定） |

**收件箱与审计的关系**：

| 维度 | `audit_log` | `admin_inbox` |
|---|---|---|
| 记什么 | 一切行为（含成功、失败、被拒） | 只有"需要人做一件事"的项 |
| 可变性 | 只追加，永不修改 | `read_at` / `read_by` 会被写入（这是有意的：**"已读"本身是一个行为**） |
| 谁看 | 管理员检索 | 管理员日常入口（登录页未读数） |
| 保留 | 按留存策略长期保留 | 已读项可归档；未读项不归档 |

- **为什么收件箱可以"可变"而审计不行**：收件箱是**工作队列**，它的价值在"哪些还没人管"；审计是**事实记录**，它的价值在"发生过什么"。把已读状态写进 `audit_log` 会让审计表出现 UPDATE 路径，而这个路径一旦存在，append-only 就名存实亡。因此：**"某人把某项标为已读"这个动作写一条审计事件（`inbox_read`），而已读状态本身写在 `admin_inbox` 表里。**
- **为什么不做实时推送**：邮箱 / Webhook 需要额外的出站基础设施与凭据管理，而 MVP 的部署形态是单二进制、本地起（PLAN 13）。登录拉未读 + 页面轮询已经能把"必须有人处理"的信号送到人眼前，且不引入新的失败面（推送通道本身会坏，坏了还没人知道）。
- **为什么目录变化要"检测到变动即写一条"而不是每日汇总一条**：`model_missing` 与 `model_added` 的处置动作不同（前者要决定是否接纳下线，后者要决定是否授权给组）。合并成"今天有 7 个模型变动"会让管理员必须再去翻审计才能知道是哪 7 个。

> **待定**：`admin_inbox` 的保留策略——已读项保留多久、是否需要"忽略 / 稍后提醒"这类状态、以及同一 `related_id` 重复产生时是去重还是追加。

> **待定**：未读计数的告警阈值（未读超过 N 条、或某条 `severity = high` 未读超过 T 小时 → 是否需要站内提示之外的通道）。

## 4. 脱敏模式

默认状态（PLAN 9.5）：**不记录请求正文**。可记录的是结构：端点、抽象模型名、状态码、TTFT、耗时、token 数、错误码。

排查模式（显式开启时）：

| 规则 | 内容 |
|---|---|
| 保留结构 | 消息条数、角色顺序、字段名、token 计数 |
| 抹掉文本 | 消息 `content` 替换为占位（如 `<redacted:N chars>`） |
| 长度保留 | 保留字符数，便于判断是截断还是内容问题 |
| UI 明示 | 界面必须显式提示"当前处于排查模式，内容已脱敏留痕" |
| 开关本身进审计 | 谁在什么时候、对哪个范围开启了脱敏模式 |

- 为什么是"保结构抹文本"而不是"全记"或"全不记"：排障需要的是形状（是不是超长、是不是某种消息序列触发的上游报错），而形状不依赖文本内容。全记等于把用户内容复制一份到审计库；全不记则让排查只能靠猜。
- 为什么"开启脱敏模式"这个动作本身要进审计：它是系统里唯一一条"可以看见用户内容的路径"。这条路径的开合必须留痕，否则它就成了一条无人监督的后门。
- 为什么 UI 必须明示：用户有权知道自己的内容在这一次请求中被记录了。

**掩码是默认值而不是可选项**：即使开启了排查模式，第 2 节列出的禁止项（Key、令牌、密码、恢复码、凭据明文）仍然不写。

## 5. 留存与轮转

| 项 | 规则 | 为什么 |
|---|---|---|
| 写入 | `append-only`；**不提供 UPDATE / DELETE 路径** | 见第 1 节 |
| 输出 | `log/slog` JSON（PLAN 9.6）+ 结构化写库 | 便于外部采集与本地查询两条路径 |
| 轮转 | 按时间 / 大小分段归档 | 单表无限增长会让查询与备份同时退化 |
| 账户删除后 | 审计行**不级联删除**，`account_id` 继续保留 | 删掉审计等于允许"删账户即抹除历史"；`merged` 状态的存在正是为了让外键不悬挂（见 [01-accounts.md](01-accounts.md#5-账户状态机)） |
| 关联 | 审计通过 `target` 指向账户 / 组 / Key，不通过外键强约束 | 被删对象的审计行仍须可读 |
| **结算事务** | 请求结束后立即扣减：同一事务写 `requests` + `usage_daily` + 账户额度；失败则整笔回滚并记 `settle_failed` | 扣减与用量必须同生共死；只扣不记或只记不扣都会让账目与事实分离 |

**为什么结算要落在同一个事务里，而这与审计是两条线**：结算事务保证的是**账目一致**（用量、聚合、额度三者对齐），它失败时整笔回滚；审计保证的是**事实可追**（尝试过结算这件事本身），它成功与否都要留一条。若把两者塞进同一个事务，就会出现"审计写失败导致额度没扣"——这在按额度计费的站点上是直接的经济损失。

**审计与请求日志的留存期可以不同**：审计回答的是合规与追责问题，请求日志回答的是计量与排障问题，两者的价值衰减速度不同。具体天数见待定。

## 6. 可观测指标

| 指标 | 来源 | 阈值动作 | 为什么 |
|---|---|---|---|
| 登录失败率（按账户 / 按 IP） | 审计 | 告警 → 退避 / 锁定 | 爆破与撞库（PLAN 9.3、[02-authn.md](02-authn.md#10-防爆破)） |
| **退避与锁定触发次数** | 审计 | 突然归零 → 告警 | 取消提权后登录是唯一一次身份证明；这个计数长期为 0 说明防线没生效 |
| 注册速率（按 IP） | 审计 | 限速 | 刷号（PLAN 2.7） |
| 鉴权失败数（无效 / 已吊销 Key） | 审计 + 判定链 | 告警 | 泄露后重放或扫描 |
| **单账户单位时间用量突增** | `usage_daily` / `requests` | 告警；可选自动暂停（PLAN 9.1） | 泄露的典型表现是"用量形状突变"，而不是"用量变大"——正常用户有节律。按账户而不是按 Key 聚合，因为额度就在账户上 |
| 账户额度拒绝数（按维度） | 审计 | 观察 | 反映额度配置是否合理；突增可能是滥用 |
| 429 数 | 审计 | 观察 | 与正常流量区分；也用于验证 `Retry-After` 是否被遵守 |
| **全局预算熔断触发** | 审计 | **必须告警**（PLAN 9.1） | 这是全站级事件，用户无法自行处置 |
| 无候选可用（503）率 | 审计 | 告警 | 上游池健康度（PLAN 3.1） |
| 上游错误率（按上游 / 按真实模型） | `requests` | 观察 → 鉴定 / 下线处置 | 关系到贡献凭据的质量 |
| 鉴定复检队列积压 | 目录 + 鉴定状态 | 告警 | `unverified` 默认放行入池，必须有人复检 |
| 账户审核队列积压 | 账户状态 | 告警 | PLAN 13 已列为风险；积压 = 用户等不到批准 |
| **`admin_inbox` 未读数（按 `kind` / `severity`）** | `admin_inbox` | 未读 > 阈值或高等级项超时 → 告警 | 收件箱的信号如果不被看见，它就只是审计表的另一个视图 |
| 组用量汇总（按 `unit` / `period`） | `usage_daily` | 只读 | 运营视角（见 [03-groups.md](03-groups.md#7-组可见性)） |
| 组共享池余量 | `group_quota_pools` | 低位告警 | 池耗尽前的唯一预警窗口 |
| `/healthz`（进程）/ `/readyz`（含上游连通性） | 运行态 | 探针 | 分离的原因：进程活着不代表能服务（PLAN 9.6） |
| govulncheck（CI） | 构建 | 阻断 | PLAN 9.6、验收 20 |

**为什么指标要区分"用量突增"与"用量变大"**：高额度用户与滥用者在总量上可能一样。可判别的是**形状**：新出现的并发、非常规时间的持续拉取、token 长短分布的突变。指标设计要能表达形状，而不只是总量。

**为什么"退避与锁定触发次数"是一个可以归零的指标**：大多数指标看"涨得太快"，这一个看"一直是 0"。取消类级提权后，登录本身承担了全部身份证明责任；如果一项本该经常被撞上的防线从未被撞上，要么是参数过宽（等于没有），要么是它根本没接上。

**为什么租户可见的指标里不能出现真实模型名**：指标面板是最容易被忽略的泄漏面。租户侧的一切可观测输出（用量图、日志、错误详情）都只能出现抽象模型名与真实落点的**非归因**部分（PLAN 3.7、验收 10 反面清单）。

## 7. 可见性

| 信息 | 账户本人 | 贡献者 | 管理员 |
|---|---|---|---|
| 自己的登录 / 会话 / 改密事件 | ✅ | ✅ | ✅ |
| 自己 Key 的事件 | ✅（有 `tenant` 类时） | ❌（无 Key 入口） | ✅ |
| 自己贡献的凭据事件 | ❌ | ✅ | ✅ |
| 自己的账户级额度变更 | ✅（只读） | ✅（只读） | ✅ |
| 他人任何事件 | ❌ | ❌ | ✅ |
| 审计日志检索 | ❌ | ❌ | ✅ |
| `admin_inbox` | ❌ | ❌ | ✅ |
| 真实模型与归因链 | ❌ | ❌ | ✅ |
| 系统级指标（熔断、上游错误） | ❌ | ❌ | ✅ |

- **为什么贡献者看不到自己的 Key 事件**：`contributor` 类不提供模型调用能力（见 [01-accounts.md](01-accounts.md#2-三个权限类)），因此该账户名下不应存在 Key；看不到对应入口是权限类隔离的直接表现（验收 10）。同一条理由反过来也成立：只有 `tenant` 类的账户看不到凭据事件。
- **为什么本人能看到自己的安全事件**：用户可以据此发现"有人在尝试登我的号"。这也是防爆破告警的用户侧落点。
- **为什么额度变更对本人可见（只读）**：额度被调到 0 与"服务坏了"在现象上完全一样。让本人能看到"我的额度是多少、什么时候被改过"，是把一次必然发生的客服工单变成一次自助查询。

## 8. 数据结构与接口签名

```go
type AuditResult string

const (
    AuditOK      AuditResult = "ok"      // 执行成功
    AuditFailed  AuditResult = "failed"  // 执行失败
    AuditDenied  AuditResult = "denied"  // 被判定链拒绝
)

type AuditEvent struct {
    ID          int64
    TS          time.Time
    AccountID   string     // 可为空（例如匿名注册失败）
    ActingClass Class      // 本次行为以哪个类进行
    // 2026-10-20 取消类级提权：Elevated 字段已删除。
    // 理由：它恒为同一值，留着会让读日志的人去猜一个不成立的区分。
    Action      string     // 闭集合，见第 3 节
    Target      string     // "类型:ID"，例如 "account:01J..." / "group:01J..."
    IP          string
    UA          string
    Result      AuditResult
    Detail      []byte     // JSON，已经过第 4 节脱敏
}

type AuditService interface {
    // Record 是唯一写入口。审计服务不提供 Update / Delete —— append-only 由接口形状保证。
    Record(ev AuditEvent) error

    // Query 供管理端检索；调用方必须持有 admin 类（见 04-authz.md 第 6 节）。
    Query(subject Subject, f AuditFilter) ([]AuditEvent, error)

    // SetRedactionMode 开启 / 关闭排查模式；该动作本身必须被 Record 记录。
    SetRedactionMode(subject Subject, scope RedactionScope, on bool) error
}

type AuditFilter struct {
    From, To    time.Time
    AccountID   string
    ActingClass Class
    Action      string
    Result      AuditResult
    Limit       int
}

// RedactionScope 是脱敏模式的生效范围；粒度与取值见待定。
type RedactionScope struct {
    AccountID string // 空表示全局
    KeyID     string
}

// InboxKind 是 admin_inbox 的信号类别（闭集合，见第 3.1 节）。
type InboxKind string

type InboxItem struct {
    ID        int64
    Kind      InboxKind
    Severity  string // high / normal / low
    Title     string
    Detail    []byte     // JSON，同样经过第 4 节脱敏
    RelatedID string     // 指向账户 / 组 / 模型 / 凭据
    CreatedAt time.Time
    ReadAt    *time.Time // 空 = 未读；已读状态写在本表，不写审计
    ReadBy    string
}

type InboxService interface {
    // List 返回未读优先的列表；管理端页面与登录时的未读计数都走这里。
    List(subject Subject, f InboxFilter) ([]InboxItem, error)

    // MarkRead 写入已读状态，并额外记一条 inbox_read 审计事件。
    // 为什么状态与审计分成两处：审计表不能有 UPDATE 路径（见第 3.1 节）。
    MarkRead(subject Subject, ids []int64) error

    // Enqueue 由后台任务与判定链调用（目录刷新、凭据失效、池耗尽、熔断等）。
    Enqueue(item InboxItem) error
}

// InboxFilter 见待定（是否需要按 severity / kind 过滤、是否需要分页游标）。
type InboxFilter struct {
    Kind      InboxKind
    UnreadOnly bool
    Limit     int
}
```

**为什么 `Record` 不接受调用方传入的 `TS`**：事件时间必须由服务端生成。允许调用方传时间，就等于允许伪造事件顺序，而顺序正是审计的核心价值。

**为什么 `MarkRead` 单独一个接口而不是复用 `Record`**：`Record` 是纯追加通道，它不该有能力改变任何表的状态。把"标记已读"塞进 `Record` 会让调用方误以为审计能改状态——而这正是 append-only 要防的误解。

## 9. 待定

> **待定**：审计日志与请求日志各自的留存期与轮转粒度（总纲只要求 append-only 与轮转，未给数值）。

> **待定**：脱敏模式的生效粒度——按账户、按 Key、按单次请求，还是全局？粒度越细越容易被用来长期偷看某一个用户，粒度越粗影响面越大。

> **待定**：是否需要外部导出（SIEM / 对象存储），以及导出动作本身是否也要进审计。

> **待定**：异常用量检测的窗口、阈值与"可选自动暂停"的默认开关（PLAN 9.1 只说"可选"）。按账户聚合后，"突增"的基线应当取该账户自身的历史，还是同组用户的同期水平。

> **待定**：`admin_inbox` 的保留策略、去重规则与告警阈值（见第 3.1 节末）。

> **已定（2026-10-19）**：管理面 IP 允许列表**不提供**（总纲 9.3 已同步），因此不存在这个事件类。

> **待定**：审计检索是否支持导出为文件，导出是否限制条数，导出行为是否留痕。

> **待定**：已删除账户 / 已吊销 Key 在审计检索界面上的展示方式（显示原 ID、显示前缀，还是显示"已删除"占位）。

> **待定**：价格乘数表的变更是否需要"生效时间"（改完之后是在途请求按旧乘数结算，还是一律按新乘数）——它同时影响 `credit` 额度与 `price` 排序。
