# 审计与可观测
## 1. 目标与三条边界
| 边界 | 内容 | 为什么 |
|---|---|---|
| **append-only** | 只追加，不提供修改 / 删除接口（PLAN 9.5） | 可被编辑的审计等于没有审计：一旦"改一条记录"成为可能，事后就无法区分"真的没发生"与"被抹掉了" |
| **默认不记录请求正文** | 默认只记结构与元数据；排查时显式开启脱敏模式（PLAN 9.5） | 中转站没有理由长期持有用户的业务文本；默认持有会把一次数据库泄露的后果从"凭据泄露"升级为"用户内容泄露" |
| **分账** | 每条记录带 `account_id + acting_class (+ elevated)`（PLAN 9.5、10） | 隔离的追责层（见 [01-accounts.md](01-accounts.md#3-隔离的准确含义)）：一个账户有多重身份时，必须能说清是哪一重做的 |

**三个数据集不是一回事**，混用会同时牺牲审计完整性与查询性能：

| 数据集 | 表 | 记什么 | 谁看 | 可变性 |
|---|---|---|---|---|
| 审计 | `audit_log` | **行为**：谁在什么时候做了什么、结果如何 | 管理端 | 只追加 |
| 请求日志 | `requests` | **计量**：每次调用的端点、抽象模型、真实落点、状态、TTFT、耗时、token（PLAN 8） | 用户看自己那部分；管理端看归因 | 只追加 |
| 用量聚合 | `usage_daily` | **汇总**：日 × Key × 抽象模型 × 真实模型的计数 | 用户 / 管理端 | 幂等累加 |

- 为什么审计不合并进 `requests`：`requests` 是**每一笔业务调用**，量级比审计大几个数量级，而审计要回答的问题（谁改了策略、谁提权了、谁在爆破）绝大多数与业务调用无关。把两者放一张表，等于用噪声最高的数据集回答最需要精度的问题。
- 为什么用量聚合独立于请求日志：额度判定发生在每个请求之前（见 [04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求) 第 6 步），实时聚合全表会让鉴权成本随历史增长（见 [05-keys.md](05-keys.md#4-配额与限速维度)）。

## 2. 字段

`audit_log(id, ts, account_id, acting_class, elevated, action, target, ip, ua, result, detail)`（PLAN 第 10 章）

| 字段 | 语义 | 为什么必须有 |
|---|---|---|
| `id` | 自增 / 单调 ID | 分页与"从上次位置继续读"；也便于证明顺序 |
| `ts` | 事件时间 | 一切排查从时间线开始 |
| `account_id` | 主体账户 | 归属；合并后旧记录仍保留原 ID（见 [01-accounts.md](01-accounts.md#4-账户合并)） |
| `acting_class` | **本次行为以哪个类进行** | 不可从 `account_id` 推导——同一账户可同时有 `admin` 与 `tenant`（PLAN 2.3）。缺这个字段，"管理员账户出事"就永远分不清是管理面失守还是 Key 泄露 |
| `elevated` | 是否处于类级提权有效期 | 管理动作的**风险等级**由此区分：同样是"改了一个组"，提权状态下做与未提权状态下做，含义完全不同（PLAN 2.5） |
| `action` | 动作标识（闭集合） | 分类统计与告警规则的基础（见第 3 节） |
| `target` | 被操作对象（类型 + ID） | 与 `action` 组成"谁对什么做了什么" |
| `ip` / `ua` | 来源 | 爆破特征是"同源多目标 / 同目标多源"，只能从聚合中看出（见 [02-authn.md](02-authn.md#10-防爆破)） |
| `result` | 成功 / 失败 / 拒绝 | 无 `result` 的日志无法区分"发生了"与"被拦住了"，而后者才是安全事件的信号 |
| `detail` | 结构化补充（JSON） | 差异信息（改了哪个策略键、从什么改成什么）。**必须经过第 4 节的脱敏** |

**为什么 `elevated` 是独立布尔而不是 `acting_class` 的派生**：`acting_class = admin` 只说明"这一重身份有管理权"，不说明"此刻是否通过了当场重验"。两者都必要（PLAN 9.5 原文即 `account_id + acting_class (+ elevated)`）。

**为什么 `ua` 要存而不是只存 IP**：共享出口（校园、公司、运营商 NAT）会让同一个 IP 承载大量无关用户。UA 是在 IP 之外唯一还能把同源事件**归并或拆开**的低成本信号。

**禁止出现在审计里的东西**（任何情况下都不写，包括 `detail`）：

| 禁止项 | 理由 |
|---|---|
| API Key 明文 | PLAN 9.4：只存哈希，明文仅创建时返回一次 |
| 会话令牌、密码、恢复码 | 同理；审计是"谁都可能读到"的表 |
| 上游凭据明文 | PLAN 9.4：永不回显，连贡献者本人也不行 |
| 请求 / 响应正文 | 默认不记录（PLAN 9.5）；脱敏模式下的例外见第 4 节 |

## 3. 事件分类表

`action` 是闭集合，按类别分组。新增事件必须先归入某一类，否则告警规则无法覆盖它。

### 认证与会话

| 事件 | 触发点 | 必带字段 |
|---|---|---|
| 登录成功 / 失败 | 密码登录、OAuth 登录、恢复码登录 | `account_id`（失败时可为空）、`ip`、`ua`、`result`、失败原因类别 |
| 登出 | 用户主动 | `account_id`、会话 ID |
| 改密（自助）/ 重置（管理员） | 见 [02-authn.md](02-authn.md#4-密码策略) | `acting_class`、`elevated`、目标账户、联动的会话吊销数 |
| 会话吊销 | 登出 / 改密 / 禁用 / 合并 | 触发原因 |

- 为什么登录**失败**也要记：爆破与撞库的特征只存在于失败样本里（PLAN 9.3 明定失败记录含 IP / UA 进审计）。

### 类级提权

| 事件 | 触发点 | 必带字段 |
|---|---|---|
| 提权挑战发起 | 进管理面 / 改配置 | `account_id`、`acting_class`、因子类型 |
| 提权成功 / 失败 | 提交第二因子 | `elevated`、`result` |
| 提权过期 | 超过有效期 | — |
| 危险操作逐次重验 | 删账户 / 改组 / 改抽象模型 / 改弃用（PLAN 2.5） | 具体操作 |

- 为什么提权事件要单独成类：它是"高权限被激活"的唯一信号。提权频率的异常上升（无论来自成功还是失败）是账户被接管的最直接指标。

### 账户与权限类

| 事件 | 说明 |
|---|---|
| 注册 | 自助注册 → `pending`；带来源 IP |
| 审核批准 / 拒绝 | 批准必须记录**选中的组与配额**（PLAN 2.7） |
| 禁用 / 恢复 | 转 `disabled` 必须记录联动的 Key 吊销数量 |
| 权限类授予 / 撤销 | 单独成条（`account_classes` 的增删） |
| 账户合并 | 记录 source / target；见 [01-accounts.md](01-accounts.md#4-账户合并) |
| 管理员导入（批次） | 一条批次事件：操作者、行数、成功 / 失败数 |
| 管理员导入（单体） | 每个成功账户一条创建事件（见 [02-authn.md](02-authn.md#3-管理员导入账密)） |

### 组

| 事件 | 说明 |
|---|---|
| 创建 / 改名 / 改描述 | — |
| 改策略（放开 / 限制） | 记录策略键、旧值、新值 |
| 成员增 / 删 | 记录账户集合；**成员列表本身不对成员可见**（见 [03-groups.md](03-groups.md#7-组可见性)） |
| 默认组变更 | — |
| 删组 | 记录成员退回默认组的数量（见 [03-groups.md](03-groups.md#6-删组不删人)） |

### API Key

| 事件 | 说明 |
|---|---|
| 创建 | 记录前缀（不是明文） |
| 改名 | — |
| 停用 / 恢复 | 可恢复的运营动作 |
| **吊销** | 不可恢复；记录操作者（本人 / 管理员） |
| 限额变更 | 记录各维度旧值 / 新值 |
| 白名单变更 | 记录抽象模型集合的差异 |

### 凭据（贡献）

| 事件 | 说明 |
|---|---|
| 新增贡献（登录态 / 未登录） | 未登录时记录新建的 `contributor` 账户与恢复码的**发放事实**（不记恢复码本身） |
| 与既有 `UNIQUE(provider, external_id)` 冲突 | 记录"已拒绝，未覆盖"（PLAN 4.2） |
| 停用 / 删除 | — |
| 登录用途开关（`login_enabled`） | — |
| 鉴定结论变化 | 记录新旧状态（`verified` / `suspect` / `unverified` / `trusted`） |

### 抽象模型与弃用

| 事件 | 说明 |
|---|---|
| 创建 / 修改 | 记录策略引擎配置、能力声明 |
| 弃用 / 撤销弃用 | 记录 `deprecated_at`、`sunset_at` |
| 替代链变更 | 记录替代目标；替代链上限 5 跳 |
| 禁用 / 恢复 | `disabled` 不接受请求（404 / 410 Gone） |

### 真实模型与鉴定（仅管理端）

| 事件 | 说明 |
|---|---|
| 目录自动变化 | `source = auto` 的新增 / 消失（`missing_since`） |
| 人工覆盖 | `source = override` 的改动 |
| `hidden` 切换 | — |
| 鉴定处置 | 对 `unverified` 模型的放行 / 拦阻决定 |

### 请求与额度（安全信号类）

| 事件 | 触发点 | 为什么算安全事件 |
|---|---|---|
| 鉴权失败 | 判定链第 2–4 步（见 [04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求)） | 无效 / 已吊销 Key 的持续使用是扫描或泄露后重放的信号 |
| 额度拒绝 | 日 / 月 token 耗尽 | PLAN 验收 4 要求留痕 |
| 限速触发（429） | RPM / TPM / 并发 | 与正常用量区分 |
| 全局预算熔断 | 全站当日超标 | PLAN 9.1：必须告警 |
| 无候选可用（503） | 策略引擎无可用候选 | 运维故障信号，与 404 区分（PLAN 3.1） |
| 上游错误 | 上游返回错误 | 关系到贡献凭据的健康度 |

### 管理与系统

| 事件 | 说明 |
|---|---|
| 管理面进入 | 首次进入管理页（提权成功后） |
| ~~管理 IP 允许列表拒绝~~ | **不适用**（2026-10-19 定案：不提供该功能） |
| 配置变更（`settings`） | 键、旧值、新值 |
| 数据迁移 | 迁移编号与结果 |

## 4. 脱敏模式

默认状态（PLAN 9.5）：**不记录请求正文**。可记录的是结构：端点、抽象模型名、状态码、TTFT、耗时、token 数、错误码。

排查模式（显式开启时）：

| 规则 | 内容 |
|---|---|
| 保留结构 | 消息条数、角色顺序、字段名、token 计数 |
| 抹掉文本 | 消息 `content` 替换为占位（如 `<redacted:N chars>`） |
| 长度保留 | 保留字符数，便于判断是截断还是内容问题 |
| UI 明示 | 界面必须显式提示"当前处于排查模式，内容已脱敏留痕" |
| 开关本身进审计 | 谁在什么时候、对哪个范围开启了脱敏模式 |

- 为什么是"保结构抹文本"而不是"全记"或"全不记"：排障需要的是形状（是不是超长、是不是某种消息序列触发的上游报错），而形状不依赖文本内容。全记等于把用户内容复制一份到审计库；全不记则让排查只能靠猜。
- 为什么"开启脱敏模式"这个动作本身要进审计：它是系统里唯一一条"可以看见用户内容的路径"。这条路径的开合必须留痕，否则它就成了一条无人监督的后门。
- 为什么 UI 必须明示：用户有权知道自己的内容在这一次请求中被记录了。

**掩码是默认值而不是可选项**：即使开启了排查模式，第 2 节列出的禁止项（Key、令牌、密码、恢复码、凭据明文）仍然不写。

## 5. 留存与轮转

| 项 | 规则 | 为什么 |
|---|---|---|
| 写入 | `append-only`；**不提供 UPDATE / DELETE 路径** | 见第 1 节 |
| 输出 | `log/slog` JSON（PLAN 9.6）+ 结构化写库 | 便于外部采集与本地查询两条路径 |
| 轮转 | 按时间 / 大小分段归档 | 单表无限增长会让查询与备份同时退化 |
| 账户删除后 | 审计行**不级联删除**，`account_id` 继续保留 | 删掉审计等于允许"删账户即抹除历史"；`merged` 状态的存在正是为了让外键不悬挂（见 [01-accounts.md](01-accounts.md#5-账户状态机)） |
| 关联 | 审计通过 `target` 指向账户 / 组 / Key，不通过外键强约束 | 被删对象的审计行仍须可读 |

**审计与请求日志的留存期可以不同**：审计回答的是合规与追责问题，请求日志回答的是计量与排障问题，两者的价值衰减速度不同。具体天数见待定。

## 6. 可观测指标

| 指标 | 来源 | 阈值动作 | 为什么 |
|---|---|---|---|
| 登录失败率（按账户 / 按 IP） | 审计 | 告警 → 退避 / 锁定 | 爆破与撞库（PLAN 9.3、[02-authn.md](02-authn.md#10-防爆破)） |
| 注册速率（按 IP） | 审计 | 限速 | 刷号（PLAN 2.7） |
| 提权成功 / 失败次数 | 审计 | 异常上升 → 告警 | 账户被接管的最直接指标（PLAN 9.5 列为必审计项） |
| 鉴权失败数（无效 / 已吊销 Key） | 审计 + 判定链 | 告警 | 泄露后重放或扫描 |
| **单 Key 单位时间用量突增** | `usage_daily` / `requests` | 告警；可选自动暂停（PLAN 9.1） | 泄露的典型表现是"用量形状突变"，而不是"用量变大"——正常用户有节律 |
| 额度拒绝数 | 审计 | 观察 | 反映额度配置是否合理；突增可能是滥用 |
| 429 数 | 审计 | 观察 | 与正常流量区分；也用于验证 `Retry-After` 是否被遵守 |
| **全局预算熔断触发** | 审计 | **必须告警**（PLAN 9.1） | 这是全站级事件，用户无法自行处置 |
| 无候选可用（503）率 | 审计 | 告警 | 上游池健康度（PLAN 3.1） |
| 上游错误率（按上游 / 按真实模型） | `requests` | 观察 → 鉴定 / 下线处置 | 关系到贡献凭据的质量 |
| 鉴定复检队列积压 | 目录 + 鉴定状态 | 告警 | `unverified` 默认放行入池，必须有人复检 |
| 账户审核队列积压 | 账户状态 | 告警 | PLAN 13 已列为风险；积压 = 用户等不到批准 |
| 组用量汇总 | `usage_daily` | 只读 | 运营视角（见 [03-groups.md](03-groups.md#7-组可见性)） |
| `/healthz`（进程）/ `/readyz`（含上游连通性） | 运行态 | 探针 | 分离的原因：进程活着不代表能服务（PLAN 9.6） |
| govulncheck（CI） | 构建 | 阻断 | PLAN 9.6、验收 20 |

**为什么指标要区分"用量突增"与"用量变大"**：高额度用户与滥用者在总量上可能一样。可判别的是**形状**：新出现的并发、非常规时间的持续拉取、token 长短分布的突变。指标设计要能表达形状，而不只是总量。

**为什么租户可见的指标里不能出现真实模型名**：指标面板是最容易被忽略的泄漏面。租户侧的一切可观测输出（用量图、日志、错误详情）都只能出现抽象模型名与真实落点的**非归因**部分（PLAN 3.7、验收 10 反面清单）。

## 7. 可见性

| 信息 | 账户本人 | 贡献者 | 管理员 |
|---|---|---|---|
| 自己的登录 / 会话 / 改密事件 | ✅ | ✅ | ✅ |
| 自己 Key 的事件 | ✅ | ❌（无 Key 入口） | ✅ |
| 自己贡献的凭据事件 | ❌ | ✅ | ✅ |
| 他人任何事件 | ❌ | ❌ | ✅ |
| 审计日志检索 | ❌ | ❌ | ✅（需提权） |
| 真实模型与归因链 | ❌ | ❌ | ✅ |
| 系统级指标（熔断、上游错误） | ❌ | ❌ | ✅ |

- **为什么贡献者看不到自己的 Key 事件**：`contributor` 类不提供模型调用能力（见 [01-accounts.md](01-accounts.md#2-三个权限类)），因此该账户名下不应存在 Key；看不到对应入口是权限类隔离的直接表现（验收 10）。
- **为什么本人能看到自己的安全事件**：用户可以据此发现"有人在尝试登我的号"。这也是防爆破告警的用户侧落点。

## 8. 数据结构与接口签名

```go
type AuditResult string

const (
    AuditOK      AuditResult = "ok"      // 执行成功
    AuditFailed  AuditResult = "failed"  // 执行失败
    AuditDenied  AuditResult = "denied"  // 被判定链拒绝
)

type AuditEvent struct {
    ID          int64
    TS          time.Time
    AccountID   string     // 可为空（例如匿名注册失败）
    ActingClass Class      // 本次行为以哪个类进行
    Elevated    bool       // 是否处于提权有效期
    Action      string     // 闭集合，见第 3 节
    Target      string     // "类型:ID"
    IP          string
    UA          string
    Result      AuditResult
    Detail      []byte     // JSON，已经过第 4 节脱敏
}

type AuditService interface {
    // Record 是唯一写入口。审计服务不提供 Update / Delete —— append-only 由接口形状保证。
    Record(ev AuditEvent) error

    // Query 供管理端检索；调用方必须已通过提权校验（见 04-authz.md 第 6 节）。
    Query(subject Subject, f AuditFilter) ([]AuditEvent, error)

    // SetRedactionMode 开启 / 关闭排查模式；该动作本身必须被 Record 记录。
    SetRedactionMode(subject Subject, scope RedactionScope, on bool) error
}

type AuditFilter struct {
    From, To    time.Time
    AccountID   string
    ActingClass Class
    Elevated    *bool
    Action      string
    Result      AuditResult
    Limit       int
}

// RedactionScope 是脱敏模式的生效范围；粒度与取值见待定。
type RedactionScope struct {
    AccountID string // 空表示全局
    KeyID     string
}
```

**为什么 `Record` 不接受调用方传入的 `TS`**：事件时间必须由服务端生成。允许调用方传时间，就等于允许伪造事件顺序，而顺序正是审计的核心价值。

## 9. 待定

> **待定**：审计日志与请求日志各自的留存期与轮转粒度（总纲只要求 append-only 与轮转，未给数值）。

> **待定**：脱敏模式的生效粒度——按账户、按 Key、按单次请求，还是全局？粒度越细越容易被用来长期偷看某一个用户，粒度越粗影响面越大。

> **待定**：是否需要外部导出（SIEM / 对象存储），以及导出动作本身是否也要进审计。

> **待定**：异常用量检测的窗口、阈值与"可选自动暂停"的默认开关（PLAN 9.1 只说"可选"）。

> **已定（2026-10-19）**：管理面 IP 允许列表**不提供**（总纲 9.3 已同步），因此不存在这个事件类。

> **待定**：审计检索是否支持导出为文件，导出是否限制条数，导出行为是否留痕。

> **待定**：已删除账户 / 已吊销 Key 在审计检索界面上的展示方式（显示原 ID、显示前缀，还是显示"已删除"占位）。
