# 组与合并语义
## 1. 组是什么、不是什么
**一个组 = 一组策略 + 一批成员**，是**管理员的批量控制单元**（PLAN 2.6、README 术语表）。
| | 不做：团队（Tingly Box 的 Team） | 做：组 |
|---|---|---|
| 性质 | 组织实体，成员归属团队 | **管理员的批量控制单元** |
| 端点 | 每团队一个共享端点 | 全站一个端点，按 Key 区分 |
| 可见性 | 成员知道同团队 | 成员**不知道**彼此同组 |
| 凭据 | 团队级共享 | 组**不持有**任何 Key 或凭据 |
| 汇总 | Team usage | 管理员视角的组用量汇总（运营用） |
| 邀请 | 有 | 无 |

**为什么要有组**：一个公网中转站要管的是"一批人能看哪些模型、能用多少额度"。如果这些策略只能挂在账户上，那么每次新批一个人就要复制一遍配置，改一次全局额度就要改几十个账户——策略的一致性靠人的记性维持，必然漂移。把策略挂在组上，账户只负责"属于哪些组"，策略就变成可复用、可审计的对象。

**为什么组不能长成团队**：一旦成员之间互相可见（成员列表、组用量、邀请），组就变成了组织，随之而来的是"我是哪个组的""为什么他额度比我高"这类协作诉求，而 PLAN 明确不做团队协作（PLAN 0、1.1）。因此可见性必须从设计上就锁死（见第 7 节）。

## 2. 组模型

```
group {
  id, name, description,
  is_default,          -- 默认组标记
  created_at
}

group_member {
  group_id, account_id  -- 多对多；成员必须是带 tenant 类的账户
}

group_model {
  group_id, abstract_model_id   -- 组可访问的抽象模型（放开类策略的载体）
}

group_policy {
  group_id, policy_key, policy_value  -- 放开类取并集 / 限制类取最严
}
```

| 约束 | 内容 | 为什么 |
|---|---|---|
| 成员资格 | 成员必须是**带 `tenant` 类**的账户（PLAN 2.6） | 组管的是模型可见性与额度，这两个都只对 `tenant` 侧有意义；把纯 `contributor` 账户放进组，等于给一个没有调用能力的主体配策略，全是死配置 |
| 归属 | 组**不持有** Key、不持有凭据、不提供端点（PLAN 2.6） | 一旦组持有 Key，"共享 Key"就等价于团队共享凭据，团队语义从后门回来了 |
| 组关系 | 一个账户可属**多个**组 | 合并语义的前提（见第 4 节） |
| 组名 | 对成员可见 | 见第 7 节 |
| 组的对象 | 策略里的模型一律是**抽象模型** | 对外只暴露抽象模型（PLAN 3.1）；组若授权真实模型，等于把池结构泄漏给租户 |

> **待定**：组的成员上限与账户可属组数上限——总纲未设限，是否需要一个防止策略组合爆炸的上限。

## 3. 组策略清单

策略按**分类**分成两组，分类不是命名习惯，而是合并时的算法依据（见第 4 节）。

### 放开类（合并时取并集）

| 策略 | 说明 | 为什么归"放开" |
|---|---|---|
| 可访问的抽象模型 | 该组的成员能看到的抽象模型集合 | 可见性天然可累加：两个组各给几个模型，多属一个组只会看到更多 |
| 能否建 Key | 布尔开关 | 是"许可"而非"数量"；许可的并集就是"任一组允许即可" |
| Key 数量上限 | 每人可持有的 Key 数 | 上限属于"资源配额"还是"许可"？见下方说明 |
| Key 白名单能否放宽 | 决定成员能否自行设置 / 放宽 Key 的模型白名单 | 是"许可" |
| 能否使用某类抽象模型（如 `smart`） | 按模型类别整批授权 | 可见性的粗粒度形式，与"可访问的抽象模型"同性质 |

**关于"Key 数量上限"归放开类的说明**：它也是一个上限数字，看起来像限制类。但它约束的是"能建多少个 Key"这种**创建能力**，与"每组日额度取最小值"的合并意图不同——把上限取最严会让"加入一个额度更小的组"顺带把 Key 数量也压掉，而这两件事在管理上通常无关。

> **待定**：`Key 数量上限` 究竟归放开类还是限制类——总纲 2.6 将"能否建 Key、Key 数量上限"一并列入放开类，本册按总纲归放开类（即取并集），但"上限取最大值"的直觉与"限制取最严"的原则存在张力，需要确认。

### 限制类（合并时取最严）

| 策略 | 说明 | 为什么归"限制" |
|---|---|---|
| 每人日 token 上限 | 数值上限 | 额度是**消耗型护栏**，护栏的作用是设上界，并集会让上界失效 |
| 每人月 token 上限 | 数值上限 | 同上 |
| 每人 RPM 上限 | 速率 | 速率是共享资源（上游账号有风控），必须取最严 |
| 每人 TPM 上限 | 速率 | 同上 |
| 每人并发上限 | 并发 | 同上 |

**为什么必须有"限制类"这个分类**：护栏的意义在于**任何一条路径都不能突破它**。如果额度取并集，那么用户只要被加进一个宽松的组，历史累计用量就会立刻获得一个新的、更大的上界——"加组即提权"。取最严让加组在额度维度上**只会收紧或不变**。

**默认组与策略完备性**：每个账户至少属于默认组（见第 5 节），因此任何账户的每个策略键都至少有一个来源，不会出现"没有策略可取"的空洞。

> **待定**：策略值的类型与取值范围（如 `policy_value` 的编码方式——统一字符串 + 类型标记，还是分列存储）——总纲只给了 `group_policies(group_id, policy_key, policy_value)`。

> **待定**：限制类策略在"某组未设置该键"时的语义——是视为"无限制（不参与取最严）"还是"取全局默认值"。这直接决定取最严的结果，不可自行拍板。

## 4. 合并语义

> **放开类取并集，限制类取最严。** 布尔开关 **deny 优先**。（PLAN 2.6）

### 公式

```
可见抽象模型 = ∪ (所属组的 group_model)
日 / 月 token 上限 = min(所属组的对应限制值)
RPM / TPM / 并发上限 = min(所属组的对应限制值)
布尔开关（能否建 Key 等）= ALL(所属组)   -- 任一为 deny 即 deny
```

### 最终可用模型

```
(∪ 所属组的抽象模型)  ∩  Key 白名单（用户自己收窄）  =  实际可用
```

（该公式的完整形式见 [04-authz.md](04-authz.md#2-三层收敛)。）

### 判定示例

| 场景 | 组 A | 组 B | 合并结果 | 依据 |
|---|---|---|---|---|
| 模型可见性 | 3 个抽象模型 | 2 个（与 A 不重叠） | 5 个 | 放开取并集（对应 PLAN 验收 17） |
| 日额度 | 100 | 200 | **100** | 限制取最严 |
| RPM | 60 | 未设置（按待定语义） | 见待定 | — |
| 能否建 Key | 允许 | 禁止 | **禁止** | deny 优先 |
| Key 白名单 | `fast` | `smart` | Key 白名单由用户自持，**不合并**；组只决定"能否放宽" | 白名单是用户侧的收窄动作，不是组策略 |

**为什么"用户自己收窄"的白名单不参与组间合并**：白名单挂在 Key 上（`key_model_allow`），是用户对自己 Key 的自我限制。如果把它也做并集，就会出现"用户在一个 Key 上的收窄被另一个组放大"，收窄动作失去意义。

**为什么 deny 优先是唯一安全的选择**：布尔开关表达的是"做 / 不做某件事"。只要有一组明确禁止，就存在一个管理员做出的、针对这个账户的显式否定判断；按"任一允许即允许"处理，会让否定随时被另一个组翻掉，管理员就无法用组表达任何否定了。

> **待定**：组级**共享额度池**（全组共用每天 N 次，先到先得）是否进 MVP——现列 P1（PLAN 2.6、15）。本册只描述"每人额度取最严"。

## 5. 默认组

| 规则 | 内容 | 为什么 |
|---|---|---|
| 新账户自动进默认组 | 注册批准时若未选组，或成员被移出其它组时 | 保证有最基本的可用性（PLAN 2.6） |
| 默认组**必须始终存在** | `is_default = true` 的组唯一且不可删除 | "删组不删人 → 成员退回默认组"必须有落点；默认组可删，就等于存在一个"无处可退"的账户状态 |
| 默认组的策略 | 由管理员配置；建议保守 | 它决定所有"没被显式分配"的账户的能力上界 |

**为什么默认组是必要设计而不是便利设计**：账户的每个策略键都需要一个来源，否则判定链要在运行期处理"没有策略"这种状态，而"没有策略"的默认解释极易写成"不限制"（fail-open）。默认组把这个空洞消灭在数据层：**任何账户永远至少有一组策略**。

> **待定**：默认组是否允许改名、是否允许改策略、以及是否允许被指定为另一个组（当已有默认组时）。

## 6. 删组不删人

| 触发 | 联动 |
|---|---|
| 删组 | 成员**退回默认组**（PLAN 2.6）；不给任何账户留下"零组"状态 |
| 删组 | 该组的 `group_model` / `group_policy` / `group_member` 行一并删除 |
| 删组 | 该组的用量汇总停止归集，**历史用量不追溯**（与真实模型目录的"历史不追溯"同原则，PLAN 3.6） |
| 删组 | **进审计** |

- 为什么要"退回默认组"而不是"账户变成无组"：见第 5 节——无组账户的策略键会缺口，缺口在实现里最容易变成 fail-open。
- 为什么历史用量不追溯：用量记录的是**已经发生的调用**，它当时的策略上下文是历史事实；事后按新归属重算会让"这个月为什么超了"永久无解。

**为什么删除组是危险操作**：组是批量控制单元，删一个组会同时改变一批账户的模型可见性与额度（见 [02-authn.md](02-authn.md#6-类级提权) 的危险操作清单）。

## 7. 组可见性

| 信息 | 成员本人 | 同组其它成员 | 管理员 |
|---|---|---|---|
| 组名 | ✅ 可见 | ✅ 可见（但不知道谁在里面） | ✅ |
| 成员列表 | ❌ | ❌ | ✅ |
| 组策略明细 | 仅自己实际生效的结果 | ❌ | ✅ |
| 组用量汇总 | ❌ | ❌ | ✅（运营用） |

- **为什么成员看不到成员列表**：避免形成组织感（PLAN 2.6）——可见的成员列表会自然演化出"我们组"的协作诉求，进而演化为团队，与 PLAN 1.1 的取舍冲突。
- **为什么组名反而可见**：成员需要能理解"我为什么能用这个模型 / 为什么额度是这个数"。完全黑盒会让每一次策略变化都变成无法解释的体验问题，而组名本身不泄露同组成员。
- **为什么策略明细只给"实际生效的结果"**：成员看到的是合并后的**结果**（我可用哪些模型、我的额度是多少），而不是"哪个组给了我什么"。后者等价于把成员列表反推出来。

**为什么组用量汇总只给管理员**：它是运营指标（判断某个组是不是被滥用），不是成员可见的社交信息。成员本人应能看到的是**自己的**用量（属于 `tenant` 类的管辖范围，PLAN 2.2）。

## 8. 组的生命周期与变更

| 动作 | 是否需提权 | 审计 |
|---|---|---|
| 创建组 | 是（进管理面） | 是 |
| 改名 / 改描述 | 是 | 是 |
| 改策略（放开 / 限制） | 是（**每次重验**） | 是 |
| 加 / 移成员 | 是（**每次重验**） | 是 |
| 设置 / 变更默认组 | 是（**每次重验**） | 是 |
| 删组 | 是（**每次重验**） | 是 |

- **"改组"= 危险操作**：PLAN 2.5 把"改组"列入要求每次重新验证的四项之一。为什么提权还不够、要每次重验：一次改组的误操作可以同时改变一批账户的可见模型与额度，而这类变更没有"撤销键"——成员可能已经据此发起过请求。
- 组变更全部进审计（PLAN 2.6）。事件字段与分类见 [06-audit.md](06-audit.md)。

## 9. 数据结构与接口签名

```go
type Group struct {
    ID          string
    Name        string
    Description string
    IsDefault   bool      // 唯一且不可删除（见第 5 节）
    CreatedAt   time.Time
}

// PolicyKind 决定该策略在合并时取并集还是取最严（见第 3 节）。
type PolicyKind string

const (
    PolicyOpen   PolicyKind = "open"   // 放开类：并集
    PolicyRestrict PolicyKind = "restrict" // 限制类：最严
)

// PolicyKey 是策略键的闭集合；新增键必须先归入放开类或限制类。
type PolicyKey string

const (
    PolicyVisibleModels    PolicyKey = "visible_models"      // 放开：抽象模型集合
    PolicyCanCreateKey     PolicyKey = "can_create_key"      // 放开：布尔
    PolicyMaxKeys          PolicyKey = "max_keys"            // 放开（见第 3 节说明与待定）
    PolicyKeyAllowlistWiden PolicyKey = "key_allowlist_widen" // 放开：布尔
    PolicyModelClass       PolicyKey = "model_class_allow"   // 放开：按类别授权

    PolicyDailyTokenCap    PolicyKey = "daily_token_cap"     // 限制
    PolicyMonthlyTokenCap  PolicyKey = "monthly_token_cap"   // 限制
    PolicyRPMLimit         PolicyKey = "rpm_limit"           // 限制
    PolicyTPMLimit         PolicyKey = "tpm_limit"           // 限制
    PolicyMaxConcurrency   PolicyKey = "max_concurrency"     // 限制
)

type GroupService interface {
    // Create / Delete：删组必须把全部成员退回默认组（见第 6 节）。
    Create(actor Subject, name, description string) (*Group, error)
    Delete(actor Subject, groupID string) error

    // SetDefault：默认组唯一且不可删除（见第 5 节）。
    SetDefault(actor Subject, groupID string) error

    // AddMembers / RemoveMembers：成员必须是带 tenant 类的账户。
    AddMembers(actor Subject, groupID string, accountIDs []string) error
    RemoveMembers(actor Subject, groupID string, accountIDs []string) error

    // SetPolicy：放开类或限制类；需每次重验。
    SetPolicy(actor Subject, groupID string, key PolicyKey, value string) error
    // SetModels：组可访问的抽象模型集合（放开类）。
    SetModels(actor Subject, groupID string, abstractModelIDs []string) error

    // EffectivePolicy 供判定链调用：对一个账户做全部所属组的合并计算。
    // 放开类取并集，限制类取最严，布尔开关 deny 优先。
    EffectivePolicy(accountID string) (*EffectivePolicy, error)
}

type EffectivePolicy struct {
    VisibleModels   []string          // ∪ 各组的抽象模型
    CanCreateKey    bool              // ALL(允许)
    MaxKeys         *int              // 放开类：并集语义下的取值规则见待定
    DailyTokenCap   *int64            // min
    MonthlyTokenCap *int64            // min
    RPMLimit        *int              // min
    TPMLimit        *int              // min
    MaxConcurrency  *int              // min
}
```

## 10. 待定

> **待定**：`Key 数量上限` 归放开类（取并集 / 最大值）还是限制类（取最严）——本册按总纲 2.6 归放开类，但与"限制取最严"的原则存在张力。

> **待定**：限制类策略"某组未设置该键"时的语义（不参与取最严 vs 取全局默认值）——直接决定取最严的结果。

> **待定**：`Key 白名单能否放宽` 的精确语义——管的是"成员能否把默认空白的白名单填上"，还是"白名单能否超出组授权"。按 PLAN 11.3 的 `组授权 ∩ Key 白名单` 公式，超出组授权在数学上无效果，因此更可能是前者，但需确认。

> **待定**：默认组能否改名 / 改策略 / 被替换为另一个默认组。

> **待定**：组级共享额度池是否进 MVP（PLAN 2.6、15）。

> **待定**：组的成员上限与账户可属组数上限。
