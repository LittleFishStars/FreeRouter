# 组与合并语义

## 1. 组是什么、不是什么
**一个组 = 一组策略 + 一批成员**，是**管理员的批量控制单元**（PLAN 2.6、README 术语表）。
| | 不做：团队（Tingly Box 的 Team） | 做：组 |
|---|---|---|
| 性质 | 组织实体，成员归属团队 | **管理员的批量控制单元** |
| 端点 | 每团队一个共享端点 | 全站一个端点，按 Key 区分 |
| 可见性 | 成员知道同团队 | 成员**不知道**彼此同组 |
| 凭据 | 团队级共享 | 组**不持有**任何 Key 或凭据 |
| 汇总 | Team usage | 管理员视角的组用量汇总（运营用） |
| 邀请 | 有 | 无 |

**为什么要有组**：一个公网中转站要管的是"一批人能看哪些模型、能用多少额度"。如果这些策略只能挂在账户上，那么每次新批一个人就要复制一遍配置，改一次全局额度就要改几十个账户——策略的一致性靠人的记性维持，必然漂移。把策略挂在组上，账户只负责"属于哪些组"，策略就变成可复用、可审计的对象。

**为什么组不能长成团队**：一旦成员之间互相可见（成员列表、组用量、邀请），组就变成了组织，随之而来的是"我是哪个组的""为什么他额度比我高"这类协作诉求，而 PLAN 明确不做团队协作（PLAN 0、1.1）。因此可见性必须从设计上就锁死（见第 7 节）。

## 2. 组模型

```
group {
  id, name, description,
  is_default,          -- 默认组标记
  created_at
}

group_member {
  group_id, account_id  -- 多对多；成员必须是带 tenant 类的账户
}

group_model {
  group_id, abstract_model_id   -- 组可访问的抽象模型（放开类策略的载体）
}

group_policy {
  group_id, policy_key, policy_value  -- 放开类取并集 / 限制类取最严
}
```

| 约束 | 内容 | 为什么 |
|---|---|---|
| 成员资格 | 成员必须是**带 `tenant` 类**的账户（PLAN 2.6） | 组管的是模型可见性与额度，这两个都只对 `tenant` 侧有意义；把纯 `contributor` 账户放进组，等于给一个没有调用能力的主体配策略，全是死配置 |
| 归属 | 组**不持有** Key、不持有凭据、不提供端点（PLAN 2.6） | 一旦组持有 Key，"共享 Key"就等价于团队共享凭据，团队语义从后门回来了 |
| 组关系 | 一个账户可属**多个**组 | 合并语义的前提（见第 4 节） |
| 组名 | 对成员可见 | 见第 7 节 |
| 组的对象 | 策略里的模型一律是**抽象模型** | 对外只暴露抽象模型（PLAN 3.1）；组若授权真实模型，等于把池结构泄漏给租户 |

> **待定**：组的成员上限与账户可属组数上限——总纲未设限，是否需要一个防止策略组合爆炸的上限。

## 3. 组策略清单

策略按**分类**分成两组，分类不是命名习惯，而是合并时的算法依据（见第 4 节）。

### 放开类（合并时取并集）

| 策略 | 说明 | 为什么归"放开" |
|---|---|---|
| 可访问的抽象模型 | 该组的成员能看到的抽象模型集合 | 可见性天然可累加：两个组各给几个模型，多属一个组只会看到更多 |
| 能否建 Key | 布尔开关 | 是"许可"而非"数量"；许可的并集就是"任一组允许即可" |
| Key 数量上限 | 每人可持有的 Key 数 | 上限属于"资源配额"还是"许可"？见下方说明 |
| Key 白名单能否放宽 | 决定成员能否自行设置 / 放宽 Key 的模型白名单 | 是"许可" |
| 能否使用某类抽象模型（如 `smart`） | 按模型类别整批授权 | 可见性的粗粒度形式，与"可访问的抽象模型"同性质 |

**关于"Key 数量上限"归放开类的说明**：它也是一个上限数字，看起来像限制类。但它约束的是"能建多少个 Key"这种**创建能力**，与"每组日额度取最小值"的合并意图不同——把上限取最严会让"加入一个额度更小的组"顺带把 Key 数量也压掉，而这两件事在管理上通常无关。

**定案（2026-10-19，写入者裁定，已与总纲 2.6 对齐）**：`Key 数量上限`归**放开类**，
取各组的**最大值**。为什么它不能归限制类：限制类的定义是「取最严，加组只能收紧」；
而 Key 数量约束的是**创建能力**，与额度、速率这类**共享资源**不是一回事。把它归
限制类会产生一个荒谬的结果：一个人本来在 A 组能有 10 把 Key，被加进一个「额度
很小、但 Key 数量未特别限制」的 B 组后，可拥有的 Key 数被压到 B 的值——而额度
收紧本身已经限制了他能拿多少，再压 Key 数量不产生任何额外护栏，只制造意外。

> 同理，「能否建 Key」（布尔）与「Key 数量上限」（数值）是**同一性质**的两个层级，
> 必须归同一类。一个归放开、一个归限制会让「禁止建 Key」与「允许多少把」的判定
> 分居两套语义，实现时必然出错。

### 限制类（合并时取最严）

| 策略 | 说明 | 为什么归"限制" |
|---|---|---|
| 每人额度上限（`unit` × `period`） | 数值上限；`unit` ∈ `request` / `token` / `credit`，`period` ∈ `day` / `month` | 额度是**消耗型护栏**，护栏的作用是设上界，并集会让上界失效 |
| **每人按模型额度上限**（`model × unit × period`） | 针对单个抽象模型的每人限额（如“`smart` 每人 50 次/日”）；声明在 `group_model_quota_caps`，生效值重算进 `account_quotas` 的 `abstract_model_id > 0` 行（见 [../architecture/05-storage.md](../architecture/05-storage.md) 3.3.1） | 与总额度同性质（逐 (model, unit, period) 键取 min），只是作用域多一维；目的是拦住“把一个贵模型刷穿”而不必关掉整个账户（2026-10-20 新增） |
| 每人 RPM 上限 | 速率 | 速率是共享资源（上游账号有风控），必须取最严 |
| 每人 TPM 上限 | 速率 | 同上 |
| 每人并发上限 | 并发 | 同上 |
| **组级共享池** | 组级总消耗上限（`unit` ∈ `request` / `token` / `credit`，`period` ∈ `day` / `month`） | 挂在**组上**而非人上；见第 4 节——它与上面的"每人上限"是**两个资源**，都设时取**交集**而不是取最严 |

**额度类策略统一用「计量维度 × 周期」表达**（2026-10-20 定案）：

| 计量维度 | 单位 | 怎么算 | 为什么需要这一维 |
|---|---|---|---|
| `request` | 次数 | 一次请求 = 1，与 token 无关 | 免费站点关心"请求数"；也让高频小请求的刷量有独立闸门 |
| `token` | token 数 | `in_tokens + out_tokens` | 最直观的用量单位 |
| `credit` | Credits | `(in_tokens × in_multiplier + out_tokens × out_multiplier) / BASE`，见 [01-accounts.md](01-accounts.md#额度在账户级不在-key-上) | `token` 把贵模型与便宜模型视为等价，改用最贵模型即可在同样 token 内烧掉几十倍成本；`credit` 让"贵模型少用一点"成为可表达的约束 |

- **为什么组策略与账户级字段用同一套维度**：组策略给的是"每人额度的**上界**"，账户字段是"这个人**当前生效**的额度"（2026-10-20 定案：额度在账户级，不在 Key 上）。若两处维度不同名，管理员每次审批账户时都无法判断"组给的 100 对应账户里的哪个数"。
- **为什么每个维度是一个独立策略键，而不是一个键里带三列**：合并算子是**逐键**的（放开取并集 / 限制取最严）。把三个维度塞进同一个键，会让"组 A 给了 token 上界、组 B 给了 credit 上界"变成同一个键的两种不同形态，无从比较谁更严，"取最严"当场失效。
- **为什么维度由管理员选而不是三档全开**：三档全开意味着每个账户要同时维护三个计数器、每次判定要三次比较，而正常运营只会关心其中一个（免费站点关心次数，按量站点关心 token 或 Credits）。允许同时配置多行（DDL 主键含 `unit`），但默认只配一行。
**为什么必须有"限制类"这个分类**：护栏的意义在于**任何一条路径都不能突破它**。如果额度取并集，那么用户只要被加进一个宽松的组，历史累计用量就会立刻获得一个新的、更大的上界——"加组即提权"。取最严让加组在额度维度上**只会收紧或不变**。

**共享池为什么也归限制类，但合并算法不同于其它限制**：它在分类上仍是护栏（属于"不能突破的上界"），但它是**逐组成员共享的同一个资源**，不能像"每人上限"那样用 `min` 压成一个数——`min` 的前提是"同一资源的多个上界"。共享池对多组/多行池的合并方式是**逐个都要满足**（见第 4 节）。分类相同、算法不同，这是本册唯一一个这样的策略键。

**默认组与策略完备性**：每个账户至少属于默认组（见第 5 节），因此任何账户的每个策略键都至少有一个来源，不会出现"没有策略可取"的空洞。

> **待定**：策略值的类型与取值范围（如 `policy_value` 的编码方式）——总纲只给了 `group_policies` 的键值形状。
>
> **共享池不在此待定范围内**：共享池的计量单位与周期**结构化落列**，不走 `policy_value` JSON（见下节与 [../architecture/05-storage.md](../architecture/05-storage.md#33-组与授权)）。为什么：它是**每周期被原子递增的状态**（`pool_used`），而 JSON 值不可索引、不可在单条条件 UPDATE 里读取与判定；把它塞进 JSON 会逼实现先读出来再改回去，正是第 4 节要禁止的读-改-写。
>
> **已定（2026-10-20）**：限制类策略在“某组未设置该键”时视为**无限制，用哨兵值 `-1` 表达**，不参与取最严（`min` 跳过 -1 行；全部未设 = 生效值为 -1 = 不构成闸）。不取全局默认值：全局默认只作为**新建账户的初值**（写入时取值，见第 3.5 节），而不是运行期合并的参与者——否则“删掉一个组的一个键”会静默改变一批账户的生效额度，而管理员看到的配置页上什么都没发生。界面与存储上未设 = `-1`；`0` 仍是“零额度全拒”，与 -1 完全相反，不可混淆。

## 4. 合并语义

> **放开类取并集，限制类取最严。** 布尔开关 **deny 优先**。（PLAN 2.6）

### 公式

```
可见抽象模型 = ∪ (所属组的 group_model)
每人额度上限 = min(所属组的对应限制值)   -- 逐 (unit, period) 键单独取 min；未设键 = -1，不参与 min
每人按模型额度上限 = min(所属组 group_model_quota_caps 的对应行)   -- 逐 (model, unit, period) 键；无行 = 不限
RPM / TPM / 并发上限 = min(所属组的对应限制值)   -- 未设 = -1 不参与 min；全部未设则落回账户列的 -1/自定义值
布尔开关（能否建 Key 等）= ALL(所属组)   -- 任一为 deny 即 deny
-- 共享池（与上面的每人上限取交集，不参与 min）
共享池判定 = ALL_AND(所属组中已配置的池：pool_used + cost <= pool_limit)
-- "ALL_AND" 表示逐个都要满足；不同于上面的 min（min 求一个更严的数）

> **并发上限的落地位置**：`min(所属组的并发限制值)` 只是算出**一个数**，真正的闸门在运行时——
> 先取组级信号量再取全局信号量，任一取不到就排队。见
> [../architecture/06-runtime.md](../architecture/06-runtime.md) 2.3 节（「组级并发上限」）。
> 本册只负责算上限，不负责实现排队。
```

### 最终可用模型

```
(∪ 所属组的抽象模型)  ∩  Key 白名单（用户自己收窄）  =  实际可用
```

（该公式的完整形式见 [04-authz.md](04-authz.md#2-三层收敛)。）

### 判定示例

| 场景 | 组 A | 组 B | 合并结果 | 依据 |
|---|---|---|---|---|
| 模型可见性 | 3 个抽象模型 | 2 个（与 A 不重叠） | 5 个 | 放开取并集（对应 PLAN 验收 17） |
| 每人额度（`token` / `day`） | 100 | 200 | **100** | 限制取最严（逐 (unit, period) 键取 min） |
| 每人额度（A 给 `token` / `day`，B 给 `credit` / `month`） | 100 token/日 | 50 credit/月 | **两个独立闸门，都生效** | 不同 `(unit, period)` 是不同的键，不互相取 min；不能比较哪个更严 |
| RPM | 60 | 未设置（= -1，不参与 min） | **60** | 未设键按 -1 视为无限制（2026-10-20 定案） |
| 按模型限额（`smart`/`request`/`day`） | 50 | 未设（无行） | **50** | 同限制类取 min；两组都设时取更小的那个 |
| 能否建 Key | 允许 | 禁止 | **禁止** | deny 优先 |
| Key 白名单 | `fast` | `smart` | Key 白名单由用户自持，**不合并**；组只决定"能否放宽" | 白名单是用户侧的收窄动作，不是组策略 |

**为什么"用户自己收窄"的白名单不参与组间合并**：白名单挂在 Key 上（`key_model_allow`），是用户对自己 Key 的自我限制。如果把它也做并集，就会出现"用户在一个 Key 上的收窄被另一个组放大"，收窄动作失去意义。

**为什么 deny 优先是唯一安全的选择**：布尔开关表达的是"做 / 不做某件事"。只要有一组明确禁止，就存在一个管理员做出的、针对这个账户的显式否定判断；按"任一允许即允许"处理，会让否定随时被另一个组翻掉，管理员就无法用组表达任何否定了。
### 3.5 全局默认值与 -1 的关系（2026-10-20 定案）

设置页的“默认额度 / 默认 RPM / TPM / 并发”只在两个时刻起作用：**审批/导入时写入账户行与账户额度行的初值**，以及新建账户的 `quota_limit = 0`（默认拒绝）。它们**不参与运行期合并**：某组未设限制键就是 -1，不会“落入”全局默认。为什么：若运行期回退，删键与改默认値两个动作都会静默改变一批账户的生效额度，而这两个动作在界面上都没有任何“我在改额度”的暗示；而写入时取初值的效果是一次一审计，可追溯。注意与 [05-keys.md](05-keys.md) 的“速率必须由全局默认兜底、不得理解为无限制”不矛盾：那条说的是**账户列**建账时不得留空白（现在写 -1 之前管理员必须显式确认一次），而不是合并时回退。

### 组级共享池（限制类，2026-10-19 定案）

组上原有的限制类策略都是"**每人**上限"，它们各自独立、成员之间互不影响。共享池是**第二种限制**：预算挂在**组上**，全体成员一起消耗，先到先得。

| 项 | 定义 |
|---|---|
| 术语 | **共享池**（英文标识 `quota_pool`）；池容量上限叫 `pool_limit`，已消耗叫 `pool_used` |
| 参数 | `(abstract_model_id, unit, limit, period)` 四元组（模型维 2026-10-20 新增，`0` = 合计池），见下表 |
| 归属 | 挂在**组**上，不挂账户、不挂 Key |
| 与个人上限的关系 | **两者都设时取交集**（都要满足），不是取最严 |

**为什么叫"共享池"而不是"组额度"**："组额度"会被读成"这个组拥有多少额度"（一个资产），而它实际是**一条消耗上限**（一道闸）。命名必须落在闸门语义上，否则界面上很容易出现"给组充额度"这种误导性的操作想象。

| 参数 | 取值 | 说明 |
|---|---|---|
| `unit` | `request` / `token` / `credit` | **与每人额度同维度口径**（见第 3 节三值表）；由管理员在组上选定。列名用 `unit`，与 `account_quotas.unit`（[../architecture/05-storage.md](../architecture/05-storage.md) 3.1）同形；旧写法 `accounts.quota_unit` 已随账户额度行化废除，旧列名 `dimension` 及 `requests`/`tokens` 两值枚举已于 2026-10-20 废弃（必须容纳第三维 `credit`） |
| `limit` | **严格正整数**（`> 0`，不可为空、不可为 0） | 组级总上限。"不设池"由**没有这一行**表达，不由任何取值表达 |
| `period` | `day` / `month` | **必填、无默认值**；界面初值 `day` 只是为了少点一次，不是可省的推断 |
| `pool_used` | 非负整数 | 当期已消耗，原子递增 |
| `period_anchor` | 日期文本 | 已消耗量所属的周期锚点，用于惰性重置 |
| `abstract_model_id` | `0` 或非零模型 id | **2026-10-20 新增**：`0` = 全模型合计池（既有形态）；非零 = **按模型的组级共享池**（如“`smart` 全组共 500 次/日”）。它和每人按模型上限是两个资源：同一个模型上两道闸可并用，都是交集 |

**为什么计量单位由管理员选、而不是三个维度全部并行**：全维度并行意味着"多个都设时取交集"要在组级再叠一层，管理员需要同时推理六个数（个人 request/token/credit × 组 request/token/credit）才能预测一次请求会不会过——而正常运营只会关心其中一个维度（免费站点关心次数，按量站点关心 token 或 Credits）。单位由**管理员的策略**选定而不是由请求自由切换，是为了避免"同一道闸时而按次、时而按量"导致池子消耗速度无法预测。同一个组**允许同时配置多行**（DDL 的主键是 `(group_id, unit, period)`，见 [../architecture/05-storage.md](../architecture/05-storage.md#33-组与授权)），它们的合并规则与多组情况完全相同（全部都要满足）。

**为什么 `credit` 必须对池可用**：池的用途是"这个组本月不要把上游订阅额度烧穿"。若池只能按 `token` 计，组员全部改用最贵模型就能在同样 token 内烧掉几十倍成本，池子完全拦不住——而这恰好是“组级预算”最核心的威胁模型。

**为什么周期允许与个人配额周期不同，且要求显式配置**：两者是不同的闸——个人日额度的用途是"别让一个人今天刷爆"，组月池的用途是"别让这个组这个月把上游订阅额度烧穿"，一个站点同时需要这两件事是正常的。但周期若可省略，管理员看到"每人 100 / 组 500"时无从判断 500 是今天的还是这个月的，而这两个配置的严格程度差 30 倍。因此 `period` 是**必填**，默认 `day` 只是界面的初值（见 [../ui/03-admin.md](../ui/03-admin.md#52-组详情-admingroupsid)），不是可省的推断。

**消耗时机：终态一次结算（流结束后按 `usage` 的实际用量扣）。** 三个候选方案一起比较：

| 方案 | 为什么不用 |
|---|---|
| 预扣 + 结算 | 需要退补或为失败请求设计返还逻辑，而每一次退补都是一次可能写错的写操作；判定与扣减还会分裂成两个时刻，中间窗口要额外处理"预扣成功但请求没发出去" |
| 请求开始时逐条扣 | 与 [../architecture/05-storage.md](../architecture/05-storage.md#73-转发热路径上不能做的事) 定下的"**请求开始时绝不写库**"直接冲突，会把每次请求的写放大一倍 |
| **终态一次结算**（选定） | 与现有的"流结束后一个事务：`INSERT requests` + `usage_daily` upsert"**同一个事务**完成；`pool_used` 与 `usage_daily` 天然同源同刻，不会出现"池子扣了但用量没记"这种对不上账的状态 |

**这个选择带来的一个必须接受的代价**："终态才扣"意味着**在途请求不占用额度**，
N 个并发请求可以同时通过判定，直到结算时才发现池子早该满了——本周期实际消耗可能**超过** `pool_limit`。
超发的上界 = 峰值并发 × 单请求消耗。为什么不预扣：预扣把"额度占用"提前到还没产生 token 的时刻，
就必须为失败/取消设计返还，而返还写错的方向恰好是**多扣**（无故停全组），比少扣危险得多（同下文结算失败那段）。
真正的护栏是**组级并发上限**与全局熔断（[../architecture/06-runtime.md](../architecture/06-runtime.md)），
池子负责的是"一天/一月不会烧穿"，不负责"瞬时精确"。

- 失败请求（上游报错、切换耗尽、客户端提前断开且**未产生任何 token**）**不扣**。为什么：池子计量的是真实发生的消耗，没有消耗的尝试扣了会让池子凭空变少，而网络上失败重试是常态。
- 客户端断开但**已产生 token** 的请求**按实际用量扣**。为什么：上游侧的额度已经真实地被消耗掉了，不扣就等于给"发出去再掐断"留了一条免费通道。
- 结算失败（进程崩溃、写库异常）不会凭空多出一条池子记录，但会**少一笔**。为什么接受：少扣无害（只会让池子更宽松），多扣有害（会无故停掉全组）；这与 [../architecture/05-storage.md](../architecture/05-storage.md#71-吞吐估算为什么-sqlite-够用) 里"在途请求没有对账价值"是同一条取舍。

### 两种限制叠加时的合并规则

| 配置 | 合并方式 | 为什么 |
|---|---|---|
| **只有一个组设了池** | 该池独立生效 | 池是挂在单个组上的，没有"跨组合并"的对象 |
| **多个组都设了池** | **全部都要满足**（逐个判定，**不是** `min` 取最严） | 池是消耗型护栏，护栏的语义是"任何一条都不能突破"；但每个池是**属于不同组的独立资源**，`min` 会把它们压成一个再丢掉"是哪个组"的归因（错误码与审计都要这个信息）。任一组的池耗尽即拒绝 |
| **同组内既有每人上限又有池** | **取交集**：两道闸都要满足 | 见下 |
| **同一模型上既有每人按模型上限、又有该模型的组池** | **仍取交集**（逐 (model, unit, period) 键各自判定） | 两个资源，与上一条同理：“每人 50 次/日”用完只停这个人，“`smart` 全组 500 次/日”用完全组停该模型（其他模型不受影响） |
| **按模型上限与账户合计额度** | **取交集**，不互相取代 | 只设 `smart` 每人 50 不解除合计额度；只设合计也不解除按模型闸。按模型上限只能比合计**更细**，不能比合计**更宽**（写入时校验 `cap ≤ 同 (unit, period) 的合计上界`，否则拒保存） |
| **两者都无** | 该组在额度维度上不构成一道闸 | 与"组授权里没勾这个模型"同理：不配置即不约束，此时额度只受全局熔断约束（[../architecture/06-runtime.md](../architecture/06-runtime.md)） |

**为什么"两者都设"是交集而不是取最严**：`min(每人 100, 组 500)` 会被压成"每人 100"，于是池子在"5 个人各用满 100"之后就再也不会生效——它成了一个永远碰不到的死配置。**这两个数是两个不同的资源**（一个随人消耗，一个随组消耗），不是同一资源的两种表达；取最严这个算子只在"同一资源的多个上界"之间才有意义。交集语义下：个人额度用完**只停这个人**，池子用完全组都停。

**为什么池的判定顺序排在个人额度之后**：个人额度是一次等值查询（按 `account_id` 查 `account_quotas` 当期行），池判定是一次带条件的原子 UPDATE（见下节），后者更贵。个人额度先查、失败即短路，可以把"本就被个人额度拦住"的请求挡在池判定之前。这是纯性能选择，**不改变结果**——两道闸取交集，谁先查都拒。**按模型上限同理排在合计额度之后、池之前**：它也是一次等值查询（多一个 `abstract_model_id` 条件）；而它只在本次请求命中的那个模型上有行，绝大多数请求根本不碰这个闸门（无行 = 不限）。

### 共享池的原子扣减与超发保护

**池是全组共享、会被并发争用的资源，禁止先读后写。** 判定与扣减必须是**同一条**带条件的 UPDATE，靠"受影响行数"判定成败：

```sql
-- 语义形态；完整 DDL 与参数化写法见 architecture/05-storage.md#33-组与授权
UPDATE group_quota_pools
   SET pool_used = pool_used + :cost
 WHERE group_id = :gid AND abstract_model_id = :mid AND unit = :unit AND period = :period
   AND period_anchor = :current_anchor      -- 由同事务内的惰性重置语句保证
   AND pool_used + :cost <= pool_limit;
-- 返回 0 行 = 额度不足（拒绝）；1 行 = 扣减成功（放行）
```

**`WHERE` 里不需要也不应该写 `pool_limit IS NOT NULL`**：`pool_limit` 在 DDL 里就是 `NOT NULL`
（[../architecture/05-storage.md](../architecture/05-storage.md#33-组与授权)），这个条件恒为真，
写上去只会让人以为存在"有行但上限为空"的状态。

**"不设池"与"停用池"都只有一种表达：删掉这一行。** 为什么不做"保留配置但停用"（例如加 `enabled` 列或把
`pool_limit` 置空）：那会引入第三种状态（有行但没生效），而三种状态里最难排查的正是这一种——
管理员看到配置还在，请求却不受限；或反过来，看到配置还在，请求被莫名拒绝。用"无行 = 不设池"，
"有行 = 必然有一个正整数上限"，两种状态在表结构层面互斥，运行期不需要任何额外分支。
代价是停用要重新填写配置才能恢复，而这个代价是**故意的**：恢复一次额度护栏应该是一个需要重新决策的动作。

**为什么单条条件 UPDATE 优于"先 SELECT 判定、再 UPDATE 扣减"**：读-改-写之间必然存在窗口，两个并发请求都会读到 `pool_used = N < limit`，然后各自扣减成功——池子被超发，且**超发的量随并发度线性增长**（N 个并发就打穿 N 次）。条件 UPDATE 把"判定 + 递增"压进一条语句，由数据库在**同一把写锁内**完成，窗口消失。这不是性能优化，而是**正确性要求**。[../architecture/05-storage.md](../architecture/05-storage.md#74-组级共享池的并发扣减与惰性重置) 同时给出为什么这里的 `WHERE` 必须能走主键。

**并发扣减的原则**（为什么只有一个写者也要写明白）：

1. **写连接只有一个**（[../architecture/05-storage.md](../architecture/05-storage.md#61-为什么-pragma-必须绑到连接上)），写-写争用不是问题；
2. **真正的窗口在"判定"与"扣减"分离时**，而不是在写锁里——所以唯一要守的纪律是"判定即扣减"；
3. 池判定**不持有任何应用层锁**。为什么：跨进程/多节点时应用层锁无法保证，而数据库行锁天然正确；引入应用层锁只会多出一个"锁没释放"的故障模式。

**超发的口径必须分两层，混为一谈会写出错误的实现或错误的告警**：

| 层 | 结论 | 为什么 |
|---|---|---|
| **单条 UPDATE 内的判定与递增** | 超发上限 **0**，这是硬要求不是目标值 | 单条条件 UPDATE 在 SQLite 的 WAL 下由单写者串行化，**不存在**先读后写那种"读到的都是同一个旧值"的窗口；给出"允许超发 ×%"的容差反而会让实现者以为可以用读-改-写的近似做法 |
| **本周期最终的 `pool_used`** | **可能**超过 `pool_limit`，上界 = 峰值并发 × 单请求消耗 | 消耗是**终态一次结算**（见上文），在途请求不占额度：它们都通过了判定，结算时才发现早该满了。要消灭它只能预扣，而预扣必须为失败/取消设计返还，返还写错的方向是**多扣**（无故停全组）——比少扣危险得多 |

因此池子承诺的是"**一天 / 一个月不会烧穿**"，不是"**瞬时精确**"。瞬时护栏由组级并发上限与全局熔断负责
（[../architecture/06-runtime.md](../architecture/06-runtime.md)），两者职责不同，不要用一个机制去兼另一个的需求。

### 池子耗尽的错误码与文案

| | 个人额度耗尽 | **组级共享池耗尽** |
|---|---|---|
| HTTP | 429 | **429** |
| `code` | `quota_exceeded` | **`pool_exhausted`** |
| `type` | `rate_limit_error` | `rate_limit_error` |
| `Retry-After` | 指向个人额度重置时刻 | 指向**池**的重置时刻（`period_anchor` + 1 日 / 1 月） |
| 提示文案 | "你的今日额度已用尽" | "**你所属组的共享额度已用尽，这是组级限制，重试无效**" |
| 日志 | `error_code = quota_exceeded` | `error_code = pool_exhausted` + `group_id` |
| 审计 | 额度熔断类（[06-audit.md](06-audit.md)） | 同上，**额外记录命中池的 `group_id`** |

**为什么必须给池子一个独立错误码，而不是复用 `quota_exceeded` 的文案**：两者对用户的可操作建议**完全相反**。个人额度耗尽时，用户能做的是等重置或申请提额；共享池耗尽时，用户**什么也做不了**——调整请求、换 Key、换账号都没用，只有等重置或者让管理员改池子。用一个码加一句文案来区分，会让客户端与用户都只能靠读文本判断"要不要重试"，而**用户反复重试池子耗尽是最典型的错误行为**（他以为是自己被限，于是换 Key、改参数、加大并发，全部无效）。

**为什么这个码不与 `no_candidate`（503）复用**：`no_candidate` 的语义是"需求侧找不到满足条件的候选"（能力 / 上下文 / 健康），校验对象是**这个请求**；`pool_exhausted` 的语义是"供给侧配额耗尽"，校验对象是**这个组**。前者可以调整请求绕开（换模型、缩短上下文），后者不能。混用会把"运维故障"与"额度用尽"这两件需要完全不同动作的事压成同一个码。

> **待定**：新增 `pool_exhausted` 错误码需要同步进 [../api/03-errors.md](../api/03-errors.md)（本册的写域不含 it）；同理，[../api/03-errors.md](../api/03-errors.md) 第 9 节的"全局预算熔断与个人额度耗尽是否分码"与本次新增码有关联，建议一并判定。

### 共享池的观测与审计

| 事项 | 结论 | 为什么 |
|---|---|---|
| 池余量给谁看 | **仅管理员** | 成员的可见面只有"本人用量"与"本人实际生效的额度"（第 7 节）；暴露池余量等于暴露全组的总消耗 |
| 池用尽告警给谁 | **管理员**（组详情页的显式状态 + 审计事件；不默认做站外推送） | 告警的唯一可行动接收者是管理员：成员既不能改池子，也不该知道池子的存在 |
| 是否进审计 | **是**，两个事件：配置变更事件（谁在何时把池从 X 改成 Y）与耗尽事件（哪个组的哪个池在何时耗尽） | 配置变更属于"改组"（第 8 节，危险操作）；耗尽事件是运营判据（这个组要不要扩容） |
| 日志粒度 | 与既有额度判定同粒度（每请求一条 `error_code`），**不额外按成员聚合写入** | 按成员聚合的"谁消耗最多"就是成员排行，等于把成员在消耗维度上互相暴露的做法，与第 7 节冲突 |

**为什么池余量不给成员看**（这是本节的硬约束）：

- **PLAN 2.6 已定"成员列表不可见"**。池余量 `已用 / 上限` 是**全组的总消耗**：知道总量、再减去自己那部分，就把其余成员的消耗暴露了出来；成员之间一旦在消耗维度上互相可比，"我们组"的认知就出现了，而这正是 PLAN 1.1 要避免的。
- **信息对成员也没有可操作性**：他既不能扩容、也不能阻止别人消耗、更不能切换组。给一个"你只能看着它变少"的数字，收益是零。
- **但"停下来了"必须能解释**：池子耗尽时用户会看到 `pool_exhausted`，文案要说明这是**组级**限制（"你所属组的共享额度已用尽"）——**说清这件事是额度耗尽**即可，不需要说清"是谁用掉的"。

> **待定**：是否给成员开放"本组共享额度是否已耗尽"这一个布尔状态（不含余量），以降低用户对"为什么我突然被拒"的困惑。倾向**不做**：它仍然会让成员意识到存在一个共享资源，即引入"组"的实体感；但这是可用性与 PLAN 1.1 取舍之间的判断题，需由 lead 拍板。

> **已定（2026-10-19）**：组级共享池**进 MVP**（非 P1）。每人额度上限与组级共享池可单用、可并用，并用时是交集。

### 4.5 按模型限额（2026-10-20 新增）

需求：管理员除了"每人总额度"与"组共享池"，还要能**单独限制某一个抽象模型的消耗**（如"`smart` 每人每天 50 次"、"`smart` 全组每月共 20 万 token"）。动机：免费额度池里贵模型/热门模型的供给最稀缺，只靠合计额度拦不住"一个人把 `smart` 刷穿而 fast 几乎未动"的用量形状；按模型限额让管理员关掉一个模型而不必关掉整个账户。

按模型限额是**两道闸，复用既有机制，不引入新的合并算子**：

| 闸 | 声明位 | 生效值/计数器 | 合并 | 超限响应 |
|---|---|---|---|---|
| 每人按模型上限 | 组侧 `group_model_quota_caps`（限制类） | `account_quotas` 的 `abstract_model_id > 0` 行 | 逐 `(model, unit, period)` 键取 **min**；无行 = 不限 | 429 `quota_exceeded`（错误体带 `model`） |
| 模型级共享池 | 组侧 `group_quota_pools` 的 `abstract_model_id > 0` 行 | 同行 `pool_used` | 逐个都要满足（ALL_AND） | 429 `pool_exhausted` |

硬规则：

1. **只能限到可见集合内**：`group_model_quota_caps` 的模型必须 ∈ 该组 `group_models`；给不可见模型设限额是死配置，保存时拒绝。
2. **不得宽于合计**：同 `(unit, period)` 下按模型 cap 必须 ≤ 该组每人额度上界；模型是合计的子集，子集闸宽于全集闸在数学上永不生效，拒绝保存胜过静默无效。
3. **消耗计量口径与合计行完全同源**：同一次终态结算里，给命中模型行与合计行同事务递增；失败请求不扣、断开但已产生 token 按实际扣，与第 4 节池的口径逐字相同。
4. **重算时机**：成员/策略变更时 `EffectivePolicy` 对每个 `(账户, 模型, unit, period)` 取所属组 cap 的 min 落行/删行（[../architecture/05-storage.md](../architecture/05-storage.md) 3.3.1）；判定链每请求只读行不现算（见第 10 节定案）。
5. **只作用于抽象模型**：与组授权口径一致（第 2 节），不存在"限某个真实模型/渠道"的闸——那会把池结构泄露进策略界面，也突破抽象层契约。
6. **成员可见面不变**：用量页按维度展示"哪个模型被单独限了、进度多少"（这本来就是他的额度，不泄露组的存在）；但不展示模型级池余量（同第 7 节池余量不给成员的硬约束）。

为什么用哨兵 `abstract_model_id` 扩行而不是另开一套判定链：按模型限额与合计额度是**同一种闸在不同作用域上的实例**，合并算子（min）、结算时机（终态）、错误码（quota_exceeded）、惰性重置（period_anchor）全部复用；另起一套只会多一处口径漂移点。与池的关系同理：`group_quota_pools` 加一列而不是另开 `group_model_pools` 表。

## 5. 默认组

| 规则 | 内容 | 为什么 |
|---|---|---|
| 新账户自动进默认组 | 注册批准时若未选组，或成员被移出其它组时 | 保证有最基本的可用性（PLAN 2.6） |
| 默认组**必须始终存在** | `is_default = true` 的组唯一且不可删除 | "删组不删人 → 成员退回默认组"必须有落点；默认组可删，就等于存在一个"无处可退"的账户状态 |
| 默认组的策略 | 由管理员配置；建议保守 | 它决定所有"没被显式分配"的账户的能力上界 |

**为什么默认组是必要设计而不是便利设计**：账户的每个策略键都需要一个来源，否则判定链要在运行期处理"没有策略"这种状态，而"没有策略"的默认解释极易写成"不限制"（fail-open）。默认组把这个空洞消灭在数据层：**任何账户永远至少有一组策略**。

> **待定**：默认组是否允许改名、是否允许改策略、以及是否允许被指定为另一个组（当已有默认组时）。

## 6. 删组不删人

| 触发 | 联动 |
|---|---|
| 删组 | 成员**退回默认组**（PLAN 2.6）；不给任何账户留下"零组"状态 |
| 删组 | 该组的 `group_model` / `group_policy` / `group_member` 行一并删除 |
| 删组 | 该组的用量汇总停止归集，**历史用量不追溯**（与真实模型目录的"历史不追溯"同原则，PLAN 3.6） |
| 删组 | **进审计** |

- 为什么要"退回默认组"而不是"账户变成无组"：见第 5 节——无组账户的策略键会缺口，缺口在实现里最容易变成 fail-open。
- 为什么历史用量不追溯：用量记录的是**已经发生的调用**，它当时的策略上下文是历史事实；事后按新归属重算会让"这个月为什么超了"永久无解。

**为什么删除组是危险操作**：组是批量控制单元，删一个组会同时改变一批账户的模型可见性与额度，且这类变更没有“撤销键”（见 [02-authn.md](02-authn.md#6-为什么不需要类级提权) 与第 8 节的二次确认表）。

## 7. 组可见性

| 信息 | 成员本人 | 同组其它成员 | 管理员 |
|---|---|---|---|
| 组名 | ✅ 可见 | ✅ 可见（但不知道谁在里面） | ✅ |
| 成员列表 | ❌ | ❌ | ✅ |
| 组策略明细 | 仅自己实际生效的结果 | ❌ | ✅ |
| 组用量汇总 | ❌ | ❌ | ✅（运营用） |

- **为什么成员看不到成员列表**：避免形成组织感（PLAN 2.6）——可见的成员列表会自然演化出"我们组"的协作诉求，进而演化为团队，与 PLAN 1.1 的取舍冲突。
- **为什么组名反而可见**：成员需要能理解"我为什么能用这个模型 / 为什么额度是这个数"。完全黑盒会让每一次策略变化都变成无法解释的体验问题，而组名本身不泄露同组成员。
- **为什么策略明细只给"实际生效的结果"**：成员看到的是合并后的**结果**（我可用哪些模型、我的额度是多少），而不是"哪个组给了我什么"。后者等价于把成员列表反推出来。

**为什么组用量汇总只给管理员**：它是运营指标（判断某个组是不是被滥用），不是成员可见的社交信息。成员本人应能看到的是**自己的**用量（属于 `tenant` 类的管辖范围，PLAN 2.2）。

## 8. 组的生命周期与变更

| 动作 | 归类 | 需要的类 | 界面二次确认 | 审计 |
|---|---|---|---|---|
| 创建组 | 普通写 | `admin` | ➖ | 是 |
| 改名 / 改描述 | 普通写 | `admin` | ➖ | 是 |
| 改模型授权 | **改组** | `admin` | ✅ | 是 |
| 改策略（放开 / 限制） | **改组** | `admin` | ✅ | 是 |
| 加成员 / 移成员 | **改组** | `admin` | ✅ | 是 |
| 设置 / 变更默认组 | **改组** | `admin` | ✅ | 是 |
| 删组 | **改组** | `admin` | ✅ | 是 |
- **"改组"是一个整体**：上表五个动作**同属一项**——不因为它们分成五个端点就变成五个独立动作，也不因为其中某个"看起来轻"（比如加一个成员）就可跳过二次确认：一次改组的误操作可以同时改变一批账户的可见模型与额度，而这类变更没有"撤销键"——成员可能已经据此发起过请求。
- **为什么这里不再有"需提权"与"每次重验"两列**（2026-10-20 取消类级提权）：改组原本是 "恰好四项每次重验" 清单里的一项。取消提权后，管理面的身份证明只有登录一次（会话 24 小时），改组的安全边际改由**界面二次确认**承担——它防的是误点，不是冒充。为什么改组仍值得二次确认：它是**一对多**动作，一次确认会同时改变一批账户，而这类变更既无撤销键也无 "预览一下" 的中间态（见 [02-authn.md](02-authn.md#6-为什么不需要类级提权)）。
- 组变更全部进审计（PLAN 2.6）。事件字段与分类见 [06-audit.md](06-audit.md)。

## 9. 数据结构与接口签名

```go
type Group struct {
    ID          string
    Name        string
    Description string
    IsDefault   bool      // 唯一且不可删除（见第 5 节）
    CreatedAt   time.Time
}

// PolicyKind 决定该策略在合并时取并集还是取最严（见第 3 节）。
type PolicyKind string

const (
    PolicyOpen   PolicyKind = "open"   // 放开类：并集
    PolicyRestrict PolicyKind = "restrict" // 限制类：最严
)

// PolicyKey 是策略键的闭集合；新增键必须先归入放开类或限制类。
type PolicyKey string

const (
    PolicyVisibleModels    PolicyKey = "visible_models"      // 放开：抽象模型集合
    PolicyCanCreateKey     PolicyKey = "can_create_key"      // 放开：布尔
    PolicyMaxKeys          PolicyKey = "max_keys"            // 放开：多组取最大值（见第 3 节定案）
    PolicyKeyAllowlistWiden PolicyKey = "key_allowlist_widen" // 放开：布尔
    PolicyModelClass       PolicyKey = "model_class_allow"   // 放开：按类别授权

    // 每人额度上限：逐 (unit, period) 键独立成键。为什么拆成三对而不是
    // 复用旧的 daily_token_cap / monthly_token_cap：合并是逐键取 min，
    // 不同单位之间无法比谁更严（见第 3 节三值表）。
    PolicyQuotaRequestDay   PolicyKey = "quota_request_day"    // 限制
    PolicyQuotaRequestMonth PolicyKey = "quota_request_month"  // 限制
    PolicyQuotaTokenDay     PolicyKey = "quota_token_day"      // 限制
    PolicyQuotaTokenMonth   PolicyKey = "quota_token_month"    // 限制
    PolicyQuotaCreditDay    PolicyKey = "quota_credit_day"     // 限制
    PolicyQuotaCreditMonth  PolicyKey = "quota_credit_month"   // 限制
    PolicyRPMLimit         PolicyKey = "rpm_limit"           // 限制
    PolicyTPMLimit         PolicyKey = "tpm_limit"           // 限制
    PolicyMaxConcurrency   PolicyKey = "max_concurrency"     // 限制

    // 共享池不在这里。为什么：PolicyKey 表达的是"可合并的单个值"，
    // 而池是 (group_id, unit, period) → (limit, pool_used) 的**有状态行**，
    // 它需要原子递增、需要自己的主键、需要惰性重置（见第 4 节）；
    // 塞进键值表会让每次判定都变成"读 JSON → 在内存里加 → 写回"。
)

type GroupService interface {
    // Create / Delete：删组必须把全部成员退回默认组（见第 6 节）。
    Create(actor Subject, name, description string) (*Group, error)
    Delete(actor Subject, groupID string) error

    // SetDefault：默认组唯一且不可删除（见第 5 节）。
    SetDefault(actor Subject, groupID string) error

    // AddMembers / RemoveMembers：成员必须是带 tenant 类的账户。
    AddMembers(actor Subject, groupID string, accountIDs []string) error
    RemoveMembers(actor Subject, groupID string, accountIDs []string) error

    // SetPolicy：放开类或限制类；属「改组」，需每次重验。
    // SetModels / AddMembers / RemoveMembers / SetDefault / Delete 同理，全部属同一项。
    SetPolicy(actor Subject, groupID string, key PolicyKey, value string) error
    // SetModels：组可访问的抽象模型集合（放开类）。
    SetModels(actor Subject, groupID string, abstractModelIDs []string) error

    // EffectivePolicy 供判定链调用：对一个账户做全部所属组的合并计算。
    // 放开类取并集，限制类取最严，布尔开关 deny 优先，共享池逐个都要满足
    // （池的"当前值"由 ChargePools 在终态结算时给出，见第 4 节）。
    EffectivePolicy(accountID string) (*EffectivePolicy, error)

    // ChargePools 对一个请求的终态消耗做**原子扣减**（判定与扣减是同一条 UPDATE）。
    // cost 按池的 unit 解释（request 时为 1，token 时为 in+out，credit 时按价格乘数折算）。
    // 返回 PoolDenied 时表至少一个池额度不足；调用方必须区分"池耗尽"与"个人额度耗尽"。
    // 为什么把扣减也放在 GroupService 而不是调用方：扣减必须与请求落库同事务
    // （见第 4 节"消耗时机"），而事务编排属于组的领域逻辑。
    ChargePools(accountID string, cost int64, period Period) ([]PoolDenied, error)
}

type EffectivePolicy struct {
    VisibleModels   []string          // ∪ 各组的抽象模型
    CanCreateKey    bool              // ALL(允许)
    MaxKeys         *int              // 放开类：并集语义下的取值规则见待定
    // 每人额度上限：逐 (unit, period) 键独立取 min，互不比较。
    // 为什么不是三个单值：`token` 下的 100 与 `credit` 下的 50 无法比谁更严（见第 3 节）。
    QuotaLimits      []QuotaLimit      // 每个已配置的 (unit, period) 一行；未设键不参与 min（-1 哨兵，见第 3 节定案）
    ModelQuotaCaps   []ModelQuotaCap   // 每人按模型上限：逐 (model, unit, period) 取 min；2026-10-20 新增
    RPMLimit         *int              // min
    TPMLimit         *int              // min
    MaxConcurrency   *int              // min
    // 账户级额度（2026-10-20 定案：额度在账户级、行化存 `account_quotas`，不在 Key 上）。
    // 组策略给的是上界；EffectivePolicy 重算后把结果**落行**进 account_quotas（含按模型行），
    // 判定链第 6 步读的是落好的行而不是每次现算（见 04-authz.md）。
    AccountQuota     AccountQuota      // 见 01-accounts.md
    // 共享池：**不合并成一个数**。为什么：池是逐组独立的资源，
    // 合并成单个数字会丢掉"是哪个组的池先耗尽"这个归因信息，
    // 而错误码与审计都需要它（见第 4 节）。
    Pools           []PoolRef         // 所属组中已配置的池（含合计池与按模型池），逐个都要满足
}
```

## 10. 待定

> **已定（2026-10-19）**：`Key 数量上限` 归**放开类**，多组取**最大值**。理由见第 3 节。
> **已定（2026-10-20）**：限制类策略"某组未设置该键"时按 **-1 哨兵 = 无限制，不参与取最严**（见第 3 节定案）。不取全局默认值参与运行期合并；全局默认只在审批/导入时作为写入初值。

> **待定**：`Key 白名单能否放宽` 的精确语义——管的是"成员能否把默认空白的白名单填上"，还是"白名单能否超出组授权"。按 PLAN 11.3 的 `组授权 ∩ Key 白名单` 公式，超出组授权在数学上无效果，因此更可能是前者，但需确认。

> **待定**：默认组能否改名 / 改策略 / 被替换为另一个默认组。

> **待定**：池的**并发上限**要不要与池一起配（当前池只管总量，瞬时并发由组级并发上限管）。区分这两件事是刻意的
> （见"共享池的原子扣减与超发保护"里的两层口径），但若实测发现"总额度超发上界 = 峰值并发 × 单请求消耗"过大，
> 就需要在池上加一个在途预占计数——那会把已否掉的预扣-返还逻辑重新引进来。

> **待定**：`period_anchor` 的滚动时刻（日界/月界**几点**、用哪个时区）。当前与 `usage_daily.day` 用同一套 UTC 日界
> （[../architecture/05-storage.md](../architecture/05-storage.md) 第 9 节已有同题待定）。这是同一个决策：
> 若将来改为本地日界，池的归零时刻必须跟着改，否则"个人额度在早 8 点重置、组池在 UTC 零点重置"会让管理员无法解释。

> **待定**：多个组都设了池时，`pool_exhausted` 的错误体是否要指明**是哪一个组**的池耗尽（当前只带 `group_id` 到日志，
> 不对调用方暴露）。暴露能让用户判断"找哪个管理员"，但也泄露了他在哪些组里。

> **已定**：`pool_exhausted` 已同步进 [../api/03-errors.md](../api/03-errors.md)（429，独立于 `quota_exceeded`）；错误体**不**指明是哪个组（只记 `group_id` 到日志），以免泄露组归属。

> **待定**：组的成员上限与账户可属组数上限。

> **已定（2026-10-20）**：组侧“每人额度上界”与账户级额度是**两层**：组策略在成员/策略变更时由 `EffectivePolicy` 重算并落行到 `account_quotas`（合计行 + 按模型行）；判定链每请求只读账户行，不再现算合并——合并成本从每请求一次降到每次变更一次。未设键 = -1 不落行（无行 = 不限）。

> **已定（2026-10-20）**：逐 `(unit, period)` 键的“未设置”语义与上面 Q141 同一条定案：**无限制，-1 哨兵，不参与 min**。按 `(model, unit, period)` 拆分后同理：无行即不限。

> **待定**：`credit` 池折算所用价格乘数表的归属——它同时被 `price` 排序策略使用（见 [../models/03-strategy.md](../models/03-strategy.md)）。当前按“全局一份表、由管理员维护、修改进审计”理解，需确认是否需要“组级覆盖乘数”。
