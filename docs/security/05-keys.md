# API Key 生命周期

## 1. 归属硬约束

> **API Key 只能归属带 `tenant` 类的账户。**（PLAN 2.2、2.3、9.4）

| 关系 | 约束 | 为什么 |
|---|---|---|
| Key → 账户 | 归属账户**必须**带 `tenant` 类 | Key 是"调用模型"的凭据；只有 `tenant` 类提供调用能力（见 [01-accounts.md](01-accounts.md#2-三个权限类)）。允许 `contributor` 或纯 `admin` 账户持有 Key，等于给没有调用能力的主体发调用凭证，判定链第 4 步就会拒掉它——发得出、用不了，是纯粹的状态污染 |
| Key → 组 | **组不持有 Key**；组只约束 Key 的**数量** | 组一旦持有 Key 就等价于团队共享凭据，团队语义会从后门回来（见 [03-groups.md](03-groups.md#1-组是什么不是什么)） |
| Key → 凭据 | **无任何关系** | 凭据不可自选（PLAN 2.3）：用哪条上游凭据由策略引擎决定，与调用方持哪把 Key 无关 |
| Key → 额度 | **无关系**。额度全部在**账户级** | 见第 4 节 |

**为什么"能建 Key"这件事由组策略决定**（PLAN 2.6 放开类）：新建 Key 是创建能力，管理员需要在组粒度上决定"这批人能不能自建"。`tenant` 类回答"你有没有调用能力"，组策略回答"你这一批人允不允许建"，两者是不同的问题。

## 2. 生命周期

### 状态

| 状态 | 可否调用 | 进入方式 | 可否恢复 | 为什么需要 |
|---|---|---|---|---|
| `active` | ✅ | 创建后默认 | — | 正常态 |
| `disabled` | ❌ | 本人停用 / 管理员停用 | ✅ 可恢复 | 需要"临时停一下"的开关（换客户端、排查异常用量） |
| `revoked` | ❌ | 即时吊销（本人或管理员） | ❌ 不可恢复 | 泄露处置必须是一条**单向**路径：可以被恢复的吊销不是吊销 |
| `expired` | ❌ | 由 `expires_at` 到期推导 | ❌ | 到期是自动事实，不需要（也不应该）由人触发 |

**为什么 `disabled` 与 `revoked` 要分开**：前者是运营动作（"先停一下"），后者是安全动作（"这把已经泄露了"）。如果只有一种状态，那么每一次临时停用都会永久毁掉一把 Key，用户下一次就倾向于不报告异常，反而降低安全水位。

> **待定**：PLAN 第 8 章 MVP 条目同时出现"创建/禁用/过期"与第 9.4 节的"支持即时吊销"，两者是同一状态还是两个状态（本册按两个状态撰写），以及 `expires_at` 为空是否表示永不过期。

### 生命周期事件

| 事件 | 触发者 | 联动 |
|---|---|---|
| 创建 | 账户本人（需组策略允许） | **明文只返回一次**；黑名单默认为空（= 不收窄，2026-11-01） |
| 改名 | 本人 | 仅影响可读性，不影响鉴权 |
| 停用 / 恢复 | 本人 / 管理员 | 停用立即 401；恢复立即生效 |
| 即时吊销 | 本人 / 管理员 | 立即 401，**不等过期**（PLAN 9.4） |
| 配置调整（黑名单） | 本人 | 只在组授权之内再隐藏个别模型（见第 5 节） |
| 账户 `disabled` | 管理员 | 名下**全部** Key 立即 401（见 [04-authz.md](04-authz.md#5-禁用联动)） |
| 账户被撤销 `tenant` 类 | 管理员 | 同上 |
| 账户被合并 | 管理员 | Key 改挂 target 账户后继续可用（见 [01-accounts.md](01-accounts.md#4-账户合并)） |
| 账户额度耗尽 | 系统 | 名下**全部** Key 一起被拒（见第 4 节） |

**为什么吊销要"立即"而不是"最多一个 TTL 后"**：吊销的语义是"从此刻起不可用"。如果实现层需要缓存，必须有失效机制（见 [04-authz.md](04-authz.md#5-禁用联动)）；把"稍后生效"写进设计，等于把泄露处置的窗口期写进设计。

**为什么吊销不删除历史 `requests`**：历史请求是**已经发生的计量事实**，也是贡献者归因链的一部分（`resolved_credential_id`，PLAN 3.7）。删 Key 就删历史，会让"这个月的用量到底是谁的"永久无解，也让贡献者的贡献统计出现空洞。

## 3. 格式、哈希与展示

| 项 | 取值 | 依据 |
|---|---|---|
| 格式 | `fr-` + 32 字节 base62 | PLAN 9.4 |
| 存储 | **只存 `key_hash`（SHA-256）** | PLAN 9.4 |
| 明文 | **仅创建时返回一次**，不落库、不落日志 | PLAN 9.4 |
| 列表展示 | `fr-xxxx…xxxx` 前缀 | PLAN 9.4 |
| 比较 | `crypto/subtle.ConstantTimeCompare` | PLAN 9.4 |
| 名字 | `name` 字段，人读用途 | PLAN 第 10 章 |

**为什么 `fr-` 前缀**：Key 是机器凭据，会被写进配置文件、环境变量、CI secret、客户端库。一个可识别的前缀让两个问题立刻可判：一是"这是不是我们的 Key"（便于泄漏扫描与日志脱敏规则命中），二是"这是哪一类凭据"（与上游凭据、会话令牌区分）。

**为什么用 SHA-256 而不是 argon2id**：密码是低熵的（人选出来的），所以必须用慢哈希抵抗离线爆破；API Key 是 32 字节随机值（≈256 位熵），离线爆破不可行，慢哈希的唯一效果是让每一个入站请求都付出一次昂贵的推导——而鉴权发生在每一个请求上（见 [04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求) 第 2 步）。

**为什么只展示前缀**：列表页要能让人区分"这是我的哪把 Key"，又不能让人从截图里读回整把 Key。展示首尾各几位是唯一同时满足这两点的做法——用户凭开头认人，泄露的片段不足以拼出可用凭据。

**为什么明文只返回一次**：与密码重置、CSV 导入生成的随机密码同一条原则（见 [02-authn.md](02-authn.md#3-管理员导入账密)）。可以被反复读取的 Key 等价于一个所有读过列表页的人共同持有的凭据，吊销粒度退化为"整账户"。

## 4. Key 没有自己的额度

> **额度全部在账户级，一个账户的所有 Key 共享同一份额度。**（2026-10-20 定案）

`api_keys` 表**保留**：`id, account_id, key_hash, prefix, name, status, expires_at, created_at, last_used_at`
`api_keys` 表**没有**：`quota_limit`、`quota_used`、`rpm_limit`、`tpm_limit`、`daily_token_cap`、`max_concurrency`

账户级额度见 [01-accounts.md](01-accounts.md#额度在账户级不在-key-上)：周期额度行化存 `account_quotas`（合计行 + 按模型限额行），速率与并发是 `accounts` 上的 `rpm_limit` / `tpm_limit` / `max_concurrency` 单列（**-1 = 不限**，2026-10-20 定案）。

**Key 只剩三件事**：

| 能力 | 说明 | 为什么留在 Key 上 |
|---|---|---|
| 认证 | 它是什么身份 | 这是 Key 存在的理由 |
| 模型黑名单 | `key_model_deny`，只可能让能力变小 | "这把 Key 不该碰某个模型"是 Key 的属性，不是人的属性（见第 5 节） |
| 生命周期 | 创建 / 禁用 / 过期 / 吊销 | 一把泄露的 Key 必须能被单独处置，而不牵连同账户的其它 Key |

**为什么额度不能挂在 Key 上**：

1. **多开 Key 就是额度翻倍。** 若每把 Key 有自己的 `quota_limit`，用户建 10 把 Key 就得到 10 份额度，账户级上限形同虚设——而建 Key 是用户自己能做的动作（只要组策略允许），这条绕过路径不需要任何越权。
2. **额度是"一个人能用多少"的问题，不是"一个客户端能用多少"的问题。** 同一个人同时用编辑器、CI 和手机访问，他的总消耗才是需要被约束的量；按 Key 计额度，等于把同一个人的总消耗拆成互不知情的几份，任何一份超限都不会让总量收敛。
3. **它让审计与对账多一层无意义的维度。** 账户级额度只需要在 `account_quotas` 上按 (unit, period)（及按模型行）维护；按 Key 维护则要么有 N 份账、要么每次判定都跨 Key 求和——后者让每个请求的鉴权成本随该账户的 Key 数量增长。

**额度判定落在哪里**：判定链第 6 步（[04-authz.md](04-authz.md#4-运行时鉴权顺序入站模型请求)），读的是 `account_quotas` 的当期行（合计行必查；请求命中的抽象模型另有按模型行时再查一行），与本次请求用的是哪把 Key 无关。**按模型限额的闸也在这里**：它是账户行上的另一道交集闸（组侧声明见 03-groups 第 4.5 节），不是 Key 属性。

**三种计量维度**（`account_quotas.unit`，逐行一个维度）：

| 维度 | 单位 | 怎么算 | 为什么需要 |
|---|---|---|---|
| `request` | 次数 | 一次请求 = 1，与 token 无关 | 免费站点关心"请求数"；也让高频小请求的刷量有独立闸门 |
| `token` | token 数 | `in_tokens + out_tokens` | 最直观的用量单位 |
| `credit` | Credits | 按价格乘数折算，见 [01-accounts.md](01-accounts.md#额度在账户级不在-key-上) | `token` 把贵模型与便宜模型视为等价，改用最贵模型即可在同样 token 内烧掉几十倍成本 |

- 同时设多种时**各自独立判定，哪个先到算哪个**。为什么不做加权合并：三个维度拦的是三种不同形状的滥用（次数刷、长请求刷、贵模型刷），合成一个数会让某一类滥用失去约束。

**速率与并发**（同样在账户级）：

| 维度 | 字段 | 超限响应 | 为什么响应形态不同 |
|---|---|---|---|
| RPM | `rpm_limit` | **429 + 有值 `Retry-After`** | "稍后就能用"，客户端必须知道多久后重试（PLAN 9.5、验收 4） |
| TPM | `tpm_limit` | 同上 | 同上 |
| 并发 | `max_concurrency` | 同上 | 同上 |
| 额度耗尽 | `account_quotas` 合计行或按模型行 | 429 `quota_exceeded` + 日志留痕 | "今天没戏"，重试没有意义；按模型行命中时错误体带 `model`，提示可换其他可用模型（见 [../api/03-errors.md](../api/03-errors.md)） |
| 全站 | 三维令牌桶（全局 / 按账户 / 按 IP） | 429 + `Retry-After` | 兜底 |
| 全站预算 | 全局预算熔断 | 拒绝 + 告警（PLAN 9.1） | 全站级事件 |

**为什么速率/并发用 -1 而不是留空或 NULL**：新建账户的合计额度默认拒绝（审批时未填即落 `quota_limit = 0` 行，PLAN 9.1：默认拒绝），但 `rpm_limit` / `tpm_limit` / `max_concurrency` 必须有一个确定的列值：留空或 NULL 会让"额度为 0 却能高频打无效请求"变成隐式状态。三列 NOT NULL DEFAULT -1：-1 是显式"不限"哨兵（与未设限制类键同一套语义，参与 min 时跳过），0 是"全拒"——两个边界值都必须写得出来，NULL 则把三态带回运行期（见 03-groups 第 3 节定案）。

**为什么额度计数器直接落在 `account_quotas.quota_used`，而不是每次从 `usage_daily` 现算**：额度要在每一个请求前判定。实时聚合会让鉴权成本随历史请求量增长；`quota_used` 是当期计数器（惰性重置，同池的 `period_anchor` 机制），`usage_daily(day, account_id, …)` 是它的报表口径投影，两者同事务写入（PLAN 第 10 章）。

> **已定（2026-10-20）**：额度行化落定——合计额度与日/月周期额度统一为 `account_quotas` 的行（逐 `(unit, period)`，含按模型行），不存在"总额度与周期额度两层叠加"的歧义；叠加关系（合计 × 按模型 × 组池交集）见 [03-groups.md](03-groups.md) 第 4.5 节与 [01-accounts.md](01-accounts.md) 第 1 节三层表。

> **已定（2026-10-20）**：允许多维度同时启用，且**已经按维度分行存储**（主键含 `(unit, period[, abstract_model_id])`），单值 `quota_unit` 字段随账户额度行化一并废除。

> **待定**：账户级 `rpm_limit` / `tpm_limit` / `max_concurrency` 的全局默认兜底值。

## 5. 模型黑名单

> **2026-11-01 定案：白名单 → 黑名单**（用户要求）。旧语义「Whitelist（默认拒绝）」改成「Denylist（默认放行）」。

| 项 | 规则 | 为什么 |
|---|---|---|
| 载体 | `key_model_deny(key_id, abstract_model_id)` | 迁移 0013 由 `key_model_allow` 改名 |
| 默认值 | **空 = 不收窄**（组授权全集直接可用） | 新建 Key 立刻可用；「全池入口」类用法不再需要逐个勾模型 |
| 方向 | **只可能让能力变小**：可见集合 = (∪ 所属组授权) **\** 黑名单 | 组授权仍是天花板（三层收敛的另外两层不变） |
| 元素 | 只能是**抽象模型** | 真实模型对租户不可见（PLAN 3.1） |
| 校验 | 形状校验（非空、不重复）；**不做 ⊆ 组授权校验** | 拉黑一个组外模型无效果但无害，是用户对自己 Key 的明确意志 |
| 组策略 | ~~`allow_widen_allowlist`~~ **已移除** | 黑名单只能缩小能力，不存在「放宽」这个动作 |

**为什么从白名单改成黑名单**：白名单是默认拒绝——每把新 Key 都必须先勾模型才能用，
把「让 DSH 用上全部抽象模型」变成了一次又一次的手工勾选（实测踩过：组里 6 个模型，
某把 Key 的白名单只写了 2 个，DSH 就只看到 2 个）。黑名单反转方向：不写就全放行，
只有「这把 Key 不该碰某个模型」时才写一行。组授权已经是天花板，黑名单再多也不可能越权。

**为什么升级时清空存量行**：白名单行在黑名单语义下会反转成「这些模型被拒」——恰好与
升级前「这些模型可用」相反。带上旧数据等于把每把 Key 的可用集合打反，所以迁移
0013 在改名后 `DELETE FROM key_model_deny`，所有 Key 从「不收窄」起步。

**为什么黑名单仍然是 Key 级而不是账户级**（这是 Key 上唯一保留的可配置项）：同一个账户常
有多把 Key（一把给本地编辑器、一把给 CI、一把给手机）。"这把 Key 不该碰某个贵模型"是
Key 的属性，不是人的属性；且黑名单只可能让能力变小，多开 Key 不会放大任何能力。

## 6. 吊销联动

| 触发 | 效果 | 依据 |
|---|---|---|
| Key 即时吊销 | 该 Key 立即 401 | PLAN 9.4 |
| Key 停用 | 该 Key 立即 401（可恢复） | 本册第 2 节 |
| Key 过期 | 该 Key 立即 401 | `expires_at` |
| 账户 `disabled` | 名下全部 Key 立即 401，**不依赖缓存** | PLAN 9.3、验收 8 |
| 撤销账户 `tenant` 类 | 名下全部 Key 立即 401 | 见 [01-accounts.md](01-accounts.md#2-三个权限类) |
| 账户额度耗尽 | 名下全部 Key 一起被拒（Key 本身仍 `active`） | 见第 4 节 |
| 账户被合并 | source 名下 Key 改挂 target，随后以 target 的身份继续服务 | 见 [01-accounts.md](01-accounts.md#4-账户合并) |
| 账户改密 | **不影响 Key** | 见下 |

**为什么改密不吊销 Key**：Key 与密码是两条独立的凭据链（一个是机器凭据，一个是人的登录凭据），它们之间没有推导关系——密码泄露不会让攻击者拿到 Key，Key 泄露也不会让他登录控制台。把两者绑在一起，会让用户每次改密码都要重新配置所有客户端，逼出一个"从不改密码"的习惯。账户禁用则是另一回事：它表示"这个人整体不可信了"，因此**所有**凭据一起失效。

**为什么额度耗尽不改变 Key 的状态**：额度是按周期重置的临时条件，Key 的状态描述的是"这把凭据是否还有效"。把"用完了"写成 `disabled`，会让用户在额度重置后仍需要手动恢复 Key——而恢复动作本身才是真正的风险点（用户会开始批量恢复）。

> **待定**：吊销一把正在被使用的 Key 时，已在途请求（已解析到上游、尚未返回）如何处理——立即中断、跑完但不再计费，还是跑完且计费。

> **待定**：Key 的 `Retry-After` 取值规则（固定值、按令牌桶补充速率计算，还是按额度重置时间）。

## 7. Key 与账户 / 组的关系

```
账户（必须带 tenant 类）
  ├── 额度 / 速率 / 并发        → 账户级，全部 Key 共享一份
  └── API Key（1..n，数量受组策略上限约束）
        ├── key_model_allow     → 只能收窄组授权
        └── (无) 与上游凭据、与额度的任何关系

组（不持有 Key，只提供上限）
  ├── group_model      → 组授权（放开类，并集）
  └── group_policies   → 每人额度 / 速率 / 并发上限（限制类，最严）
```

| 问题 | 答案 | 为什么 |
|---|---|---|
| 一个账户能有几把 Key？ | 受组策略 `Key 数量上限` 约束（多组取**最大值**） | 该键归放开类（[03-groups.md](03-groups.md#3-组策略清单) 第 3 节定案） |
| 多开 Key 能提高额度吗？ | **不能** | 额度在账户级，多开 Key 共享同一份（见第 4 节） |
| 组能共用一把 Key 吗？ | **不能** | 组不持有 Key（PLAN 2.6） |
| 别人的 Key 我能看到吗？ | 不能（404 或空集） | PLAN 2.3 资源分表归属 |
| 管理员能看到我的 Key 吗？ | 能看到**前缀与元数据**（审计与处置需要），看不到明文 | PLAN 9.4：明文永不回显，连创建者本人之后也看不到 |
| 一把 Key 能跨账户吗？ | 不能 | 归属唯一 |

## 8. 数据结构与接口签名

```go
type KeyStatus string

const (
    KeyActive   KeyStatus = "active"
    KeyDisabled KeyStatus = "disabled" // 可恢复
    KeyRevoked  KeyStatus = "revoked"  // 单向，不可恢复
    KeyExpired  KeyStatus = "expired"  // 由 expires_at 推导
)

// APIKey 只有身份、生命周期与白名单三件事。
// 2026-10-20 定案：额度与速率全部移到 Account（见 01-accounts.md）。
type APIKey struct {
    ID        string
    AccountID string     // 必须带 tenant 类
    KeyHash   []byte     // SHA-256；不存明文
    Prefix    string     // 展示用：fr-xxxx…xxxx
    Name      string     // 人读
    Status    KeyStatus
    ExpiresAt *time.Time
    CreatedAt time.Time
    LastUsedAt *time.Time
}

type KeyService interface {
    // Create：归属账户必须带 tenant 类；组策略必须允许建 Key；数量未超上限。
    // 返回值中的明文只在此刻出现一次。白名单建为空。
    Create(subject Subject, name string) (plaintext string, key *APIKey, err error)

    List(subject Subject) ([]APIKey, error)          // 只回前缀，不含明文
    Rename(subject Subject, keyID, name string) error
    Disable(subject Subject, keyID string) error     // 可恢复
    Revoke(subject Subject, keyID string) error      // 不可恢复
    Delete(subject Subject, keyID string) error      // 若支持删除，见待定

    // SetAllowlist：白名单必须 ⊆ ∪ 所属组的抽象模型；元素必须是抽象模型。
    // Key 上没有 SetLimits —— 额度在账户级，由 AccountService 管理。
    SetAllowlist(subject Subject, keyID string, abstractModelIDs []string) error

    // Usable 供判定链调用：Key 自身状态 + 归属账户实时状态（不依赖长 TTL 缓存）。
    Usable(rawKey string) (*APIKey, error)
}
```

## 9. 待定

> **待定**：`disabled` 与 `revoked` 是否为两个独立状态（本册按两个撰写）。

> **待定**：`expires_at` 为空表示永不过期，还是表示"使用组默认有效期"。

> **待定**：Key 是否支持物理删除，还是只允许吊销 + 隐藏（涉及历史 `requests` 的归因链与外键）。

> **待定**：账户的 `rpm_limit` / `tpm_limit` / `max_concurrency` 与组策略的关系——组策略里的"每人 RPM 上限"若与账户字段同时存在，是"账户字段必须 ≤ 组策略"（收窄），还是"账户字段独立、由管理员同时负责两边一致"。
