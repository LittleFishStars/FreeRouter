# 登录、会话与访问控制

## 1. 认证路径总览

| 路径 | 适用账户 | 前提 | 得到的会话 |
|---|---|---|---|
| 密码登录 | 账户带 `admin` 或 `tenant` 类 | 状态为 `active` | 该账户**全部权限类**的完整权限 |
| 上游 OAuth 登录 | 账户带 `contributor` 类 | 贡献过该供应商账号（`UNIQUE(provider, external_id)` 命中） | 同上（见第 7 节） |
| 恢复码登录 | 无密码的 `contributor` 账户 | 持有一次性展示过的恢复码 | 同上 |
| 导入账户首登 | 管理员导入的账户 | 拿到一次性展示的随机密码 | 同上 |

**一个账户有多个类时取并集**（PLAN 4.3）：同时有 `tenant` 与 `contributor` 的账户，既能密码登录，也能用自己贡献过的账号 OAuth 登录。这与 [01-accounts.md](01-accounts.md#3-隔离的准确含义) 的隔离口径一致——隔离在类之间，不在登录方式之间。

**登录一次 = 该账户所有权限类的全部权限**（2026-10-20 定案，取代旧的类级提权）。

- 为什么不做"分档上下文"：见第 6 节。
- 因此本册不再有"低权限上下文"这个状态：会话要么有效（带全部类），要么无效。

## 2. 注册 → 审核 → 激活

### 注册

| 规则 | 取值 | 为什么 |
|---|---|---|
| 全局开关 | **默认开启但需审核**（PLAN 2.7） | 公网形态下"注册即用"等于把上游额度直接挂公网（PLAN 9.1）；默认需审核是唯一不需要额外配置就安全的默认值 |
| 初始状态 | `pending`，**未审核不能登录** | 状态机第一道关卡（见 [01-accounts.md](01-accounts.md#5-账户状态机)） |
| 初始权限类 | 只给 `tenant` | PLAN 2.7 明定；且审核界面要展示"申请人想要什么能力"，一个空集合无法审核 |
| 限速 | **按 IP 限速** | 开放注册必然被刷号；限速在审核之前生效，避免队列被垃圾申请淹没 |
| 防枚举 | 见第 9 节 | 注册是攻击者最方便的用户名探测面 |
| 密码 | ≥12 字符，argon2id 存储 | 见第 4 节 |

**注册不产生 `admin` 类，也不产生 `contributor` 类**：`admin` 只能由现有管理员授予（PLAN 2.7）；`contributor` 由贡献动作直接授予（PLAN 4.1），不经过注册表单。

### 审核

管理端审核队列 → 三选一：

| 动作 | 前置 | 结果 | 附带 |
|---|---|---|---|
| 批准 | **必须选组 + 额度**（PLAN 2.7） | 状态转 `active` | 进审计 |
| 拒绝 | 可填理由 | 状态转 `rejected` | 理由进审计；用户提示不区分具体理由 |
| 搁置（不动作） | — | 保持 `pending` | 队列待办计数 +1 |

- **为什么批准必须同时选组 + 额度**：组是**策略载体**（见 [03-groups.md](03-groups.md)），额度是**账户级**的护栏（见 [01-accounts.md](01-accounts.md#额度在账户级不在-key-上)）。一个新 `active` 账户如果没有任何组、额度为 0，就既没有模型授权也没有可用额度。允许"先激活、事后再配"会产生一段"有账户、有 Key、但什么都没配"的窗口——虽然默认拒绝使这段窗口不产生损失，但会让每次审批都变成两次操作。
- **为什么队列要置顶 + 待办计数**：审核积压会让用户等不到批准（PLAN 13 已列为风险），而积压的唯一补救是让管理员看见它。

### 激活

`active` 之后的**第一条可用请求仍然打不通**，这是有意的：

1. 账户转 `active` 只是解除了登录与建 Key 的封锁；
2. 新账户的**额度默认 0**，新建 API Key 的**模型白名单默认空**（PLAN 9.1）；
3. 因此"新账户 → 建 Key → 直接调模型"必然失败，必须由管理员显式给出额度、由本人或管理员给出模型白名单。

- 为什么：默认值必须是拒绝。若新账户默认带额度，那么任何一次"注册漏审"或"审批手滑"都会直接变成额度损失，而默认 0 让漏审的损失上界为零。

## 3. 管理员导入账密

导入与注册是两条**平行**的准入路径：注册要审核，导入**不需要**，因为导入本身就是管理员的动作。

### 单个添加

| 字段 | 必填 | 说明 |
|---|---|---|
| 用户名 | 是 | 冲突即拒绝，不覆盖 |
| 密码 | 否 | 留空则生成随机密码，**一次性展示** |
| 组 | 否 | 可多选；不选则进默认组 |
| 额度 | 否 | 留空则取默认组策略；语义是 `account_quotas` 的合计额度行（2026-10-20 定案：额度行化） |

### CSV 批量

列格式（PLAN 2.7，第 4 列按账户级额度落地）：`用户名,密码[,组][,额度]`

| 列 | 语义 | 约束 |
|---|---|---|
| 1 用户名 | 登录名 | 必填；与现有账户或本批次内重复即该行失败 |
| 2 密码 | 初始密码 | 可空 → 生成随机密码，随结果一次性展示 |
| 3 组 | 目标组 | 可空 → 默认组；多组表达方式见待定 |
| 4 额度 | `account_quotas` 合计额度行 | 可空 → 取组策略；格式 `unit:数值[:period]`（如 `request:2000:day`），省略 period = `day`；按模型限额不支持 CSV 简写，进管理页再配 |

**导入语义**：

| 项 | 处理 | 为什么 |
|---|---|---|
| 结果状态 | **导入即 `active`**（PLAN 2.7） | 导入是管理员的直接动作，再走一遍审核等于让管理员审自己 |
| 权限类 | 给 `tenant`；**`admin` 类绝不通过导入授予** | `admin` 只能由现有管理员授予（PLAN 2.7）；批量入口一旦能发管理权，一次误操作即可导致全站失守 |
| 冲突 | 该行**拒绝**，不静默覆盖 | 与 `UNIQUE(provider, external_id)` 同一条精神（PLAN 4.2）：撞身份必须显式处置 |
| 审计 | 导入动作**全进审计**（PLAN 2.7） | 一次批量导入能凭空造出几十个可用账户，是权限变更里影响面最大的操作 |
| 密码展示 | 随机密码**只展示一次**，不落库明文 | 与 API Key 同一原则（PLAN 9.4）；管理员拿不到第二次，就没人能拿它当长期口令 |

**审计形态**：一次导入产生**一条批次事件 + 每个成功账户一条账户创建事件**。为什么拆两层：批次事件回答"谁在什么时候倒进来多少人"（运营与追责），单体事件回答"这个账户是哪来的"（单账户溯源），只留一层必然有一类问题答不上来。

> **待定**：CSV 中"组"列如何表达多个组（分隔符与转义规则）——总纲只给了 `[组]` 单列，未定义多值语法。

> **待定**：CSV 第 4 列的计量单位——是固定 `token`、由第 5 列显式指定，还是只允许留空走组策略。

> **待定**：导入时部分行失败的事务语义——整批回滚，还是逐行提交并按行报告结果？

## 4. 密码策略

| 项 | 取值 | 依据 |
|---|---|---|
| 最小长度 | **≥12 字符** | PLAN 2.7、9.3 |
| 存储 | **argon2id**（`golang.org/x/crypto/argon2`） | PLAN 7、9.3 |
| 比较 | 定长常数时间比较，不短路 | 避免用比较耗时区分"前缀对/错" |
| 自助改密 | 提供 | PLAN 8 MVP 会话条目 |
| 管理员重置 | 提供 | 同上 |

**argon2id 参数（2026-10-20 升级为必须定）**：

| 参数 | 取值 | 为什么 |
|---|---|---|
| 内存 `m` | **64 MiB** | 离线爆破的成本主要由内存带宽决定；OWASP 的 19 MiB 基线面向"广谱 Web 应用"，本站在公网暴露管理面且没有第二因子，故取更高的档 |
| 迭代 `t` | **3** | 与 64 MiB 配合，单次校验约几十毫秒，对交互登录无感，但把离线爆破的每次尝试成本抬到与内存同量级 |
| 并行度 `p` | **2** | 单次校验占用 2 核；取值过高会让并发登录把 CPU 打满，反而形成一条廉价的拒绝服务路径 |
| salt / tag | 16 字节随机 salt / 32 字节 tag | salt 每条记录独立，防彩虹表；tag 长度对齐 SHA-256 |
| 登录时重算 | 校验成功后若参数低于当前档，**用新参数重算并写回** | 否则改参数只对未来的新密码生效，存量密码永远停在旧成本上 |

- **为什么长度门槛定在 12 而不是 8**：管理面是公网暴露的，密码是这个系统唯一的长效秘密。防爆破的退避与锁定只能延缓在线猜测，不能改变"密码空间太小"这个事实；长度是唯一不需要额外基础设施就能提高离线破解成本的措施。
- **为什么参数必须写死在这里而不是留到实现时调**：取消类级提权之后，"管理面被盗 = 全站失守"的抵抗力**全部**落在登录这一环上（见第 6 节）。一个没有下界的参数值等于没有防线——实现者按"跑得动"来选，通常会选到 8 MiB。

**改密与重置的联动**：

| 动作 | 联动 |
|---|---|
| 自助改密 | **吊销该账户的全部其它会话**（保留当前会话或一并吊销，见待定） |
| 管理员重置 | **吊销该账户的全部会话** |
| 账户转 `disabled` | 吊销全部会话（PLAN 9.3、[01-accounts.md](01-accounts.md#5-账户状态机)） |

- 为什么：改密的语义是"之前的凭据不再可信"。如果旧会话继续有效，攻击者只要已经拿到一个会话，改密就只是给受害者一个安全感，实际什么都没堵住。

> **待定**：除长度外是否要求字符类别、字典黑名单、泄露库比对——总纲只规定了长度。

> **待定**：argon2id 参数是否需要按服务器实际内存做上限保护（多实例并行登录时的峰值内存 = 并发数 × 64 MiB）。

> **待定**：自助改密时当前会话是否保留（保留体验好，吊销更保守）。

## 5. 会话管理

会话记录（PLAN 第 10 章 `sessions`）：

```
session {
  id, account_id,
  token_hash,        -- 只存哈希，不存会话令牌明文
  created_at, expires_at,   -- expires_at = created_at + session_ttl
  ip, ua
}
```

| 属性 | 取值 | 为什么 |
|---|---|---|
| 有效期 | **24 小时**（`session_ttl = 24h`，可配） | 2026-10-20 定案。取消类级提权后，一次登录的有效期就是高权限的总暴露时长，24 小时是"一天一个工作日不用重登"与"泄露窗口不超过一天"之间的取舍 |
| 存储 | 只存 `token_hash` | 库被拖走时会话不能直接复用；与 API Key 只存哈希同一原则（PLAN 9.4） |
| Cookie | `HttpOnly` | PLAN 8 明定；挡 XSS 直接把会话读走 |
| Cookie | `Secure` | **仅在启用 TLS 时加**（PLAN 9.2 定案：默认直连 IP + 端口，TLS 可选）。未启用 TLS 时**不加**——浏览器不会通过 HTTP 回传带 `Secure` 的 Cookie，无条件加等于登录直接不可用；这种形态下的风险由"非回环监听 + 无 TLS"的启动告警提示，而不是靠一个会把服务弄坏的属性 |
| Cookie | `SameSite` 取值见待定 | 与 CORS 默认关闭（PLAN 9.2）配套，防止跨站请求携带会话 |
| 绑定 | 记录 `ip` / `ua` 仅**留痕**，不做强绑定 | 移动网络下 IP 常变，强绑定会频繁踢人；留痕用于审计与异常告警 |
| 续期 | 不做滑动续期，到期即失效 | 滑动续期会把"有效期"变成"最后一次操作后 24 小时"，长期开着的标签页就成了永久会话；固定窗口才能给出可预测的上界 |

**吊销触发点**（必须穷举，漏一个就是绕过）：

| 触发 | 范围 |
|---|---|
| 用户登出 | 该会话 |
| 改密（自助或管理员重置） | 该账户全部会话 |
| 撤销 `admin` 类 | 该账户全部会话 |
| 账户转 `disabled` | 该账户全部会话 |
| 账户被合并 | source 账户全部会话 |

- 为什么"撤销 `admin` 类"要吊销全部会话：取消提权后，会话本身就携带全部类。撤销一个类若不改会话，等于让一个已经不该有管理权的会话继续管理到 24 小时后；吊销会话是把"类的变化"翻译成"必须重新登录"的唯一干净做法。

> **待定**：会话的绝对有效期 `session_ttl` 的可配置范围（是否允许管理员按账户或按角色调整）。

> **待定**：`SameSite` 取 `Lax` 还是 `Strict`（`Strict` 更安全但会影响从外部链接点回来后的登录态）。

## 6. 为什么不需要类级提权

**旧设计（2026-10-19）**：登录后停在低权限上下文，进管理面要当场再验一次，提权 15 分钟有效，四项危险操作每次重验，审计带 `elevated=true`。

**现行设计（2026-10-20 定案）**：**没有类级提权**。登录一次 = 该账户所有权限类的全部权限。

| 维度 | 旧设计 | 现行设计 |
|---|---|---|
| 权限来源 | 登录 × 提权动作 | **仅登录** |
| 数据模型 | `sessions.elevated_until` | 无该字段 |
| 审计 | 每条带 `elevated` | 只带 `account_id + acting_class` |
| 危险操作 | 四项每次重验第二因子 | **界面二次确认**（不是认证） |
| 会话时长 | 12 小时 | **24 小时** |

**为什么可以去掉**：

1. **提权保护的是"多一个人知道密码"的场景，而本站没有这个场景。** 账户模型选方案 A 的前提就是"管理员 = 站长本人"（见 [01-accounts.md](01-accounts.md#1-账户模型)）。在没有第二个人持有管理员密码的情况下，"当场再验一次"验的还是同一个人、同一个密码——它增加的是一个仪式，而不是一个新的信息。
2. **它把一条攻击面换成了另一条。** 提权引入了新的状态（`elevated_until`）、新的凭据（第二因子或重复密码）、新的失败路径（提权过期与权限不足必须区分），这些都会成为新的 bug 面；而它能挡的攻击（会话被劫持后立刻改配置）已经被更硬的手段覆盖：会话 24 小时过期、改密/禁用即吊销、危险操作界面二次确认。
3. **它让"审计分账"复杂化到失真。** `elevated` 这个布尔一旦存在，任何一次"该提升却没提升""不该提升却提升了"的判断都需要额外上下文；而没有它之后，一条记录只回答两个清楚的问题：谁、以哪个类。

**代价必须写清楚**：提权拿掉之后，"管理面被盗 = 全站失守"这件事的抵抗力**全部落在登录本身**上。

| 替代防线 | 作用 | 在哪一节 |
|---|---|---|
| ① 登录强度 | 提高在线猜测与离线爆破的成本 | 第 4 节的 argon2id 参数 |
| ② 退避与锁定 | 让在线猜测在有限次数内不可能成功 | 第 10 节 |
| ③ 会话 24h 过期 + 改密/禁用即吊销 | 把一次会话泄露的价值压缩到一天以内 | 第 5 节 |
| ④ 危险操作界面二次确认 | 防**误点**，不是防冒充 | [../ui/06-design.md](../ui/06-design.md) |

- 为什么第 ④ 项不能算认证：它发生在同一个已认证会话里，用户点"确认"不产生任何新的身份证明。把它写进"防线"是为了说明**误操作**这条独立的风险线仍然有人在管，而不是说它补上了提权的空缺。
- 因此第 4 节的 argon2id 参数与第 10 节的退避曲线、锁定阈值，从"实现时再调"升级为**必须在本册定死**：它们是这道唯一防线的全部内容。

**保留**：界面上的二次确认（AlertDialog：影响面 + 不可逆程度 + 具体动作按钮）不动，见 [../ui/06-design.md](../ui/06-design.md)。

> **待定**：是否需要在"高风险操作"上额外做一次**站内密码重输**（作为界面的输入框，而不是新的会话状态）。它与二次确认的区别是：二次确认只点按钮，重输密码需要知道密码；但两者都在同一会话内完成，都不产生新的身份证明。

## 7. 上游 OAuth 登录

**定位规则**：`UNIQUE(provider, external_id)` 定位账户（PLAN 2.4、4.2）。命中后直接看该账户有哪些类，不做账户切换。

| 规则 | 为什么 |
|---|---|
| **只有带 `contributor` 类的账户能用 OAuth 登录** | 登录凭证来自"贡献过的上游账号"，没贡献过就没有这个凭证 |
| OAuth 登录不需要密码 | 无密码登录路径的存在，是"纯贡献者不该被迫设一个自己不会维护的密码"这一需求的直接结果 |
| 登录后得到的会话与该账户的任何其它会话**权限完全相同** | 取消类级提权后不存在"低权限会话"这一形态；权限差异只来自账户本身有哪些类 |

**安全红线**（PLAN 4.3）：**上游账号当密码，等于把站内账户的安全性绑在第三方共享号的下限上。**

- 为什么这条仍是红线：贡献来的上游账号往往是共享号、廉价号、甚至短期号。取消提权之后这条红线**更**需要写清楚——因为再没有"进管理面前再验一次"这道缓冲，所以真正要守的是**账户本身不因为持有贡献凭据而获得管理能力**：`contributor` 类不提供模型调用能力，也不提供管理能力（见 [01-accounts.md](01-accounts.md#2-三个权限类)）。一个只有 `contributor` 类的账户，即使它的 OAuth 账号被完全接管，被接管的也只是贡献侧。
- **管理员账户若同时贡献过账号**：它的 OAuth 登录会话同样带 `admin` 类。这是"登录一次 = 全部权限"的直接后果，接受它的理由是：能在本站 OAuth 登录成功的前提是"这个上游账号的凭据归属于这个账户"，而管理员贡献账号本身是站长的自愿行为。这一条与"上游账号安全性不要和站内账户绑定"的张力是**已知且已选择接受**的，代价由第 6 节的登录加固承担。

**`login_enabled` 字段的作用**（PLAN 第 10 章 `upstream_credentials`）：某条凭据可以显式关闭其登录用途，而仍然留在池子里供路由使用。

> **待定**：一个账户贡献过多个上游账号时，OAuth 登录命中多个候选的处理——任一命中即登录，还是要求用户选定某一条凭据？

> **待定**：上游 OAuth 登录时，若该上游账号对应的凭据状态为不可用（`status` 非正常），是否仍允许登录。

> **待定**：是否禁止"带 `admin` 类的账户"通过 OAuth 登录（即管理员只能用密码登录），以此把"上游账号安全性"与"管理面"彻底隔开。当前按不禁止撰写。

## 8. 恢复码

**触发场景**（PLAN 4.1）：未登录用户贡献时若**没有可识别的账号身份**——即纯 API Key 型贡献——当场给恢复码。

| 贡献类型 | 找回路径 | 为什么不同 |
|---|---|---|
| OAuth 型 | 提示"用任意用过的账号登录即可回来" | 身份由 `UNIQUE(provider, external_id)` 承载，天然可再现 |
| 纯 Key 型 | 一次性展示**恢复码** | Key 本身不携带任何身份信息，无法作为登录凭证；不给恢复码，这个账户在丢失会话后就永久失联 |

**实现要点**：

| 项 | 取值 | 为什么 |
|---|---|---|
| 存储 | `recovery_code_hash`（PLAN 第 10 章） | 与密码、会话同原则：库里不存可直接使用的凭据 |
| 展示 | **仅一次** | 可以被反复读取的恢复码等于一个永不过期的后门口令 |
| 账户能力 | 只给 `contributor` 类 | 该账户是贡献动作的副产物，PLAN 4.1 明确"仅 `contributor` 类" |
| 与密码的关系 | 有恢复码的账户可以有 `password_hash = NULL` | 无密码账户是合法状态，"用恢复码登录"与"用密码登录"是并列路径（PLAN 4.3） |
| 哈希 | 与密码同一套 argon2id 参数 | 恢复码是人可抄写的短串，熵远低于 API Key，因此不能像 API Key 那样只做 SHA-256 |

**为什么不用邮箱找回**：邮箱验证与找回密码在 PLAN 中属于 P1（需要 SMTP）。MVP 阶段没有出站邮件能力，恢复码是唯一不依赖外部基础设施的找回手段。

> **待定**：恢复码使用后是否立即轮换（一次性使用）并展示新码——总纲只写了"一次性展示"，未定义使用后的语义。

> **待定**：恢复码的有效期与长度/字符集。

> **待定**：`contributor` 账户后来被授予 `tenant` 类后，是否应强制设置密码（否则该账户仍然只有恢复码这一条密码登录路径）。

## 9. 防枚举

**目标**（PLAN 9.3、验收 9）：注册"已存在的名字"与"全新的名字"，**响应时间与文案无差异**。

攻击面有**两条独立信道**，必须同时堵：

| 信道 | 泄露什么 | 措施 |
|---|---|---|
| 文案 / 状态码 | "该用户名已被占用" | 注册与登录对"存在 / 不存在"返回**同一文案、同一状态码** |
| 响应时间 | 存在走完整流程（哈希、写库），不存在提前返回 | 让**两条分支做等量的工作**：注册若用户名已存在，仍执行一次等价的哈希计算再返回同一结果；登录若账户不存在，也执行一次等价的密码校验（哑验证）后返回同一结果 |

- 为什么必须两条一起堵：只统一文案，攻击者用时间差照样能把用户名库刷出来；只统一时间，文案又直接告诉答案。

**适用范围**：注册、密码登录、**恢复码登录**、以及"用户名是否可用"这类实时校验接口（若提供）。

- 为什么把恢复码登录也算进来：它同样是"输入一个标识符 + 一个秘密"，也同样能用来判断某个标识符是否存在。

## 10. 防爆破

**基线**（PLAN 9.3）：失败计数 + 指数退避 + 锁定；失败记录含 IP / UA 进审计。

| 维度 | 计数对象 | 为什么必须有 |
|---|---|---|
| 按账户 | 该账户连续失败次数 | 攻击者盯着一个账户硬猜时，这是唯一能收敛的维度 |
| 按 IP | 该来源的失败次数 | 攻击者用一个密码横扫大量账户（撞库）时，账户维度永远不到阈值 |

**注册与登录的限速**：

| 入口 | 限速维度 | 依据 |
|---|---|---|
| 注册 | 按 IP | PLAN 2.7 |
| 登录 | 按 IP + 按账户，与三维令牌桶（全局 / 按账户 / 按 IP，PLAN 9.5）同源 | PLAN 9.3 |

**参数（2026-10-20 升级为必须定）**：

| 参数 | 取值 | 为什么 |
|---|---|---|
| 计数窗口 | **15 分钟** | 窗口太长会把"偶尔记错密码"累积成锁定；太短则一次慢速爆破可以靠时间分散绕过 |
| 退避曲线 | 前 2 次失败**不退避**；第 3 次起 `delay = min(2^(n-2) 秒, 60 秒)` | 前两次留给正常的手误；从第 3 次开始指数抬升，让在线猜测的成功率随时间急剧下降；60 秒封顶是为了让**合法用户**在记错四五次后仍能在一分钟内重试，而不是等十分钟 |
| 账户锁定阈值 | 窗口内连续 **5 次**失败 → 锁定 **15 分钟**（2026-10-21 定案：与 PLAN / `security.login_max_failures` 默认值统一，旧值 10 废除） | 5 次足以覆盖手误（第 3 次起已有指数退避提醒），又远小于有意义口令空间的猜测次数；锁定时长与计数窗口同量级，使"锁定期满自动解锁"的语义简单 |
| IP 锁定阈值 | 窗口内连续 **50 次**失败 → 锁定 **15 分钟** | IP 维度必然覆盖共享出口（校园、公司、运营商 NAT），阈值必须**显著高于账户维度（5 次）**——正因账户阈值定得低，IP 阈值才更要拉开十倍量级，否则一个同事输错几次密码就能让整栋楼登不上；50 次对应"横扫多个账户"的形态 |
| 解除方式 | **自动到期** + 管理员可提前解锁（解锁动作进审计） | 只有自动到期会让被恶意打锁的合法用户干等；只有人工解锁会让管理员成为瓶颈。两者并存 |
| 锁定粒度 | **账户与 IP 分别锁定**，互不包含 | 把两者合并会让一次针对单个账户的爆破顺带锁掉整个出口网段，攻击者反而获得一个廉价的拒绝服务手段 |

- 为什么失败记录必须含 IP 与 UA 且进审计：爆破的特征是"同一来源、多目标"或"同目标、多来源"，这两种模式只能从聚合后的记录里看出来，单条日志看不出来。
- 为什么这些数值必须写在设计里：取消类级提权后，退避与锁定是"在线猜测不可能成功"这条承诺的唯一承载（见第 6 节）。留到实现时调，等于把这条承诺交给一个没有上下文的实现者。

**可信代理的前提**：IP 维度只有在 `TRUSTED_PROXIES` 显式配置后才可信。**未配置则忽略 `X-Forwarded-For`**（PLAN 9.2、13），否则伪造头即可让 IP 维度彻底失效。

### 10.1 IP 维度必须区分 IPv4 与 IPv6（全库口径）

限速键取的是**规范化后的 IP 字符串**，不能直接用 `r.RemoteAddr`：

| 情形 | 处理 | 为什么 |
|---|---|---|
| `RemoteAddr` 形如 `10.0.0.5:54321` | **必须 `net.SplitHostPort` 取 host 部分** | `RemoteAddr` 带端口；直接当键会让每次连接都是新键，限速完全失效 |
| IPv6 形如 `[2001:db8::1]:54321` | 取 host 后按 `net.ParseIP` 归一，**输出统一小写、无前缀零的规范形式** | 同一个地址可能以 `2001:db8::1` / `2001:0db8:0:0:0:0:0:1` 等多种写法到达；不归一会得到多个限速桶 |
| IPv4-mapped IPv6（`::ffff:10.0.0.5`） | **归一为 IPv4**（`ip.To4() != nil` 时取四字节形式） | 否则同一个客户端在 IPv4 与双栈环境下得到两个不同的桶，而攻击者只要轮流用两种形式就能把配额翻倍 |
| 反代场景 | 先跑 `TRUSTED_PROXIES` 判定，再从 `X-Forwarded-For` **取最右侧第一个不被信任的项** | 左侧项由客户端完全控制，可直接伪造 |

**为什么必须写进安全分册而不是留到实现时再想**：这些细节写错**不会报错**，只表现为限速"好像没生效"——最难发现的一类错。`TRUSTED_PROXIES` 的 CIDR 列表也必须同时接受 IPv4 与 IPv6 网段（反代在本机时通常是 `::1/128` 而不是 `127.0.0.1/32`）。

> 同一规则适用于：注册限速、登录限速、模型请求的 IP 维度限速、审计里的「来源 IP」字段、以及 `TRUSTED_PROXIES` 匹配本身。

| 失败后的动作 | 内容 |
|---|---|
| 记录 | IP、UA、时间、目标用户名、失败原因类别 → 审计 |
| 退避 | 见上表参数 |
| 锁定 | 见上表参数 |
| 告警 | 连续失败达到更高阈值时进入可观测指标（见 [06-audit.md](06-audit.md)） |

> **待定**：上述参数是否需要按实际流量微调（尤其是共享出口场景下 IP 锁定阈值 50 是否偏严）。

> **待定**：锁定状态的存储位置（内存 / 库）——重启后是否保留锁定。

## 11. 数据结构与接口签名

```go
type Session struct {
    ID         string
    AccountID  string
    TokenHash  []byte     // 只存哈希
    CreatedAt  time.Time
    ExpiresAt  time.Time  // = CreatedAt + session_ttl（默认 24h）
    IP         string     // 仅留痕
    UA         string     // 仅留痕
}

// 2026-10-20 取消类级提权：sessions 不再有 elevated_until，
// 也不再需要 StepUpFactor / DangerOp —— 权限全部来自账户的权限类集合。

type AuthnService interface {
    // ---- 注册与审核（见第 2 节）----
    // Register 建 pending 账户，只给 tenant 类；按 IP 限速；防枚举（时间与文案恒定）。
    Register(displayName, username, password, ip string) (*Account, error)
    // Approve 必须带组与账户级额度，否则账户无策略载体。
    Approve(actor Subject, accountID string, groups []string, quota AccountQuota) error
    Reject(actor Subject, accountID, reason string) error

    // ---- 导入（见第 3 节）----
    // Import 解析单条或 CSV；逐行结果；不授予 admin 类；密码留空则生成并一次性返回。
    Import(actor Subject, rows []ImportRow) ([]ImportResult, error)

    // ---- 登录与找回（见第 1、7、8 节）----
    // 三条路径返回的会话权限完全相同：都是该账户全部类。
    Login(username, password, ip, ua string) (*Session, error)
    OAuthLogin(provider, externalID, ip, ua string) (*Session, error)
    RecoverWithCode(username, recoveryCode, ip, ua string) (*Session, error)

    // ---- 会话（见第 5 节）----
    Logout(sessionID string) error
    ChangePassword(actor Subject, sessionID, oldPw, newPw string) error
    ResetPassword(actor Subject, accountID string) (oneTimePassword string, err error)
    // RevokeAll 在改密 / 重置 / 转 disabled / 合并 / 撤销 admin 类时被调用。
    RevokeAll(accountID string, reason string) error
}

// AccountQuota 是账户级额度（见 01-accounts.md 第 1 节）。
type AccountQuota struct {
    Limit     int64
    Unit      string // request / token / credit
}

type ImportRow struct {
    Username   string
    Password   string // 空 = 生成随机密码
    Groups     []string
    QuotaLimit *int64 // 账户级额度；空 = 取组策略
}

type ImportResult struct {
    Username        string
    OK              bool
    OneTimePassword string // 仅当生成了随机密码时返回一次
    Err             string
}
```
