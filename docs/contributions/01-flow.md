# 贡献流程

## 1. 谁能贡献、贡献什么

总纲 4.1：**任何人都可以贡献**。

| 贡献物 | 形式 | 说明 |
|---|---|---|
| dsh-providers-hub 的**供应商账号** | 走该供应商 OAuth 授权 | 17 家已由 providers-hub 实现 |
| **API Key** | 任意 OpenAI 兼容端点的 key | 不要求属于任何已知供应商 |

### 1.1 为什么门槛要低到"任何人"

FreeRouter 的上游供给有两个来源：平台自己配的官方 key（`owner_account_id = NULL` 的平台自有凭据），以及众包。众包是**长尾供给**的唯一来源——官方 key 覆盖的是我们付得起钱的模型，而用户手上往往有我们自己拿不到的额度（各家的中转过、内部渠道、区域特供）。

门槛每高一级，供给就少一批。所以设计目标是：**从"打开页面"到"凭据进池"之间不出现人工环节**。

### 1.2 为什么要分"账号"与"Key"两类

两类贡献物的**可验证程度不同**，这直接决定了后面能拿到什么：

| | 供应商账号（OAuth） | API Key |
|---|---|---|
| 我们能验证的身份 | **有**：`provider` + `external_id`（该供应商下的账号标识） | **无**：key 本身不是身份 |
| 能否作为登录身份 | 能（见第 4 节） | 不能 |
| 恢复方式 | OAuth 找回 | **恢复码** |

## 2. 两条贡献路径

### 2.1 已登录用户

```
已登录 → 提交贡献物 → 给该账户加 `contributor` 类 → 凭据入池
```

**为什么不另建账户**：他已经有一个站内账户了。再加一个"贡献专用账户"只会制造两个身份、两份记忆负担，并且让"我贡献过什么"这个问题分裂成两处。给现有账户**加一个类**是权限类并集模型的自然用法（总纲 2.2）。

### 2.2 未登录用户（匿名贡献）

```
未登录 → 提交贡献物 → 创建账户（仅 `contributor` 类）→ **当场给恢复路径** → 凭据入池
```

**为什么允许未登录**：要求先注册再贡献，等于把"注册"这个动作放在了价值交换之前——用户还没得到任何东西就要先交出邮箱/密码。对贡献这种"我方受益"的行为，这个顺序是反的。

**为什么可以当场建账户**：`contributor` 类**没有密码、没有调用能力**（见第 6 节），所以这个账户是一个**零权限的凭证容器**。创建一个零权限容器不需要任何审批——这与 `tenant` 类必须审核（总纲 2.7）并不矛盾：审核的意义在于"放一个能花钱的身份进来"，而 `contributor` 花不了我们的钱。

## 3. 恢复路径

未登录贡献的最大问题是"你怎么回来"。总纲 4.1 按贡献物的类型分两种：

| 贡献物 | 恢复方式 | 文案 |
|---|---|---|
| 供应商账号（OAuth 型） | **用任意用过的账号登录即可回来** | 提示"用任意用过的账号登录即可回来" |
| 纯 Key 型（没有可识别的账号身份） | 一次性展示**恢复码** | 即刻展示，且说明"只显示这一次" |

**为什么 OAuth 只在 sidecar 里做**：PLAN §5.5 —— 这些供应商的授权与续期细节只有
providers-hub 的实现覆盖过；用 Go 重写是另一个量级的工程，且必然在每次上游改版后
重新逆向。主进程只做编排（发 URL、收回调、落库），协议细节全在 Node 侧。

**OAuth 贡献的落库状态**：拿到凭据后立即落库（上游行 `enabled=false` + AES-GCM 密文
+ 凭据行），状态停在 `pending/unverified`。这与 §5.2「落库与可调用分开」一致——
未通过目录探测的凭据不进候选池；探测通过后由鉴定流水线把上游行打开。

### 3.1 为什么 OAuth 型不需要恢复码

OAuth 型贡献在提交时**已经拿到了一个可验证的外部身份**（`provider` + `external_id`）。用户下次用同一个人账号登录时，我们能在库里按 `UNIQUE(provider, external_id)` 找到他贡献过的那条凭据，从而定位到那个匿名账户——**身份是现成的，不需要另发凭证**。

> **当前实现的偏差（诚实记录）**：上面这条依赖「用上游账号登录本站」这条通道
> （§4 的 `LoginByUpstreamOAuth`），而它**尚未实现**。所以在它落地之前，匿名的
> OAuth 贡献**也会拿到一次性恢复码**——否则按现在的代码路径，这个账户就真的失联了。
> 等上游账号登录通道就位后，可以去掉 OAuth 路径上的恢复码发放（保留字段与兑换
> 入口不删，避免历史账户失去找回手段）。

### 3.2 为什么纯 Key 型必须给恢复码

纯 Key 型贡献在提交时只有一串 key，没有可识别的账号身份。如果当时不给任何凭证，这个账户从此**永久失联**：贡献者的成果还在池子里被调用，但他再也看不到自己的贡献统计。

恢复码是这种情形下唯一可行的锚点。它落在 `accounts.recovery_code_hash`（只存 hash，与密码同规格）。**只展示一次**的理由与 API Key 明文只返回一次相同（[../security/05-keys.md](../security/05-keys.md)）：我们拿不到明文，就没有"忘了再查一下"这条路径，泄露面因此为零。

> **待定**：恢复码的形态（字符集、长度、是否含校验位）与展示形式（纯文本 / 可下载 / 二维码）。总纲只定了"一次性展示"。

> **待定**：恢复码是否可重新生成（旧码作废）。可重生成会增加"账户可被窃取"的面，但也会救回"码丢了但贡献过很多"的人。

## 4. 登录与身份映射

总纲 4.3 的身份表与本节直接相关：

| 账户的类 | 密码登录 | 上游 OAuth 登录 |
|---|---|---|
| 有 `admin` | ✅ | ❌ |
| 有 `tenant` | ✅ | ❌ |
| 有 `contributor` | 无密码（只有恢复码） | ✅ 用自己贡献过的任一账号 |

**一个账户有多个类时取并集**：同时有 `tenant` 与 `contributor` 的账户，既能密码登录，也能用自己贡献过的账号 OAuth 登录。

**安全红线**：上游账号当密码，等于把站内账户的安全性绑在第三方共享号的下限上。因此 OAuth 登录通道**只对 `contributor` 开放**（不对 `admin` / `tenant` 开放）：能拿到的就是该贡献者账户的全部权限，**不存在低权限上下文**。

**为什么不再有「OAuth 登录后先给低权限、要进管理面再提权」这层设计**：2026-10-20 定案取消类级提权（ALIGN-SPEC A）——登录一次就是该账户全部权限。对 `contributor` 而言这个变化是零成本的：它本来就只有贡献者那几项权限，OAuth 登录给全也越不过权限类集合；真正需要保护的是 `admin`，而 `admin` 压根不走 OAuth（下一段）。把高低权限两层差异从身份层移到**权限类集合**后，控制点反而只剩一个、更容易验证。

**为什么 OAuth 只对 `contributor` 开放、不对 `admin` / `tenant` 开放**：`admin` / `tenant` 是有花钱能力的身份，它们的安全性不能依赖第三方账号。反过来，`contributor` 本来就是"用第三方账号换来的身份"，用第三方账号登录它不增加任何新的风险面——**它本来就没有可失去的东西**。

**映射规则**：OAuth 登录时用 `UNIQUE(provider, external_id)` 反查用户贡献过的凭据，从而定位账户。因此**只有该凭据的 `login_enabled = true` 时才能用于登录**（见 [02-credentials.md](02-credentials.md) 第 8 节）。

> **待定**：一个用户贡献了 A、B 两家的账号，用 A 登录与用 B 登录是否都该进同一个账户（若 A、B 分别属于两个匿名账户，则"用任意用过的账号登录"会命中其中任意一个，需要确定择优/合并规则）。

## 5. 贡献即生效，无需审核

总纲 4.1：**贡献即生效，无需审核**（账号审核只用于 `tenant` 类）。

```
提交凭据
  → 落库（status = pending，尚不可调用）
  → L0 形式校验（几秒）        ← 唯一的入口闸门
  → L1 标准鉴定（~1 分钟）
  → verify_status 写回
  → 通过则进候选池（可被调用）
```

### 5.1 为什么"无需审核"

人工审核会带来两个后果：**延迟**与**成本**。而在这套系统里，审核能提供的东西已经被两样东西替代了：

| 审核原本要解决的问题 | 替代机制 |
|---|---|
| "这个 key 是不是真的能调通？" | L0 形式校验（秒级、机器判定） |
| "它是不是假的/冒充的模型？" | L1 鉴定（[../models/05-verification.md](../models/05-verification.md)） |
| "它会不会乱来、把我的用户数据拿走？" | 凭据只被我们**出站调用**，不参与入站鉴权；候选归因链落在 `requests` 表 |

所以"无需审核"不是省了一道工序，而是**把审核换成了两段自动判定**——比人工更准、更快、且不占人。

### 5.2 为什么"落库"与"可调用"要分开

凭据一提交就落库（`upstream_credentials`），但**在 L0/L1 走完之前不进入候选池**。为什么不让它直接可调用：

- L0 未过时，我们连"它是不是一个 chat 端点"都不知道，直接调用只会产生无意义的错误与告警噪音；
- 未鉴定的凭据可调用，等于让一个陌生的、可能是恶意的端点**接到我们的真实用户流量**——这是 [../models/05-verification.md](../models/05-verification.md) 4.2 节"廉价闸门"要防的那类风险。

`status = pending` 与 `verify_status` 是**两个正交维度**（见 [02-credentials.md](02-credentials.md) 第 5 节），前者表示"还没走完流程"，后者表示"声称是否相符"。

### 5.3 时间预算：为什么贡献者只等一分钟

从提交到"进池/被拒"，贡献者等待的是 **L0 几秒 + L1 约一分钟**。这不只是体验问题：

- 参考别人做中转站的经验，贡献者提交后如果看不到任何反馈，多数人不会等第二次。**过程的可见性**是贡献留存的关键。
- 一分钟这个量级允许我们**同步完成**流程并当场展示结果（判定、证据、它在池子里的状态），而不是"提交后过几天来看"——后者需要一个通知系统，而通知系统又需要邮箱/联系方式，会把匿名贡献的简单路径重新变复杂。

> **待定**：贡献页面在等待期间展示什么（进度 / 逐项结果 / 只显示最终判定）。

## 6. `contributor` 类的能力边界

| 能做 | 不能做 |
|---|---|
| 看到自己贡献的凭据的**标签与状态**（绝不含明文） | 创建 API Key（需 `tenant` 类） |
| 看到自己贡献量的统计（贡献数、被调用次数、消耗 token） | 调用模型 |
| 用自己贡献过的账号 OAuth 登录 | 进管理面 |
| 撤销自己的凭据（见 [02-credentials.md](02-credentials.md) 第 5 节） | 看别人的凭据、看真实模型目录 |

**为什么 `contributor` 看不到真实模型名**：真实模型的渠道构成是**平台的商业信息**（总纲 11.3 的"可见性三层收敛"）。贡献者能看到的是"我这条凭据被调用了多少次、贡献了多少 token"，而不是"它被用来服务哪个抽象模型"。

**为什么"没有调用能力"是一个真问题**：贡献是无偿的，我们不提供额度、优先使用权或升级凭据作为回报——所以"贡献者拿不到调用能力"本身已经不是一个待解决的问题。但它仍留下一个真问题：贡献者**无法自己验证**贡献是否可用。一条凭据今天还通不通、这几天调用有没有掉，他只能从界面得到答案。因此贡献者控制台必须给出**健康度与最近调用记录**——这不是回报的替代品，而是无偿定位下唯一需要兑现的东西：让贡献者看得见自己的贡献在不在生效（贡献统计口径见 [02-credentials.md](02-credentials.md) 第 7.2 节，界面见 [../ui/05-contributor.md](../ui/05-contributor.md) 第 5 节）。

## 7. 失败与异常路径

| 情形 | 处置 |
|---|---|
| L0 不通过 | 拒绝入池，给出**可执行**的原因（如"该端点不提供 chat completions"）。凭据记录保留以便贡献者修正后重试 |
| L1 判 `suspect` | 拒绝入池并给证据（[../models/05-verification.md](../models/05-verification.md) 5.3） |
| L1 判 `unverified` | **入池**，标「未鉴定」，进复检队列 |
| 撞 `UNIQUE(provider, external_id)` | 走**合并或拒绝**，不得静默覆盖（见 [02-credentials.md](02-credentials.md) 第 3 节） |
| 上游调用失败 | 只影响该凭据；不阻塞贡献流程本身，判定按已有信号给出 |
| 中途关闭页面（匿名贡献） | 凭据与账户**照常落库**。恢复码未展示则只能靠再次贡献同身份来找回（OAuth 型），纯 Key 型会丢——UI 必须明确警告 |

**为什么"失败了也保留记录"**：对 `suspect` 与 L0 失败，记录是**证据**。它支撑三件事：贡献者申诉、管理端复核、以及未来"同一个 endpoint 反复提交假模型"这类**惯犯识别**（同一 `base_url` 的多次 `suspect` 应该被关联起来看）。

## 8. 接口签名

```
-- 贡献提交
SubmitOAuth(provider string, oauthGrant Grant, session *Session) -> (Credibility, Account, RecoveryPath)
SubmitAPIKey(provider string, baseURL string, key string, claimedModel string, session *Session) -> (Credibility, Account, RecoveryPath)

-- 匿名贡献的账户生成（仅 contributor 类）
CreateAnonymousContributor(recoveryMode RecoveryMode) -> (Account, RecoveryCode)

-- 恢复
LoginByUpstreamOAuth(provider string, oauthGrant Grant) -> (Session, Account, error)
RedeemRecoveryCode(code string) -> (Session, Account, error)

-- 流程编排
IntakeCredibility(credibility Credibility) -> (Status, Verdict)
    -- 落库(pending) → L0 → L1 → 写 verify_status → 通过则进候选池
```
