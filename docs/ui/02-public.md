# 公共页面

## 1. 公共区的定位
公共区是**未登录状态下唯一可访问的界面集合**，也是登录/注册/贡献三个动作的入口。 它承载三件事：进入站点（登录 / 注册）、零门槛贡献（总纲 4.1）、以及出错时的可读反馈。
**为什么把"贡献"放在公共区而不是登录后**：众包供给是供给侧的**入口漏斗顶端**。 如果把贡献放在"注册 → 等审核 → 登录"之后，漏斗顶端就被 `tenant` 类的审核卡住了， 而总纲明确"贡献即生效，无需审核"。所以贡献页的一级目标动词是"开始贡献"， 而不是"登录后贡献"。
**公共区的三条约束**：

| 约束 | 表现 | 依据 |
|---|---|---|
| 不泄露真实模型名 | 公共区**没有任何模型列表**，只提"抽象模型"这一层 | 总纲 3.1 |
| 不出现内部术语 | 用户可见文案用"租户 / 贡献者"描述能力，不用"权限类 / classes / acting_class" | 本分册 7 节文案规范 |
| 反枚举 | 注册与登录的"已存在 / 不存在"响应时间与文案一致 | 总纲 2.7、9.3 |

## 2. 首页 `/`

未登录首页是**落地页 + 三个动作**，不做营销长页。

```
┌──────────────────────────────────────────────┐
│ FreeRouter                                   │
│ （一句话说明：统一的模型出口 + 众包供给）      │
│                                              │
│   [ 登录 ]   [ 注册 ]   [ 我有凭据要贡献 ]    │
└──────────────────────────────────────────────┘
```

| 区块 | 内容 | 为什么 |
|---|---|---|
| 一句话说明 | 站点做什么，以及"对外只有抽象模型"这一层 | 用户第一次来需要知道"我会看到什么模型名" |
| 登录 | 主按钮 | 已有账户是最高频动作 |
| 注册 | 次按钮，旁注"注册后需管理员审核" | 事先说明 `pending` 态，避免注册完发现进不去 |
| 贡献 | 第三个按钮，文案是动词 | 与总纲"贡献即生效"一致，不放在登录流程之后 |
| 运行态横幅 | 上游离线等 | 见第 8.3 节 |

已登录用户访问 `/` 时**不做重定向**，而是按 [01-ia.md](01-ia.md) 3.2 渲染导航并把 内容区替换为"我的概览"（账户有 `tenant` 类时给 Key 与用量摘要； 只有 `admin` 类时给审核队列待办计数；只有 `contributor` 类时给凭据状态摘要）。

**为什么不重定向到默认页**：重定向会让 `/` 这个地址在四类账户下指向完全不同的 URL， 不利于用户记住入口，也让"回到首页"这个动作失去统一语义。

## 3. 登录页 `/login`

### 3.1 两种登录方式

| 方式 | 适用账户 | 表单 |
|---|---|---|
| 密码登录 | 有 `admin` 或 `tenant` 类的账户 | 显示名/用户名 + 密码 |
| 上游 OAuth 登录 | 有 `contributor` 类且贡献过凭据的账户 | 选择供应商 → 跳转授权 → 回跳 |

两种方式**同屏并列**，不做 tab 切换。

**为什么不做 tab**：账户的类是并集（总纲 4.3），一个账户可能两种都行。 tab 会暗示"二者只能选一"，与"取并集"矛盾。

**为什么 OAuth 登录只列"你贡献过的供应商"**：总纲 4.3 定 "用自己贡献过的任一账号"登录。列出全部 17 家供应商会让人以为可以随便挑一家登录， 而实际是"必须是你贡献过的那个账号"，列出未贡献过的供应商只会制造失败路径。

### 3.2 OAuth 登录的会话降级

用上游 OAuth 登录成功后，会话**默认只给低权限上下文**（总纲 4.3 安全红线）。

| 账户的类 | OAuth 登录后能做什么 |
|---|---|
| 只有 `contributor` | 看自己的贡献；无管理面、无模型调用 |
| `tenant` + `contributor` | 能看 Key 与用量，但要进行敏感操作（如创建 Key）需重验密码 |

**为什么 OAuth 登录的会话也管不住 Key 页**：上游账号是共享号， 其安全性不由我们控制。把站内 `tenant` 类的能力挂在一个我们控制不了的身份上， 等于把 Key 的安全性绑在第三方共享号的下限上。因此 OAuth 会话进入 `tenant` 区域时 需要一次密码重验（若该账户没有密码，则不提供该区域，只提供贡献区）。

### 3.3 防枚举与限速的界面表现

| 场景 | 界面行为 | 为什么 |
|---|---|---|
| 用户名不存在 | 与密码错误**完全相同的文案与相近的响应时间** | 总纲 2.7 防枚举 |
| 密码错误 | 统一文案"用户名或密码不正确" | 同上 |
| 连续失败 | 指数退避，退避期间提交按钮变为倒计时 | 总纲 9.3 登录防爆破 |
| 登录成功 | 强制跳转到 `/`（或原目标），不提示"上次登录地点" | 未定义该功能，不擅自增加 |

**为什么统一文案里连"密码错误"都不区分**：区分会让攻击者用一次请求确认用户名有效性， 防枚举就失效了。总纲验收第 9 条的判据正是"注册已存在的名字与全新名字，响应时间与文案无差异"。

### 3.4 未通过审核的账户登录

| 账户状态 | 登录结果 | 界面 |
|---|---|---|
| `pending` | 允许建立会话，但**只能到 `/pending`** | 待审核提示页 |
| `active` | 正常 | 按类渲染 |
| `disabled` | 拒绝 | 错误页 `/error/403`，文案"账户已被禁用，请联系管理员" |
| `rejected` | 拒绝 | 同 `disabled` 的形态，文案"注册申请未通过" |
| `merged` | 拒绝 | 文案"该账户已合并到另一个账户，请用合并后的账户登录" |

**为什么 `pending` 可以建会话却锁在 `/pending`**：如果登录直接失败， 用户无法区分"密码错了"和"还在审核中"，会反复尝试或以为密码记错。 允许建一个受限会话来显示明确状态，是更低成本的沟通方式。 这个会话**不能访问任何数据接口**，只能在白名单的几个路由上工作。

**为什么 `merged` 要给出明确指引**：总纲 2.1 的"合并 = 两个账户并成一个、类取并集"， 用户手里可能还留着旧账户的记忆。只说"账户不存在"会让人以为被删号了。

## 4. 注册页 `/register`

### 4.1 表单字段

| 字段 | 必填 | 约束 | 说明 |
|---|---|---|---|
| 显示名 | ✅ | 唯一 | 登录用，也是审计里出现的人名 |
| 密码 | ✅ | ≥12 字符 | argon2id 存储（总纲 9.3） |
| 密码确认 | ✅ | 相等 | 单纯的输入防错 |
| 邮箱 | ➖ | 无 | **MVP 不收集**：总纲把"邮箱验证与找回密码"列在 P1 |

**为什么不收邮箱**：收了就要处理"邮箱是否已验证""忘密码怎么找回"两条分支， 而这两条都在 P1。MVP 收集一个用不上的字段只会制造一个无法兑现的承诺。

**为什么显示名同时是登录名**：总纲的 `accounts` 表同时有 `display_name` 与 `username`。 界面上把它们合为一个输入框，减少一次"我到底该填哪个"的犹豫； 后端是否落成同一列由数据分册决定，界面不为这个差别增加字段。

### 4.2 注册结果

| 情况 | 响应 | 界面 |
|---|---|---|
| 成功 | 账户 `pending`，默认只给 `tenant` 类 | 跳 `/pending`，页面立即进入待审核态 |
| 全局注册关闭 | 拒绝 | 表单替换为"本站当前未开放注册" |
| 显示名已存在 | **与成功响应表现一致**（防枚举） | 依然跳 `/pending` |

**为什么"名字已存在"也跳待审核页**：这是防枚举的执行细节。 如果已存在时给出"这个名字被占用了"，攻击者可以批量探测账户列表。 代价是用户可能等一场空审核——总纲已接受这个代价（验收第 9 条）， 因此本分册不再"优化"它。

> **待定**：注册成功后的通知路径。总纲 P1 列了"审核通知（需 SMTP）"， MVP 只有站内提示。用户是否需要主动回来查看审核结果，暂无通知手段。

### 4.3 注册后的默认权限类

新账户默认只给 `tenant` 类（总纲 2.2）。**为什么界面要明说这一点**： 用户注册后最可能的问题是"我能不能贡献"。答案是可以（贡献不需要权限类， 见 [01-ia.md](01-ia.md) 第 5 节的矩阵），所以待审核页必须把这条讲清楚， 否则用户会以为一切都得等审核。

## 5. 待审核提示页 `/pending`

```
你的账户正在等待管理员审核
─────────────────────────────
显示名：alice
当前状态：待审核
审核通过后你会获得：调用模型、创建 API Key 的权限

在等待期间你可以：
  [ 贡献一个凭据 ]   ← 不需要审核，立即生效

[ 刷新状态 ]   [ 登出 ]
```

| 元素 | 说明 |
|---|---|
| 当前状态 | 五态之一的用户可读文案 |
| 已获得的权限类 | 明确列出（`pending` 默认无类，或 `contributor`） |
| 贡献入口 | 直接可达，同步显示"贡献后立即获得贡献者能力" |
| 刷新状态 | 手动刷新审核结果；不做轮询自动跳转 |
| 登出 | 必须可达，否则用户被卡在一个没有出口的页面 |

**为什么不自动轮询**：自动轮询会让"审核队列置顶"的运营手段变成无声的后台流量， 也让用户以为不用做任何事。手动刷新把主动权交回用户，语义更清楚。

**为什么贡献入口在这里再次出现**：这是唯一一个能把"等待"变成"有效动作"的路径， 而总纲第 13 章明确"贡献者无偿导致供给不足"是最大风险之一——多一个贡献入口就多一分供给（当然，入口处必须先把"无偿"说清楚，见第 6 节）。

## 6. 贡献入口 `/contribute`（未登录也可用）

### 6.1 两种贡献物

| 贡献物 | 需要什么 | 之后发生什么 |
|---|---|---|
| 供应商账号 | 该供应商的 OAuth 授权（17 家由 providers-hub 实现） | 走 Node sidecar 完成授权，凭据入池 |
| API Key | 任意 OpenAI 兼容端点的 key + 端点地址 | 入池并进入鉴定 L0 + L1 |

**为什么把贡献物做成两个并列卡片而不是向导**：两者的输入完全不同 （一个是跳转授权，一个是填表），做成多步向导会让"我只想交个 key"的用户走三步空页。

### 6.2 供应商 OAuth 贡献

流程：

1. 选择供应商 → 2. 跳转该供应商授权页 → 3. 回跳 `/contribute/callback` → 4. 判定"新凭据 / 撞身份" → 5. 结果页

| 步骤 | 界面要点 |
|---|---|
| 选择供应商 | 只列**可用**的供应商；不可用的折叠并在 hover 说明原因 |
| 授权中 | 明确的等待态；失败时给出"重新授权"而不是空白页 |
| 撞身份 | 见 6.5 |
| 成功（已登录） | 提示"已加入凭据池"，并说明该账户已获得 `contributor` 类 |
| 成功（未登录） | 提示"已为你创建账户"，给出**恢复路径**（见 6.4） |

**为什么"可用供应商"要标出不可用的原因**：不可用的常见原因是 "该供应商当前未配置或上游离线"。不写原因，用户会把系统故障归因到自己操作错误。

### 6.3 API Key 贡献

| 字段 | 必填 | 说明 |
|---|---|---|
| 端点地址 | ✅ | 该 key 指向的 OpenAI 兼容 base URL |
| API Key | ✅ | 提交后**永不回显**（总纲 9.4） |
| 标签 | ✅ | 用户自己认得出的名字，如"我的备用号" |
| 声称的模型 | ✅ | 这个 key 能提供哪些模型——鉴定就是检验"声称与事实是否相符" |

**为什么必须填"声称的模型"**：总纲 4.4 把鉴定目标收窄为 "**这个 key 提供的模型是否与声称的名字相符**"。没有声称就没有对照物， 鉴定会退化成"这是什么模型"——而总纲明确说那不是目标。

**为什么"标签"必填**：凭据明文不可回显，标签是贡献者在列表里唯一能识别凭据的线索。 标签缺失会让"我的凭据"列表变成一排无法区分 ID。

### 6.4 未登录贡献后的恢复路径

| 凭据类型 | 恢复路径 | 界面呈现 |
|---|---|---|
| OAuth 型 | "用任意用过的账号登录即可回来" | 说明文案 + 登录按钮 |
| 纯 Key 型 | **一次性展示恢复码** | 大字号、要求用户勾选"我已保存"，提供复制按钮 |

**为什么恢复码只展示一次**：它等价于账户的凭据。如果能反复查看， 它就退化成"只要登录就能拿到的密码"，失去恢复码的意义。 界面必须用**强提示**（不是 Toast，而是需要确认的阻塞式区块）保证用户看到。

**为什么 OAuth 型不给恢复码**：OAuth 型已经把身份绑定到上游账号， 再用恢复码会形成第二条同样强的入口，扩大攻击面。总纲 4.1 只用恢复码兜住 "没有可识别身份"的纯 Key 型。

### 6.5 撞身份（`UNIQUE(provider, external_id)`）

总纲 4.2 定"撞身份必须走合并或拒绝，**不得静默覆盖**"。界面必须显式分叉：

| 情况 | 界面 |
|---|---|
| 该上游账号已被**当前登录账户**绑定 | 提示"你已经贡献过这个账号"，不再重复创建 |
| 该上游账号已被**别的账户**绑定 | 提示"该账号已绑定到另一个账户"，给出两条路：申请合并 / 联系管理员 |
| 未登录且撞身份 | 提示"该账号已绑定"，引导用 OAuth 登录回来 |

**为什么把"合并"暴露成用户可见动作**：总纲 2.1 把"贡献者账户和租户账户可以合并" 列为需求原话之一，说明合并是预期发生的事件。隐藏它会让用户只能找管理员， 而管理员侧只能"拒绝"。合并的实际执行仍在管理端（见 [03-admin.md](03-admin.md)）， 贡献页只负责**发起与说明**。

## 7. 提权页 `/elevate`

| 项 | 设计 |
|---|---|
| 触发 | 访问 `/admin/**` 且 `elevated_until` 为空或已过期 |
| 手段 | TOTP 或重输密码（总纲 2.5） |
| 有效期 | 15 分钟，空闲即失效 |
| 回跳 | 提权成功后回到原目标 URL；失败留在原地 |
| 危险操作 | 每次重新验证，不复用这 15 分钟（总纲 2.5） |

**为什么提权失败要留在原地而不是回首页**：回首页会让"我刚才点的那个危险按钮"丢失上下文， 用户需要重新导航一遍。留在原地并显示失败原因，成本更低。

**为什么提权页要显示"这次提权可以用来做什么"**：让用户明确知道这 15 分钟是有边界的， 从而理解为什么某些操作还要再验一次，减少"为什么又要我输密码"的困惑。

## 8. 错误页与状态页

### 8.1 错误页清单

| 路由 | 触发 | 文案要点 |
|---|---|---|
| `/error/403` | 已登录但无权限类 / 无提权 | 说明缺哪个能力，给出下一步（如"先提权"） |
| `/error/404` | 资源不存在或对该账户不可见 | 不确认资源是否存在 |
| `/error/410` | 实体已禁用（如 `disabled` 的抽象模型详情页） | 与 404 的区别是"它曾经存在" |
| `/error/500` | 未预期的服务端错误 | 给出可复制的请求 ID，便于排查 |

**为什么 403 与 404 要分页面**：403 的"你有账户但没有这个能力"是可行动信息 （比如去提权、去申请权限类），而 404 是"没有这个资源"。合并成一个页面会让用户 无法判断自己是不是操作错了。

### 8.2 页面级错误体

错误码与 HTTP 状态码的完整映射见 [../api/03-errors.md](../api/03-errors.md)。 界面**必须**把机器码翻译成可读句，并保留原始码供排障：

```
请求失败（no_candidate）
当前抽象模型暂时没有可用候选，请稍后重试。
请求 ID：8f3c...a1
```

**为什么保留原始码**：用户向管理员报障时，机器码是最短的对齐单位； 只给自然语言会让排查变成猜谜。

### 8.3 运行态横幅

| 横幅 | 触发（总纲 11.1） | 可见范围 |
|---|---|---|
| 上游离线 | 8326 端口不通，每 30s 重试 | 全站（含未登录） |
| 迁移链过长告警 | 某替代链深度 > 2 跳（总纲 3.5） | 仅管理端 |
| 鉴定回归告警 | 复检得分下滑（总纲 4.4） | 仅管理端 |

**为什么"上游离线"对未登录也显示**：它描述站点健康。 未登录用户看到"上游离线"不会泄露内部结构，但会解释"为什么现在注册完也用不了"。

## 9. 文案规范（公共区）

| 场景 | 用 | 不用 |
|---|---|---|
| 描述能力 | "调用模型 / 创建 API Key" | "租户权限" 作为动词 |
| 描述权限类 | 只在必要时说"贡献者" | "权限类是 contributor" |
| 描述模型 | "可用模型"（公共区无列表） | 任何具体模型名 |
| 描述后台 | "管理员" | "admin 用户" |
| 失败 | "用户名或密码不正确" | "用户不存在" |

**为什么公共区连"租户"这个词都要少用**：`tenant` 是内部术语（见 [../README.md](../README.md) 术语表），把它当作对外的用户称呼会把 "权限类"这个内部模型暴露成产品概念，进而引出"我能不能升级成租户"这类不存在的路径。

## 10. 待定项

> **待定**：注册是否需要图形验证码？总纲只定"按 IP 限速"。 加验证码会与总纲 9.3 的"无障碍"要求和防枚举文案一致性问题相互影响，暂不加。

> **待定**：贡献页在未登录状态下是否需要先要求一个"我同意"的说明 （例如"仅限本人已登录账号、自用"）？总纲第 13 章提到 README 要写明这个边界， 但没说是否需要在贡献流程里显式确认。

> **待定**：`/error/410` 在 MVP 是否真的会被页面层触发？ 总纲 3.5 的 410 Gone 是针对 `disabled` 的**模型**（API 侧）。 页面层是否会产生 410 取决于实体页面是否允许访问已禁用实体的历史详情页。

> **待定**：恢复码的格式与长度未定（总纲只定 API Key 为 `fr-` + 32 字节 base62）。 界面按"高熵、可复制、可手抄"设计，具体格式待密钥分册定。
