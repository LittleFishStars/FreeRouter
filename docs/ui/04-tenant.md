# 租户界面

## 1. 租户端的第一条硬约束
> **租户端整片界面不得出现任何真实模型名。**
这条是总纲第 14 章反面验收的显式检查项（"租户界面看不到任何真实模型名"）， 也是总纲 3.1 的"对外只暴露抽象模型"在界面上的落点。
它在实现上意味着三件事：

| 层 | 约束 |
|---|---|
| 数据层 | 租户端所有查询**只返回抽象模型维度**的聚合，不 select 真实模型字段 |
| 渲染层 | 任何模板变量都不含真实模型名；日志页的"模型"列取抽象模型名 |
| 排障层 | 上游错误回显里如果带真实模型名，**必须剥离后再展示** |

**为什么连错误回显都要剥离**：上游的错误体里常常带 `model` 字段， 如果原样透传，租户在报错信息里就能看到真实模型名——一条"不出现"的约束会从后门失效。

**为什么租户端连"渠道 / 供应商 / 上游"这些概念都不出现**：候选集包含渠道范围， 一旦界面上出现渠道维度，用户就能反推池结构。总纲 11.3 的三层收敛 （组授权 ∩ Key 白名单）是在**抽象模型**维度上做的收敛，渠道构成对租户根本不可见。

## 2. 租户端总览 `/usage`

**用途**：一屏回答"我现在能用多少、用了多少、还剩多少"。

**关键字段**：

| 分区 | 字段 |
|---|---|
| 身份 | 显示名、所属组名（只读，见 [01-ia.md](01-ia.md) 3.5） |
| Key 概览 | Key 数量 / 上限、启用数、最近 7 天有调用的 Key 数 |
| 用量 | 今日 token、本月 token；各自的上限与剩余百分比 |
| 速率 | 当前生效的 RPM / TPM / 并发上限 |
| 告警 | 接近上限的红色提示（阈值如 80%） |

**主要操作**：跳转到 Key / 日志 / 模型；切换统计时间范围。

**为什么把"生效额度"而不是"各组的额度"作为主展示**：总纲 2.6 的合并语义是 "限制类取最严"。用户需要的是"我实际有多少"，而不是"我为什么有这么多"。 显示多组明细既泄露了成员关系（见 [01-ia.md](01-ia.md) 3.5），又增加理解成本。

**为什么要有"接近上限"的告警而不是等打满再说**：总纲 9.1 的原则是 "额度护栏先行"。等打满才显示，用户看到的是已经失败的请求， 而不是一个可以提前扩容的信号。

**为什么统计范围的默认是"本月"而不是"今日"**：日限额是硬的，月限额更容易先撞上； 且月视图能看出增长趋势。日视图用一行数字就够，不需要单独的时间选择器。

## 3. 我的 API Key

### 3.1 列表 `/usage/keys`

**用途**：管理自己名下的 API Key。

**关键字段**：

| 列 | 说明 |
|---|---|
| 名称 | 用户自己起的名字 |
| 前缀 | `fr-xxxx…xxxx` 形态（总纲 9.4：列表只显示前缀） |
| 状态 | 启用 / 已禁用 / 已过期 |
| 过期时间 | 未设则显示"永不过期" |
| 额度 | `quota_limit` / `quota_used` |
| 速率 | RPM / TPM / 并发上限 |
| 模型白名单 | 数量 + hover 展开抽象模型名列表 |
| 最近使用 | 判断是否僵尸 Key |
| 创建时间 | —— |

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 新建 | 进入创建页 | 否 |
| 禁用 / 启用 | 立即生效 | 否（可逆） |
| 吊销 | **不可恢复** | **是**（⚠️） |
| 编辑 | 改名、额度、速率、白名单、过期时间 | 否（收窄白名单/降额度立即生效） |

**为什么"禁用"与"吊销"是两个动作**：禁用可恢复（用户可能只是临时停用）， 吊销是终局。合并成一个"删除"会让用户不敢用这个功能， 而残疾的 Key 管理恰恰是安全事件的主要来源（用户懒得停用，就留着不管了）。

**为什么编辑白名单与额度不需要二次确认**：这两个方向的操作里，
**收窄**是安全的，**放宽**受组的放开类上限约束（总纲 2.6）。 用户放宽最多放到组允许的天花板，不会突破管理员的授权。

### 3.2 创建 Key `/usage/keys/new`：一次性展示

这是租户端最重要的一个交互。总纲 9.4 定"只存 SHA-256，明文仅创建时返回一次"。

流程：

1. 填写名称、额度、速率、白名单、过期时间
2. 提交 → 服务端返回明文一次
3. **切换到"已创建"视图**：明文占据页面主体，带复制按钮、下载按钮
4. 用户确认"我已保存"后才能离开
5. 此后任何页面都拿不到明文；列表只显示前缀

```
┌─ API Key 已创建 ──────────────────────────────┐
│ 这是唯一一次显示完整 Key。离开本页后无法再次查看。│
│                                              │
│  fr-3Kd9...（64 字符）        [ 复制 ]        │
│                                              │
│  [ 下载为 .txt ]                              │
│                                              │
│  ☐ 我已保存好这个 Key                         │
│  [ 完成 ]（未勾选时禁用）                      │
└──────────────────────────────────────────────┘
```

**为什么用整页而不是弹窗**：弹窗可以被 ESC 关掉、被误点关掉。 一次性展示的机会只有一次，必须用一个"必须显式离开"的形态。

**为什么离开时需要勾选确认**：这是唯一能降低"用户没保存就关掉"概率的机械手段。 它不能杜绝，但能把最常见的路径堵住。

**为什么提供下载**：复制到剪贴板在某些环境下会被拦截或丢失， 下载文件是另一条可靠路径，成本几乎为零。

**为什么不做"再次显示"的例外**：哪怕管理员也不行。 总纲 9.4 的"只存 hash"意味着服务端**没有**明文可展示， 任何"再显示一次"的实现都会要求把明文存起来，直接破坏该约束。

### 3.3 Key 详情 `/usage/keys/:id`

**关键字段**：同列表，加"最近 20 次调用摘要"（只含抽象模型名）与"本次 Key 的生效配额解释"。

**主要操作**：编辑、禁用、吊销、查看该 Key 的调用日志（带筛选跳转）。

**为什么详情页要有"生效配额解释"**：默认额度 0、白名单为空（总纲 9.1 第 1 条） 意味着**新建 Key 不改任何配置时无法发起请求**（验收第 5 条）。 用户第一次建完 Key 去试会直接失败，页面必须主动解释这个"默认拒绝"而不是让他猜。

## 4. 用量与配额

### 4.1 数据视图

| 视图 | 维度 | 为什么 |
|---|---|---|
| 按时间 | 小时 / 日 / 月 | 定位突发 |
| 按 Key | 每个 Key 的 token 与请求数 | 定位"哪个 Key 在烧" |
| 按抽象模型 | 每个抽象模型的 token 与请求数 | 定位"哪类需求在烧" |

**为什么没有"按真实模型"和"按渠道"的维度**：总纲 3.7 明确 "用户日志只出现抽象模型名，真实目标与贡献者归因仅管理端可见"。 用量是日志的聚合，必须遵守同一条约束。

**为什么没有"费用"维度**：总纲 1.3 已删 `cost` 字段， 理由是"订阅额度没有单价，算不出真钱"。界面上出现金额等于把删掉的字段偷偷装回来。

### 4.2 配额展示规则

| 项 | 展示 |
|---|---|
| token 上限 | 数值 + 进度条 + 重置时间 |
| RPM / TPM / 并发 | 数值（瞬时值不画图，避免误导） |
| 打满 | 明确说明"将在 X 时间重置"或"需要联系管理员调高" |

**为什么不给速率画历史曲线**：速率是瞬时的令牌桶状态， 画成时间序列会让人以为"平均 RPM"是一个可比的指标，而实际生效的是峰值。 误导性的图表比没有图表更糟。

## 5. 调用日志 `/usage/logs`

**用途**：租户排障的主要界面。

**关键字段**：

| 列 | 说明 |
|---|---|
| 时间 | —— |
| 端点 | `/v1/chat/completions` / `/v1/messages` |
| **抽象模型** | 请求里用的名字（如 `smart`）——**这一列绝不含真实模型名** |
| Key | 名称 + 前缀 |
| 状态 | 成功 / 失败 |
| 错误码 | 机器码（如 `no_candidate`），见 [../api/03-errors.md](../api/03-errors.md) |
| TTFT | 首字节时间 |
| 总耗时 | —— |
| 输入 / 输出 token | —— |

**主要操作**：按时间 / Key / 抽象模型 / 状态 / 错误码筛选；查看单条详情；导出。

**为什么日志页不提供"请求正文"**：总纲 9.5 定"默认不记录请求正文； 排查时开脱敏模式并在 UI 明示"。这是**管理端**的排障开关。 租户端只提供结构化元数据，不给正文——正文里可能含用户的敏感内容， 而租户自己本来就有原始请求记录。

**为什么日志页必须有错误码列**：没有错误码，"失败"就是一个无法行动的状态。 有了 `no_candidate` 与 `rate_limited` 的区分，用户能立刻知道自己该等还是该改配置。

**为什么日志详情里没有"真实落点"**：总纲 3.7 明确把它限定在管理端。 即便这是用户自己的请求，暴露真实落点也等于暴露池结构。

**为什么日志页不列"贡献者归因"**：同上。归因是对管理端的运营信息， 出现在租户端会暴露"你的请求被别人提供的凭据服务过"这件事，进而暴露贡献者存在。

## 6. 可用抽象模型目录 `/usage/models`

**用途**：告诉用户"我能用哪些名字调模型"。

**关键字段**（每个抽象模型一张卡）：

| 字段 | 说明 |
|---|---|
| 名称 | 抽象模型名（`smart` / `fast` / …） |
| 显示名 | 可读描述 |
| 能力声明 | 上下文窗口、最大输出、视觉 / 工具调用 / JSON mode |
| 状态 | `active` / `deprecated`（含替代提示） / `disabled`（不在列表内） |
| 可见性来源 | "你所属组的授权 ∩ 本 Key 的白名单" 的说明性文字（不含组名明细） |

**主要操作**：查看能力详情；复制模型名；对 `deprecated` 的项查看替代提示； 跳转到迁移指引（如果管理员配了链接）。

**为什么这个列表必须是"按当前 Key 收敛后"的集合**：总纲 11.3 的三层收敛是 "组的模型授权 ∩ Key 白名单"。如果页面展示的是全站抽象模型清单， 用户会看到自己其实调不通的名字，每次尝试都得到 `model_not_found`。

**为什么需要提供"按 Key 查看"**：不同 Key 的白名单可能不同。 页面顶部必须有一个 Key 选择器（默认"全部"），否则用户无法解释 "为什么这个模型在 A Key 上能用、在 B Key 上不能用"。

**为什么 `deprecated` 的项仍然留在列表里**：总纲 3.5 定"**弃用不是关闭**"， 仍然接受请求。把它从列表里删掉会误导用户以为不能用了， 从而主动改配置——而弃用的设计目的正是"已有客户端不用改配置"。

**为什么 `disabled` 的项不在列表里**：`disabled` 不接受请求（404 / 410 Gone）， 列出来只会制造失败。

**为什么目录里要显示状态徽章而不是只在详情里**：用户在选择模型时需要立刻看到 "这个名字是不是快到期了"。把弃用信息藏在详情页等于让它在最需要的时候不可见。

**为什么替代提示只说"请改用 X"而不说"将路由到 X"**： 总纲 3.5 的对外表现是"响应 `model` 仍回显 `old`"。 用户从响应上看不出发生了替换，所以界面上的正确表述是建议迁移， 而不是描述一次用户感知不到的内部动作。

## 7. 空态、错态与边界

| 情况 | 界面 |
|---|---|
| 还没有任何 Key | 空态 + "新建 API Key" 主按钮 + 一句"新建的 Key 默认额度为 0、白名单为空，需要先配置" |
| 无任何可用抽象模型 | 空态 + "你所属的组当前没有授权任何模型，请联系管理员" |
| 有 `tenant` 类但组授权为空 | 同上的文案，不暴露"组"的具体名称 |
| 日志为空 | 空态 + 一句"还没有调用记录"，并给出最小 `curl` 示例（只含抽象模型名） |
| 账户被禁用 | 全站 401，跳到 `/error/403` |
| Key 被禁用 | 列表里标红 + 说明"该 Key 的请求将返回 401" |

**为什么日志空态要给 `curl` 示例**：这是从"注册好了"到"真的跑通"之间的一道坎。 示例里只能用占位符抽象模型名（如 `smart`），**绝不能**用真实模型名举例——

> **待定**：示例里用哪个抽象模型名？这取决于总纲 15.5"是否预置抽象模型名 （`fast` / `balanced` / `smart` / `vision` / `long-context`）"的拍板结果。 在拍板前，示例统一用 `<抽象模型名>` 占位符。

**为什么"无可用模型"不显示具体是哪个组造成的**：组名对成员可见， 但"你被哪个组限制"会把组与组之间的人关联起来（见 [01-ia.md](01-ia.md) 3.5）。

## 9. 待定项

> **待定**：Key 白名单的编辑形态——是勾选抽象模型列表，还是允许"跟随组授权"？ 总纲 2.6 的公式是"（∪ 所属组的抽象模型）∩ Key 白名单（用户自己收窄）"， 说明白名单**只能收窄**。界面需要一个"全选组的授权"的快捷动作， 但它的语义还没定（选中的是新集合还是跟随集）。

> **待定**：日志保留期。租户能查多久的历史？总纲只定了 `requests` 与 `usage_daily` 两张表， 没有保留策略。租户端需要一个"更早的记录暂不可查"的明确文案。

> **待定**：是否允许用户自助申请提高配额？总纲 2.7 只定义了"管理员批准时选配额"， 没有自助申请路径。当前界面只给"请联系管理员"的文案。

> **待定**：`/usage/models` 要不要展示"这个抽象模型当前的健康度"？ 如果展示，会引入一个用户可见的可用性指标（可能与真实候选状态相关）， 需要先确认它是否会泄露池结构。
