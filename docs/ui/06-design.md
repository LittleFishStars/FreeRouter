# 设计规范

## 1. 本分册的适用范围
本分册定义全站界面的交互约定，被 [02-public.md](02-public.md)、[03-admin.md](03-admin.md)、 [04-tenant.md](04-tenant.md)、[05-contributor.md](05-contributor.md) 共同引用。
**本分册约束用户可见的行为与形态，不约束实现机制**。
**为什么这样分层**：本册写于前端选型未定的时期，当时把它定为硬要求是为了避免选型反向时整份文档作废。选型已于 2026-10-19 定为 Vite + React（总纲 7.1），但这条分层仍然保留——它现在的作用不是防返工，而是**把交互约定与技术选择分离开**：技术选型会变（React 19 → 未来的某个版本，或 shadcn/ui 换成别的组件库），而“危险操作要二次确认”这类约定不该跟着变。
实现级的约定（骨架屏形态、动画时长、具体组件映射）见下面第 10 节。

## 2. 布局骨架

### 2.1 三段式骨架

```
┌───────────────────────────────────────────────────────┐
│ 顶栏：站点名 · 运行态横幅 · 账户菜单（显示名 / 登出）    │
├──────────┬────────────────────────────────────────────┤
│ 一级导航  │ 内容区                                      │
│ （按      │  面包屑                                    │
│  classes  │  页面标题 + 主操作按钮（右上）               │
│  渲染）   │  ──────────────────────────────────────    │
│          │  正文                                       │
│          │                                            │
├──────────┴────────────────────────────────────────────┤
│ 页脚：版本 · /healthz 与 /readyz 的轻量指示 · 文档链接   │
└───────────────────────────────────────────────────────┘
```

三段的职责：

| 区域 | 职责 | 不做什么 |
|---|---|---|
| 顶栏 | 身份、登出、全局运行态横幅 | 不放业务导航 |
| 一级导航 | **按 `classes` 渲染**的入口集合 | 不跨类聚合 |
| 内容区 | 单页职责 | 不再嵌一层导航 |

**为什么一级导航由 `classes` 渲染而不是固定的全集**：总纲 2.5 定 "一个账户登录一次，界面按 `classes` 渲染"。一个只有 `tenant` 类的账户 看不到管理入口，这不是"隐藏"而是"不存在"。两者的区别在 [01-ia.md](01-ia.md) 第 7 节的三层守卫里已经定义。

**为什么顶栏只放运行态横幅、不放具体告警**：总纲 11.4 要求 "上游离线"横幅全站可见；而"弃用链异常""鉴定回归"这类告警只在管理端出现 （见 [02-public.md](02-public.md) 8.3）。顶栏是所有页面共享的， 因此它只承载**全站同质**的信息。

### 2.2 内容区的固定顺序

1. 面包屑（仅在有层级时出现）
2. 页面标题 + 一句话说明
3. 主操作按钮组（右对齐）
4. 分区内容

**为什么标题下必须有一句话说明**：管理端的页面名（例如"候选集"） 对不熟悉系统的人没有信息量。一句话说明的成本近零， 但它决定了新管理员能否独立操作。

## 3. 表单约定

### 3.1 字段级约定

| 约定 | 规则 | 为什么 |
|---|---|---|
| 标签 | 左对齐，必填项加 `*` | —— |
| 帮助文本 | 放在字段下方，恒定占位 | 输入时页面不跳动 |
| 校验反馈 | 失焦时校验，不在每次按键时校验 | 输入途中报错会打断输入 |
| 错误文案位置 | 紧贴字段下方 | 与帮助文本互换位置，不新增一行 |
| 危险字段 | 例如"关闭注册"，用边框强调 | 与普通开关区分 |

### 3.2 提交约定

| 约定 | 规则 |
|---|---|
| 提交按钮 | 提交中禁用 + 显示进行中文案（不换位置，避免误点） |
| 二次确认 | 走 [03-admin.md](03-admin.md) 1.3 的统一确认框形态 |
| 提交失败 | 保留用户已填内容，不回滚表单 |
| 提交成功 | 短操作原地反馈；长操作跳转到结果页 |
| 幂等 | 可重复提交的动作不产生重复资源 |

**为什么提交中不移动按钮位置**：移动会导致用户第二次点击落在别处， 在管理端可能触发一个完全不同的危险操作。

**为什么失败时不回滚表单**：表单可能是几十个字段的组策略配置。 清空等于让用户重做一遍，这是最容易促使用户放弃配置大表单的体验。

### 3.3 一次性展示类表单

新建 API Key（[04-tenant.md](04-tenant.md) 3.2）与生成恢复码 （[05-contributor.md](05-contributor.md) 第 6 节）共用同一形态：

1. 提交后**整页替换**为一次性展示视图
2. 提供复制与下载
3. 需要显式勾选"我已保存"才能离开
4. 不提供任何形式的"再次显示"

**为什么共用同一形态**：两者的安全语义完全相同（服务端只存 hash、 明文只出现一次）。共用形态让用户只学一次，也让实现只有一处需要保证正确。

## 4. 四种页面状态

每个列表页与详情页都必须定义这四种状态。**缺一种就是缺陷**。

| 状态 | 触发 | 形态 |
|---|---|---|
| 空态 | 查询成功但结果为空 | 一句解释 + 一个下一步动作 |
| 加载态 | 首次加载 / 翻页 | 骨架屏或进度指示；**不用全屏遮罩** |
| 错误态 | 请求失败 | 错误码 + 人话 + 请求 ID + 重试 |
| 部分失败 | 多数据源中有失败的 | 成功部分照常渲染，失败部分内联提示 |

**为什么空态必须带"下一步动作"**：空态是用户最需要指引的时刻。 只写"暂无数据"等于把用户留在一个死路上。

**为什么不用全屏遮罩**：遮罩会隐藏导航，用户在等待期间无法离开。 加载是常态，不是阻塞。

**为什么错误态必须给请求 ID**：总纲第 11 章的打标对账用 `x-free-router-request-id` 头。让用户把 ID 报给管理员， 是把一次"报障"变成一次可定位的排查的最低成本手段。

### 4.1 错误态的分级

| 级别 | 表现 | 例子 |
|---|---|---|
| 字段级 | 字段下方红字 | 密码不足 12 字符 |
| 页面级 | 错误卡片，页面其余部分可用 | 列表加载失败 |
| 全局级 | 跳转错误页 | 401 / 403 / 404 / 410 / 500 |

**为什么字段级错误不进全局**：注册页的密码长度错误不应该让人离开当前页面。

## 5. 危险操作的确认

统一形态定义在 [03-admin.md](03-admin.md) 1.3。本分册补充**什么算危险**：

| 判据 | 说明 |
|---|---|
| 不可逆 | 吊销 Key、封禁凭据、拒绝账户 |
| 一对多 | 改组策略、改模型授权、改抽象模型策略 |
| 影响面跨账户 | 改全局设置、改熔断阈值 |
| 失去可恢复性 | 重新生成恢复码、重置密码 |
| 权限面变更 | 授予或回收 `admin` / `tenant` 类 |

四条共同要求：

1. 列出**影响面**（受影响的 Key / 组 / 候选数量）
2. 准确描述**不可逆程度**（"可恢复"与"不可恢复"必须区分）
3. 确认框里**输入目标资源的名称或 ID**（不要求密码、不要求第二因子），不是复选框
4. 确认按钮的文案是**具体动作**（"确认停用 smart"），不是"确定"

### 5.1 确认框不承担认证（2026-10-20 改定）

这张表把这件容易混的事一次讲清：

| 层 | 触发条件 | 强制方 | 表现 |
|---|---|---|---|
| **二次确认** | 本节 5 条判据任一命中 | 界面 | AlertDialog 四要素（影响面 / 不可逆程度 / 输入目标名称 / 具体动作按钮） |
| **认证** | 每次请求 | 服务端 | 唯一的认证动作是**登录**；会话 24h 过期，改密或禁用即吊销 |

三条关系：

1. 判据命中 = 要做二次确认，**且只做二次确认**。确认框不验证任何身份，它验证的是"操作者是否读懂了影响面"（[../security/02-authn.md](../security/02-authn.md) 第 6 节）。
2. 判据可以往后扩（新增一类"看起来危险"的写操作），但扩展只影响**界面上多一个框**，不影响服务端判定链——服务端对每个写请求做的是同一套检查（会话 → 账户状态 → 类 → 资源）。
3. 界面上只剩**一个标记** `🔒`（含义：该路由上有危险写，提交前必须确认，路由图例见 [01-ia.md](01-ia.md) 4.3）。旧的 `⚠️` 不再使用，因为它曾经表达的是"服务端会再拦一次"，而那件事已经不存在。

**为什么确认框里改要"输入目标名称"而不是"重输密码"**：取消类级二次验证后，重新输密码在同一会话内**不产生任何新的身份证明**——它只是把同一个密码再算一遍哈希。它唯一还能起的作用是拖慢手速，而拖慢手速用"输入目标名称"就能做到，且后者的信息量更高：管理员必须读一遍自己要动的是哪个对象。代价是确认框比密码框更依赖管理员的注意力，这一点由"按钮写具体动作"与"列出影响面"共同兜。

**为什么不用两种危险等级**：分级的意义在于"让实现者知道哪些要多做一步"，而这里所有命中的操作都要做同一件事——走同一个确认框。用两个符号表达同一件事的两种语气，只会让读者以为背后还有一道拦截。强度差异改由**框内文案**表达：影响面越大、越不可逆，框里的文字越长、动作按钮越具体。

## 6. 文案规范

### 6.1 基本规则

| 规则 | 反例 → 正例 |
|---|---|
| 说清"发生了什么"和"你能做什么" | "操作失败" → "Key 未被创建，因为白名单为空。请至少选择一个抽象模型" |
| 用术语表口径 | "虚拟模型" → "抽象模型" |
| 不暴露内部结构 | "候选 3 全部处于冷却" → "当前没有可用资源，请稍后重试" |
| 不给伪造的精度 | "节省了 3.7 元" → 不出现金额 |
| 面向用户的文案不用机器码 | "返回 no_candidate" → "当前没有可用资源" + 折叠的 `no_candidate` |

**为什么机器码仍要出现但折叠**：用户需要它来搜索与报障（见 [../api/03-errors.md](../api/03-errors.md)），但它不该是句子的一部分。

### 6.2 禁用词表

以下元素在全站界面**不得出现**（总纲 1.2 的"明确不做" + 反面验收）：

| 禁用元素 | 为什么 |
|---|---|
| 团队、团队成员、组织 | 总纲 1.2：做组不做团队 |
| 共享端点、组端点 | 总纲 2.6：全站一个端点按 Key 区分 |
| 邀请成员、邀请链接 | 总纲 1.2：无邀请 |
| 「已接入客户端」引导、客户端接入向导 | 总纲 1.2：智能应用已移除 |
| IM Bot 配置（TG / 微信 / 企业微信 / 飞书 / Lark / 钉钉）、`bashAllowlist`、`chatIdLock`、`proxyUrl` | 总纲 1.2：远程配置已移除 |
| 任何形式的费用 / 金额 / 价格 | 总纲 1.3：`cost` 字段已删 |
| 租户界面的真实模型名 | 总纲第 14 章反面验收 |

**为什么把这七项做成词表而不是原则**：原则会在具体页面里被遗忘， 词表可以在验收时被机械检查。总纲第 14 章的反面验收正是按条目列的。

### 6.3 状态词表

| 对象 | 用户可见状态词 |
|---|---|
| 账户 | 待审核 / 正常 / 已禁用 / 已拒绝 |
| API Key | 启用 / 已禁用 / 已过期 |
| 抽象模型 | 可用 / 已弃用 / 已停用 |
| 凭据 | 启用 / 已暂停 / 已封禁 |
| 鉴定 | 已鉴定 / 未鉴定 / 未通过 / 官方来源 |

**为什么不直接用英文枚举值**：`pending` 在不同上下文里含义不同 （账户待审核 vs 鉴定待跑）。中文状态词强制区分。

## 7. 响应式断点

| 断点 | 宽度 | 布局 |
|---|---|---|
| 桌面 | ≥ 1024 px | 三段式，一级导航常驻左侧 |
| 平板 | 768–1023 px | 一级导航收起为图标条，内容区全宽 |
| 手机 | < 768 px | 一级导航进抽屉；宽表格横向滚动 + 首列吸附 |

**为什么管理端也要支持手机**：管理员的常见场景是"手机上收到告警、 先看一眼、必要时再找电脑"。如果管理端在手机上不可读， 这类快速查看会退化成"必须开电脑"，等于把响应时间拉长。

**手机端表格的现状（2026-10-24 修正）**：本节原本要求"宽表在手机上转成卡片列表"。
实际实现是**横向滚动 + 首列吸附**，与原文不符，这里如实记录并说明原因。

没做转卡片的原因不是省事：`DataTable` 的 children 契约是页面直接传
`<tr>` / `<td>`（38 个页面都这么写），转卡片必须给每个单元格补上列名
（`data-label`），等于逐页重写一遍表格——那是比本次重新设计更大的一次改动。
首列吸附是当前能拿到的 80% 收益：横滑时你始终知道自己在看哪一行。

> **待定**：是否值得为手机端把宽表真正改成卡片列表？如果做，建议一次做成
> `DataTable` 接收"列定义（含表头）"的新契约，而不是继续在 `<tr>` 上打补丁。

**为什么不是"先做桌面端再补手机"**：一旦桌面端定型， 把宽表改成卡片是一次数据展示层的重写。在约定阶段定下来， 代价只是选型时多考虑一个约束。

## 8. 无障碍

| 项 | 要求 | 为什么 |
|---|---|---|
| 键盘可达 | 所有交互元素可 Tab 到达，焦点可见 | 危险操作的确认框必须能用键盘完成 |
| 语义结构 | 标题层级正确、表格带表头、表单 `label` 与控件关联 | 屏幕阅读器依赖它 |
| 对比度 | 正文 ≥ 4.5:1，状态徽章上文字 ≥ 4.5:1 | 状态徽章是承载关键信息的 |
| 不只靠颜色 | 状态必须同时有文字或图标 | `suspect` / `unverified` 的区分不能只靠颜色（见 [05-contributor.md](05-contributor.md) 第 4 节） |
| 焦点管理 | 打开确认框时焦点移入，关闭后回到触发元素 | 键盘用户不会"丢失位置" |
| 动效 | 尊重系统"减少动态效果"设置 | —— |

**为什么"不只靠颜色"在这里是必须项而不是加分项**： 本设计里有两处关键区分是纯颜色区分（`suspect` 与 `unverified`、 `deprecated` 与 `active`）。这两处区分决定了用户是否需要采取行动， 所以必须有第二重信号。

## 9. 站内一致性检查清单

交付界面前逐项核对：

| # | 检查项 |
|---|---|
| 1 | 一级导航完全由 `classes` 渲染，无跨类入口 |
| 2 | 每个列表页与详情页都有空态 / 加载态 / 错误态 |
| 3 | 所有危险操作走统一确认框，且按钮文案是具体动作 |
| 4 | 一次性展示类页面无法在不勾选的情况下离开 |
| 5 | 页面上没有任何"禁用词表"里的元素 |
| 6 | 租户端所有页面都不含真实模型名（含错误回显与日志详情） |
| 7 | 每个页面在手机断点下可用 |
| 8 | 所有状态区分都有颜色以外的第二重信号 |
| 9 | 错误提示都带请求 ID |
| 10 | 没有任何金额 / 费用字段 |

**为什么把它做成可勾选的清单**：总纲第 14 章是 20 条可验证的验收标准。 本分册的约定要能被同样机械地验证，否则它会停留在"理念"层面。

## 10. 待定项

**已定（2026-10-24）**：组件库定为 **Material UI v9 + Emotion**，替换先前
约定的 shadcn/ui + Tailwind。理由是中文控制台的实际收益：MUI 现成提供
表格、抽屉、对话框、无障碍与深浅主题的一致性，而 Tailwind 方案要自己拼装
这些组件。下面是落地后的实现级约束——**表内第一列是实际实现，不是设想**。

| 项 | 实际技术形态 | 状态 |
|---|---|---|
| 主题与令牌 | `src/theme.ts`：两个 `createTheme`（light / dark）+ `cssVariables: { cssVarPrefix: 'fr' }`；配色取 slate/indigo 色阶 | ✅ |
| 加载态 | MUI `Skeleton`（`ui.tsx` 的 `LoadingBlock`）；列表页默认 3 行 | ✅ |
| 路由与布局 | React Router 7 + `HashRouter`；路由由 `routes.ts` 的 `PAGES` 表生成，`App.tsx` 只做装配 | ✅ |
| 导航 | 桌面 MUI `AppBar` + 常驻侧栏；< 768px 收进 `Drawer` 抽屉 | ✅ |
| 数据获取 | 自研 `useApi` hook（`staleTime` 语义未引入：页面切换即重取，控制台数据要求新鲜） | ✅ |
| 轮询（唯一一处） | `useInboxUnread`：60s + 窗口 `focus` 时立即刷（[03-admin.md](03-admin.md) 第 12.4 节） | ✅ |
| 轮询的例外 | 其余页面一律不轮询 | ✅ |

**为什么组件库的 token 与 `style.css` 各存一份颜色**：`theme.ts` 管 MUI 组件，
`style.css` 管**原生控件**（页面里的 `<input>/<select>` 与 `muted`/`metric`
这类语义类名）。两份都从同一批色阶取值，改色要动两处——这是"不想把 38 个
页面全部改写成 MUI 受控组件"的代价，已明确接受。
