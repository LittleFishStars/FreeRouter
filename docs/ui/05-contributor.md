# 贡献者界面

## 1. 贡献者端的定位
`contributor` 类是三条权限类里唯一**没有模型调用能力**的一条（总纲 2.2）。 它的全部界面围绕一件事展开：**我贡献了什么、它现在是什么状态、它被用了多少**。
三条边界：
| 边界 | 说明 |
|---|---|
| 只看自己 | 永远只列出 `owner_account_id = 当前账户` 的凭据 |
| 不看明文 | 凭据 secret 不落可逆存储给贡献者，界面不提供查看（总纲 9.4） |
| 不看路由 | 看不到自己的凭据被哪个抽象模型选中、被谁的请求用走（总纲 2.4 隔离四条） |

**为什么第三条件单独强调**：贡献者最容易产生的诉求是"我的号被谁用了"。 总纲把归因限定在管理端（3.7），是因为"某个贡献者的凭据服务了某个抽象模型" 本身就是池结构信息。界面如果用任何形式（图表、占比、明细）透出它， 隔离四条里的"审计分账"就失效了。

## 2. 贡献入口 `/contributions`

**用途**：已登录用户的贡献起点。它复用公共区的贡献流程（[02-public.md](02-public.md) 第 6 节）， 差别只在"已登录"这一事实。

**关键字段**：当前账户已有的凭据数量、上次贡献时间、可贡献的两种类型。

**主要操作**：

| 操作 | 说明 |
|---|---|
| 贡献供应商账号 | 走供应商 OAuth，完成后自动加 `contributor` 类 |
| 贡献 API Key | 填端点、Key、声称的模型、标签 |
| 查看已有凭据 | 跳转到凭据列表 |

**为什么已登录用户也要看到贡献入口**：一个只有 `tenant` 类的账户 可以通过贡献当场获得 `contributor` 类（总纲 4.1"贡献即得 contributor 类无需审批"）。 把入口藏起来会让人以为贡献需要申请。

**为什么贡献后不跳回到租户首页而是跳到"我的凭据"**：贡献是异步的， 用户最关心的是"我交的东西到哪一步了"。跳到凭据列表能看到 L0 的结果。

## 3. 我的凭据列表 `/contributions/credentials`

**用途**：贡献者的主界面。

**关键字段**：

| 列 | 说明 |
|---|---|
| 标签 | `external_label`，贡献时必填 |
| 类型 | 供应商 OAuth / API Key |
| 声称的模型 | **贡献时自己填的那个名字** |
| 状态 | 启用 / 暂停 / 封禁 |
| 鉴定判定 | `verified` / `suspect` / `unverified` / `trusted` |
| 贡献时间 | —— |
| 最近被调用 | **只给"有没有"和"最近时间"，不给次数与对象** |

**主要操作**：查看详情与鉴定证据；暂停 / 恢复自己贡献的凭据；更新凭据（重新授权或换 Key）。

**关于"声称的模型"这一列的用词**：

> 这一列显示的是**贡献者自己填写并声称的那个模型名** （例如他在自己申请的第三方服务上看到的模型 id）， 它**不是**平台内部的真实模型目录名。

**为什么要把这两者分开**：平台的真实模型命名是限定名 `dsh:渠道/上游模型 id` （总纲 11.2），只有管理端可见；而贡献者必然知道自己在什么服务上有什么模型， 否则无法完成"声称"（总纲 4.3 的 L0 校验就是比对 `/v1/models` 是否含声称的 id）。 让他看到自己填的名字，不构成池结构泄露； 把平台的限定名显示给他，才是泄露。

**为什么"最近被调用"不给次数与对象**：次数会让人反推"我的凭据在这池子里占多大份额"， 对象会暴露归因。给"有没有被用过"是为了让贡献者知道自己的贡献是否真的在生效， 这是一个正当且不泄露的需求。

**为什么暂停 / 恢复由贡献者自己控制**：总纲 4.1 定"贡献即生效无需审核"， 对应的对称设计是"贡献者可以自己撤下"。否则贡献者一旦发现自己的账号有异常用量， 唯一的路径是找管理员——而管理员可能不在。

## 4. 凭据详情与鉴定结果 `/contributions/credentials/:id`

**用途**：解释"这个凭据现在是什么状态、为什么"。

**关键字段**：

| 分区 | 字段 |
|---|---|
| 基本信息 | 标签、类型、声称的模型、创建时间、最近被调用 |
| 状态 | 启用 / 暂停 / 封禁 + 状态原因 |
| 鉴定判定 | 四态之一 + 判定时间 |
| 鉴定流水线 | L0 形式校验（结果）/ L1 标准鉴定（若已跑）/ L2 深度鉴定（若被抽检） |
| 证据 | 达标或未达标的具体项 |
| 复检历史 | 历次判定的时间与结论变化 |
| 可用性 | 是否在候选池中（**不给"被哪些抽象模型引用"**） |

**主要操作**：重新授权 / 更换 Key；暂停 / 恢复；导出鉴定结果（便于申诉）；查看处置建议。

**为什么把 L0 / L1 / L2 三个阶段的进度分开显示**：总纲 4.3 的三级流水线 耗时差异极大（L0 几秒，L1 约 1 分钟，L2 是抽检）。 合成一个"鉴定中"会让贡献者以为卡住了，而实际上 L0 早就过了、L1 还没跑完。

**为什么 `unverified` 要用与 `suspect` 不同的视觉**：总纲 4.4 定 `unverified` 是**默认放行**（库里没有参考指纹的冷门模型）， `suspect` 是**拒绝并给证据**。如果两者同色， 贡献者会以为自己的冷门模型出了问题，从而反复重新提交。

| 判定 | 视觉 | 文案要点 |
|---|---|---|
| `verified` | 绿 | 已鉴定通过，正在参与路由 |
| `trusted` | 蓝 | 官方域名，免检 |
| `unverified` | 灰（不是黄） | 未鉴定（暂无参考指纹），**已放行**，进入复检 |
| `suspect` | 黄 | 未通过，已停止使用；附证据与申诉路径 |

**为什么 `unverified` 用灰色而不是黄色**：灰色在视觉语言里是"信息缺失"， 黄色是"警告"。这个判定确实只是信息缺失，不是警告。

**凭什么可以显示"证据"**：总纲 4.4 要求 `suspect` 的处置是"拒绝并给证据"。 证据的具体披露粒度见 [03-admin.md](03-admin.md) 第 12 节的待定项—— 本分册只规定"必须给"，粒度由那条待定项决定。

**为什么详情里不给"被哪些抽象模型引用"**：这是池结构信息。 给"是否在候选池中"是必要的（否则贡献者不知道自己的贡献有没有意义）， 给"被哪个抽象模型选中"就越界了。

## 5. 被调用统计与收益视图 `/contributions/stats`

**用途**：让贡献者看到自己贡献的价值。

**关键字段**（当前形态）：

| 字段 | 说明 |
|---|---|
| 贡献量 | 凭据数量、其中在池中的数量、覆盖的声称模型数 |
| 被调用次数 | **聚合总量**，不按抽象模型拆分 |
| 消耗 token | 输入 / 输出合计 |
| 时间范围 | 日 / 月切换 |
| 健康度 | 各凭据的当前状态汇总（正常 / 暂停 / 封禁的数量） |

**主要操作**：切换时间范围；跳转到凭据详情。

**为什么"被调用次数"不做按抽象模型的拆分**：一旦按抽象模型拆分， 贡献者就能画出"我的凭据在 `smart` 上被用得多、在 `fast` 上用得少"的画像， 进而推断抽象模型与真实候选之间的映射。总纲 2.4 的"凭据不可自选、 路由决定"依赖的正是这种不可见性。

**为什么统计里没有"节省了多少钱"**：总纲 1.3 已删 `cost` 字段， 理由是订阅额度算不出真钱。用金额表达贡献价值会引入一个伪造的精度。

### 5.1 收益视图（当前状态）

总纲 4.5 的贡献者回报机制**尚未拍板**，因此本页在拍板前**只呈现可观测统计**， 不呈现任何形式的"折算"。

> **待定**：贡献者回报机制采用总纲 4.5 的哪一种？ 方案 1（把贡献折算成额度挂着，自己用不了，需要另加 `tenant` 类）； 方案 2（只有统计：贡献量 / 被调用次数 / 消耗 token）； 方案 3（作为升级凭据：贡献到量换取 `tenant` 类的优先审批）。 总纲第 15 章已把它列为待拍板项。

**为什么在拍板前只给统计而不先给一个"积分"**：三种方案的界面后果完全不同—— 方案 1 需要一个"额度余额"组件，方案 3 需要一个"进度条 + 升级入口"组件。 先做一个占位组件，会诱导后续实现向占位形态收敛，等于用界面反过来拍板。

**界面必须显式说明当前处于哪种状态**：给出一句"回报机制尚未确定， 当前展示的是你的贡献统计"，避免贡献者以为统计数字背后挂着一个他还看不到的收益。

## 6. 恢复入口 `/contributions/recovery-code`

**用途**：只有 `contributor` 类的账户**没有密码**（总纲 4.1 登录身份表）， 唯一的找回路径是恢复码或 OAuth。

**关键字段**：恢复码状态（已生成 / 未生成）、生成时间、最近一次使用时间。

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 重新生成恢复码 | 作废旧码，**一次性展示**新码（同 [04-tenant.md](04-tenant.md) 3.2 的整页形态） | **是**（⚠️ 旧码立即失效） |
| 绑定 OAuth 身份 | 把已贡献过的供应商账号绑定为登录身份 | 否 |
| 查看找回说明 | 说明"用任意用过的账号登录即可回来" | 否 |

**为什么重新生成要二次确认**：新的恢复码只显示一次。如果用户没保存好， 旧码又被作废了，这个账户就彻底失去自助找回路径——只能靠管理员介入。 这是典型的"可恢复性损失"，属于危险操作。

**为什么恢复码用与 API Key 相同的一次性展示形态**：两者都是 "服务端只存 hash、明文只出现一次"的秘密。共用同一套交互形态， 用户只需要学一次，也避免两套实现里有一套漏掉"勾选后才能离开"的约束。

## 7. 空态、错态与边界

| 情况 | 界面 |
|---|---|
| 还没有任何凭据 | 空态 + 两种贡献方式的入口 + 一句"贡献即生效，无需审核" |
| 凭据正在鉴定中 | 状态列显示"鉴定中（L1）"，不显示判定徽章 |
| 全部凭据被暂停 | 明确说明原因类别（上游限流 / 鉴定未通过 / 管理员操作） |
| 账户只有 `contributor` 类 | 不显示任何模型调用入口（见 [01-ia.md](01-ia.md) 3.2） |
| 统计为空 | 空态 + "你的凭据还没有产生调用" |

**为什么"账户只有 contributor 类"要特别列一行**：这是三类里唯一 "登录了但看不到任何模型相关界面"的情况，最容易让贡献者以为系统坏了。 界面必须有一条明确的说明，解释"贡献者身份不包含模型调用能力， 如需调用请另行申请"。

**为什么"鉴定中"不显示判定徽章**：判定还没出来。 显示一个中间态徽章（例如"待定"）会与 `unverified` 的"未鉴定"混淆。
