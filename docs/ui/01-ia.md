# 信息架构

## 1. 本分册的职责与边界
本分册回答一个问题：**一个账户登录之后，界面上到底出现哪些入口、不出现哪些入口， 以及每个入口背后是哪一页。** 页面内部的字段与操作分别见 [02-public.md](02-public.md)、[03-admin.md](03-admin.md)、[04-tenant.md](04-tenant.md)、 [05-contributor.md](05-contributor.md)；统一的视觉与交互规则见 [06-design.md](06-design.md)。
不做的事（与总纲第 1 章一致）：本分册不定义接口返回什么、不定义数据表、不定义视觉风格。
**为什么单独立一篇**：导航是"权限类渲染"这条决策唯一能被验收的地方。 总纲第 14 章的**反面验收**（控制台没有团队 / 共享端点 / 邀请成员入口、没有客户端接入引导、 没有 IM Bot 配置）只能在信息架构层面判定——一旦某个入口被写进导航表，它就已经违约了。 所以路由表必须显式列出，而不是散落在各页描述里。

## 2. 站点总地图

站点只有**一个域**、**一个登入点**，登录后按权限类分流。没有多站点、没有子域、 没有第二套账号体系。

```
FreeRouter
├── 公共区（未登录可访问，部分永远可访问）
│   ├── 登录 / 注册 / 待审核提示
│   ├── 贡献入口（未登录可贡献，见 05-contributor.md）
│   └── 错误页 / 状态页
├── 低权限上下文（登录后默认落点，只读自己的信息）
│   └── 账户自助：改密、登出、我的权限类
├── 管理入口（仅 admin 类出现；登录即生成，无二次验证）
│   └── 账户 / 组 / 真实模型 / 抽象模型 / 上游与凭据 / 鉴定 / 审计 / 设置
├── 租户入口（仅 tenant 类出现）
│   └── 我的 API Key / 用量与配额 / 调用日志 / 可用抽象模型
└── 贡献者入口（仅 contributor 类出现）
    └── 贡献凭据 / 我的凭据状态 / 鉴定结果与证据 / 被调用统计
```

**为什么贡献入口同时存在于公共区和贡献者入口**：总纲 4.1 定"贡献即生效，无需审核"， 且未登录也能贡献。如果贡献只放在登录后的贡献者入口，未登录用户必须先注册再等审核， 这与"贡献不需要审核"直接矛盾。因此贡献是一个**独立的公共动作**， 登录与否只决定贡献完落在哪里（已有账户 vs 新建仅 `contributor` 类的账户）。

**为什么管理入口、租户入口、贡献者入口三者平级**：它们代表的是三种**能力**， 不是三个页面组。总纲 2.3 的"隔离发生在权限类之间"，在界面上就表现为： 三个入口各自有独立的一级导航，互不嵌套、互不跳转。管理界面里不会出现任何"去看看我的 Key" 的链接，因为那会把管理上下文和调用上下文混在一起，破坏审计分账（总纲 2.3 第 4 条）。

## 3. 按权限类渲染的导航规则

### 3.1 渲染输入

导航只由两个输入决定：

| 输入 | 来源 | 说明 |
|---|---|---|
| `classes` | 账户的权限类集合 | `admin` / `tenant` / `contributor` 的布尔组合 |
| `status` | 账户状态 | `pending` / `active` / `disabled` / `rejected` / `merged` |

**为什么渲染输入里没有"角色"**：总纲 2.1 已经把 v3 的"角色二选一"改成了权限类集合。 界面上如果还保留一个"当前角色"的概念，就等于把已经删掉的东西偷偷装回来， 并且会立刻引出"切换账户/切换角色"的交互——而总纲 2.4 明确说不需要切换。

**为什么 `status` 也是渲染输入**：`pending` 账户压根不能登录（总纲 2.7）， 所以它唯一能看到的登录后界面是"待审核提示页"。把 `status` 当渲染输入， 可以避免出现"登录成功了但每个页面都报错"的体验。

### 3.2 导航生成的确定性规则

规则按顺序求值，先命中先生效：

| # | 条件 | 结果 |
|---|---|---|
| R1 | `classes.admin = true` | 渲染管理一级导航；其中「待处理」项右上角带未读计数徽标 |
| R2 | `classes.tenant = true` | 渲染租户一级导航 |
| R3 | `classes.contributor = true` | 渲染贡献者一级导航 |
| R4 | 无任何权限类 | 只渲染公共区 + 账户自助；页面提示"你的账户尚未获得任何权限类" |

**为什么导航里没有「可见但锁定」这一档**：「登录一次 = 该账户所有权限类的全部权限」，不存在"已经登录但还差一步"的中间态。因此 `classes` 是导航的唯一判定输入，上面这张表是纯函数——同样的 `classes` 永远得到同样的导航。**为什么这条要写死**：一旦允许"可见但锁定"，界面就必须为每个入口准备两种形态（可点 / 灰掉并引导去解锁），而灰掉的入口本身就在告诉用户"这里有个你还没解锁的东西"，它既增加实现面积，又引入一个必须被单独测试的状态。**代价与补偿**：管理面直接暴露在公网上，抵抗力全部落在登录这一环——argon2id 口令哈希参数、登录退避与锁定阈值、会话 24h 过期（改密 / 禁用即吊销）三项必须认真取值。

**未读计数徽标的位置与刷新**：「待处理事项 `/admin/inbox`」是管理导航里唯一带徽标的项。登录时拉一次未读数，页面打开期间每 60 秒轮询、窗口重新获得焦点时立即刷一次（[03-admin.md](03-admin.md) 第 12.4 节）。

**为什么徽标挂在导航项上而不是做成独立的"通知中心"弹层**：待处理事项的处置地点是具体页面（注册审批在 `/admin`、弃用在抽象模型页），导航项本身就是"去处理"的入口。做成弹层会引出"在弹层里就地处理"的诱惑，而那必然复制各页面的校验逻辑（见 [03-admin.md](03-admin.md) 第 12.2 节）。**为什么这里不出现"通知"这个词**：通知暗示推送与订阅，而本设计明确不做实时推送；叫"待处理"才准确表达它是**工作队列**而不是消息流——队列是"必须逐条清掉的"，消息流是可以扫一眼就划走的。

### 3.3 共存示例

同一账户的三种典型组合，导航实际长什么样：

| 组合 | 一级导航 |
|---|---|
| `{admin}` | 公共区 · 账户 · 管理 |
| `{admin, tenant}`（管理员默认组合，总纲 2.2） | 公共区 · 账户 · 管理 · 我的使用 |
| `{tenant}` | 公共区 · 账户 · 我的使用 |
| `{contributor}` | 公共区 · 账户 · 我的贡献 |
| `{tenant, contributor}` | 公共区 · 账户 · 我的使用 · 我的贡献 |
| `{admin, tenant, contributor}` | 公共区 · 账户 · 管理 · 我的使用 · 我的贡献 |
| `{}`（无类） | 公共区 · 账户 · ＋ 空态提示 |

**为什么 `{admin, tenant}` 下"管理"排在"我的使用"前面**：管理员的主要身份是管理， 把管理放在更靠前的位置可以让高频动作更近；但这只是排序， 两者之间不存在任何跳转或数据共享——见 3.4。

### 3.4 三个入口之间的三条硬性隔离（界面侧）

| 隔离 | 界面表现 | 依据 |
|---|---|---|
| 数据不交叉 | 管理端的账户列表**不提供**"查看该账户的 Key"链接；租户端**不提供**"查看我的权限类来源组"的成员列表 | 总纲 2.3 第 2 条资源分表归属 |
| 上下文不冒充 | 同一账户在管理端的写操作，在审计里记 `acting_class=admin`；在租户端的调用记 `acting_class=tenant` | 总纲 2.3 第 4 条审计分账 |
| 凭据不预览 | 贡献者入口**不出现**自己的凭据被哪个请求用掉了的细节；管理端**不出现**凭据明文 | 总纲 2.3 第 3 条、9.4 |

> **为什么管理端不给"跳去看该用户的 Key"**：这看起来是便利功能，实际是越权入口—— 它把 `admin` 类的可见性延伸到了 `tenant` 类的资源上。管理员要排查某个 Key， 走的是**调用日志**（按 Key 前缀筛选），日志是管理面本来就该看的观测数据， 而不是 `api_keys` 这张归 `tenant` 类所有的表。

### 3.5 组对界面的唯一影响

组（`group`）是管理员的批量控制单元（总纲 2.6），**不产生任何新页面**。它在界面上的表现只有三处：

| 位置 | 表现 |
|---|---|
| 管理端 · 账户详情 | 显示该账户所属的组，可增删 |
| 租户端 · 可用抽象模型 | 实际可见集合 =（∪ 所属组的抽象模型）∩ Key 白名单 |
| 租户端 · 用量与配额 | 显示生效额度（各组最小值），**不显示"因为你在 X 组所以是 N"** |

**为什么租户端不显示"这个额度来自哪个组"**：总纲 2.6 定"组名对成员可见， 成员列表不可见"，目的是避免形成组织感。如果把额度来源指向具体组， 用户会自然地推断"哪些人和我一个组"，等于绕过成员列表不可见。

> **待定**（继承总纲 2.6 与 15.3）：租户端是否需要集中展示"我所属的组名"列表？ 当前设计只在"可用模型/配额"旁以只读文本展示组名，不设独立的"我的组"页面。

## 4. 完整路由表

约定：`:id` 为路径参数；带 🔒 的路由上有**危险写**，提交前必须走统一二次确认框（[06-design.md](06-design.md) 第 5 节）。**全站只有这一个标记**：它的含义是"这条路由上有不可逆或跨账户的写操作，界面必须拦一道"。标记只描述危险程度，不描述任何服务端机制——服务端对每个写请求做的是同一套检查。

### 4.1 公共区

| 路由 | 页面 | 未登录 | 说明 |
|---|---|---|---|
| `/` | 首页 | ✅ | 未登录时是落地页 + 登录/注册/贡献三个动作；已登录时按 3.2 分流 |
| `/login` | 登录 | ✅ | 密码登录；OAuth 登录入口见 [02-public.md](02-public.md) |
| `/register` | 注册 | ✅ | 默认开启但需审核 |
| `/pending` | 待审核提示 | 不适用 | 仅 `pending` 账户登录后可见 |
| `/contribute` | 贡献入口 | ✅ | 供应商 OAuth 与 API Key 两种贡献物 |
| `/contribute/oauth/:provider` | 供应商 OAuth 跳转 | ✅ | 回调落在 `/contribute/callback` |
| `/contribute/callback` | 贡献回调 | ✅ | 成功后进入"已受理"或新建账户的恢复路径页 |
| `/contribute/recovery` | 恢复码兑换 | ✅ | 纯 Key 型贡献者的一次性恢复路径 |
| `/status/upstream-offline` 等横幅 | 状态提示 | ✅ | 上游离线等运行态提示，见 [06-design.md](06-design.md) |
| `/error/403`、`/error/404`、`/error/410`、`/error/500` | 错误页 | ✅ | 文案规范见 [06-design.md](06-design.md) |

### 4.2 账户自助（任何已登录的 `active` 账户）

| 路由 | 页面 |
|---|---|
| `/account` | 账户概览：显示名、账户 ID、权限类徽章、登录方式、最近登录 |
| `/account/password` | 自助改密（改密即吊销全部会话，含当前会话并强制重新登录） |
| `/account/sessions` | 我的会话列表 + 单独吊销 |
| `/logout` | 登出（POST，避免被预取触发） |

**为什么账户概览要显示权限类徽章**：权限类是账户的唯一能力声明， 用户必须能自己确认"我有没有租户类"。不显示会直接把权限问题变成客服问题。

**为什么没有"账户/资料编辑（改显示名）"**：显示名参与审核与审计的可读性， 改名会让审计日志里的历史记录难以对应。总纲未定义改名流程， 因此本分册不给入口，登记为待定项（见第 8 节）。

### 4.3 管理入口（`admin` 类）

一级入口 `/admin` 默认落在**审核队列**（总纲第 13 章"审核积压无人处理"的对策：队列置顶）。

| 路由 | 页面 | 标记 |
|---|---|---|
| `/admin` | 审核队列（含待办计数） | 🔒 |
| `/admin/inbox` | 待处理事项（注册申请 / 模型变动 / 故障通知 / 池与熔断告警，见 [03-admin.md](03-admin.md) 第 12 节） | 🔒 |
| `/admin/accounts` | 账户列表与筛选 | 🔒 |
| `/admin/accounts/:id` | 账户详情与权限类管理 | 🔒 |
| `/admin/accounts/:id`（删账户动作：禁用 / 合并 / 合并回滚） | — | 🔒 |
| `/admin/accounts/import` | 管理员导入账密（单个 / CSV） | 🔒 |
| `/admin/groups` | 组列表 | 🔒 |
| `/admin/groups/:id` | 组成员、模型授权、策略 | 🔒 |
| `/admin/groups/:id`（改组动作：授权 / 策略 / 成员 / 默认组 / 删组） | — | 🔒 |
| `/admin/real-models` | 真实模型目录（含 `missing` 巡检） | 🔒 |
| `/admin/abstract-models` | 抽象模型列表 | 🔒 |
| `/admin/abstract-models/:id` | 抽象模型编辑（能力、策略链） | 🔒（保存类动作） |
| `/admin/abstract-models/:id/candidates` | 候选集编辑 | 🔒 |
| `/admin/abstract-models/:id/deprecation` | 弃用配置与替代链预览 | 🔒 |
| `/admin/upstreams` | 上游：`relay` 与 `vendor`（含 `selfhosted`）渠道 | 🔒 |
| `/admin/credentials` | 凭据池（含平台自有凭据） | 🔒 |
| `/admin/credentials/:id` | 凭据详情（明文永不显示） | 🔒 |
| `/admin/credentials/:id`（封禁动作） | — | 🔒（二次确认） |
| `/admin/verifications` | 鉴定队列与复检队列 | 🔒 |
| `/admin/verifications/:id` | 鉴定结果与证据 | 🔒 |
| `/admin/audit` | 审计日志（append-only，只读） | 🔒 |
| `/admin/settings` | 全局设置 | 🔒 |
| `/admin/settings`（危险项动作） | — | 🔒（二次确认） |
| `/setup` | 初始化向导（无账户时唯一可见页面） | 不适用 |

**为什么不用两个标记区分危险程度**：区分危险程度的价值在于"让实现者知道哪些要多做一步"，而这一步已经是同一件事——都走同一个确认框。用两个符号表达"同一个框里的两种语气"，只会让人以为背后还有一道拦截。强度的差异放在**框内文案**里：影响面越大、越不可逆，文字越长、按钮越具体（[06-design.md](06-design.md) 第 5 节）。

**为什么危险写仍要确认**：确认框拦的是误点，不是身份。它列出影响面（受影响的账户 / 组 / Key / 候选数量）与不可逆性的准确程度——这两项信息在二次验证取消后反而更重要，因为已经没有服务端环节会在事后拦第二次。

### 4.4 租户入口（`tenant` 类）

| 路由 | 页面 |
|---|---|
| `/usage/dashboard` | 仪表盘（2026-10-30 新增，Tingly Box 式：五指标卡 + Token 时间序列 + 按模型用量；admin 可切「全站」口径，详见 04-tenant.md 第 10 节） |
| `/usage` | 用量与配额总览 |
| `/usage/keys` | 我的 API Key 列表 |
| `/usage/keys/new` | 创建 Key（明文一次性展示） |
| `/usage/keys/:id` | Key 详情：模型白名单、过期时间、最近调用；**额度与速率是账户级的**，此处只读展示账户值 |
| `/usage/logs` | 调用日志（**只出现抽象模型名**） |
| `/usage/models` | 可用抽象模型目录 |

**为什么租户入口的一级前缀选 `/usage` 而不是 `/tenant` 或 `/keys`**： `/keys` 太小（还有用量、日志、模型），`/tenant` 会把内部术语（租户类）泄露成用户可见的口语。 `/usage` 对用户来说就是"我在用多少"，同时覆盖了 Key、日志、模型三个页面。

### 4.5 贡献者入口（`contributor` 类）

| 路由 | 页面 |
|---|---|
| `/contributions` | 我的贡献总览 |
| `/contributions/credentials` | 我的凭据列表与状态 |
| `/contributions/credentials/:id` | 凭据详情：标签、状态、鉴定判定与证据 |
| `/contributions/stats` | 贡献统计（**无「收益」区域**，见第 5 节） |
| `/contributions/recovery-code` | 恢复码（仅纯 Key 型账户，展示一次） |

**为什么贡献者主体页叫 `/contributions` 而复用公共区的 `/contribute` 作为动作入口**： `/contribute` 是"去做一次贡献"（动词，未登录可用）， `/contributions` 是"看我贡献过什么"（名词，需登录且有 `contributor` 类）。 两者分开可以避免"未登录点进我的贡献列表"这种状态错配。

## 5. 页面 × 权限矩阵

图例：✅ 可见可操作 · ➖ 不可见（且直接访问返回 403/404） · ⛔ 仅此状态可见

| 页面 | 未登录 | pending | 无类 | admin | tenant | contributor |
|---|---|---|---|---|---|---|
| 首页 `/` | ✅ | ⛔（重定向 `/pending`） | ✅ | ✅ | ✅ | ✅ |
| 登录 `/login` | ✅ | — | ✅ | ✅ | ✅ | ✅ |
| 注册 `/register` | ✅ | — | ➖ | ➖ | ➖ | ➖ |
| 待审核 `/pending` | ➖ | ⛔ | ➖ | ➖ | ➖ | ➖ |
| 贡献 `/contribute` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 恢复码兑换 `/contribute/recovery` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 账户概览 `/account` | ➖ | ➖ | ✅ | ✅ | ✅ | ✅ |
| 待处理事项 `/admin/inbox` | ➖ | ➖ | ➖ | ✅ | ➖ | ➖ |
| 管理端 `/admin/**` | ➖ | ➖ | ➖ | ✅ | ➖ | ➖ |
| 初始化向导 `/setup` | ⛔（无账户时） | ➖ | ➖ | ➖ | ➖ | ➖ |
| 租户端 `/usage/**` | ➖ | ➖ | ➖ | ➖ | ✅ | ➖ |
| 贡献者端 `/contributions/**` | ➖ | ➖ | ➖ | ➖ | ➖ | ✅ |

**为什么"注册"对已登录账户不可见**：注册产出的是一个新账户， 已登录用户注册不会改变当前会话，只会制造一个孤儿 `pending` 账户。 关掉它比允许"顺手注册一个"更干净。

**为什么"贡献"对 `pending` 账户仍可见**：总纲 4.1 定"贡献即生效，无需审核"， 且"账号审核只用于 `tenant` 类"。如果 `pending` 账户不能贡献， 就等于用 `tenant` 类的审核卡住了 `contributor` 类的能力，违背类级隔离。

**为什么"无类"账户能贡献**：同上。一个 `{}` 账户贡献成功后即获得 `contributor` 类， 这正是总纲 14.15 验收的路径。

## 6. 未登录可见范围

| 范围 | 可见性 | 为什么 |
|---|---|---|
| 首页落地内容、登录、注册 | ✅ | 站点的正常入口 |
| 贡献入口全流程 | ✅ | 众包供给必须能零门槛开始（总纲 4.1） |
| 恢复码兑换 | ✅ | 纯 Key 型贡献者没有可识别身份，唯一回站路径 |
| 抽象模型目录 | ❌ | 目录依赖 Key 的可见性（总纲 11.3 三层收敛），无 Key 无集合 |
| 任何账户 / Key / 凭据 / 用量数据 | ❌ | 总纲 2.3 |
| 真实模型名 | ❌ | 总纲 3.1：只有管理员可见 |
| 上游离线等运行态横幅 | ✅ | 它描述站点健康，不含内部结构 |

**为什么抽象模型目录不对外开放**：它是"我能用什么"的答案， 取决于组的授权与 Key 的白名单两层收敛。未登录没有 Key，也就没有收敛结果； 公开一份"全站抽象模型清单"会给未注册用户一个不存在的能力承诺。

## 7. 入口守卫

导航隐藏**不是**授权。三层各自独立，任何一层缺失都视为缺陷：

| 层 | 职责 | 失败表现 |
|---|---|---|
| 渲染层 | 按 3.2 决定是否输出入口 | 入口不该出现却出现 → 反面验收不通过 |
| 路由层 | 直接访问 URL 时的判定 | 无权访问的管理路由返回 404 `not_found`；资源存在但归别人所有返回 403 `forbidden` |
| 数据层 | 查询强制带 `account_id` 过滤 | 越权数据出现在合法页面里 |

**为什么路由层对「无权访问的管理页」返回 404 而不是 403**：管理面的路由结构本身就是信息（存在哪些页面、页面 id 是什么形态）。对无 `admin` 类的账户统一返回 404，不确认资源是否存在，减少探测价值。**为什么只剩这一条判定**：取消类级二次验证后，"有 `admin` 类但尚未过第二道验证"这一档不再存在，管理面不再出现 403 中间态——有 `admin` 类即放行，没有即 404。

> **待定**：404 与 410 在页面层的分工。总纲 3.5 已定 `disabled` 的**模型**返回 404/410 Gone； 页面层的禁用实体（如被禁用的账户详情页）是否也区分 404 与 410，需在后端契约定稿时一起定。

## 8. 反面清单：界面上绝不出现的入口

以下每一项都来自总纲第 1 章的"明确不做"，且会被总纲 14 的反面验收检查。 本分册把它们列成清单，作为设计评审时的对照表：

| 绝不出现 | 为何不能出现 |
|---|---|
| 团队 / 团队成员 / 团队用量 | 总纲 1.1、1.2：不做团队，用组替代 |
| 共享端点 | 总纲 1.2：全站一个端点，按 Key 区分 |
| 邀请成员 / 邀请码入口（MVP） | 总纲 1.2：组无邀请；邀请码是 P1 且属注册侧 |
| 「已接入客户端」引导 / 逐客户端监控台 | 总纲 1.1：观测维度是 API Key 与抽象模型，不是客户端 |
| IM Bot / 远程控制配置 | 总纲 1.1：整个模块从路线图删除 |
| 计费 / 金额 / 单价 | 总纲 1.3：订阅额度没有单价，只记 token 消耗量 |
| 租户侧的真实模型名 | 总纲 3.1 与第 14 章反面验收 |
| 贡献者的凭据明文 | 总纲 9.4：凭据明文永不回显 |

**为什么把反面清单放进信息架构分册**：这些不是某个页面的细节， 而是**导航层面**的承诺。任何一项一旦进入路由表，就再也不会有人去删它。
