# 管理端页面

## 1. 管理端的定位与共同约定
管理端是 `admin` 类的全部界面，覆盖总纲第 8 章 MVP 清单里的账户、模型体系、贡献与观测三块运维面。
### 1.1 三条全站约定
| 约定 | 规则 | 为什么 |
|---|---|---|
| 提权 | 所有 `/admin/**` 都要先提权（15 分钟）；危险操作每次重验 | 总纲 2.5 |
| 审计 | **每一个写操作**都产生一条审计记录，读操作不产生 | 总纲 9.5 的 append-only 审计要能解释"谁改了什么" |
| 不可逆 | 界面不给"物理删除"，一律是状态迁移（`disabled` / `merged`） | 总纲的数据模型里 `requests` / `audit_log` 要保留历史引用 |

### 1.2 管理端的"真实模型名可见"边界

真实模型名（`dsh:deepseek-official/deepseek-flash` 这类限定名）**只允许**出现在：

| 允许出现的页面 | 为什么 |
|---|---|
| 真实模型目录 | 它就是目录本身 |
| 抽象模型的候选集编辑 | 候选 = 真实模型 × 渠道范围 × 约束 |
| 凭据详情 / 鉴定结果 | 鉴定要回答"这个 key 给的模型与声称是否相符" |
| 调用日志（管理端视图） | 总纲 3.7：真实落点与贡献者归因仅管理端可见 |
| 审计日志 | 记录必须可解释 |

**不得出现**的地方：任何会被租户看到的页面、任何导出给租户的报告。
**为什么单独写这一条**：管理端是全站唯一能合法看到真实模型名的地方， 把它写成规则可以避免后续开发"顺手"把这些字段复用到面向租户的组件里。

### 1.3 危险操作的统一二次确认形态

总纲 2.5 要求危险操作"每次重新验证"。统一形态：

```
┌─ 确认：停用抽象模型 smart ─────────────────────┐
│ 影响：所有指向该模型的客户端将收到 410 Gone     │
│ 影响对象：smart（当前 12 个 Key 的允许列表含它）│
│ 不可逆性：可通过"重新启用"恢复，但期间请求已失败 │
│                                               │
│ 请重新输入密码确认本次操作：                    │
│ [ •••••••••• ]                                │
│                                               │
│            [ 取消 ]   [ 确认停用 ]             │
└───────────────────────────────────────────────┘
```

三条要求：

| 要求 | 为什么 |
|---|---|
| 必须列出**影响面**（受影响的 Key / 组 / 候选数量） | 管理员只看到"改这个模型"无法判断爆炸半径 |
| 必须写**不可逆性的准确程度** | "可恢复"与"不可恢复"的操作，管理员的犹豫程度不同 |
| 必须**重新输入凭据**，不是勾选"我确认" | 勾选是肌肉记忆，重输密码才是有意识动作 |

## 2. 初始化向导 `/setup`

**用途**：首次启动若库中无任何账户，站点只监听 `127.0.0.1` 并引导创建管理员 （总纲 2.7）。管理员创建完成前不开公网。

**关键字段**：

| 字段 | 必填 | 约束 |
|---|---|---|
| 显示名 | ✅ | 唯一 |
| 密码 | ✅ | ≥12 字符，**无默认值** |
| TOTP 绑定 | ➖ | 建议但非阻塞；未绑定时提权只能用重输密码 |

**主要操作**：

| 操作 | 结果 |
|---|---|
| 创建管理员 | 账户以 `{admin, tenant}` 建立（总纲 2.2 默认组合），状态 `active` |
| 完成向导 | 站点转入正常监听；此后 `/setup` 永久返回 404 |

**危险操作与二次确认**：向导期间只有一步写操作（创建管理员），
**不做**二次确认——此时还没有第二个身份可以验证，强行加确认只是形式。 真正需要保护的是"向导不可被重放"，这由 `/setup` 的永久关闭保证。

**为什么不预置默认密码**：总纲 2.7 明确"无默认密码"。 带默认密码的初始账户是公网服务的头号事故来源。

**为什么管理员默认带 `tenant` 类**：总纲 2.2 已定。 向导页要**明说**这一点，避免管理员以为自己不能调模型。

## 3. 账户审核队列 `/admin`

**用途**：处理 `pending` 账户的准入。它是 `/admin` 的默认落地页。

**关键字段**（列表列）：

| 列 | 说明 |
|---|---|
| 显示名 | 申请人的名字 |
| 申请时间 | 排序默认按此倒序 |
| 来源 IP | 判断是否被批量刷号（总纲第 13 章） |
| 申请时提供的类 | 默认只有 `tenant`；贡献后自动获得 `contributor` 的不进此队列 |
| 备注 | 管理员审批时的自由文本 |

**主要操作**：

| 操作 | 输入 | 结果 | 二次确认 |
|---|---|---|---|
| 批准 | **必选组 + 配额**（总纲 2.7） | 账户转 `active`，加 `tenant` 类，进所选组 | 否（可逆：随时可禁用） |
| 批量批准 | 多选 + 同一组与配额 | 同上，逐条审计 | 否 |
| 拒绝 | 可填理由 | 转 `rejected`，理由可被申请人在登录时看到 | **是**（⚠️） |
| 忽略 | 无 | 保持 `pending` | 否 |

**为什么批准必须同时选组 + 配额**：组决定模型可见性，配额决定消耗上限。 如果批准时不选，新账户会落在一个"有账户但什么都不可见"的状态， 而总纲 2.6 的默认组机制正是为了避免这一点。强制二选一， 等于强制管理员在放人进来的那一刻就想清楚这个人能用什么。

**为什么拒绝要二次确认而批准不用**：拒绝是**面向人**的负面动作， 误点的代价由申请人承担；批准误点则可以被后续的禁用撤销。 二次确认的成本应该花在难撤销的动作上。

## 4. 账户与权限类管理

### 4.1 账户列表 `/admin/accounts`

**用途**：全站账户的检索、状态管理、导出。

**关键字段**：显示名、账户 ID、权限类集合（徽章）、状态、所属组、创建时间、最近登录、名下 Key 数量、名下凭据数量。

**主要操作**：按权限类 / 状态 / 组筛选；按显示名搜索；进入详情；导出 CSV。

**为什么列表里给"名下 Key 数量"却不给 Key 列表**：数量是运维判断"这个人活跃度"的必要信号， 而 Key 列表属于 `tenant` 类资源（见 [01-ia.md](01-ia.md) 3.4）。 给数量不给内容，既保留了运营视角，又不越类。

### 4.2 账户详情 `/admin/accounts/:id`

**用途**：单个账户的全量管理。

**关键字段**：

| 字段 | 可改 | 说明 |
|---|---|---|
| 显示名 | 只读 | 改名的审计对应问题未定，见 [01-ia.md](01-ia.md) 第 9 节 |
| 账户 ID | 只读 | 内部唯一 |
| 权限类集合 | ✅ | 三个复选框 |
| 状态 | ✅ | `active` / `disabled` / `rejected` |
| 所属组 | ✅ | 多选 |
| 备注 | ✅ | 内部备注，不进审计正文 |
| 会话 | 只读列表 | 显示 IP / UA / 是否提权；可单独吊销 |

**主要操作**：

| 操作 | 效果 | 二次确认 |
|---|---|---|
| 增删权限类 | 立即生效 | **是**（⚠️ 变更能力面） |
| 授予 `admin` 类 | 该账户获得管理面 | **是**（⚠️ 且提示"这是全站最高权限"） |
| 禁用账户 | 名下所有 Key **立即** 401（总纲 9.3） | **是**（⚠️） |
| 启用账户 | 恢复 | 否 |
| 重置密码 | 生成随机密码，**一次性展示** | **是**（⚠️） |
| 吊销全部会话 | 立即踢下线 | 否 |
| 合并账户 | 选目标账户，类取并集 | **是**（⚠️ 不可逆，见 4.3） |
| 删除账户 | —— | **不提供**（改为禁用） |

**为什么"授予 admin 类"要单独一条二次确认**：它不改变该账户的 `tenant` 侧任何东西， 但把全站控制权交给一个人。界面上必须用与其它权限类不同的措辞强调这一点， 否则三个复选框看起来是同级的。

**为什么允许"删除账户"被替换成禁用**：总纲的数据模型里 `requests` / `audit_log` 引用了 `account_id`，物理删除会让历史记录悬空。禁用保留了追溯能力。

### 4.3 账户合并

总纲 2.1 定"合并 = 两个账户并成一个、类取并集"。合并的界面流程：

1. 在**源账户**详情点"合并到…"
2. 选择目标账户（搜索 + 二次确认选中的是谁）
3. 预览：将要并入的权限类、将迁走的凭据、将迁走的 Key、将失效的会话
4. 重验密码确认
5. 源账户转 `merged`，`account_merges` 留痕，`reversible_until`（= 合并 + **7 天**）内可回滚

**为什么必须先预览再确认**：合并会一次改动三种资源（类、凭据、Key）， 是全站影响面最广的单个操作。没有预览，管理员等于在盲操作。

**为什么合并可以"可逆"**：`reversible_until` 固定为 7 天窗口（[../security/01-accounts.md](../security/01-accounts.md) 第 4 节）。界面必须把回滚入口放在**合并后立即出现的横幅**里，否则管理员不知道有这个能力。**回滚只拆回类与资源归属，不回滚已产生的用量与审计**——预览页必须把这句话写出来，避免管理员以为能“一切复原”。

## 5. 组管理

### 5.1 组列表 `/admin/groups`

**用途**：维护批量控制单元。组 = 一组策略 + 一批成员（总纲 2.6）。

**关键字段**：组名、描述、是否默认组、成员数、授权抽象模型数、策略摘要（限额）、创建时间。

**主要操作**：新建、编辑、复制、删除、设为默认组。

**为什么支持"复制组"**：组策略常常是一组模板（例如"新手上限"）， 手工重配一遍容易漏项。复制是把"策略是一组整体"这个语义落到界面上的最低成本方式。

### 5.2 组详情 `/admin/groups/:id`

**用途**：单个组的成员、模型授权、策略。

**关键字段**：

| 分区 | 字段 |
|---|---|
| 基本信息 | 组名、描述、是否默认组 |
| 成员 | 账户列表（增删；成员必须是带 `tenant` 类的账户） |
| 模型授权 | 可选抽象模型多选列表 |
| 放开类策略 | 可访问的抽象模型、能否建 Key、Key 数量上限、Key 白名单能否放宽、能否使用某类抽象模型 |
| 限制类策略 | 每人日 / 月 token 上限、每人 RPM / TPM / 并发上限 |
| 组级共享池 | 周期（日 / 月，**必填**）、计量方式（`requests` 次数 / `tokens` 用量）、上限值、当期已用、当前周期锚点 |

**组级共享池这一块在界面上必须显式回答的三个问题**：

| 界面元素 | 为什么必须有 |
|---|---|
| 周期（日 / 月）是**单选且必填**，不给"默认"这回事 | 管理员看到"全组 500"时无从判断 500 是今天还是这个月的，而这两个配置的严格程度差 30 倍（[../security/03-groups.md](../security/03-groups.md) 第 4 节） |
| 计量方式**二选一**，且与个人额度的标记并列显示 | 次数的池与 token 的池消耗速度完全无关，混在一个数字里无法预测；同一组允许同时配两条，此时界面上要显示成"两行、都要满足"，而不是"合并成一个" |
| 当期已用 / 上限 + **所属周期与重置时刻** | 只显示 `120 / 500` 会让管理员以为这是累计值；必须让人一眼看出"什么时候归零"。归零是**惰性**的（下一次被用到时），所以展示的是"周期锚点 + 下个锚点"而不是一个倒计时秒数 |

**三种组合用"独立输入"呈现，不用"模式选择器"。** 具体形态：每人上限一组输入框（可留空 = 不设），
共享池一块（可"不设" / 设一行或两行），两者互不约束。为什么不做"仅个人 / 仅共享 / 两者都设"的三选一模式：

| 方案 | 问题 |
|---|---|
| **三选一模式选择器**（否决） | ① 它与"可单用、可并用"的语义是**重复表达**——模式本身不携带任何信息，只是两个开关的排列组合，却多出一个必须被维护的 UI 状态；② 切换模式会让另一侧的已填值变成"隐藏但可能仍生效"的幽灵配置，最难排查；③ 后续新增第三种限制（如"每 Key 上限"）时，模式数会爆炸成排列组合 |
| **独立输入**（选定） | 每个限制只有"设了 / 没设"两种状态，与数据层的"无行 / 有行"一一对应（[../architecture/05-storage.md](../architecture/05-storage.md#33-组与授权)），界面上看到什么就是数据库里有什么 |

留空即"不设"而不是"填 0 表示不设"：`0` 在语义上是"零额度"（全拒），与"不设"（不构成闸）是完全相反的两件事，
用一个值表达两种含义必然有人填错。

**池与其他额度在界面上的关系**：个人上限与共享池是**交集**（[../PLAN.md](../PLAN.md) 2.6、[../README.md](../README.md) 术语表）。
因此界面上不做"取最严"的自动收缩——两个数字都原样呈现，并加一句说明"个人额度用完只停这个人，池子用完全组都停"。
为什么不做自动收缩：收缩会隐藏管理员自己填的那个数，之后没人能解释"为什么显示 150 而我填的是 500"。

**成员看不到池，界面上也不提供任何"给成员看"的开关**：组是管理员视角的控制单元，成员之间互不可见（PLAN 2.6、
[../README.md](../README.md) 术语表）。池余量 `已用 / 上限` 是**全组总消耗**，成员看到它就知道"别人用了多少"。
成员在池耗尽时只会收到 `pool_exhausted` 的文案（说明是**组级**限制即可，不说谁用掉的）。
为什么不做成可配开关：一个"允许成员看池余量"的开关，等于把一个与 PLAN 1.1 冲突的选项留给管理员去误开。

**为什么组详情里不放"组用量明细"表**：池的权威数字在服务端一条条件 `UPDATE` 上（[../architecture/05-storage.md](../architecture/05-storage.md#74-组级共享池的并发扣减与惰性重置)），
界面读到的只是某一刻的快照，且会因在途请求而略滞后。放一张明细表会诱导管理员把"界面上的数"当成"闸门的数"，
从而在两次刷新之间反复质疑"为什么还能请求"。这里只显示汇总数字，逐请求明细与对账口径去 [租户端页面](04-tenant.md) 与 [审计分册](../security/06-audit.md)。

**主要操作**：

| 操作 | 二次确认 |
|---|---|
| 增删成员 | 否 |
| 改模型授权 | **是**（⚠️ 会立即改变一批人的可见模型） |
| 改限额策略 | **是**（⚠️） |
| **调小**共享池上限 | **是**（⚠️ 且文案说明"已用量不受影响，超额部分不追扣"） |
| 重置共享池当期已用 | **是**（⚠️ 且记录操作人；用于应急开闸） |
| 改放开 / 限制类开关 | **是**（⚠️） |
| 删除组 | **是**（⚠️ 成员退回默认组，总纲"删组不删人"） |

**为什么改策略要二次确认，增删成员不要**：改策略是**一对多**的广播动作， 一次误操作会同时影响组内所有人；增删成员是单人动作，且可立即撤销。

**为什么"调小池子上限"与"重置已用"都要二次确认，且文案不同**：调小上限是**立即生效的关闸**——
当已用已超过新上限时，全组下一个请求就会被拒，这是管理员最可能的误操作方向（想"收紧一点"，结果直接停组）；
文案必须说清"不追扣已用量"，否则管理员会以为系统会倒扣或报错。重置已用则是**唯一的开闸手段**，
它把 `pool_used` 清零（[../security/03-groups.md](../security/03-groups.md) 第 4 节"池子耗尽的错误码与文案"），
属于绕过正常周期的人工干预，必须留操作人以便事后解释"这个组这个月为什么超了"。

**为什么删除组要提示"成员退回默认组"**：这是总纲定的降级路径， 用户必须知道删组的后果是"降级"而不是"这些人没权限了"， 否则管理员会不敢删组，导致组越积越多。

**为什么界面不显示"组用量汇总"以外的团队类信息**：总纲 1.2 的表格里， 组与团队的关键差异是"全站一个端点""成员不知道彼此""组不持有 Key 或凭据"。 界面必须避免出现"组端点""组密钥""组邀请"这三类元素， 它们是把组误做成团队的最短路径。

## 6. 真实模型目录 `/admin/real-models`

**用途**：池内管理。真实模型的增减**不动对外契约**（总纲 3.6）。

**关键字段**：

| 字段 | 可改 | 说明 |
|---|---|---|
| 限定名 | 只读 | `dsh:渠道/上游模型 id`（总纲 11.2） |
| 显示名 | ✅ | 仅管理端可见的别名 |
| 分组 | ✅ | 目录里的归类 |
| 上下文窗口 / 模态 / 思考档位 | ✅ | 从上游 `GET /v1/models` 自动发现，管理员可覆盖 |
| 来源 | 只读 | `auto` / `override`（管理员改过后刷新不覆盖） |
| 状态 | ✅ | 含 `missing` |
| 隐藏 | ✅ | 在候选编辑里折叠 |
| 排序 | ✅ | 置顶 |
| 最后出现时间 | 只读 | 上游目录连续 N 天未出现 → 自动标 `missing` |

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 刷新目录 | 重新拉上游 `GET /v1/models` | 否 |
| 编辑覆盖 | 写 `source=override`，刷新不再覆盖 | 否 |
| 处理 `missing` | 二选一：一键弃用（跳转抽象模型弃用页）/ 忽略 | **是**（⚠️ 弃用会产生对外可见的头） |
| 排除出候选 | 默认排除 `aggregate/*`（总纲 1.4） | 否 |

**为什么"一键弃用"要跳到抽象模型的弃用页而不是就地完成**： 弃用是**抽象模型**层的动作（`abstract_models.status`）， 在真实模型目录里就地改会绕过替代链的环检测与深度校验（总纲 3.5）。 强制跳转保证所有弃用都走同一套校验。

**为什么 `aggregate/*` 的排除是默认而不是可选项**：总纲 1.4 把它定为硬约束， 理由是"我们的策略与上游的策略叠在一起，出问题无法归因"。 界面把它显示为默认勾选且带说明，允许管理员看到"为什么这里没有 22 个模型"。

## 7. 抽象模型

### 7.1 列表 `/admin/abstract-models`

**关键字段**：对外名（`smart` / `fast`）、显示名、状态、候选数、可用候选数、是否在某组的授权里、弃用链深度。

**主要操作**：新建、编辑、复制、进入候选集 / 弃用配置、查看"被哪些组引用"。

**为什么列表里要显示"可用候选数"**：状态是 `active` 但候选全部不可用， 对外表现就是 `no_candidate` 503。这个差值必须在列表就能看出来， 否则管理员只会在用户报障后才发现。

### 7.2 抽象模型编辑 `/admin/abstract-models/:id`

**用途**：定义对外模型的名称、能力声明、策略链。

**关键字段**：

| 字段 | 说明 |
|---|---|
| 对外名 | 客户端请求时用的名字，创建后**不可改**（改等于换了一个模型） |
| 显示名 | 管理端可读别名 |
| 能力模式 | **严格模式**（默认，取候选最小值）/ **过滤模式**（取并集 + 路由前筛掉不支持的候选） |
| 能力声明 | 上下文窗口、最大输出、视觉 / 工具调用 / JSON mode |
| 策略链 | 排序链，可组合多个排序键 |

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 改能力声明 | 严格模式下多数值由候选集推导，只读 | 否 |
| 切换能力模式 | 严格 ↔ 过滤 | **是**（⚠️ 面向所有客户端的语义变化） |
| 编辑策略链 | 从可用排序键里选并排序 | **是**（⚠️ 直接改变路由结果） |
| 保存前干跑 | 用历史请求回放验证候选可达（总纲第 13 章对策） | 不适用 |

**为什么"保存前干跑"是操作而不是可选项**：总纲第 13 章把"抽象模型策略配错 → 全站不可用" 列为风险，对策就是干跑。既然它是风险对策，就必须是保存路径上的强制步骤， 而不是一个管理员可能忘记点的按钮。

**为什么"对外名不可改"**：契约的稳定性来自名字。改名等于把旧名字的所有客户端 一次性打断，而 RFC 9745 提供的正确手段是**弃用 + 替代链**。 界面不给改名，是把管理员推向唯一正确的路径。

### 7.3 候选集编辑 `/admin/abstract-models/:id/candidates`

**用途**：声明该抽象模型的候选来源。

**关键字段**：

| 字段 | 说明 |
|---|---|
| 真实模型 | 从真实模型目录选择（`aggregate/*` 默认不可选） |
| 渠道范围 | 限定可用渠道（如仅 `contributed` 或全部） |
| 约束 | 该候选的附加条件（如必须支持某能力） |
| 权重 | 供加权类排序使用 |
| 可用性预览 | 声明式候选 → 当前可用的凭据实例数量 |

**主要操作**：增删候选、调权重、调渠道范围、查看"当前可展开的实例数"。

**为什么必须显示"声明式候选 → 可用实例"的展开预览**：总纲 3.2 明确 "候选集是声明式的，不绑定具体凭据。运行时才展开成候选 × 可用凭据实例再排序"。 如果界面只显示声明，管理员无法知道某条候选实际上有没有凭据支撑—— 这正是"配了但永远选不中"的静默故障来源。

**危险操作与二次确认**：增删候选与调权重都需要 **⚠️ 二次确认**， 因为它们直接影响线上路由；确认框里必须显示"当前有多少请求正在使用被移除的候选"。

### 7.4 弃用与替代链预览 `/admin/abstract-models/:id/deprecation`

**用途**：配置三态（`active` / `deprecated` / `disabled`）与替代链。

**关键字段**：

| 字段 | 说明 |
|---|---|
| 状态 | `active` / `deprecated` / `disabled` |
| 替代目标 | 一跳（管理员只配一跳，总纲 3.5） |
| `Deprecation` 时间 | RFC 9745 Structured Field Date |
| `Sunset` 时间 | RFC 8594 HTTP-date；**可选**，不设 = 永久兼容壳 |
| 迁移文档链接 | 用于 `Link: rel="deprecation"` |
| 链预览 | `old → mid → new`，标注总跳数与最终 active 落点 |
| 能力校验结果 | 替代目标的能力是否逐项 ≥ 原模型 |

**主要操作**：

| 操作 | 校验 | 二次确认 |
|---|---|---|
| 保存弃用配置 | 环检测 + 深度 ≤ 5 + 能力逐项 ≥ | **是**（⚠️） |
| 设为 `disabled` | 立即 404 / 410 Gone | **是**（⚠️） |
| 取消弃用 | 回到 `active` | 否 |

**为什么预览必须显示"最终 active 落点"而不是只显示一跳**： 总纲 3.5 定"`Link: rel="deprecation"` 必须指向最终 active 目标，不能指向中间节点"。 管理员配一跳，但客户端看到的是链尾。如果界面只显示一跳， 管理员无法发现"我这个 `old` 实际上会跟到第三手新模型"——而这正是客户端迁移时会踩的坑。

**为什么能力校验的结果要在页面上实时显示**：总纲 3.5 规定能力不足时 "**禁止保存**这条弃用配置"。如果只在保存时弹一个错误， 管理员要反复试。实时显示可以让他在选替代目标的那一刻就知道行不行。

**为什么深度 > 2 跳要告警**：总纲 3.5 明确"深度 >2 跳时告警管理员「迁移链过长，建议收敛」"。 告警必须是页面内的持续提示，而不是一次性 Toast。

## 8. 上游与凭据

### 8.1 上游 `/admin/upstreams`

**用途**：管理渠道。`kind` 有两种：`dshgateway` / `contributed`（总纲第 10 章）。

**关键字段**：

| 字段 | 说明 |
|---|---|
| 类型 | `dshgateway`（复用 providers-hub 池）/ `contributed`（贡献者凭据） |
| 名称 | 可读名 |
| base_url | 上游地址。**`dshgateway` 必须是 `127.0.0.1:8326`**（总纲 5.3 唯一出口原则） |
| 归属 | `owner_account_id = NULL` 表示平台自有（总纲 4.2） |
| 启用 | 开关 |
| 最后连通时间 | 健康信号 |

**主要操作**：新建、编辑、启用 / 禁用、测试连通性。

**为什么 `dshgateway` 类型的 base_url 在界面上被锁定为回环地址**： 总纲 5.3 的"唯一出口原则"是硬约束（上游拒绝通配地址）。 把它做成可编辑字段等于给管理员留了一个必然失败、且会破坏归因的配置项。

**危险操作与二次确认**：禁用上游需要 ⚠️ 确认，且必须显示"当前有多少候选依赖该上游"。

### 8.2 凭据池 `/admin/credentials`

**用途**：查看与维护所有上游凭据（平台自有 + 贡献）。

**关键字段**：

| 字段 | 说明 |
|---|---|
| 归属 | 账户显示名，或"平台自有" |
| 供应商 | 供应商标识 |
| 外部标签 | `external_label` |
| 状态 | 启用 / 暂停 / 封禁 |
| 登录可用 | `login_enabled`（能否用于 OAuth 登录） |
| 鉴定判定 | `verified` / `suspect` / `unverified` / `trusted` |
| 创建时间 / 最后使用 | 用于判断"僵尸凭据" |

**明文永不显示**（总纲 9.4）。界面上连"查看"按钮都不提供——
**为什么**：任何"点击查看明文"的实现都会留下一条可被利用的路径 （截图、浏览器缓存、审计日志），而它带来的便利为零。

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 暂停 / 恢复 | 候选级熔断的手动版（总纲第 13 章） | 否 |
| 封禁 | 永久不可用 | **是**（⚠️） |
| 删除 | —— | **不提供**（改为封禁） |
| 通知贡献者 | 暂停时给贡献者提示 | 否 |

**为什么"暂停"和"封禁"是两个动作**：暂停对应"这个凭据现在被上游限流了， 过一会可能恢复"，封禁对应"这个凭据被上游封了或者鉴定判为 `suspect`"。 语义不同，恢复路径也不同。合并成一个"禁用"会让贡献者无法理解发生了什么。

## 9. 鉴定队列与复检 `/admin/verifications`

**用途**：模型鉴定（防假模型）的结果处理与复检跟进。

**关键字段**：

| 分区 | 字段 |
|---|---|
| 队列项 | 凭据、供应商、声称的模型、提交时间、来源（新贡献 / 复检） |
| 流水线进度 | L0 形式校验 / L1 标准鉴定 / L2 深度鉴定（抽检） |
| 判定 | `verified` / `suspect` / `unverified` / `trusted` |
| 证据 | 各信号的得分、命中 / 未命中的具体项 |
| 复检历史 | 历次得分与下跌告警 |

**主要操作**：

| 操作 | 说明 | 二次确认 |
|---|---|---|
| 查看证据 | 只读明细 | 否 |
| 手动触发 L2 | 对可疑项跑深度鉴定 | 否 |
| 复核并改判 | 人工覆盖自动判定 | **是**（⚠️ 且必须填写理由，进审计） |
| 加入 / 移出复检队列 | 定时复检 + 回归告警（总纲 4.4） | 否 |
| 通知贡献者 | 把判定与证据推给贡献者 | 否 |

**为什么判定为 `suspect` 时界面必须同时给证据**：总纲 4.4 的表格里 `suspect` 的处置是"拒绝并给证据"。给不出证据的拒绝会被贡献者理解为系统故障， 而证据也是贡献者申诉的唯一依据。

**为什么"人工改判"必须填理由**：鉴定是安全链路的一环， 人工覆盖自动结论是一个需要事后解释的动作。理由会进审计。

**为什么"冷门模型放行"要在队列里有独立标记**：`unverified` 是**放行**的 （总纲 4.4：默认放行、标「未鉴定」、进复检队列）。如果界面把它和 `suspect` 渲染成同一种"红色异常"，管理员会倾向去处理它，等于把放行策略又收紧回去。

## 10. 审计日志 `/admin/audit`

**用途**：append-only 的只读审计。总纲 9.5 要求覆盖管理操作、鉴权失败、 额度熔断、上游错误、提权事件、组的变更、凭据的增删。

**关键字段**：时间、`account_id`、`acting_class`、`elevated`、动作、目标、IP、UA、结果、详情。

**主要操作**：筛选（时间 / 账户 / 权限类 / 动作 / 结果 / 是否提权）、导出、查看单条详情。

| 约束 | 为什么 |
|---|---|
| 无删除、无编辑 | append-only 的价值全在"不可改" |
| 提权事件单列过滤项 | 总纲 9.5 要求提权事件可分离观察 |
| 详情不记录请求正文 | 总纲 9.5：默认不记录正文；排查时开脱敏模式并在 UI 明示 |
| 脱敏模式在页面上有显著横幅 | 管理员必须知道自己正在看一个"保留结构、抹掉文本"的视图 |

**为什么审计页不提供"清空"**：哪怕加二次确认也不行。 审计的用途是事后追溯，一个可以被管理员清空的审计等于没有审计。

## 11. 全局设置 `/admin/settings`

**用途**：全站配置项。

**关键字段**（分组）：

| 分组 | 配置项 |
|---|---|
| 注册 | 是否开放注册、注册 IP 限速阈值 |
| 默认值 | 默认组、新建 Key 的默认日 / 月额度与并发上限、全局兜底上限 |
| 熔断 | 全站当日预算上限（总纲 9.1 第 3 条） |
| 观测 | 是否记录请求正文（默认关，开启即脱敏模式）、异常用量告警阈值 |
| 安全 | `TRUSTED_PROXIES`（未配则忽略 `X-Forwarded-For`）、会话有效期（**不做** IP 允许列表，2026-10-19 定案） |
| 响应 | 调试响应头 `x-fr-trace` 的开放范围（管理端 / 特定组） |

**主要操作**：编辑并保存；恢复默认；查看"上次修改人与时间"。

**危险操作与二次确认**：以下每项都要 ⚠️ 二次确认：

| 配置 | 为什么要确认 |
|---|---|
| 关闭注册 | 立刻切断新增账户 |
| 全局熔断阈值 | 配错会导致全站拒绝 |
| `TRUSTED_PROXIES` | 配错会让 IP 限速失效或误封（总纲第 13 章） |
| 开启请求正文记录 | 直接把用户内容纳入存储 |
| `TRUSTED_PROXIES` 以外无自锁风险项 | — |

**为什么这里不再有「我现在就在这个列表里吗」的自检**：管理面不提供 IP 允许列表（2026-10-19 定案，见总纲 9.3）。曾经考虑过这个功能，但它是我方**唯一能让管理员把自己锁在外面**的配置；公网形态下管理员 IP 会变，而管理员被锁在外面的恢复手段只有改配置文件重启。补偿手段是类级提权 + 登录退避 + 审计。

## 12. 待定项

> **待定**：管理端是否需要"操作撤销"（例如组策略改错后一键回滚）？ 总纲只给了账户合并的 `reversible_until`，其余操作都是"改回去"。 若要统一引入，需要先定审计与回滚的关系。

> **待定**：鉴定证据对贡献者展示到什么粒度？总纲 4.4 说 `suspect` 要"给证据"， 但强信号的**具体探测方法**如果被完整披露，会变成绕过指引。需要定一个披露边界。

> **待定**：`/admin` 的默认落地页是否需要可配置（按权限类/按习惯）？ 当前固定为审核队列（总纲第 13 章的对策）。

> **待定**：凭据池里"平台自有凭据"是否需要第二个管理员复核才能操作？ 它不属于任何账户，出问题时没有"贡献者"可以追责。

> **待定**：审计日志的保留期与导出格式。append-only 但没有保留策略， 长期会让 SQLite 单文件无限增长。
