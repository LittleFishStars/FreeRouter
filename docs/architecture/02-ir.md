# IR 与四协议转换

IR（中间表示）是 FreeRouter 内部**唯一的请求与响应表示**。本册定义它的数据结构、流式事件、
四个入站协议与它的双向映射，以及"能力缺失怎么办"的判定规则。

---

## 1. 为什么要有 IR

### 1.1 N×M 问题

入站协议 4 个（OpenAI Chat Completions / OpenAI Responses / Anthropic Messages / Gemini
generateContent），上游协议至少 2 个形状（OpenAI 兼容、以及未来可能的其它形状）。
若让每对入站/上游直接互转，组合数是 4×M；引入 IR 后是 4+M。

**为什么这对本项目尤其重要**：协议转换不是"翻译字段"，还包括**能力判定**（C6：缺能力要 400）。
如果转换逻辑散在各处，能力判定就像补丁一样散在各处，必然漏项。IR 把判定点收敛到一处：
"入站解析成 IR 时"与"IR 编码成上游请求时"。

### 1.2 IR 的取舍原则

| 原则 | 含义 | 为什么 |
|---|---|---|
| **够富** | 能无损表达四个协议里我们**选择支持**的全部语义 | 表示不了的语义只能丢弃，而丢弃就是静默降级 |
| **不做超集** | 不支持的语义显式拒绝，不"预留字段" | 预留字段会诱使下游写出"有就用、没有就算了"的代码 |
| **三态表达** | "不支持"、"未指定"、"明确为零"必须可分 | 见第 9 节，这是计量与行为正确性的基础 |
| **协议无关** | IR 里不出现任何协议原生字段名 | 出现即意味着某处映射缺失，且会污染路由核心 |

## 2. 消息模型

### 2.1 结构

```go
type Role string

const (
    RoleSystem    Role = "system"
    RoleUser      Role = "user"
    RoleAssistant Role = "assistant"
)

type Message struct {
    Role  Role
    Parts []Part
}

type PartType string

const (
    PartText       PartType = "text"
    PartImage      PartType = "image"
    PartToolCall   PartType = "tool_call"
    PartToolResult PartType = "tool_result"
    PartThinking   PartType = "thinking"
)

type Part interface {
    PartType() PartType
    // Index 是 parts 在所属消息内的序号，用于错误定位与流式重组
    Index() int
}
```

### 2.2 为什么只有三种 role

四个协议对"谁说的话"表达方式不同：

| 协议 | 系统提示 | 工具结果 |
|---|---|---|
| OpenAI Chat | `messages[].role = "system"` | `role = "tool"` + `tool_call_id` |
| OpenAI Responses | 顶层 `instructions` | `function_call_output` item |
| Anthropic | 顶层 `system` 参数 | `user` 消息里的 `tool_result` block |
| Gemini | `systemInstruction` | `functionResponse` part |

三种 role 是四者的公共子集：**系统提示统一提升为一条 `RoleSystem` 消息**（因为它在四个协议里
都位于对话之外），**工具结果用 `tool_result` part 承载并保持在 `RoleUser` 消息里**
（Anthropic 的形状，同时也是最能表达"工具结果是内容而非说话人"的形状）。

**为什么不设 `RoleTool`**：设了以后，"一条 user 消息里同时有文本和工具结果"（Anthropic 允许、
Gemini 也允许）就没有合法表示，只能拆成两条消息，然后在映射回 Anthropic 时再合并——多一次
有损往返。这属于"预留字段"的反面教材。

### 2.3 parts 的顺序与 index

`parts` 顺序**有意义**（文本与图片的相对位置影响多模态理解），映射到任何协议都必须保序。
`Index()` 返回按序计算的序号，由解析层填充一次，之后不再改。

**为什么 index 由我们计算而不是复用协议给的 index**：Anthropic 给 `content_block` index，
OpenAI 给 `tool_calls[].index`，Gemini 根本没有。由我们统一编号，才能让错误信息
（"第 3 个 part 的图片不被该模型支持"）在四个协议里语义一致。

## 3. parts 类型

### 3.1 text

```go
type TextPart struct {
    Idx  int
    Text string
}
```

空字符串的 text part **允许存在**但不参与上游编码（映射时可省略）。**为什么允许**：某些客户端会
发空的 assistant 消息作为占位，拒绝它会让别的部分正常的历史对话整体失败。

### 3.2 image

```go
type ImagePart struct {
    Idx    int
    MIME   string // image/png | image/jpeg | image/webp | image/gif
    Data   []byte // 已解码的原始字节
    Detail string // "" | "low" | "high" | "auto"（协议方言，见下）
    Source ImageSource // inline | url
    URL    string      // Source == url 时有效
}
```

| 决策 | 理由 |
|---|---|
| 内部保存**原始字节**而不是 base64 字符串 | base64 膨胀 4/3；一次解码后多处复用（能力探针、鉴定流水线、重试编码） |
| 保留 `Source` | 上游若支持 URL 直取，可避免我们中转大对象；不支持时退回内联 |
| `Detail` 保留原样字符串而不枚举 | 各家方言不同（OpenAI `detail`、Anthropic 无此概念、Gemini 用 `mediaResolution`）。用枚举会强行归一，归一不了的就得丢——丢就是静默降级 |

### 3.3 tool_call

```go
type ToolCallPart struct {
    Idx       int
    ID        string // 稳定 id，流式下由 index 重组得出（见第 6 节）
    Name      string
    Arguments string // 上游给的 JSON 文本，**不做解析**
    Partial   bool   // 流式过程中为 true，重组完成后为 false
}
```

**为什么 `Arguments` 不做解析**：上游可能给出非法 JSON（模型输出被截断），此时正确的行为是
把原样透传给客户端让它自己决定，而不是我们报 500。我们只在需要读参数的内部场景
（如能力探针）才尝试解析，失败则按"无法判定"处理。

### 3.4 tool_result

```go
type ToolResultPart struct {
    Idx        int
    ToolCallID string  // 必须与某个 ToolCallPart.ID 对应，否则 400
    Parts      []Part  // 允许嵌套 text / image
    IsError    bool
}
```

**为什么允许多 part**：Anthropic 的 `tool_result` 的 `content` 可以是 block 数组，能带图片
（例如截图工具的结果）。只允许字符串会让这类客户端在最常见的场景下直接失败。

**为什么 `ToolCallID` 必须在校验阶段匹配**：四个协议里"工具结果找不到对应调用"都是硬错误，
越早报错越好；等到上游返回 400 时，错误信息会指向上游而不是我们的请求，排障成本高得多。

### 3.5 thinking

```go
type ThinkingPart struct {
    Idx       int
    Text      string
    Signature string // 上游签名（Anthropic 需要回传），可空
    Redacted  bool   // 上游明确表示内容被加密/隐去
}
```

**为什么需要这个 part 而不是把 thinking 当 text**：Anthropic 要求把上一轮的 thinking block
（含 signature）原样回传才能继续推理；若混入 text，回传时会破坏签名校验。
`Redacted` 用于表达"上游说有思考但不给内容"——这是**有信息量的三态**，与"没有思考"不同。

**不能做**：不能把 thinking 文本当作普通 text 回显给不支持 thinking 的协议端点，
那会泄露模型内部状态且改变客户端行为。不支持时按第 8 节处理。

## 4. 请求对象

```go
type Request struct {
    Model    string    // 抽象模型名（L1 已解析，内核不认识真实模型）
    Messages []Message // 含 RoleSystem 的那条
    Tools    []ToolDef
    Choice   ToolChoice
    Sampling Sampling
    Format   *ResponseFormat // nil = 未指定
    Effort   Effort          // off | low | high | max | unknown | ""（未指定）
    Stream   bool
    Extra    RequestMeta     // 审计与归因用（请求 ID、account、key），不参与上游编码
}

type ToolDef struct {
    Name        string
    Description string
    Schema      string // JSON Schema 原文，不解析
    Strict      bool
}

type ToolChoice struct {
    Mode ToolChoiceMode // auto | none | required | specific
    Name string         // Mode == specific 时有效
}

type Sampling struct {
    Temperature *float64
    TopP        *float64
    TopK        *int
    MaxOutput   *int // 不同协议叫 max_tokens / max_completion_tokens / maxOutputTokens
    Stop        []string
    Seed        *int64
}

type ResponseFormat struct {
    Kind   ResponseFormatKind // text | json_object | json_schema
    Schema string             // Kind == json_schema 时有效
    Name   string
}

type Effort string

const (
    EffortUnspecified Effort = ""
    EffortOff         Effort = "off"
    EffortLow         Effort = "low"
    EffortHigh        Effort = "high"
    EffortMax         Effort = "max"
    EffortUnknown     Effort = "unknown" // 客户端给了我们不认识的档位
)
```

**为什么采样参数用指针**：`temperature: 0` 与"没给 temperature"在上游语义不同（前者是贪心，
后者用服务端默认）。用零值会把两者混为一谈，属于典型的三态丢失。

**为什么 `EffortUnknown` 必须单独存在**：各家档位方言不一（PLAN 13 风险表）。客户端给了
`xhigh` 而我们不认识时：
- 若当"未指定"处理 → **静默改变行为**（用户要的是最强推理）；
- 若直接 400 → 客户端没法用，且很多时候上游确实支持。
正确做法是标 `unknown`，交给**能力匹配**：候选声明支持哪些档位，不认识此档位的候选被过滤；
若过滤后无候选 → 503（不是 400，因为请求本身没写错）。

**为什么 `Extra` 不参与上游编码**：`account_id / key_id / request_id` 是我们的归因信息，
一旦进入上游编码路径，就有泄露给第三方上游的风险（C4 的隔离要求）。

## 5. 流式事件

### 5.1 事件类型

```go
type EventType string

const (
    EvStart          EventType = "start"
    EvThinkingDelta  EventType = "thinking_delta"
    EvTextDelta      EventType = "text_delta"
    EvToolCallStart  EventType = "tool_call_start"
    EvToolCallDelta  EventType = "tool_call_delta"
    EvToolCallEnd    EventType = "tool_call_end"
    EvUsage          EventType = "usage"
    EvError          EventType = "error"
    EvDone           EventType = "done"
)

type Event struct {
    Type  EventType
    Index int      // 内容块序号；EvStart / EvUsage / EvDone / EvError 为 0
    Text  string   // thinking_delta / text_delta
    Call  *ToolCallPart // tool_call_start / delta / end
    Usage *Usage
    Err   *Error
    // Signature 只在 EvThinkingDelta 上有意义：Text 为空、Signature 非空时是
    // “思考块收尾携带签名”的终帧（Anthropic 的 signature_delta 在块 stop 才齐）。
    // 为什么不另开事件类型：§5.1 事件集合保持封闭，新类型会迫使四个编码器都加防御分支；
    // 签名本质是 thinking 的附属元信息，挂在同一事件上最接近它的生成时机（2026-10-21 定案）。
    Signature string
    // Stop 只在 EvDone 上有意义：把结束原因带过解码→编码边界（2026-10-21 定案）。
    // 若不在 EvDone 上携带，编码器只能猜（“有工具调用就是 tool_use”），
    // 会把“模型说完了”与“被长度截断”混为一谈——两者在计费与重试决策上不同。
    Stop StopReason
}
```

**编码参数（EncodeOptions）的两个追加字段（2026-10-21 定案）**：

| 字段 | 语义 | 为什么在参数里而不在 Event 上 |
|---|---|---|
| `Stop StopReason` | 本次生成的结束原因，供编码流末帧（OpenAI `finish_reason` / Anthropic `stop_reason` 均为**流末帧必填**） | 非流式的 Response 上也有同名字段；事件流的 `EvDone.Stop` 与它同源，编码层两处消费一处来源 |
| `CreatedAt int64` | 本次生成的 Unix 秒，由路由层注入；`0` 时编码器自取时钟 | 契约 golden 必须逐字节稳定而时间戳每跳都变；时钟属运行时关注点，IR 层只消费不归因 |

**错误帧的两条定案（2026-10-21）**：① 错误体的 `type` 字段永远是 §2.4 八值枚举（见 `api/03-errors.md`），细粒度 `code` 走 `code` 字段（Anthropic 原生错误对象没有 `code`，我们**扩展**一个，§2.2 已写明理由）；type↔code 双向映射由 `ir.CodeToErrorType`/`ErrorTypeToCode` 唯一表提供，入站面与控制台面共用，不得另起第二份表。② 上游协议违规（如 I3 的 index 跨块复用）归 `UpstreamProtocolError` → 502 `upstream_error`，**不得**误报为客户端 400（谁的数据坏了谁担错）。

### 5.2 流的不变式（映射层可以依赖）

| # | 不变式 | 违反时的处理 |
|---|---|---|
| I1 | `start` 是流的第一个事件，且只出现一次 | 上游没有对应概念时由编码层合成 |
| I2 | 每个 `tool_call_start` 必有配对的 `tool_call_end` | 流在中间结束时，编码层补发 `end`（`Partial=true`） |
| I3 | 同一 `Index` 的 delta 归属同一内容块 | 上游 index 复用（跨块）视为协议违规 → `UpstreamProtocolError`（502 `upstream_error`，见 §5.1 错误帧定案） |
| I4 | `usage` 至多一次，且若存在必在 `done` 之前 | 上游给多次时取最后一次 |
| I5 | `done` 之后不再有事件 | 编码层丢弃 |
| I6 | `error` 之后只允许 `done` | 与 I5 一致 |
| I7 | 事件流按生成顺序单向交付，不做重排 | 需要重排的信息在生成侧就用 buffer 解决（第 6 节） |

**为什么把这些写成"编码层的依赖"**：四个协议对"流应该长什么样"要求不同（Anthropic 要求
`message_start` 先发、OpenAI 要求 `[DONE]` 结尾），如果上游事件的顺序不保证，每个编码器都要
自己防御，等于把这套不变式复制四遍。

### 5.3 与"可见内容"的关系

对 [06-runtime.md](06-runtime.md) 的切换状态机而言，**可见内容**定义为：

```
EvThinkingDelta | EvTextDelta | EvToolCallStart | EvToolCallDelta | EvToolCallEnd
```

即除 `start` / `usage` / `error` / `done` 之外的一切。

**为什么 `start` 不算可见内容**：它是我们合成的协议壳（Anthropic 的 `message_start`），
不携带模型产出。若把它算作可见，任何一次"上游刚建连就断"都会让请求不可恢复地失败；
而若不算，我们可以在已开始 SSE 响应的情况下换候选——只要还没写任何模型内容。

> **待定**：`thinking_delta` 是否算"可见内容"。当前按"算"处理（客户端可能已经在渲染），
> 但这意味着一个只产出 thinking 的候选失败后无法切换。这条需要在压测中用真实上游行为确认。

## 6. tool_call 的 id 按 SSE index 重组

### 6.1 问题

OpenAI 流式工具调用是分片到达的：

```
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_abc","function":{"name":"read_file","arguments":""}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"pa"}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"th\":\"/tmp\"}"}}]}}]}
```

各上游实现不一致，实测存在几种变形：

| 变形 | 说明 |
|---|---|
| 首片带 id | 规范形态 |
| 首片**不带** id，后续某片才带 | 部分上游把 id 放在参数之后 |
| 只有首片带 id | 最常见；后续片完全没有 id 字段 |
| 每片都重复 id | 幂等，可直接取首个 |
| `name` 也被分片 | 少数实现会把函数名拆开 |
| 多 index 交错 | 并行工具调用，`index=0` 与 `index=1` 的事件交错到达 |

若按"到达顺序"或"每片重建 id"，会得到凭空生成的 id（客户端无法把结果对回调用），
表现为"工具调用错乱"（PLAN 13 已列为风险）。

### 6.2 重组规则

以 `Index` 为唯一键，维护每流一份的缓冲表：

```go
type toolCallBuffer struct {
    Index     int
    ID        string
    Name      string
    Arguments strings.Builder
    Started   bool
    Bytes     int
}
```

| 情形 | 处理 |
|---|---|
| 某 index 首片带 `id` | 记为该 index 的权威 id |
| 后续片带 `id` 且与权威 id **相同** | 忽略 |
| 后续片带 `id` 且与权威 id **不同** | 保留首个为权威，记 `warn`（可能是上游复用 index 的错误） |
| 首片无 `id` | **暂不发出** `tool_call_start`，继续缓冲 |
| 缓冲期间拿到 `id` | 立即发出 `tool_call_start`（含已缓冲的 name 与已有 arguments 片段） |
| 流结束仍无 `id` | 用确定性合成 id：`call_{request_id}_{index}`（同一次请求内稳定，可对账） |
| `name` 分片 | 拼接；`tool_call_start` 在 name 确定前不发 |
| 缓冲超过阈值（默认 8 KiB 或 2s） | 放弃等待，用合成 id 发出 `start`，避免内存被恶意上游拖爆 |
| 同一 index 出现第二个 `name`（非分片） | 视为协议违规 → `error` 结束 |

**为什么"推迟发出 start"是对的**：C7 要求已吐可见内容后不能切换候选；若我们先用合成 id
发出 `tool_call_start`，后面拿到真 id 就无法回头改（客户端已经收到）。推迟发 start 把
"等 id"的成本限制在缓冲里，而缓冲的失败成本只是延迟。

**交付语义（2026-10-21 定案）**：`tool_call_end` 携带的 `arguments` 是**全量拼接结果**，
与 `start` 前缀 + 全部 `delta` 之和逐字节相等（`start('{"ci') + delta('ty":"北京"}') = end('{"city":"北京"}')`）。
下游可任选其一消费，也可断言两者相等作上游真实性探针对；消费方**不得假设 end 只携带尾段增量**。
实现与 golden 证据见 `internal/ir/toolcall.go` 注释与 `testdata/openai/request_tools.*`。

**为什么 id 不依赖到达顺序**：`index` 是协议内的稳定标识，而到达顺序受网络分片、上游并发写
影响。用 index 做键，即使 0/1 交错也能各自正确重组。

**为什么合成 id 要带 `request_id`**：若两台并发请求都产生 `call_..._0`，客户端日志与会话
记录会混淆。带请求 ID 后 id 全局唯一且可反查归因。

## 7. 四协议双向映射

### 7.1 汇总表（入站解析方向）

| 概念 | OpenAI Chat Completions | OpenAI Responses | Anthropic Messages | Gemini generateContent | → IR |
|---|---|---|---|---|---|
| 系统提示 | `messages[].role=system` | 顶层 `instructions` | 顶层 `system` | `systemInstruction` | `RoleSystem` 消息 |
| 用户文本 | `messages[].content`（字符串） | `input[].content[].input_text` | `content[].text` | `contents[].parts[].text` | `TextPart` |
| 图片 | `content[].image_url.url`（data URL） | `input_image.image_url` | `image.source.base64` | `parts[].inlineData` | `ImagePart` |
| 工具定义 | `tools[].function` | `tools[]`（平铺） | `tools[].input_schema` | `tools[].functionDeclarations` | `ToolDef` |
| 工具调用（请求侧历史） | `messages[].tool_calls[]` | `function_call` item | `content[].tool_use` | `parts[].functionCall` | `ToolCallPart` |
| 工具结果 | `messages[].role=tool` | `function_call_output` | `content[].tool_result` | `parts[].functionResponse` | `ToolResultPart` |
| 思考内容 | 无（不回传） | `reasoning` item（仅 summary） | `content[].thinking`（含 signature） | `parts[].thought` | `ThinkingPart` |
| 工具选择 | `tool_choice` | `tool_choice` | `tool_choice` | `toolConfig.functionCallingConfig` | `ToolChoice` |
| 输出上限 | `max_completion_tokens` | `max_output_tokens` | `max_tokens` | `generationConfig.maxOutputTokens` | `Sampling.MaxOutput` |
| 抽取温度 | `temperature` / `top_p` | 同左 | `temperature` / `top_p` / `top_k` | `generationConfig.temperature` / `topP` / `topK` | `Sampling` |
| 停止词 | `stop` | —— | `stop_sequences` | `stopSequences` | `Sampling.Stop` |
| 结构化输出 | `response_format` | `text.format` | 无原生（走工具） | `responseMimeType` + `responseSchema` | `ResponseFormat` |
| 思考档位 | 部分模型 `reasoning_effort` | `reasoning.effort` | `thinking.budget_tokens` | `thinkingConfig.thinkingBudget` | `Effort` |

**为什么 `thinking.budget_tokens` 要归一到 `Effort`**：providers-hub 的目录条目给的是
`reasoning.efforts`（`off/low/high/max`），说明档位是上游可查询的离散集合。把它归一成枚举
才能做能力匹配；若保留各家原始数值（budget tokens），候选之间就不可比，过滤无从下手。

> **待定**：`thinking.budget_tokens` → `Effort` 的映射阈值（多少 token 算 `low` / `high`）。
> 需要一个实测表，否则映射是拍脑袋的。当前先按"客户端给 budget → 映射到最接近的档位 +
> 记 `warn`"处理。

### 7.2 汇总表（响应编码方向：IR → 协议）

| IR 事件 | OpenAI Chat Completions | OpenAI Responses | Anthropic Messages | Gemini |
|---|---|---|---|---|
| `start` | （无显式帧，首个 chunk 隐含） | `response.created` | `message_start` | （无，首个 chunk 隐含） |
| `thinking_delta` | 不输出（协议无位） | `response.reasoning_summary_text.delta` | `content_block_delta` / `thinking_delta` | `parts[].thought` 增量 |
| `text_delta` | `choices[].delta.content` | `response.output_text.delta` | `content_block_delta` / `text_delta` | `parts[].text` 增量 |
| `tool_call_start` | `delta.tool_calls[]`（含 id/name） | `response.output_item.added` | `content_block_start` / `tool_use` | `functionCall`（一次性） |
| `tool_call_delta` | `delta.tool_calls[].function.arguments` | `response.function_call_arguments.delta` | `content_block_delta` / `input_json_delta` | 拼接后一次性给出 |
| `tool_call_end` | 滚到下一 index | `response.output_item.done` | `content_block_stop` | —— |
| `usage` | `usage`（需 `stream_options.include_usage`） | `response.completed` 内 | `message_delta.usage` | `usageMetadata` |
| `error` | `data: {"error": ...}` | `response.failed` | `error` 事件 | 错误对象 |
| `done` | `data: [DONE]` | `response.completed` | `message_stop` | 流结束 |

**为什么 Gemini 的 `functionCall` 是"一次性"**：Gemini 的流式把函数调用作为完整 part 给出，
不支持参数分片。这意味着 IR 的 `tool_call_delta` 在编码到 Gemini 时必须**缓冲到 `end`** 再发。
这条约束反过来影响实现顺序：Gemini 入站的工具调用**不能**用增量编码，必须走缓冲。

> **待定**：Gemini 是否接受 `alt=sse` 的流式形态作为入站（而非 JSON 数组流）。这决定
> `/v1beta/models/{m}:generateContent` 的 `streamGenerateContent` 是否复用同一套 SSE 编码器。

## 8. 能力缺失时不静默降级

### 8.1 总则

**IR 里存在、而目标不支持的东西，只有两种合法处置：**

1. **过滤候选**：把不支持该能力的候选从候选集中剔除（需要抽象模型处于过滤模式，见 PLAN 3.4）；
2. **明确报错**：400，并指出**哪一个 part、缺哪个能力**。

**唯一不允许的是"丢掉它继续跑"。**

### 8.2 为什么不能丢

| 丢掉什么 | 客户端会看到 | 实际后果 |
|---|---|---|
| 图片 | 请求成功，模型对着空气回答 | 用户以为模型不会看图，实则是我们没传 |
| `tool_use` | 请求成功，但模型不调用工具 | 编码任务静默失败，用户排查自己的代码 |
| `json_schema` | 请求成功，返回非结构化文本 | 客户端解析崩溃，错误指向客户端 |
| `thinking` 回传 | 请求成功，但模型失忆 | 多轮推理质量下降，无从归因 |

四者都是"错误在最不该出现的地方暴露"。PLAN 6.1 明确"绝不悄悄丢图片 / 丢 `tool_use`"。

### 8.3 判定表

| 缺失项 | 严格模式（默认） | 过滤模式 |
|---|---|---|
| 图片，候选无视觉 | 400 `capability_missing` | 剔除该候选；全被剔 → 503 |
| `ToolDef` 非空，候选不支持工具 | 400 `capability_missing` | 同上 |
| `ThinkingPart` 回传，候选不支持 thinking | 400 `capability_missing` | 同上 |
| `Format.Kind = json_schema`，候选不支持 | 400 `capability_missing` | 同上 |
| `Effort` 非空且候选中无该档位 | 400 `capability_missing` | 同上 |
| 上下文超候选窗口 | 400 `context_too_long` | 剔除；全被剔 → 503 |
| `Sampling.TopK` 有值，候选不支持 | **忽略并 warn** | 忽略并 warn |
| `Stop` 项目数超候选上限 | 400 `invalid_request` | 同上 |

**为什么 `TopK` 是例外**：它是采样细节，丢弃只影响生成多样性，不改变"模型做了什么"。
把它当硬能力会让大量 OpenAI 协议的客户端（它们不发 top_k）与支持 top_k 的客户端走上完全
不同的失败路径，收益为零。**例外清单必须短且逐条有理由**，否则它会变成静默降级的后门。

**为什么"上下文超窗"不是 503**：这是请求本身的属性（消息太长），换个候选可能就好了，
所以严格模式下报 400 让客户端自己缩短；过滤模式下剔除候选后如果还有别的候选能装下，
就应当成功——两种模式都合理，但都不能变成"截断消息后继续"（那就是静默降级）。

### 8.4 明确可忽略的字段白名单

以下字段不影响模型行为，**允许忽略并记 `warn`**：

| 字段 | 协议 | 为什么可忽略 |
|---|---|---|
| `user` / `metadata.user_id` | OpenAI | 上游用于滥用追踪，与模型行为无关 |
| `stream_options.include_usage` | OpenAI | 我们**总是**回 usage，客户端要或不要都不影响正确性 |
| `store: false` | Responses | 与我们"不落请求正文"的默认行为一致 |
| `safety_settings` | Gemini | 我们不转发安全设置，忽略等于用上游默认 |
| `cached_content` | Gemini | 我们的候选**不保证**支持缓存，忽略后行为退化但正确 |

**不在白名单里的一律按 8.3 处理。** 特别注意 `store: true`（Responses）**必须 400**：
客户端据此期望稍后能用 `previous_response_id` 取回结果，而我们是无状态转发，
静默接受会让它在检索时才发现没有——这正是"错误在最不该出现的地方暴露"。

## 9. usage 的三态

```go
type Usage struct {
    InputTokens      *int
    OutputTokens     *int
    CacheReadTokens  *int
    CacheWriteTokens *int
    ReasoningTokens  *int
    Source           UsageSource // upstream | estimated | unknown
}
```

| 值 | 含义 | 落库 | 展示 |
|---|---|---|---|
| `nil` | 上游没给这个字段 | `NULL` | 显示 `—` |
| `0` | 上游明确说是 0 | `0` | 显示 `0` |
| `Source = estimated` | 上游没给，我们自己估的 | 存值 + 标记 | 显示带「估算」标记 |

**为什么必须区分 `nil` 与 `0`**：
- 计量的正确性：把 `nil` 当 0 累加，会让"用了很多但上游不报账"的凭据看起来零消耗，
  **配额护栏失效**；
- 归因的正确性：贡献者归因（PLAN 11.4 的双向对账）按 token 数对齐，`0` 与未知不能被混淆；
- 审计的正确性：事后看账时，"未知"是一个需要追查的信号，"零"不是。

**为什么不把估算值写进同一个字段**：一旦估算与上游上报混在一起，后续任何"对不对得上账"的
判断都失效。`Source` 字段保证两类数据永远可分离。

**估算口径**：只在 `Source = estimated` 时使用，且**必须**标注。估算本身需要用独立分词器
（PLAN 4.4 把"独立 tokenizer 估算 vs 上报用量"列为中级鉴定信号，说明我们迟早要有这个能力）。

## 10. IR 的演进规则

| 规则 | 理由 |
|---|---|
| **只加不改** | 已有字段的语义改变会同时影响四个映射器与所有历史数据的解释 |
| 新增 `PartType` 时，四个映射器必须同时给出映射或"明确 400" | 否则新 part 会在某个协议上被静默处理 |
| 遇到**未知的 part type** → 400，不忽略 | 忽略未知 part 正是静默降级的定义；且未知 part 可能携带关键语义 |
| IR 不引入协议原生字段名 | 见 1.2 |
| 需要新概念时，先写进 [../README.md](../README.md) 术语表 | README 文档约定第 6 条 |
