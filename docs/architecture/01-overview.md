# 架构总览

本册回答三个问题：系统分几层、跑成几个进程、一次请求从进来到回写经过哪些环节。
IR、上游、sidecar、存储、运行时的细节分别在 [02-ir.md](02-ir.md)、[03-upstream.md](03-upstream.md)、
[04-sidecar.md](04-sidecar.md)、[05-storage.md](05-storage.md)、[06-runtime.md](06-runtime.md)，
本册只给骨架和决策理由，不重复细节。

---

## 1. 架构要满足的硬约束

这些约束来自总纲，**不是可选项**；下面每一层设计都是在满足它们。

| # | 约束 | 出处 | 对架构的强制影响 |
|---|---|---|---|
| C1 | 只做协议转换、访问控制、可观测 | PLAN 0 | 不引入队列、工作流、消息总线；请求路径上只有同步调用 |
| C2 | 对外只暴露**抽象模型** | PLAN 3.1 / 3.7 | 路由决策必须在**入站之后、上游之前**完成，且真实模型名不得出现在任何客户端可见字段 |
| C3 | 上游**只绑 `127.0.0.1`**，拒绝通配地址 | PLAN 5.2 / 5.3 | 上游客户端必须能与主进程同机部署；唯一出口原则写进适配层 |
| C4 | 多用户、多**权限类**、**隔离** | PLAN 2 | 每个请求必须携带 `account_id + acting_class + key_id` 三元归因，且这条链路不能断 |
| C5 | 单机优先（P2 才多节点） | PLAN 8 / 3.5 | 存储用 SQLite(WAL)；限速与配额是**进程内**状态 |
| C6 | 能力缺失**不静默降级** | PLAN 6.1 | 必须在解析阶段就能判断"这个请求我能不能完整履约"，不能等到中途 |
| C7 | 已吐可见内容后**不得切换候选** | PLAN 3.3 | 能否切换由运行时状态机判定，不由策略引擎判定（见 [06-runtime.md](06-runtime.md)） |

**为什么先把约束列出来**：本项目最容易犯的错是"多加一层抽象来解耦"，但 C1 明确砍掉了
队列与异步链路，C5 明确砍掉了分布式协调。任何看起来更"干净"的架构，只要引入这两种东西，
就直接违背总纲。

## 2. 分层模型

### 2.1 三层与各自边界

```
        L1 入站（公网，TLS 终止）
        ├── POST /v1/chat/completions      OpenAI Chat Completions
        ├── POST /v1/responses             OpenAI Responses
        ├── POST /v1/messages              Anthropic Messages
        └── POST /v1beta/models/{m}:generateContent   Gemini
                     │
                     ▼  鉴权 → 限速 → 配额 → 解析成 IR
        L2 内核
        ├── abstract  抽象模型：替代链解析 → 过滤 → 排序 → （未吐字时）切换
        ├── call      一次上游调用的生命周期：重试 / 超时 / 取消传播
        ├── meter     token / TTFT / 归因打标
        └── store     SQLite(WAL)
                     │
                     ▼
        L3 上游
        ├── dshgateway   → 127.0.0.1:8326（providers-hub 的 OpenAI 兼容网关）
        └── contributed  → 贡献者凭据直连
```

| 层 | 职责 | **明确不做** |
|---|---|---|
| L1 入站 | 协议识别、鉴权、限速、配额、请求体解析、响应编码与 SSE 帧格式 | 不决定"用哪个真实模型"，不做重试，不写库（除审计与日志） |
| L2 内核 | **抽象模型**解析、**策略引擎**、候选选择、重试与切换、计量、持久化 | 不认识任何 HTTP 协议细节；不知道 `tool_use` 的 JSON 形状 |
| L3 上游 | 把 IR 变成具体上游请求、连接池、健康、重试的物理实现 | 不做访问控制，不做抽象模型解析 |

**为什么 L1 不认识真实模型、L2 不认识协议**：
- L1 若知道真实模型，就等于把池结构泄露到对外契约层，C2 迟早被破（某个错误信息里带出上游 id）；
- L2 若认识协议，四协议 × 策略引擎会退化成一堆 `if protocol == ...`，加第五个协议就要改路由核心。
  分成两层后，新增协议只改 L1 + [02-ir.md](02-ir.md) 的映射表，路由核心零改动。

### 2.2 层间的唯一数据格式是 IR

层间**只**传两种东西：入站解析出的 `ir.Request`，以及上游产出的 `ir.Event` 流。
不传 `map[string]any`、不传原始字节、不传协议结构体。

**为什么**：IR 是四协议映射的公共分母（见 [02-ir.md](02-ir.md) 第 6 节）。如果某一层偷偷
传协议原生结构，映射就会从"一次性集中"退化为"每一层各自兼容"，C6（不静默降级）也就
无处可判——因为你只有到最深处才知道这个字段有没有对应物。

## 3. L1：入站层

### 3.1 中间件顺序

顺序是**固定的**，不可调换：

```
1. 恢复 / 请求 ID 注入      （最早，保证 panic 也能带 ID）
2. 安全头 + 可选 TLS       （TLS 默认关闭；非回环监听未启用时告警，见 ../ops/01-security.md）
3. 可信代理判定 → 真实 IP   （只有在 TRUSTED_PROXIES 命中时才信 XFF）
4. 请求体上限                （32 MiB，超限 413，早于读 body）
5. 鉴权                      （API Key → account + acting_class + key_id）
6. 限速                      （全局 / 按 Key / 按 IP 三维令牌桶）
7. 配额                      （日 / 月 token 上限、并发上限）
8. 抽象模型解析              （名字 → abstract_model；含禁用 / 弃用 / 替代链）
9. 协议解析 → IR             （含能力校验，失败即 400）
10. 交给 L2
11. 响应编码 → SSE / JSON    （按入站协议回写）
```

**为什么鉴权在限速之前**：未鉴权的请求连"这一发算谁的"都不知道，若先限速，攻击者可以用
无效 Key 把 IP 维度的令牌桶打空，造成对**其他**用户的拒绝服务；反过来，鉴权失败本身也是一次
可审计事件，需要在限速之前就拿到 `account_id`（或标记为匿名）。

**为什么配额在解析之前**：C6 要求能力校验失败要报 400，但"这个人今天已经没有额度了"是更便宜的
拒绝理由。先查配额可以避免为注定失败的请求做完整的 IR 解析与图片 base64 解码。

### 3.2 入站端点与协议归属

| 端点 | 协议 | MVP | 说明 |
|---|---|---|---|
| `POST /v1/chat/completions` | OpenAI Chat Completions | ✅ | 最广客户端面 |
| `POST /v1/messages` | Anthropic Messages | ✅ | Claude Code |
| `POST /v1/responses` | OpenAI Responses | P1 | |
| `POST /v1beta/models/{m}:generateContent` | Gemini | P1 | |
| `GET /v1/models` | OpenAI 形状 | ✅ | **只列抽象模型**，按 Key 可见性过滤 |
| `GET /healthz` `/readyz` | —— | ✅ | 进程 / 上游连通性分离 |

**为什么 `/v1/models` 归 L1 而不是 L2**：它必须按**合并语义**（组的并集 ∩ Key 白名单）过滤，
而这需要 `account_id`。把过滤放在入站层，L2 只提供"这个账户的可用抽象模型集合"这一个只读查询。

> **待定**：`/v1/responses` 与 Gemini 入站是否提供与 OpenAI 完全一致的错误响应形状，
> 还是各自按自家规范返回。两条都要在 [02-ir.md](02-ir.md) 与 `../api/03-errors.md` 中对齐。

## 4. L2：内核

### 4.1 四个模块与它们之间的顺序

| 模块 | 输入 | 输出 | 关键点 |
|---|---|---|---|
| `abstract` | 抽象模型名 + 请求特征 | 有序**候选**列表 | 替代链解析在最前，且只解析一次 |
| `call` | 一个候选 + IR | `ir.Event` 流 | **唯一**知道重试与切换状态机的地方 |
| `meter` | 事件流 + 候选 | 计量与归因 | 只观察，不改变流 |
| `store` | 结构化记录 | —— | 写操作绝不在持有事务时跨网络 |

处理顺序**不可交换**：`abstract` 必须先完成过滤与排序，`call` 才能在"有序列表"上做切换；
`meter` 挂在事件流上被动采样，任何"因为计量失败而返回错误"的设计都不可接受（计量是观测，
不是前置条件）。

**为什么替代链只解析一次**：替代链可在运行时被管理员改动。若在重试循环里每跳都重新解析，
链变更会让同一次请求落到不一致的语义上；一次解析+缓存失效（见 [05-storage.md](05-storage.md)）
既省查询也保证同请求内一致。

### 4.2 候选展开：声明式到实例

**候选**是"真实模型 × 渠道范围 × 约束"的声明，**不绑凭据**。运行时才展开成
"候选 × 可用凭据实例"，再按**策略引擎**排序。

**为什么拆成两步**：若候选直接绑凭据，管理员每加一个贡献凭据就得改抽象模型配置，
且贡献凭据的失效会污染抽象模型定义（管理员无从知道某个 `smart` 为什么突然只剩一个候选）。
声明式候选让"策略"与"供给"彻底解耦：凭据来去只影响展开结果，不动配置。

## 5. L3：上游

两类上游共用一套接口，差异只在"凭据从哪来、目标地址是什么"：

| kind | 目标 | 凭据来源 | 协议 |
|---|---|---|---|
| `dshgateway` | `127.0.0.1:8326` | `$DSH_HOME/openai-gateway/api-key`（平台自有，`owner_account_id = NULL`） | OpenAI Chat / Responses |
| `contributed` | 贡献凭据自带的第三方端点 | `upstream_secrets`（AES-GCM）+ `upstream_credentials` | 视凭据而定，默认 OpenAI 兼容 |

细节见 [03-upstream.md](03-upstream.md)。这里只强调一条：

> **唯一出口原则**：`dshgateway` 永远走 `127.0.0.1`，配置层拒绝任何通配或非回环地址。
> 这条不是"建议"，是 providers-hub 的硬约束（它拒绝绑定 `0.0.0.0`），配置校验必须前置拒绝，
> 否则失败会推迟到第一次真实请求，表现为令人误解的连接错误。

## 6. 进程模型

### 6.1 两个进程

```
┌────────────────────────────────────────────┐
│ FreeRouter 主进程（Go）                      │
│  HTTP 服务 · L1/L2 · SQLite · 上游客户端      │
└───────────────┬────────────────────────────┘
                │ Unix socket（0600，仅同用户可达）
┌───────────────▼────────────────────────────┐
│ Node sidecar（子进程）                       │
│  providers-hub 的 auth / oauth 模块          │
│  17 家 provider 的登录流 · 凭据续期           │
└───────────────┬────────────────────────────┘
                │ HTTPS
                各供应商官方端点
```

| 决策 | 选择 | 理由 |
|---|---|---|
| 登录/续期复用方式 | **进程级 sidecar**，不 import | providers-hub 的 `package.json` 只导出 `.` 与 `./client`，深路径 import 随版本漂；且直接 import 会与 DSH 进程内模块状态冲突（PLAN 5.5） |
| 传输 | Unix domain socket | 文件系统权限天然隔离其他本机用户；不占端口，避免与 8326 冲突；比 TCP 回环少一层可被误连的面 |
| sidecar 是否有状态 | **无状态**（凭据经 IPC 回传给 Go，由 Go 加密落库） | 有状态就必须给 sidecar 一份存储，等于再造一个凭据库；无状态让"授权一次、Go 侧一份密文"成立 |
| sidecar 失败时 | 主服务照常转发，仅贡献与续期不可用 | 转发不依赖 sidecar，若因 sidecar 崩溃就整体 503，等于用一个可选组件拖垮核心功能 |

### 6.2 启动顺序

顺序有依赖，不能并发乱序：

1. 读配置，校验（含"公网监听必须 TLS"、"上游必须回环"）；
2. 打开数据库，执行迁移（见 [05-storage.md](05-storage.md)）；
3. **初始化向导判定**：库中无任何账户 → 只监听 `127.0.0.1`，等管理员创建完成；
4. 上游自举：读 api-key → 加密入库 → `GET /v1/models` 拉目录（**失败不阻塞启动**）；
5. 拉起 sidecar → 等 `handshake` → 标记"贡献能力可用"；
6. 启动 HTTP 服务，`/healthz` 立刻可用，`/readyz` 视上游连通性。

**为什么第 3 步要先于开公网**：初始化向导会给"第一个创建账户的人"`admin` 类。如果先开公网，
从进程启动到管理员创建完成之间存在一个**无认证的提权窗口**，扫到端口的人可以直接成为管理员。

**为什么第 4 步失败不阻塞**：上游离线时管理面仍然必须可用——否则运营连"去检查 DSH"的
告警横幅都看不到。第 4 步的重试是每 30s 一次的后台任务，不进入就绪判定之外的路径。

### 6.3 优雅关闭

顺序与启动相反：

1. `/readyz` 立即变红（让反代先摘流量）；
2. 关闭 listener（不再接新连接）；
3. 等在飞请求完成，上限 30s（见 [06-runtime.md](06-runtime.md)）；
4. 关闭 sidecar（先 `shutdown` 通知，超时强杀）；
5. 关闭数据库（WAL checkpoint）。

**为什么先关 listener 再等**：只"等"不"关"，新的连接会持续进来，drain 永远结束不了。

## 7. 部署形态

### 7.1 三种形态共用一个二进制

| 形态 | 入口 | 适用 |
|---|---|---|
| 裸机 + systemd | `freerouter serve -c /etc/freerouter/config.yaml` | 开发、单机自托管 |
| Docker Compose | 主容器 + 反代容器（Caddy） | 推荐生产 |
| 反代终止 TLS | 主进程只监听 `127.0.0.1:8080`，Caddy 持证书 | 已有反代体系 |

**为什么主进程自己不强制内置 ACME**：autocert 需要独占 80/443 与可写证书缓存，而多数生产
环境由反代统一管理证书。把两者做成二选一（`tls.mode: acme | reverse-proxy`），避免"两处都想
持证书"导致启动时端口冲突。配置校验对 `mode: reverse-proxy` 强制要求监听地址是回环。

### 7.2 数据目录

```
$FR_DATA_DIR/
├── freerouter.db              SQLite 主库
├── freerouter.db-wal          WAL
├── freerouter.db-shm
├── sidecar.sock               Unix socket（0600，运行期）
├── master.key                 主密钥（0600，可选改用环境变量）
└── backups/
```

**为什么主密钥允许放文件**：容器里用环境变量注入更自然，但裸机部署往往没有 secrets 管理，
只能靠 `0600` 文件。两者都支持、且**都不入库**，是唯一能同时满足这两种环境的做法
（PLAN 9.4 明确"主密钥来自环境变量或 `0600` 文件，永不入库"）。

## 8. 一次请求的完整数据流

以 `POST /v1/messages`（Anthropic，`stream: true`，带 `tool_use`）为例：

| # | 阶段 | 组件 | 失败时的行为 |
|---|---|---|---|
| 1 | TCP 接受、TLS 终止 | 反代 / 主进程 | TLS 失败：连接层错误，不进日志正文 |
| 2 | 请求 ID 注入 + 安全头 | L1 中间件 | 不失败 |
| 3 | 真实 IP 判定 | L1 | 未配 `TRUSTED_PROXIES` 则忽略 XFF |
| 4 | body 上限校验 | L1 | 413，**不读 body** |
| 5 | 鉴权：Key → 账户 + 类 + 状态 | L1 + store | 401；账户 `disabled` 时**立即** 401（实时查，不靠缓存） |
| 6 | 三维限速 | L1 | 429 + `Retry-After` |
| 7 | 配额（日/月 token、并发） | L1 + store | 429 / 402 语义见 `../api/03-errors.md` |
| 8 | 抽象模型解析（含替代链） | L2 `abstract` | 名字不存在 → 404；`disabled` → 410；无候选 → 503 |
| 9 | 协议解析 → IR + 能力校验 | L1 映射层 | 缺能力 → 400，并指出第几个 part |
| 10 | 候选过滤 → 排序 → 展开凭据实例 | L2 `abstract` | 展开为空 → 503（不是 500） |
| 11 | 逐候选调用上游 | L2 `call` + L3 | 首字节前失败 → 换下一个；见第 8 节末 |
| 12 | 事件流回写（SSE） | L1 编码层 | 写失败 → 取消上游，记录"客户端断开" |
| 13 | usage 落库、`requests` 落库 | L2 `meter` | **失败不影响请求结果**，只记日志 |
| 14 | `done` / `[DONE]` | L1 | 正常收尾 |

**第 11 步的边界（最容易写错的地方）**：

```
候选 A 成功返回 200 → 尚未吐出任何可见内容 → 可切换（A 中途失败就换 B）
候选 A 已吐出第一个 text_delta / tool_call_start → 不可切换（只能发 error 结束）
```

判断依据是**是否已向客户端写入可见内容**，而不是"是否已收到字节"。上游的心跳、注释帧、
`message_start` 之类不构成"可见内容"，可以直接丢弃并换候选——这一点在
[06-runtime.md](06-runtime.md) 的状态机里定义，因为它属于运行时判定，不属于策略。

**为什么第 13 步失败不能影响请求**：计量与日志服务于运营，不是请求的前置条件。反过来要求
"写不进库就不回给客户端"会让数据库抖动直接变成用户可见故障，而库抖动在生产里是常态。

## 9. 关键技术决策与理由

| # | 决策 | 理由 | 代价 / 缓解 |
|---|---|---|---|
| D1 | Go 1.27 + chi | 单二进制、低内存；chi 的 handler 就是标准 `http.Handler`，SSE 可直接写 `ResponseWriter` 并 Flush（PLAN 7） | 生态不如框架丰富 → 只用标准库 + 少量明确依赖 |
| D2 | SQLite(WAL) + 纯 Go 驱动 | CGO-free 交叉编译无忧；单机场景写并发足够（PLAN 7） | 单写者 → 写操作串行化，事务边界严格（[05-storage.md](05-storage.md)） |
| D3 | 对外只有抽象模型 | 泄露池结构等于泄露供给弱点；且 C2 让"渠道构成"成为内部信息 | 客户端不能按真实模型精确选型 → 用能力声明与弃用信号缓解 |
| D4 | IR 以 Anthropic content block 为粒度 | 它最能表达富内容（thinking / tool_use / 图片块），向下映射到 OpenAI 最简单（PLAN 6.1） | 映射到 Gemini 时需处理 `parts` 合并规则 |
| D5 | 四协议在**入站**全部转 IR，在**出站**按上游协议再编码 | N×M 问题变 N+M | IR 必须足够富；不足处显式 400 而不是丢弃 |
| D6 | 登录/续期走 Node sidecar | 17 家 OAuth 与静默续期不可能用 Go 重写（PLAN 5.5） | 多一个进程 → 无状态化 + 崩溃不影响转发 |
| D7 | 不静默降级 | 悄悄丢图片 / 丢 `tool_use` 会让客户端以为成功，错误在用户侧才暴露（PLAN 6.1） | 保守声明会让部分组合直接 400 → 用 `capability_mode` 让管理员显式放宽 |
| D8 | 已吐可见内容后不切候选 | 流式串话是 providers-hub 已经踩过的坑（PLAN 3.3） | 部分可恢复故障变成失败 → 用健康探测把坏候选提前摘掉 |
| D9 | 策略引擎三段式且默认 `expiry-first` | 最快作废的额度优先用，直接复用 providers-hub 的到期语义 | 可能选到较慢的候选 → 排序链可组合（`fastest` 等） |
| D10 | 上游永走 `127.0.0.1` | providers-hub 硬约束，且把我们与上游的信任边界收在本机 | 不能跨机部署上游 → 与 P2 多节点方案一起再议 |
| D11 | 错误码区分"模型不存在"(404) / "无候选"(503) / "已禁用"(410) | 三种情况的运维处置完全不同；混成一个 500 会让排障方向错误 | 客户端需要理解三态 → 文档与 SDK 说明 |
| D12 | 控制面与数据面同进程 | C1 砍掉队列；单机形态下没有理由拆服务 | 管理操作可能影响转发 → 管理面重查询加超时与限流 |

## 11. 待定项

> **待定**：前端形态（Next.js + `embed.FS` 还是 Go 模板 + htmx）会影响 L1 是否要挂静态资源
> 中间件，以及构建产物是否包含 Node 工具链。总纲第 7 章与第 15 章均列为待拍板，本册不预设。

> **待定**：P2 多节点时，SQLite → Postgres 会改变事务边界（[05-storage.md](05-storage.md)）；
> 同时限速与配额要从进程内状态迁到共享设施。多节点下的 sidecar 是"每节点一个"还是
> "独立服务"需要届时决定——现在不做，但本册的分层不应妨碍这两种走法。

> **待定**：`contributed` 上游是否允许非 OpenAI 兼容协议（例如直接对接某家 Anthropic 兼容端点）。
> 若允许，L3 需要第二套编码器，IR 的出站映射也要按上游协议而非入站协议选择。

> **待定**：管理面与数据面是否需要在同一进程内做资源隔离（例如管理查询的并发上限、
> 独立 goroutine 池）。当前假设管理面流量远小于转发流量，先不隔离。
