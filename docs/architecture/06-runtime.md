# 运行时

本册写清楚：进程里到底跑着多少个 goroutine、谁在什么条件下取消谁、
流式响应怎么在不停顿的情况下写出去、超时如何分层、以及进程收到信号时
进行中的请求怎么办。

**为什么运行时值得单列一册**：前面几册描述的是「系统应该做什么」，
本册描述的是「系统在压力与异常下会怎样」。中转站的绝大多数线上事故
不是逻辑写错，而是**连接泄漏、取消没传播、缓冲把流式变成批式**这三类。
它们都不体现在功能测试里，只体现在运行时设计里。

---

## 2. 并发模型

### 2.1 goroutine 拓扑

```
main
 ├─ http.Server.Serve（每连接一个 goroutine，由 net/http 管理）
 │    └─ 每请求一个 handler goroutine
 │         ├─ [流式] upstream reader goroutine（读上游 SSE）
 │         └─ [流式] 写出发生在 handler goroutine 内（不另起）
 ├─ sidecar 监控 goroutine（1 个，长期）
 ├─ 后台任务调度（1 个，长期）
 │    ├─ 模型目录刷新
 │    ├─ 鉴定复检
 │    ├─ missing 巡检
 │    ├─ 用量聚合与留存清理
 │    └─ 配额重置
 └─ 信号处理 goroutine（1 个，长期）
```

**长期 goroutine 只有 4 类**，其余都是每请求生命周期。

**为什么上游读取要单独一个 goroutine**：HTTP 响应体读取是阻塞的，
而我们要在读取的同时响应 context 取消（客户端断开）。如果读上游和
写客户端在同一条执行流上串行，客户端断开时我们只能在「下一次读到数据」
时才察觉，中间可能挂着几十秒。

### 2.2 每请求的 goroutine 数量上限

| 场景 | goroutine 数 |
|---|---|
| 非流式请求 | 1（handler 内同步完成） |
| 流式请求 | 2（handler + upstream reader） |

**没有**为每个候选尝试起 goroutine。候选是**串行**尝试的。

**为什么候选串行而不是并发竞速**：并发竞速会在多个上游同时产生
真实计费（每次请求都算钱），且无法保证「只把最快那个的响应给客户端」
——输掉的那些请求已经花掉了额度。串行尝试在失败时才付下一次成本，
与我们「额度是第一资源」的定位一致。

### 2.3 全局并发闸门

在进入上游调用前经过**全局信号量**（容量 = `limits.global_concurrency`，
在进入上游调用前经过**全局信号量**（容量 = `limits.global_concurrency`，
默认 200）。取不到则排队，队列超过 `queue_timeout`（默认 5s）返回
**503 + `overloaded` + `Retry-After: <queue_timeout 秒>`**（2026-10-21 定案：
码与语义见 `api/03-errors.md` §3.1/§5.2；账户级闸门超限仍是 429 `rate_limited`，
两层闸拆码的归因理由见 `api/03-errors.md` §3.1）。

**为什么在全局而不只在 Key 级**：Key 级并发限制防的是单个租户超用，
但多个租户同时打满会压垮上游连接池与内存。全局闸门是最后一道，
保证进程不会因为并发过高而 OOM。

**组级并发上限**（`max_concurrency`，属组的限制类策略）与全局闸门是两
层不同的闸门：前者约束「一个组的成员加起来同时打多少」，后者约束
「整个进程」。组级闸门在下游——先取组级信号量，再取全局信号量，
任一取不到都排队。为什么两层而不是只留一层：全局闸门保证进程不死，
但一个组把所有并发占满时其他人只能排队；组级闸门把这种影响限制在组内。
共享额度池只在**终态结算**时扣减，不占进程内计数，所以池耗尽与并发
闸门互不影响（见 [../security/03-groups.md](../security/03-groups.md)）。

## 3. goroutine 生命周期与泄漏防护

### 3.1 规则

1. **每个 goroutine 必须有明确的退出条件**，且退出条件必须由 context 驱动。
2. **不做「起一个 goroutine 就不管」的写法**——除 4 类长期任务外，
   所有 goroutine 都必须在请求返回前结束（或已被取消）。
3. 长期任务必须在 `main` 的 context 取消后于 `shutdown_grace` 内退出。
4. 向 channel 发送必须 `select` 上 `ctx.Done()`，否则接收方退出会永久阻塞发送方。

### 3.2 上游 reader 的生命周期

```
handler 启动 upstream reader
  ├─ ctx 取消（客户端断开 / 客户端超时 / 进程关闭）
  ├─ 上游流正常结束（EOF）
  ├─ 上游返回错误
  └─ 写出侧返回错误（写入失败 → 取消上游，不再继续读）
```

四个条件**任一**触发即结束，并在 `defer` 中关闭上游响应体。

**为什么写出失败要取消上游**：客户端已经断开，继续读上游只会
白耗额度并把数据丢进废纸篓。这是最常见的「隐形浪费」——用户在浏览器里
按了停止，服务端还在把整个回答生成完。

**为什么 `defer resp.Body.Close()` 不够**：`Close` 只是释放连接，
不会停止一个正在阻塞的 `Read`。必须**同时**取消 context。
两者缺一都会留下挂住的 goroutine。

### 3.3 泄漏的检测手段

- 单元测试中用 `runtime.NumGoroutine()` 在用例前后对比（允许 ±2 的噪声）。
- 长期任务暴露「最后执行时间」指标，超过 3 个周期未执行即告警。
- 压测后观察 goroutine 数是否回到基线。

## 4. context 取消传播

### 4.1 传播链

```
http.Request.Context()
  └─ 请求级 ctx（附带 requestID）
       ├─ 鉴权与配额（只读缓存，不产生子 ctx）
       ├─ 候选尝试 1 的 ctx（带 attempt timeout）
       ├─ 候选尝试 2 的 ctx（带 attempt timeout）
       └─ ...
```

**每一层都从上层派生**，不新建根 context。

### 4.2 什么会触发取消

| 触发源 | 传播到 |
|---|---|
| 客户端断开 TCP | 请求 ctx → 当前候选尝试 → 上游 reader → 上游连接 |
| 客户端总超时（`request_timeout`） | 同上 |
| 候选尝试超时（`attempt_timeout`） | 该次尝试，**不影响下一个候选** |
| 服务关闭信号 | 根 ctx → 全部 |
| 写出失败 | 请求 ctx → 上游 reader |

**关键区分**：候选尝试超时用**子 ctx**，不取消整个请求；
其余用请求 ctx。这样才能实现「第一个候选超时后换第二个」。

### 4.3 取消后的状态码

| 情况 | 返回 |
|---|---|
| 客户端主动断开 | 无需返回（连接已断），只记日志 |
| 客户端总超时 | `504` + `upstream_timeout`（若还没写响应头） |
| 已开始输出后中断 | 无法改状态码，发送 SSE 错误事件后关闭流 |

**为什么流式开始后不能改状态码**：HTTP 状态行已经发出，
任何后续错误只能通过 SSE 数据帧表达。这就是为什么
**候选切换必须发生在「还没写出任何可见内容」之前**——
一旦写出，就只能把这次失败如实告诉客户端。

## 5. 超时体系

分四层，逐层收紧：

| 层 | 默认 | 作用 |
|---|---|---|
| `connect_timeout` | 5s | 建立到上游的 TCP/TLS |
| `first_byte_timeout` | 60s | 从请求发出到收到**首个** SSE 帧或响应体首字节 |
| `attempt_timeout` | 300s | 单个候选的完整尝试 |
| `request_timeout` | 600s | 整个请求（含所有候选尝试） |

**为什么 `first_byte_timeout` 要远小于 `attempt_timeout`**：
上游「连上了但一直不说话」与「正在慢慢生成」是两种完全不同的故障。
前者应在 60 秒内判定失败并换候选，后者可能是正常的长思考。
用一个总超时无法区分，会把正常的慢回答误判为失败。

**为什么 `request_timeout` > `attempt_timeout`**：要给候选切换留出预算。
若两者相等，第一个候选超时就用光了全部时间，切换逻辑永远不会执行。

> **待定**：是否允许按抽象模型覆盖超时（如 `long-context` 类模型给更长的
> `first_byte_timeout`）。倾向允许，但需要在 UI 上明确提示，
> 避免管理员误配成「永不超时」。

## 6. SSE 写入与 flush

### 6.1 写出路径

```
上游 SSE 帧 → 解析为 IR 流事件（见 02-ir.md）
           → 转成对外协议的帧
           → 写入 http.ResponseWriter
           → Flush
```

**每一帧都 Flush**，不缓冲。

### 6.2 三个必须做的动作

1. **`w.Header().Set("Content-Type", "text/event-stream")`**
2. **`w.Header().Set("Cache-Control", "no-cache")`** 与 `X-Accel-Buffering: no`
3. **每帧 `http.NewResponseController(w).Flush()`**

**为什么用 `ResponseController` 而不是断言 `http.Flusher`**：中间件包装后
w 可能不再是原始类型，类型断言会静默失败——表现为「流式变成一次性输出」，
而且不报错。`ResponseController` 会穿透包装（Go 1.20+）。

**为什么 `X-Accel-Buffering: no`**：Nginx 默认缓冲响应，会把 SSE 攒起来。
这个头是反代场景下让流式真正生效的最省事办法，但仍需反代侧
`flush_interval -1` 配合（见 [../ops/02-deploy.md](../ops/02-deploy.md#6-反代前置形态-c可选)）。

### 6.3 写超时与背压

- 每次写设置**写超时**（默认 30s）；超时视为客户端过慢，取消请求。
- **不做无限缓冲**：写出慢时自然阻塞在上游 reader 上，
  形成背压（上游也会因为 TCP 窗口缩小而放慢）。
- **不在内存里攒完整响应**：任何「先收集再一次性写出」的写法都是错的。

**为什么依赖背压而不是自己缓冲**：自己缓冲会把「客户端慢」的问题
转化为「服务端内存涨」的问题，在并发高时直接 OOM。
让阻塞发生在 TCP 层，代价最小。

### 6.4 流结束的收尾

1. 写出协议规定的结束帧（OpenAI：`data: [DONE]`）。
2. 记录用量（token 数、TTFT、总耗时）。
3. 结算配额。
4. 关闭上游响应体。

**为什么用量在结束时记录而不是逐帧累加**：逐帧累加会在中途断开时
留下不完整记录，且难以区分「上游没给 usage」与「真的用了 0」。
结束时以最终 usage 为准，中途断开按已收到的帧**估算**并标记 `estimated`。

## 7. 错误处理与码映射

### 7.1 错误分层

| 层 | 例子 | 处理 |
|---|---|---|
| **传输层** | 连不上、TLS 失败、`http=000` | 重试（幂等时）→ 换候选 |
| **上游协议层** | 上游返回 4xx / 5xx | 按类型决定换候选或直接透传 |
| **上游业务层** | 内容审核拒绝、额度耗尽 | **不重试**，如实返回 |
| **本地层** | 配额超限、鉴权失败、无候选 | 直接返回，不触达上游 |

### 7.2 换候选的条件（关键规则）

**只有**以下情况换候选：

- 传输层失败，且**尚未写出任何可见内容**
- 上游返回 429 / 5xx，且**尚未写出任何可见内容**
- 上游返回「模型不可用」类错误，且**尚未写出任何可见内容**

**绝不**换候选：

- 上游返回 400（请求本身有问题，换谁都一样）
- 内容审核拒绝（换候选等于**绕过审核**）
- 已经开始输出内容

**为什么内容审核拒绝不能换候选**：这是**合规红线**。一个渠道拒了，
换另一个渠道重试等于「换个供应商试试能不能过审」。这是有意规避
上游的内容政策，会连累所有使用该渠道的账号。

### 7.3 对外错误码

| 码 | HTTP | 触发 |
|---|---|---|
| `model_not_found` | 404 | 请求的模型不存在（含**真实模型名**——不区分，避免探测池结构） |
| `no_candidate` | 503 | 抽象模型存在但当前无可用候选 |
| `overloaded` | 503 | 全局闸门排队超 `queue_timeout`（2026-10-21 定案） |
| `upstream_unavailable` | 502 | 上游整体不可达 |
| `upstream_timeout` | 504 | 超时 |
| `quota_exceeded` | 429 | 账户级额度（合计行或按模型限额行）打满（Key 无额度） |
| `pool_exhausted` | 429 | 所属组的共享额度池耗尽 |
| `rate_limited` | 429 | 触发限速 |
| `capability_unsupported` | 400 | 请求的能力候选不支持（且无法过滤出候选） |
| `platform_forbidden` | 403 | 该操作只能由平台自身（非 API 客户端）触发，如界面上的人工审核 |
| `invalid_api_key` | 401 | Key 无效或账户被禁用 |

**为什么 `model_not_found` 不区分「不存在」与「无权访问」**：
若区分，租户可以逐一试探模型名来枚举池子里有什么。
统一返回 404 让「不知道」与「不允许」不可分辨。

### 7.4 错误体形状

对外错误体保持 OpenAI 兼容：

```json
{
  "error": {
    "message": "…",
    "type": "invalid_request_error",
    "code": "no_candidate",
    "param": null
  }
}
```

**为什么保留 OpenAI 形状**：客户端 SDK 会解析这个结构做重试判断。
自定义形状会让 SDK 报解析错误，把一个可处理的服务端问题
变成客户端崩溃。

## 8. 优雅关闭与 drain

### 8.1 顺序

```
收到 SIGTERM/SIGINT
 1. 停止接受新连接（Listener.Close）
 2. 把 /readyz 置为不就绪
 3. 等待进行中的请求完成，最多 shutdown_grace（默认 30s）
 4. 取消根 ctx（中断仍在跑的流）
 5. 关闭 sidecar（拒新 IPC 等 5s → 发 shutdown 等 3s → SIGTERM 等 2s → SIGKILL）
 6. 关闭数据库（checkpoint WAL）
 7. 退出
```

**为什么先置 `/readyz` 不就绪再等待**：负载均衡需要时间感知。
如果直接停，仍然会被导流过来。先摘流、再 drain，是标准的两步。
第 5 步的四级超时（5s / 3s / 2s / SIGKILL）以
[04-sidecar.md](04-sidecar.md) 第 5.4 节为权威，本节只记总体顺序。
**为什么第 4 步要强制取消而不是无限等待**：流式请求可能持续很久
（长回答、客户端挂着不读）。无限等待会让部署卡死，
也会让 Kubernetes 在 `terminationGracePeriodSeconds` 超时后 SIGKILL，
反而丢掉数据库的干净关闭。

### 8.2 关闭期间的行为

| 请求类型 | 行为 |
|---|---|
| 已开始的流式请求 | 继续到 `shutdown_grace`；到点后发终帧并关闭 |
| 新到达的请求 | 连接被拒（连接层） |
| 后台任务 | 完成当前一轮，不再排下一轮 |
| 迁移 | 不在关闭时执行 |

> **待定**：`shutdown_grace` 是否需要大于 `request_timeout` 才能保证
> 不截断长回答。当前默认 30s ≪ 600s，意味着部署时长时间回答会被截断。
> 倾向提供 `--drain-forever` 选项给单机自用场景。

## 9. 运行时接入点

按一次请求的执行顺序，各机制的接入位置：

| 顺序 | 环节 | 机制 | 超限结果 |
|---|---|---|---|
| 1 | 连接 | 连接数上限 | 拒绝 |
| 2 | 入站 | 请求体大小 ≤ `max_body_bytes` | 413 |
| 3 | 鉴权 | Key 查表 + 账户状态实时校验 | 401 |
| 4 | 限速 | IP / Key / 全局令牌桶 | 429 + `Retry-After` |
| 5 | 模型解析 | 抽象模型 → 候选（过滤） | 404 或 `no_candidate` |
| 6 | 授权 | 模型是否在租户/组的授权集内 | 404（不暴露） |
| 7 | 配额 | 预估额度是否够 | 429 |
| 8 | 并发 | 全局闸门 + Key 并发 | Key 超限/排队超时 → 429；全局闸排队超时 → 503 `overloaded`（2026-10-21 定案） |
| 9 | 上游 | 候选尝试（带超时） | 换候选 |
| 10 | 写出 | SSE 逐帧 flush | 客户端断开 → 取消 |
| 11 | 结算 | 用量记账 + 配额扣减 | 记 `estimated` |

**为什么鉴权（3）在限速（4）之前**：未认证的请求不应消耗
IP 限速的额度——否则攻击者可以用无效 Key 把某个 IP 的配额打满，
让该 IP 后的正常用户无法使用。

## 10. 观测点

| 指标 | 采集位置 | 用途 |
|---|---|---|
| `ttft_ms` | 首帧写出 | 用户体验的核心指标 |
| `total_ms` | 请求结束 | 与 TTFT 对比可区分「首字慢」与「生成慢」 |
| `upstream_ms` | 上游调用 | 与本地处理时间分离 |
| `attempts` | 候选切换 | 突增说明某渠道在劣化 |
| `tokens_in/out` | 结束结算 | 计费与配额 |
| `goroutines` | 定期采样 | 泄漏检测 |
| `active_streams` | 实时 | 并发闸门与容量规划 |

**为什么 TTFT 与总耗时都要采**：只采总耗时无法定位问题。
TTFT 高说明上游排队或连接慢；TTFT 正常但总耗时高说明生成慢。
两者的排查方向完全不同。
