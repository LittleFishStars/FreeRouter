- **Q178** Gemini 是否接受 `alt=sse` 的流式形态作为入站（而非 JSON 数组流）。这决定 `/v1beta/models/{m}:generateContent` 的 `streamGenerateContent` 是否复用同一套 SSE 编码器。
- **Q179** Gemini 的 `thoughtSignature` 需要在多轮里回传（与 Anthropic 的 thinking signature 同类），但 IR 的 `ThinkingPart.Signature` 是单字段。是否需要改成 `map[协议]signature`， 取决于是否会出现"同一会话跨协议切换"的场景。
- **Q180** 图片 `Detail` 的语义在四个协议里不同名不同义（OpenAI `detail`、Gemini `mediaResolution`）。当前选择原样保留字符串，但**编码到不支持该值的上游时**如何处理 （忽略 / 400 / 映射到最近档位）尚未定，需要实测各上游行为后再决定。
- **Q181** OpenAI Responses 的 `previous_response_id` 与 `store: true` 是否在 P1 支持。 当前一律 400（第 8.4 节），但这会让部分 Responses 客户端完全不可用。若要在 P1 支持， 需要在 [05-storage.md](architecture/05-storage.md) 里为"响应对象"增加存储与保留策略。
- **Q182** `tool_call` 缓冲的阈值（8 KiB / 2s）是拍定的初值，需要用真实上游的 "id 出现在第几片"的分布来校准。校准前不要把它当作可调优参数对外暴露。

### architecture/03-upstream.md

- **Q183** `contributed` 上游是否允许非 OpenAI 兼容协议（原生 Anthropic / Gemini 端点）。 若允许，[02-ir.md](architecture/02-ir.md) 的出站映射要按上游协议选择，`Dialect` 需要扩充， 且契约测试要覆盖新方言。当前按"只支持 OpenAI 兼容"实现。
- **Q184** 是否需要给单个凭据设连接数上限（防止一个贡献凭据被大量并发打爆）。 当前用 `MaxConnsPerHost` 在 host 级别兜底，逐凭据上限留到有真实滥用数据后再加。
- **Q185** 是否给单个**凭据**（而非 host）设置连接数上限。当前只有 host 级 `MaxConnsPerHost`，无法阻止一个贡献凭据被大量并发请求打爆（对贡献者是实际损失）。
- **Q186** `contributed` 上游的模型目录以"贡献者声明"为准还是以 `/v1/models` 为准。 前者可能造假（正是**鉴定**要防的），后者可能不被支持。当前倾向"声明为主 + L0 形式校验"， 但需要与 [../contributions/02-credentials.md](contributions/02-credentials.md) 对齐。
- **Q187** 上游是否需要一个显式的"出口代理"配置（`HTTP_PROXY`）。当前假设 `dshgateway` 永在回环不需要代理、`contributed` 直连。若部署环境强制出网代理， 需要在 Transport 层统一注入，并保证代理不改变唯一出口原则。
- **Q188** 多节点（P2）下每个节点各自连接 8326 是可接受的（同机多进程）， 还是需要独立的网关侧连接复用服务。当前按"每节点各自连"设计。

### architecture/04-sidecar.md

- **Q189** 是否需要在多实例部署（P2）下让多个主进程共用一个 sidecar（需要改为 Unix socket + 0600 权限 + 并发连接管理）。当前按"每个主进程一个 sidecar"设计。
- **Q190** `login.start` 返回的凭据如何"交付"给贡献者最安全。当前设计是控制台内一次性展示 + 直接写入 `upstream_secrets`，用户看不到明文；但若用户需要把同一个凭据也用于自己的 DSH， 就需要一次显式的一次性展示。安全面与可用性的取舍未定。
- **Q191** `codearts` 的登录实现位置。`lib/` 下只有 `codearts-credits.js`（余额查询）， 没有 oauth/login 模块。可能实现位于 lib 之外或另一个包。在确认前该 provider 的 `loginImplemented = false`，控制台不展示登录入口。
- **Q192** `modelscope` 的初始凭据从哪来。该模块只有刷新逻辑，说明用户是在别处（浏览器/其它 工具）拿到首个 token 后粘进来的。若不支持粘贴，这个 provider 在 FreeRouter 里无法自助接入。
- **Q193** 各登录流在**无图形环境**（纯 CLI / 容器）下的完整闭环未验证。设备码类理论上可行， 但需要实测 `openBrowser` 失败时是否仍有可用的降级路径（把 URL 打印给用户）。 这也是 [../RESEARCH-UPSTREAM-REUSE.md](RESEARCH-UPSTREAM-REUSE.md) 里明确未验证的部分。
- **Q194** `trae` 的固定回调端口 18080 与其它服务冲突时的表现（是报错还是静默失败）。 这决定我们是否需要给它做端口检测与提示。
- **Q195** sidecar 是否需要独立的日志文件与轮转策略。当前设计是 sidecar 的 stderr 直接并入 主进程日志流（`slog` 统一输出），但第三方库可能往 stdout 写非协议内容——那会**污染 NDJSON 帧**。 需要确认"第三方库不写 stdout"这一假设；若不成立，就要改用 fd 3/4 或 Unix socket。

### architecture/05-storage.md

- **Q196** 是否需要独立的 `verifications` 表来记录**历史**鉴定过程（当前只存最新结果）。 影响：无法回答"这个凭据是什么时候从 `verified` 变成 `suspect` 的"。
- **Q197** P2 多节点下的迁移协调（谁执行、其它节点怎么等）。当前设计是单进程， 若检测到库正在被迁移则拒绝启动。
- **Q198** `audit_log` 的 append-only 触发器与保留期清理冲突（不能 `DELETE`）。 可选方案：① 导出到归档后**整库重建**该表；② 用按月分表 + 丢整表；③ 放宽为"允许 保留期外的删除，但记一条删除审计"。三者都改变了 append-only 的强度，需要拍板。
- **Q199** `usage_daily.day` 的时区。当前用 **UTC** 日界。但用户看"今日用量"时用的是 本地时间（`Asia/Shanghai`），UTC 日界会让"今天"从早上 8 点开始。改为本地日界会影响 历史数据的可比性，需要一次明确的迁移决策。
- **Q200** `requests` 与 `audit_log` 是否需要分区/归档表。SQLite 单表在十万到百万行级别 仍可用，但"保留 90 天明细"在大流量下会产生可观的表大小与 `VACUUM` 成本。
- **Q201** `verify_detail` 之外是否要独立的历史鉴定表（见 3.5）。
- **Q202** `group_policies` 的 `policy_key` 是否需要一张"策略定义"元数据表来约束取值形状。 当前靠应用层校验。
- ~~**Q203** 是否给「贡献者回报」单独建表~~ → **已定案**（2026-10-19）：**不建**。无回报；贡献统计从 `requests.resolved_credential_id` 聚合，不单独建表。

### architecture/06-runtime.md

- **Q204** 是否允许按抽象模型覆盖超时（如 `long-context` 类模型给更长的 `first_byte_timeout`）。倾向允许，但需要在 UI 上明确提示， 避免管理员误配成「永不超时」。
- **Q205** `shutdown_grace` 是否需要大于 `request_timeout` 才能保证 不截断长回答。当前默认 30s ≪ 600s，意味着部署时长时间回答会被截断。 倾向提供 `--drain-forever` 选项给单机自用场景。
